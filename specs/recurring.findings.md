- *"that node" when several running nodes declare the job with different code.* REQ-206's trigger says "a running worker node declares", and the `shall` compares "that node's" code.   - **If it picks the new one**, the code takes over, as REQ-204 would do at that node's start.

## How to reproduce
From `specs/model/recurring`: `sh gen_cfgs.sh` regenerates every cfg except the scenario cfgs (`SCN*`, including `SCN209L` / `SCN209LH`, and the six `RSCN*`), and `sh run_all.sh` reruns every check below. Each check is one `run_tlc.py <module> --config <cfg> --stop-at-first` call, where the module is `Recurring.tla`, or `RecurringRace.tla` for the `Race_*` and `RSCN*` cfgs. Scenario, race and `RSCN*` cfgs add `--no-deadlock`. `run_all.sh <name>` runs one check. `TLC_WORKERS` (default 4) and `TLC_TIMEOUT` (default 400 s) set the workers and the per-run limit. A TLC still running after the limit is killed, because `run_tlc.py`'s timeout does not stop it on Windows. The `run*.json`/`run*.md` outputs and `run_all.log` are gitignored.

- TLC 2.19 throws "unexpected exception" when `-continue` has to rebuild many traces, so every check uses `--stop-at-first`. This run grepped every output for that message and found none.
- This run used `TLC_WORKERS=8 TLC_TIMEOUT=400`, with nothing else being model-checked on the machine, so the times are not comparable with run 9. Trace lengths of liveness counter-examples can differ from run 9's, because TLC with several workers does not always return the shortest one: `Liv_CF_ConvergeHost` is 9 states ending in stuttering (run 9: a 10-state lasso), and `Race_LiveStarve` is a 13-state lasso (19). The same applies to `RSCN216` / `RSCN216a`, which are 4 and 3 states (5 and 4).
- Don't start a second TLC run in this folder while one is running: TLC's `-cleanup` removes the shared `states/` folder, and the other run fails with "when reading the disk". The eighteen largest as-written race checks (`Race_UpdateSch`, `…_UpdateSchO`, `…_Update`, `…_ResumeSch`, `…_Pause`, `…_Resume`, `…_Reapply`, `…_ReapplySch`, `…_Remove`, `…_ORemove`, `…_OPause`, `…_OResume`, `…_Restore`, `…_TriggerSch`, `…_Trigger`, `…_OTrigger`, `…_Orphan`, `…_Create`) ran from a scratch copy of this folder, with identical `.tla` and `.cfg` files, at the same time as the rest. The rerun of `Race_LiveConvO` ran from a second copy. Their outputs were copied here. Each batch gave Java its own temp folder (`JAVA_TOOL_OPTIONS=-Djava.io.tmpdir=…`), so the standard modules TLC unpacks there (run 9 lost `Sequences.tla` mid-run) could not be removed by another run.
- **Timeout:** `Race_LiveConvO` was first generated with schedule content (`SchedOn = TRUE`) and was killed at the 400 s limit. That is a modeling smell, not something a requirement forces: its liveness properties do not read schedules. It was regenerated with `SchedOn = FALSE` (A-37) and passed. No other check came near the limit; the slowest was `Race_UpdateSchO` at 208 s.
