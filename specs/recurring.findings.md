## F-1 · unprovable · medium — Nothing obliges REQ-206 to restore a declared orphan
<!-- finding: unprovable | Liv_DeclaredConverges | INV-212,REQ-203,REQ-206,REQ-207 -->

**Requirements involved**
- INV-212 (notes): *"… one that changed before the write is corrected at the scheduler's next pass: a job removed while a node that just started declares it is created again (REQ-203), **a job orphaned that way is restored (REQ-206)**, and a definition taken from a node that has just stopped is updated again (REQ-241)."*
- REQ-206 (`actor: Host`): ***When a running worker node declares an orphaned recurring job again**, the system shall return the job to the state it had before it was orphaned, update the stored definition and definitionHash to match that node's code definition, and compute nextRunAt from now.*
- REQ-203 (`actor: system`, changed this run): *When a node with the worker registered starts, **or the scheduler finds** a code-defined recurring job that a running worker node declares, and that job has no stored definition with its name, the system shall create the definition …*
- REQ-205: *When the scheduler finds a stored code-defined recurring job that no running worker node declares, if the job's orphanPolicy is Orphan, the default, the system shall record the job's current state and mark it orphaned …*

**What happens** (TLC, `Recurring.tla`, `Recurring_Liv_Converge.cfg`: `Liv_DeclaredConverges` violated, 9-state trace ending in stuttering; the race model gives the same with the sweep split, `Race_LiveConvW`). `weekly-report` is code-defined, orphanPolicy Orphan (the default). Release N declares it and N+1 does not:
1. Node B starts on N, and `weekly-report` is created, active (REQ-203). The operator pauses it (REQ-214).
2. B is redeployed on N+1. No running node declares `weekly-report`, so the sweep records "Paused" and marks it orphaned (REQ-205). That is correct, and SCN-209's first step.
3. The deploy is rolled back: node A starts on N, and declares `weekly-report` again. It is stored, with N's hash, so REQ-203 and REQ-204 do nothing.
4. From here nothing has to happen. REQ-206's trigger holds ("a running worker node declares an orphaned recurring job again"), but its actor is Host, so the model, by the rules for actors, may never take the step. TLC finds the behaviour in which `weekly-report` stays orphaned for ever while A runs and declares it. The running nodes do not change, and no operator removes it.

The race that INV-212's notes talk about is the same, with one step moved. The sweep's write lands just after A starts, so A starts while `weekly-report` is still paused and orphaning it comes second (the `Race_OrphDecl` race with orphanPolicy Orphan, run-7 F-2's second paragraph). Read as an event at a node's start, which is what `actor: Host` suggests (REQ-204, REQ-210 and REQ-236 are the module's other Host items, all node-start events), REQ-206 has already passed by then, and the job stays orphaned until some node starts again. This is the run-7 F-2 gap, for the default orphan policy.

With orphanPolicy Delete the healing works as written: REQ-203's scheduler branch is `system` and weakly fair, and `Liv_DeclaredConverges` holds (`Liv_ConvergeDel`, `Race_LiveConvDel`). With REQ-206 weakly fair as well, it holds for both policies, also with the sweep, the restore, REQ-241 and the create split (`Liv_ConvergeOpt` 30,854 distinct; `Race_LiveConv` 272,096 distinct).

**Why** Run 7 changed REQ-203 to `actor: system` precisely so that the scheduler re-creates a declared job. REQ-206 is the matching rule for an orphaned job, and it still has `actor: Host` and a trigger that reads as "when a node declares it", not "when the scheduler finds it". The model has always let REQ-206 happen at any time (run 7's SysKinds counted the restore as a scheduler write). It was never checked as an obligation until this run asked for convergence. Severity is medium: the transient the notes accept as healed at the next pass may not heal until a node restarts. SCN-209 (rolled-back removal restores the earlier state) is reachable, but it is not guaranteed.

**Options**
1. *(recommended)* **Make REQ-206 the scheduler's, like REQ-203.** `actor: system`, and the trigger becomes *"the scheduler finds an orphaned recurring job that a running worker node declares"*. Nothing else changes: the restore keeps its effects (earlier state, that node's code definition, nextRunAt from now) and its compare-and-set (INV-212). It runs with the orphan sweep and REQ-241, which are worker duties (hosting REQ-40).
   - **Checked:** `Recurring_Liv_ConvergeOpt.cfg` and `Recurring_Race_LiveConv.cfg` (REQ-206 weakly fair): `Liv_DeclaredConverges` holds. Every safety check in this report already lets the restore happen at any time, so none of them changes.
2. **Keep REQ-206 at node start and correct INV-212's notes.** INV-212's and REQ-207's notes would then say that a job orphaned by the race stays orphaned, with no occurrences, until a node that declares it starts again, and that REQ-213 lets an operator remove it in the meantime. The actor stays Host. This is cheaper, but the default orphan policy is then the one that does not heal.
3. **Make the sweep's orphaning compare the heartbeats** (run-7 F-2 option 1, for REQ-205 only). This prevents the race instead of healing it, but it does not oblige the plain rollback restore of steps 1 to 4, so option 1 would still be needed. Not recommended.

| A-26 | *(changed)* In `RecurringRace.tla` a split write is a read, which checks the atomic action's guard and keeps what the write will use, and a later write. With state, nextRunAt and definition all compared, any ghost dooms the write, so the three are kept as one. | INV-212 |

| A-29 | *(changed)* The scheduler's writes (trigger, orphan sweep, restore, REQ-241, REQ-203's create) run on a node. When a node stops, a write in flight may be lost, and when no node runs it is lost. Operator writes are never lost. | INV-212, liveness |

## How to reproduce
From `specs/model/recurring`: `sh gen_cfgs.sh` regenerates every cfg except the six `RSCN*` scenario cfgs, and `sh run_all.sh` reruns every check below. Each check is one `run_tlc.py <module> --config <cfg> --stop-at-first` call, where the module is `Recurring.tla`, or `RecurringRace.tla` for the `Race_*` and `RSCN*` cfgs. Scenario, race and `RSCN*` cfgs add `--no-deadlock`. `run_all.sh <name>` runs one check. `TLC_WORKERS` (default 4) and `TLC_TIMEOUT` (default 400 s) set the workers and the per-run limit. A TLC still running after the limit is killed, because `run_tlc.py`'s timeout does not stop it on Windows. The `run*.json`/`run*.md` outputs and `run_all.log` are gitignored.

- TLC 2.19 throws "unexpected exception" when `-continue` has to rebuild many traces, so every check uses `--stop-at-first`. The run that produced this report grepped every output for that message and found none.
- This run used `TLC_WORKERS=4 TLC_TIMEOUT=400`, with three other modules being model-checked on the same machine, so the times are not comparable with run 7. No check hit the limit.
- Don't start a second TLC run in this folder while one is running: TLC's `-cleanup` removes the shared `states/` folder, and the other run fails with "when reading the disk". Twelve of the large as-written race checks ran from a scratch copy of this folder, with identical `.tla` and `.cfg` files, at the same time as the rest. The copy was then deleted, and its outputs copied here.
