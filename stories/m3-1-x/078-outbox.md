# ST-078 — Relay jobs through an outbox in the application's database

**Milestone:** M3 · **Epic:** m3-1-x · **Priority:** must · **Depends on:** ST-041, ST-073, ST-077

## Context

Adds outbox mode to Bellhop.EntityFrameworkCore, for applications whose job store is not in their database: dbContext.EnqueueAsync writes the job as an outbox row that commits or rolls back with the application's transaction (REQ-430), and a relay on the one worker node that holds the relay lease (REQ-435) moves each pending row into the job store under its outboxId and then deletes it (REQ-432). It creates at most one job per row, even across a relay crash (INV-406), and every pending row is eventually relayed (LIV-400). Without outbox mode and without a shared database, EnqueueAsync fails closed (REQ-437). This is BLT-17, which REQ-36 puts in M3, and TECH-49's notes make the outbox part M3. The Redis store's first page already says that transactional enqueue is not available (NFR-32, ST-073); once an outbox relay sample exists (ST-073's open question 7), the page can point to it too.

Builds on ST-041 (Bellhop.EntityFrameworkCore, dbContext.EnqueueAsync and the direct path of REQ-431, which this story keeps holding with TECH-49), ST-073 (the Redis store's first page, whose NFR-32 statement it keeps holding, and the option reference, whose NFR-26 and NFR-2 must cover outbox mode's options) and ST-077 (the M2 acceptance run, which gates every M3 story). It keeps TECH-31 (ST-004) holding if the relay adds a store operation, and TECH-105 (ST-054) by testing that operation in the conformance suite. The relay is a background duty, so it runs only on worker nodes (hosting REQ-40, ST-007), and its lease uses the job lease's LeaseDuration and HeartbeatInterval (jobs REQ-102, ST-008). The retention it relies on is ST-021's (jobs REQ-104) and operator deletes are ST-020's (jobs REQ-144). ST-090, the M3 acceptance run, builds on it.

Lives in Bellhop.EntityFrameworkCore (TECH-49), which provides dbContext.EnqueueAsync(job) and the outbox table and relay. How outbox mode is configured, and the outbox table's name, columns and place in the application's model, are not in the specs (open questions 1 and 2). The relay lease is a store lease (RelayLease, integrations glossary). The relay's "create nothing if a job with that id is still stored" runs in the job store, in the same write as the check that the node still holds the relay lease, which is a store lease too (REQ-432's criteria); if that needs a new IJobStore operation, every store implements it (TECH-31), in-memory, PostgreSQL, SQL Server, SQLite and Redis, and the conformance suite (TECH-105) gains a test for it.

## Acceptance criteria

### AC-1 · REQ-436 · must

> The system shall assume that every finished-job retention (jobs REQ-104) is much longer than LeaseDuration, so a crashed relay is replaced while the job it created is still stored.
>
> *Notes:* refiner-model 2026-11-06 F-11: with the defaults (7 to 30 days against 60 s) this holds by a wide margin. If an application sets a retention close to the lease length, a row can be relayed twice. The model cannot judge durations, so this is stated rather than checked. Run 2 F-16 (recommended option, accepted): an operator who deletes an outbox-created job (jobs REQ-144) while the relay that created it has crashed or lost its relay lease and not yet deleted the row gets the job back once. The window is at most LeaseDuration, and the operator gets an extra job rather than losing one.

- Given the default retentions, 7 days for succeeded and cancelled jobs and 30 days for dead-lettered ones (jobs REQ-104), and the default LeaseDuration of 60 s (jobs REQ-102), when the relay holder crashes after enqueueing row o1's job and before deleting the row, and that job finishes at once, then a running worker node takes the relay lease once LeaseDuration has passed (REQ-435), finds job o1 still stored, creates nothing and deletes the row (REQ-432).
- Given an operator deletes job o1 (jobs REQ-144) while the relay that created it has crashed, or lost its relay lease, before deleting row o1, when the next holder processes o1, then job o1 is created again, once, and the row is deleted. The notes accept this (run 2 F-16): the operator gets an extra job rather than losing one.
- Given the row has been deleted, when the operator then deletes job o1, then no job o1 is created again.
- Given a retention set close to LeaseDuration, the notes accept that a row can be relayed twice, so no criterion is set there. Whether the system should warn about it is open question 5.

### AC-2 · REQ-430 · should

> Where outbox mode is configured, when an application calls dbContext.EnqueueAsync, the system shall write the job as an outbox row in the application's DbContext so it commits or rolls back with the application's transaction.
>
> *Transition:* OutboxRow: (new) → Pending · *Actor:* Application

- Given outbox mode is configured, when the application calls dbContext.EnqueueAsync(job) in a transaction and commits it, then the application's database holds a pending outbox row with the job and an outboxId, written through the application's DbContext, and the job store holds no job for it until the relay runs (REQ-432).
- Given the same, when the application rolls the transaction back, or it fails to commit, then neither the row nor the application's other changes in that transaction are stored, and no job is ever created from it.
- Given outbox mode is configured and the job store shares the application's database, then EnqueueAsync still writes an outbox row (REQ-430 depends only on outbox mode).
- Whether EnqueueAsync adds the row for the application's next save or writes it at once, what happens with no open transaction, and what it returns, is open question 2.

### AC-3 · REQ-432 · should

> While an outbox row is pending, when the relay, running on one worker node that holds the relay lease, processes its next batch, the system shall enqueue the row's job in the job store with the row's outboxId as its job id, creating nothing if a job with that id is still stored in any state, and then delete the row.
>
> *Transition:* OutboxRow: Pending → (removed) · *Actor:* system
>
> *Notes:* Decided by the owner on 2026-11-06: the relay deletes relayed rows, so the outbox table stays small. The job store and the application database are different databases in outbox mode, so the two steps cannot share a transaction; idempotency by outboxId (INV-406) covers a crash between them. refiner-model 2026-11-06 F-11 option 1, decided by the owner: the outboxId is the job id and the insert checks every stored job, not only active ones. A unique key would not do, because it is released when the job finishes (jobs REQ-107) and the crash window can end after that. The remaining risk, retention removing the job before a crashed relay is replaced, is covered by assumption REQ-436.

- Given pending row o1 and a worker node that holds the relay lease, when the relay processes its next batch, then the job store holds a job with id o1, the row's outboxId, built from the row's job, and only after that is row o1 deleted.
- Given a job with id o1 is still stored, in any state (Enqueued, Processing, Succeeded, DeadLettered, Cancelled or another), when the relay processes row o1, then it creates nothing, leaves that job unchanged and deletes the row.
- Given the enqueue fails, for example because the job store is unreachable, then the row is not deleted and stays pending.
- Given a node that does not hold the relay lease, or a node without the worker registered (hosting REQ-40), then it relays nothing.
- Given a relay that read its batch while it held the relay lease and has since lost it, for example by pausing past LeaseDuration (integrations A-11), when it resumes and processes row o1, then it creates no job: the enqueue checks that this node still holds the lease, in the same write, as the model's `RelayEnqueues` does (`holder = n`). Only its row delete is unfenced, which integrations A-11 accepts because the delete is idempotent. REQ-432 does not state this check in words (open question 7).
- A row whose job the store refuses is open question 3. The batch size and how often a batch runs are open question 4.

### AC-4 · INV-406 · should

> The system shall never create more than one job from the same outbox row, even if the relay crashes between enqueueing the job and deleting the row.

- Property: over random interleavings of the transitions that could break it, as the model lists them, the relay enqueueing a row's job (`RelayEnqueues`), deleting the row (`RelayDeletes`), crashing between the two (`RelayCrashes`), losing its lease while it keeps running (`RelayLeasePauses`, integrations A-11), another worker node taking the lease (`AcquireRelayLease`), the job finishing (`JobFinishes`) and retention removing a finished job only after a crashed relay has been replaced (`RetentionRemoves` under REQ-436, integrations A-13): the number of jobs ever created from each outbox row is at most one.
- Concurrency, against each job store, the stale relay: relay A reads row o1 and pauses past its lease (integrations A-11); B takes the lease, relays o1 and deletes the row; an operator deletes job o1; A resumes. Then A creates nothing, because it no longer holds the lease (REQ-432), and no job o1 is created a second time. A's late row delete does no harm. This is not the operator-delete case that REQ-436's notes accept, because the row was already gone when the operator deleted the job.
- Concurrency, against each job store: relays on two nodes process row o1 at the same moment. Only the lease holder's enqueue can create a job, so exactly one job o1 exists afterwards and the row is deleted.
- What is observed is every job creation with id o1, not only the jobs stored at the end, so a job created, finished, removed and created again is caught.
- Outside the guarantee, as REQ-436's notes accept: an operator delete during the crash window, and a retention shorter than the time it takes to replace a crashed relay (REQ-436).

### AC-5 · REQ-435 · should

> Where outbox mode is configured, when no running worker node holds an unexpired relay lease, the system shall let one running worker node take the relay lease for LeaseDuration and renew it every HeartbeatInterval while it runs.
>
> *Notes:* refiner-model 2026-11-06 F-12 option 1: nothing obliged a node to take over a free relay lease, so a relay crash could leave rows pending for ever. The relay stays a worker duty (hosting REQ-40). Uses the job lease's length and heartbeat (jobs REQ-102) instead of a new RelayLeaseDuration constant.

- Concurrency: given outbox mode is configured on several running worker nodes and no node holds an unexpired relay lease, when they all try to take it at once, then exactly one holds it and the others relay nothing.
- With a fake `TimeProvider` (TECH-12): the holder renews the lease every HeartbeatInterval, which is LeaseDuration / 3 (jobs REQ-102), and while it runs and renews, no other node takes the lease, however long it runs.
- Given the holder stops renewing, by a crash or a pause, then no other node takes the lease before LeaseDuration has passed since its last renewal, and once it has, one running worker node takes it.
- Given LeaseDuration configured to another value, then the relay lease's length and renewal interval follow it.
- Given a node without the worker registered (hosting REQ-40), or a node where outbox mode is not configured, then it never takes the relay lease.

### AC-6 · REQ-437 · should

> Where the job store does not share the application's database and outbox mode is not configured, when an application calls dbContext.EnqueueAsync, the system shall reject the call with an error that names outbox mode, and enqueue nothing.
>
> *Notes:* refiner-model 2026-11-06 F-13 option 1: fail closed. The API's name promises transactional enqueue, and enqueueing outside the transaction would lose atomicity silently.

- Given the job store does not share the application's database, for example the Redis store, which reports no transactional enqueue (redis REQ-512), and outbox mode is not configured, when the application calls dbContext.EnqueueAsync, then the call fails with an error that names outbox mode, and nothing is enqueued: no job in the store and no outbox row.
- Property: over every combination of a shared or separate database and outbox mode on or off, EnqueueAsync takes exactly the path the items give: outbox mode on, an outbox row (REQ-430); off with a shared database, the direct enqueue (REQ-431, ST-041); off with a separate database, this rejection.
- The error's type, and how the system decides that the store shares the database, are open question 1.

### AC-7 · LIV-400 · should

> While an outbox row is pending and at least one worker node is running, the system shall eventually enqueue its job and delete the row.
>
> *Notes:* Decided by the owner on 2026-11-06: rows are deleted by the relay once their job is enqueued (REQ-432). refiner-model 2026-11-06 F-12: provable once a running worker node is obliged to take a free relay lease (REQ-435).

- Given outbox mode, one pending row and one running worker node, when time advances with a fake `TimeProvider`, then eventually the row's job is in the job store and the row is deleted.
- Given the relay holder crashed after enqueueing and before deleting (SCN-403), when LeaseDuration has passed and another running worker node has taken the lease (REQ-435), then the row is eventually deleted, with exactly one job for it (INV-406).
- Given the holder paused past its lease and then resumed, then the row is still relayed and deleted.
- Given no worker node is running, then rows stay pending (hosting REQ-40), and they are relayed once one starts.
- No bound beyond LeaseDuration for a takeover is given; the relay's cadence is open question 4. A row the store refuses is open question 3, and running worker nodes without outbox mode are open question 6.

### AC-8 · SCN-403 · scenario

> **Relay crash does not duplicate a job**
>
> *Given:* Outbox row o1 is pending; worker nodes A and B are running.
>
> 1. REQ-435 — B takes the relay lease
> 2. REQ-432 — B enqueues job o1 and crashes before deleting the row
> 3. REQ-435 — B's lease expires and A takes it
> 4. REQ-432 — A processes o1 again: job o1 is still stored, so nothing is created, and the row is deleted
>
> *Then:* Exactly one job exists for o1, whether or not it has already finished, and o1 is no longer in the outbox.

## Out of scope

- The direct path when the store shares the application's database: REQ-431 and INV-101, ST-041.

- Retention and operator deletes themselves: jobs REQ-104 (ST-021) and jobs REQ-144 (ST-020).

4. **Decide in delivery** · REQ-432, LIV-400: how many rows does a batch take, and how often does the relay process one? LIV-400 says only "eventually"; if either is an option, NFR-2 and NFR-26 need its name and default.

6. **Decide in delivery** · LIV-400, REQ-435: LIV-400 holds while "at least one worker node is running", but only nodes where outbox mode is configured take the relay lease (REQ-435). Should LIV-400 say "where outbox mode is configured", or must pending rows be relayed by worker nodes that no longer configure it?
7. **Decide in delivery** · REQ-432, INV-406: should REQ-432 state that the relay's enqueue checks, in the same write, that its node still holds the relay lease?
