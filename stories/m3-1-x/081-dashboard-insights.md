# ST-081 — Compute insights rollups and show the insights page

**Milestone:** M3 · **Epic:** m3-1-x · **Priority:** should · **Depends on:** ST-071, ST-077

## Context

Adds insights. Worker nodes compute per-minute and per-hour rollups of enqueued, succeeded, failed and dead-lettered counts and duration percentiles per job name and per queue (REQ-332). Each interval is computed under a lease in the store and written once, in one batched write fenced by that lease (INV-305). The dashboard shows the rollups on an insights page (REQ-333).

Builds on ST-071 (node samples written in one batched store write per interval and pruned as a worker duty, REQ-314 and REQ-343, the closest pattern), ST-007 (hosting REQ-40, which lists rollup computation among the background duties only a worker node runs, and which this story must keep holding) and the dashboard pages before it (ST-032 to ST-034), and comes after the accepted 1.0 (ST-077). It must keep NFR-16 holding (the insights page's lists are paged and its queries indexed) and NFR-15 holding (rollup pruning runs through an index in small paced batches). Only ST-090 builds on it.

Rollups and their lease live in the job store, so this story implements them on every store (TECH-31): in-memory, PostgreSQL, SQL Server, SQLite and Redis, all of which exist once ST-077 is done. The page lives in Bellhop.Dashboard (TECH-88) and reads its data through the JSON API (TECH-92), whose insights endpoints are not in the specs (open question 4).

### Modeling assumptions

Decisions the model took where the sentences were silent. Build to them, or raise an open question.

- dashboard A-5 (affects INV-300…INV-308, REQ-300, REQ-302…REQ-306, REQ-319…REQ-322, REQ-337, REQ-338, REQ-342): The authorization sentences are rules on each request's outcome (authenticated flag plus 200/401/403/other); any outcome that satisfies all of them is allowed. A request with the level it needs (authenticated, or anonymous with a granted level), not refused by INV-302 or INV-307, is served. Launches and key management happen only on a request that could be served
- dashboard A-15 (affects INV-305): A rollup lease is time-limited and can lapse at any moment, including while its holder computes and after it has written. A holder whose lease is gone has its write refused and drops the computation. Rollup nodes are worker nodes
- dashboard A-18 (affects INV-305): No sentence releases the rollup lease after the write; it lapses (A-15). A node does not start a second computation of an interval while it is still computing one, and does not take the lease again while computing: a lease that lapsed and was taken again is not the lease the node "still holds". `Inv_RollupOneWrite` tracks *which nodes* wrote, so it catches a second node's write, not the same node writing twice
- dashboard A-19 (affects INV-305): New in run 4. "Has not been written yet" is judged at the moment the node starts computing, which in the model is the same step in which it takes the lease. An implementation that decides which interval to compute *before* taking its lease, and does not look again after, reads a stale "not written" and can write a finished interval a second time (run 3's F-1 trace with the read moved before step 4). The sentence already rules this out ("start computing each rollup interval that has not been written yet … only while the node holds the interval's lease"), so it is not a finding; it is the place an implementation is most likely to diverge

## Acceptance criteria

### AC-1 · INV-305 · should

> Where the worker is registered on a node, the system shall start computing each rollup interval that has not been written yet, as one of that node's background duties, only while the node holds the interval's lease in the store, and write the interval in one batched write that succeeds only if the node still holds the lease.
>
> *Notes:* refiner-model 2026-11-06 F-7 (option 1): the write is fenced by the lease, so at most one result is written per interval even when a lease expires mid-computation; duplicate computation stays possible and harmless. F-8 (option 1): rollups are a worker duty (hosting REQ-40). Run 2 F-3 (recommended option): the sentence says 'start computing', because a node cannot know its lease expired mid-computation until it next talks to the store; the fenced write is what keeps the result single. Run 3 F-1 (recommended option): a node skips an interval that is already written. The fence alone keeps one writer at a time, but once the writer's lease lapsed a later holder could compute and write a finished interval again; skipping it is what makes the result single, and it is what any implementation needs anyway to find the next interval to compute.

- Given a node without the worker registered, then it never computes, writes or prunes a rollup, whatever leases are free (hosting REQ-40).
- Given two worker nodes and an interval that has not been written, when both try to compute it, then only the node that holds the interval's lease starts computing, and the interval is written once.
- Given node n1 holds the lease and the lease lapses while n1 computes (fake `TimeProvider`), when n2 takes the lease, computes and writes, then n1's later write is refused, nothing from n1's write is stored, and the interval holds n2's result only (dashboard A-15).
- Given an interval that is already written, when a worker node later holds its lease, then it does not compute or write that interval again (INV-305's notes, run 3 F-1). A test lets another node write the interval between the moment a node picks the interval and the moment it takes the lease; the node still does not write it again (dashboard A-19).
- Given a write is refused, then no rollup of that interval from that write is stored, for any job name or queue.
- Concurrency, against every store: over random interleavings of lease acquisition, lapse, computation and write by two or more worker nodes, at most one result is written per interval (`Inv_RollupOneWrite`), and every computation starts while its node holds the interval's lease and the interval is unwritten (`Inv_RollupStartWithLease`).

### AC-2 · REQ-332 · should

> The system shall keep insights rollups of enqueued, succeeded, failed and dead-lettered counts and duration percentiles per job name and per queue, per minute for 24 hours and per hour for 30 days.
>
> *Notes:* refiner-model 2026-11-06 F-8 (option 1): computing and pruning rollups are worker background duties (INV-305, hosting REQ-40). While no worker is alive no rollups are computed, and the insights pages show that gap; this is accepted.

- Given jobs of two names in two queues enqueued, succeeded, failed and dead-lettered within one minute, when that minute's rollup is written, then it holds, per job name and per queue, each of the four counts and the duration percentiles, including the p50 and p95 that REQ-333 shows.
- Given the same events within one hour, then the hour's rollup holds the same figures for the hour.
- Property: over random event streams, the counts of an hour's rollup equal the sum of the counts of its minute rollups when both were computed from the same recorded events.
- Given a worker node and a fake clock, then minute rollups are kept for 24 hours and hourly rollups for 30 days, and the worker's pruning duty deletes older ones (REQ-332's notes); a node without the worker prunes nothing (hosting REQ-40).
- Given no worker node is alive during an interval, then no rollup is written for it while none is alive, and the insights page shows that interval as having no data, not as zero jobs (REQ-332's notes). Whether a worker that comes back computes it later is open question 2.
- Which events fall into an interval and whose durations feed the percentiles are open question 1.

### AC-3 · REQ-333 · should

> The system shall show an insights page with a throughput chart, a 7-day heatmap by hour, per-job-name tables of p50 and p95 duration, failure rate and trend, and lists of the slowest and most-failing jobs.

- Given rollups written directly into the store for the last 7 days, when a viewer opens the insights page, then it shows a throughput chart, a heatmap of the last 7 days by hour, a table per job name with p50 and p95 duration, failure rate and trend, and lists of the slowest and most-failing jobs.
- Given those seeded rollups, then every p50 and p95 the table shows equals the value in the rollups, and the heatmap's cells are built from the hourly rollups.
- Given a request without view permission, then the page and the JSON API reads behind it are refused (INV-301).
- Given the new page, then ST-032's dashboard-wide checks hold on it: no inline script under the strict Content-Security-Policy (NFR-42) and no axe violation at WCAG 2.2 AA (NFR-50).
- How failure rate and trend are computed, what the heatmap measures, the chart's range and what the two lists rank are open question 3.
