# ST-079 — Send alerts by email over SMTP

**Milestone:** M3 · **Epic:** m3-1-x · **Priority:** should · **Depends on:** ST-050, ST-077

## Context

Adds an SMTP email channel to the notification engine (TECH-119), next to the webhook, Slack, Teams and ILogger channels. A delivery sent by email follows the lifecycle every channel shares: Sent when the mail server accepts the message (REQ-407), retried with backoff while the server rejects it or cannot be reached (REQ-408), and Failed after NotificationMaxAttempts attempts (REQ-415).

Builds on ST-049 (rules from configuration and code, the alerts registration and the notification lease: REQ-410, INV-411) and ST-050 (the delivery lifecycle and the test delivery: REQ-407, REQ-408, REQ-409, REQ-412, REQ-415), and comes after the accepted 1.0 (ST-077). It must keep NFR-26 and NFR-2 holding: the channel's options join the option reference, each with a documented default. Only ST-090, the M3 acceptance run, builds on it.

The notification engine is part of the core package (TECH-112), which depends only on the BCL and Microsoft.Extensions.* abstractions (TECH-8), so the channel either uses the BCL's SMTP client or lives in a package the specs do not name (open question 1). How a rule selects the channel, and where the server, credentials, sender and recipients are configured, are not in the specs (open question 2).

## Acceptance criteria

### AC-1 · TECH-119 · should

> **SMTP channel** — The notification engine shall offer an SMTP email channel.

- Given a rule whose channel is SMTP and a mail server that accepts the message, when the rule has a pending delivery, then the server receives one message built from the rule's template, and the delivery is marked Sent (REQ-407).
- Given the mail server rejects the message or cannot be reached, when fewer than NotificationMaxAttempts attempts have been made, then the delivery stays Pending and is retried with backoff (REQ-408, REQ-412); it is not marked Sent.
- Given the same failure on the NotificationMaxAttempts-th attempt (integrations A-8 counts the rejected attempt), then the delivery is marked Failed, an error is logged that names the rule and the channel, and the failure is counted in the metric (REQ-415).
- Given an operator presses "send test" on a rule with the SMTP channel, then a test delivery is created outside the cooldown (REQ-409) and the node holding the notification lease sends it by email (INV-411).
- Given the channel is configured with credentials, then no log line, startup summary or dashboard response contains them (NFR-41).
- Inspection: the channel adds no dependency to the core package beyond the BCL and Microsoft.Extensions.* abstractions (TECH-8), or it sits where open question 1 places it. The reviewer records the dependency audit in Notes.
- A server that accepts some recipients and refuses others is open question 3; whether the destination allowlist applies is open question 4.

## Open questions

1. **Decide in delivery** · TECH-119, TECH-8: does the SMTP channel live in the core package and use only the BCL's SMTP client, or in a separate package that may take a mail library? TECH-112 puts notifications in core and TECH-8 limits core to the BCL and Microsoft.Extensions.* abstractions; no item names a package for the channel.
2. **Decide in delivery** · TECH-119: how a rule selects the SMTP channel; the option names and configuration shape for server, port, TLS, credentials, sender and recipients; and how the rule's template becomes the subject and body. None is in the specs, and all become public contracts that NFR-20 then freezes.
3. **Decide in delivery** · TECH-119, REQ-407, REQ-408: when the server accepts the message for some recipients and refuses others, is the delivery Sent or retried? REQ-407 and REQ-408 speak of the channel accepting or rejecting "the message" as a whole.
4. **Decide in delivery** · TECH-119, INV-401, INV-402: do the destination allowlist and the private-address check apply to the mail server's host? INV-401 and INV-402 name HTTP job requests and notification webhooks only, and the allowlist is empty by default, so the answer decides whether email works without configuring it.
