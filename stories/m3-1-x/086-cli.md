# ST-086 — Ship the Bellhop CLI tool

**Milestone:** M3 · **Epic:** m3-1-x · **Priority:** may · **Depends on:** ST-067, ST-055, ST-056, ST-077

## Context

Ships Bellhop.Cli, a dotnet tool that exports schema scripts, requeues dead letters, inspects jobs and generates basic-auth password hashes (TECH-122), so DBAs, operators and scripts can do these from a shell.

Builds on the SQL stores' schema scripts (TECH-47: PostgreSQL in ST-029, SQL Server in ST-055, SQLite in ST-056), the dashboard JSON API (TECH-92, ST-031), which the CLI calls with an API key (REQ-305, ST-066), dead-letter requeue (REQ-141, REQ-142, ST-020) and basic-auth hashing (TECH-94, ST-067), and comes after the accepted 1.0 (ST-077). It must keep NFR-26 and NFR-2 holding (any options the tool adds join the option reference, each with a documented default) and TECH-94 holding (the hashes it generates are the salted PBKDF2-HMAC-SHA256 hashes RequireBasicAuth() verifies). Only ST-090 builds on it.

Lives in the Bellhop.Cli package (TECH-122, TECH-124), a dotnet tool built for net8.0 and net10.0 (TECH-1). The tool infers M1 for TECH-122, but REQ-36 puts the CLI in M3, and TECH-122's source calls it post-1.0. The tool's command name, its commands, arguments, output and exit codes are not in the specs (open question 1).

## Acceptance criteria

### AC-1 · TECH-122 · may

> **CLI tool** — The Bellhop.Cli dotnet tool shall export schema scripts, requeue dead letters, inspect jobs and generate basic-auth password hashes.

- Export: given a SQL store's provider and a fromVersion, when the CLI exports the schema script, then its output is exactly what `BellhopSchema.GetScript(provider, fromVersion)` returns (TECH-47), for PostgreSQL, SQL Server and SQLite. Given an unknown provider or a version that store does not have, then no script is written and the CLI exits unsuccessfully with an error.
- Requeue: given an operate-scope API key, when the CLI requeues dead letters through the JSON API, then each job is requeued as REQ-141 (one job) or REQ-142 (in bulk) says, under the principal name "apikey:" followed by the key's name (REQ-305), and a bulk requeue prints REQ-142's three counts: requeued, skipped because the state changed, and skipped because the unique key is held.
- Given a view-scope key, when the CLI requeues, then the JSON API refuses with 403 (INV-300, INV-301), nothing is requeued and the CLI exits unsuccessfully, reporting the refusal. Given a revoked, expired, past-expiresAt or unknown key, then the API answers 401 (INV-308) with the same outcome. Given a ReadOnly dashboard, then the requeue is refused whatever the key's scope (INV-302).
- Inspect: given a view-scope key and a job id, when the CLI inspects the job, then it shows what the JSON API returns for that job; given an id no job has, then it reports that and exits unsuccessfully.
- Hash: given a password, when the CLI generates a hash, then the result is a salted PBKDF2-HMAC-SHA256 hash with at least 600,000 iterations computed with `Rfc2898DeriveBytes.Pbkdf2` (TECH-94), in the form RequireBasicAuth() reads: configured for a user, it lets that user sign in with that password and with no other (REQ-303). Two runs on the same password give two different hashes, and both verify.
- Given a hash is generated, then neither the CLI's output nor any log contains the password (NFR-41).

## Tests

Every test carries one `Trait("Req", "<id>")` for each item it verifies.

- Unit: export output equals `GetScript` for each provider, and bad providers and versions fail (TECH-122, TECH-47); hash generation and verification (TECH-122, TECH-94).
- Integration, the CLI against the dashboard in an in-process test server with RequireApiKey(): requeue and inspect with operate, view, revoked, expired and unknown keys and on a ReadOnly dashboard, plus REQ-142's counts with jobs whose state changes and whose unique key is held (TECH-122, REQ-305, INV-300, INV-301, INV-302, INV-308, REQ-142).
- Integration: a hash from the CLI configured in RequireBasicAuth() and used to sign in (TECH-122, REQ-303).
- Packaging: the built package installs as a dotnet tool and each command runs from it (TECH-122).
- Must keep holding: NFR-26 and NFR-2 (ST-073). The option-reference check stays green with the tool's options listed and each given a documented default. TECH-94 (ST-067): ST-067's hashing tests stay green, and the CLI's hashes pass them as the helper's do. ST-020's (REQ-141, REQ-142) and ST-066's (REQ-305, INV-308) tests and ST-067's REQ-303 tests stay green.

## Out of scope

- The JSON API, API keys and permissions: ST-031 and ST-066 (TECH-92, REQ-305, REQ-337, INV-301).
