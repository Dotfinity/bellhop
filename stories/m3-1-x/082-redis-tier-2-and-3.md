# ST-082 — Support Tier 2 and Tier 3 Redis-compatible servers

**Milestone:** M3 · **Epic:** m3-1-x · **Priority:** must · **Depends on:** ST-062, ST-077

## Context

Proves the Redis store on the Tier 2 servers Garnet, Dragonfly and Kvrocks and the Tier 2 hosted services Azure Managed Redis, Redis Cloud and Dragonfly Cloud, makes it work on the Tier 3 servers KeyDB and Redict and on Upstash over TCP, and writes one documentation section per supported server with its caveats, licence status and recommended settings (NFR-34). The store's command baseline (TECH-54, TECH-55) and Lua subset (TECH-60) were chosen to keep these servers usable; this story shows that they do.

Builds on ST-057 (the command baseline and the Lua subset), ST-059 (server detection with each family's adjustments, REQ-500, and the startup failure and durability warning that name Garnet's flags, REQ-502 and REQ-503) and ST-062 (the Tier 1 servers and the standalone, Sentinel and Cluster topologies, TECH-64), and comes after the accepted 1.0 (ST-077). ST-083 (the in-process Garnet fixture) and ST-084 (the CI matrix, the compatibility page and Redis conformance and chaos testing) build on it.

The work lives in Bellhop.Redis (TECH-70) and the Redis store documentation. The tool infers M2 for TECH-74, TECH-76, TECH-77, TECH-83, TECH-84 and TECH-85, but REQ-36 puts Tier 2 Redis-compatible servers in M3, and TECH-87's notes say Tier 2 servers join CI in M3. REQ-36 does not place Tier 3 (TECH-78, TECH-79, TECH-86); the planner put it here because TECH-87 runs KeyDB and Redict nightly in the M3 matrix, which is a planning assumption. NFR-34 comes here because its measure covers the Tier 2 and Tier 3 servers, which exist only from this story; its Valkey and Redis sections (TECH-71, TECH-73) are written here too.

## Acceptance criteria

### AC-1 · TECH-74 · must

> **Garnet** — The Redis store shall support Microsoft Garnet as a Tier 2 server, with Cluster supported and Sentinel not supported, RESP3 off and no reliance on WAIT or atomic MSET.
>
> *Version:* >= 2.1
>
> *Notes:* Lua is opt-in and slow on Garnet, so throughput is bounded by its Lua performance (documented in NFR-34).

- Given Garnet 2.1 and its newest release, started with Lua enabled, standalone and as a Cluster, when the store conformance suite (TECH-105) runs against each, then it passes.
- Given Garnet started without Lua, when a node starts on it, then the start fails with REQ-502's message naming --lua.
- Given Garnet without AOF, when the store becomes ready, then REQ-503's warning names --aof-commit-wait.
- Command audit over the conformance run: the store sends Garnet no WAIT and no MSET (TECH-55), and its connection does not use RESP3. Whether "RESP3 off" is also a server setting for users is open question 1.
- Sentinel is not run against Garnet; the Garnet section of the docs says Sentinel is not supported (NFR-34's statement asks for caveats).

### AC-2 · TECH-76 · must

> **Dragonfly** — The Redis store shall support Dragonfly as a Tier 2 server on database 0 only, never using EVAL inside MULTI.
>
> *Version:* >= 2.0
>
> *Notes:* Dragonfly is BSL 1.1, not OSI; the docs state the licence and the recommended flags --cluster_mode=emulated --lock_on_hashtags (NFR-34). Decided by the owner on 2026-11-06 (§9 Q8): listed as supported at Tier 2.

- Given Dragonfly 2.0 and its newest release, started with the recommended flags --cluster_mode=emulated --lock_on_hashtags (TECH-76's notes), when the conformance suite runs, then it passes. Whether it must also pass without those flags is open question 2.
- Command audit over the conformance run: every command goes to database 0 and no SELECT is sent (TECH-54, TECH-55), and no EVAL or EVALSHA is sent between MULTI and EXEC.
- Given Dragonfly whose INFO persistence shows AOF off or snapshot-only persistence, when the store becomes ready, then REQ-503's warning is logged (TECH-76 applies to REQ-503).
- The docs state Dragonfly's BSL 1.1 licence, that it is not OSI, and the two recommended flags (NFR-34).

### AC-3 · TECH-77 · must

> **Apache Kvrocks** — The Redis store shall support Apache Kvrocks as a Tier 2 server, with Cluster through the Kvrocks controller and Sentinel for primary/replica both exercised in CI.
>
> *Version:* >= 2.14
>
> *Notes:* BRPOPLPUSH, keyspace notifications and hash-field TTL are absent, and ZRANGEBYLEX and SCAN semantics differ; none of them is used (TECH-55). Documented as the self-hosted durable option.

- Given Kvrocks 2.14 and its newest release, standalone, as a Cluster through the Kvrocks controller and as primary and replica with Sentinel, when the conformance suite runs against each as a CI job, then it passes. ST-084 keeps these jobs in the matrix.
- Command audit over the conformance runs: the store sends no BRPOPLPUSH, ZRANGEBYLEX or SCAN, subscribes to no keyspace notification and uses no hash-field TTL (TECH-77's notes, TECH-55).
- The docs present Kvrocks as the self-hosted durable option (NFR-34).
