# ST-090 — Accept M3: run 1.x end to end, including Tier 2 servers

**Milestone:** M3 · **Epic:** m3-1-x · **Priority:** – · **Depends on:** ST-078, ST-079, ST-080, ST-081, ST-083, ST-084, ST-085, ST-086, ST-087, ST-088, ST-089 · **Kind:** acceptance

## Context

Accepts M3 by running 1.x end to end on real infrastructure, including the Tier 2 Redis-compatible servers, with deliberate failures, and recording what happened in Notes. REQ-36 lists M3's scope: BLT-13 to BLT-19, Tier 2 servers, the Garnet fixture, the CLI, Native AOT verification and community stores. No M3 item is verified by demonstration, so this story owns nothing; it checks that the M3 stories hold together on a real deployment and repeats the dashboard demonstrations (NFR-48, NFR-49) for the pages M3 adds.

Builds on every M3 story: ST-078 (outbox), ST-079 (SMTP channel), ST-080 (exception chains, branding, localisation), ST-081 (insights), ST-082 to ST-084 (Tier 2 and Tier 3 servers, the Garnet fixture, the CI matrix), ST-085 (Native AOT), ST-086 (CLI), ST-087 (MCP server), ST-088 (soak tests) and ST-089 (community stores). Nothing builds on it.

Touches no package. It needs the M3 build deployed on PostgreSQL, SQL Server, SQLite and Redis (Tier 1 and Tier 2 servers), the hosted services ST-082 used, a mail server, an MCP client and the CLI. A finding where the specs are wrong or silent goes to refiner-requirements first; a finding where the build is wrong becomes a new story with the next free number.

## Tests

Automated steps carry one `Trait("Req", "<id>")` for each item they exercise; manual steps are recorded in Notes with the ids they cover, the environment, versions, results and findings.

- Upgrade: a 1.0 deployment upgraded node by node to the M3 build, with 1.0 and 1.x nodes side by side on schema 1.0 (NFR-18) and jobs enqueued by 1.0 run by 1.x (NFR-19); the API-compatibility check against 1.0 shows no breaking change (NFR-20).
- Redis Tier 2: the end-to-end flows on Garnet, Dragonfly and Kvrocks and on Azure Managed Redis (both clustering policies), Redis Cloud and Dragonfly Cloud (TECH-74, TECH-76, TECH-77, TECH-83 to TECH-85); a primary killed mid-job on a replicated set, with a forced failover (NFR-58).
- Garnet fixture: the Redis conformance suite run through the fixture on a machine without Docker (TECH-75).
- Outbox: jobs relayed from the application's database, with the relay node killed mid-relay (ST-078: LIV-400, INV-406).
- Alerts by email: a rule on the SMTP channel delivering to a real mailbox, then the mail server stopped until the delivery fails, and restarted (TECH-119, REQ-408, REQ-415).
- Insights: two worker nodes with one paused past its rollup lease mid-computation, each interval written once (INV-305); a period with no worker shown as a gap (REQ-332).
- Dashboard: an exception chain from a real failure, branding options and a second language bundle (REQ-330, REQ-331, NFR-52); the insights page and the changed job page in all three themes (NFR-48) and at the four widths (NFR-49), recorded with screenshots.
- CLI: a script exported for each SQL store, dead letters requeued with an operate key and refused with a view key, a job inspected, and a hash generated and used to sign in (TECH-122).
- MCP: a real MCP client lists, inspects, requeues, triggers and pauses with view and operate keys (TECH-121).
- Native AOT: the native test application runs its jobs (TECH-4).
- Soak and listing: the latest NFR-3 and NFR-61 results from ST-088 and the community store list (NFR-59) are linked in Notes.
- Not automated: the run as a whole. It is done by hand against real infrastructure and recorded in Notes.
