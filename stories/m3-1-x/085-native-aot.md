# ST-085 — Verify Native AOT with a JsonSerializerContext

**Milestone:** M3 · **Epic:** m3-1-x · **Priority:** should · **Depends on:** ST-077

## Context

Verifies that the core package runs in a Native AOT application that supplies its own JsonSerializerContext (TECH-4). This is the Native AOT verification that REQ-36 puts in M3; the trimming safety it rests on has been checked since M1 (TECH-3).

Builds on ST-001 (the trimming analysis of the core package, TECH-3), ST-002 (the payload serializer and its JsonSerializerContext option, TECH-5 and TECH-6) and the whole of 1.0 (ST-077), because the check covers everything the core package contains (TECH-112). Only ST-090 builds on it.

Touches the core package, Bellhop (TECH-112, TECH-124), and adds an AOT test application to the repository; no other package is covered by TECH-4.

## Acceptance criteria

### AC-1 · TECH-4 · should

> **Native AOT** — The core package shall support Native AOT when the application supplies a JsonSerializerContext.
>
> *Notes:* A source generator MAY later be offered purely for AOT registration (JOB-1).

- Given a console application that references only the core package, uses the in-memory store (TECH-112), registers jobs and supplies a JsonSerializerContext for their payloads (TECH-6), when it is published with Native AOT for net8.0 and for net10.0 (TECH-1), then the publish reports no AOT or trimming warning from the core package's assemblies.
- Given that native executable, when it runs, then it enqueues, schedules and runs jobs, retries a failing job to a dead letter and runs a recurring job, with every payload serialized and read back through the supplied context.
- The AOT publish runs in CI for both target frameworks, and a warning from the core package fails the build.
- Given an AOT application that supplies no JsonSerializerContext, then TECH-4 promises nothing; what it observes is open question 1.
