# ST-084 — Run the Redis CI matrix and publish the compatibility page

**Milestone:** M3 · **Epic:** m3-1-x · **Priority:** must · **Depends on:** ST-082

## Context

Puts the Redis store under continuous test. CI runs the store conformance suite and the chaos tests against the Docker matrix of TECH-87, with KeyDB and Redict as a nightly smoke test; the store must pass both on every server in that matrix, including a primary killed mid-job and a forced failover (NFR-58); and the documentation gains a compatibility page generated from the CI results, showing each server's last green date (NFR-35).

Builds on ST-054 (the conformance suite, TECH-105, and the concurrency and chaos tests of NFR-57), ST-062 (the Tier 1 servers and topologies) and ST-082 (the Tier 2 and Tier 3 servers). Only ST-090 builds on it. TECH-87's notes say Tier 2 servers join CI in M3.

Lives in the repository's CI configuration and in the documentation, which is versioned with the code (NFR-28). No package changes.

## Acceptance criteria

### AC-1 · TECH-87 · must

> **Redis CI matrix** — CI shall run the conformance suite and the chaos tests against a Docker matrix of redis:7.2, redis:8, valkey:8.1, valkey:9, a Valkey cluster, a Redis Sentinel set, Garnet, Dragonfly and Kvrocks, with KeyDB and Redict as a nightly smoke test.
>
> *Notes:* Tier 2 servers join CI in M3 (§8).

- Inspection: the CI configuration runs the conformance suite and the chaos tests against each of redis:7.2, redis:8, valkey:8.1, valkey:9, a Valkey cluster, a Redis Sentinel set, Garnet, Dragonfly and Kvrocks, and a smoke test against KeyDB and Redict every night. The Kvrocks entries include Cluster through the Kvrocks controller and Sentinel (TECH-77). The reviewer records in Notes the workflow and one run in which every entry ran.
- Given a failing test on any entry, then that entry's run fails; no entry is marked as allowed to fail.
- Garnet runs with Lua enabled (REQ-502), and Garnet, Dragonfly and Kvrocks run at versions that TECH-74, TECH-76 and TECH-77 allow. Which versions are pinned, and which entries run on every commit and which nightly, are open question 1; what the smoke test covers is open question 2.

### AC-2 · NFR-35 · must

> **Compatibility page** — The documentation shall include a compatibility page generated from CI results that shows the last green date per server.
>
> *Measure:* page regenerated by CI; every server in the matrix has a last-green date · *Verification:* inspection

- Inspection: a CI step generates the compatibility page from the matrix results, and the published page is that output, not edited by hand. The reviewer checks that every entry of the TECH-87 matrix, the nightly KeyDB and Redict smoke test included, has a last-green date, and records the check in Notes.
- Given an entry whose latest run failed, then its last-green date stays at its last passing run.
- Given an entry that has never passed, then it has no last-green date, and the measure is not met until it passes.
- Whether hosted services appear on the page is open question 4.

### AC-3 · NFR-58 · must

> **Redis conformance and chaos testing** — The Redis store shall pass the store conformance suite against every Tier 1 and Tier 2 server, including Sentinel and Cluster topologies for Redis and Valkey, plus chaos tests that kill the primary mid-job and force a failover.
>
> *Measure:* suite green on every server in TECH-87 · *Verification:* test

- Test: the conformance suite (TECH-105) is green on every entry of TECH-87's matrix in the CI run the reviewer records in Notes.
- Chaos: on every entry that has a replica to fail over to, a test kills the primary while a job runs and forces a failover. Then the store reconnects and repeats server detection (redis REQ-529), the node keeps running without refusing the topology (REQ-511), and the job that was running reaches a final state, running again if needed (hosting REQ-10). Which entries run the chaos tests and what a failover may lose are open question 3.
- NFR-58's statement also names Redis Cluster, Valkey Sentinel and every Tier 1 and Tier 2 server, which the matrix does not hold (open question 4).

## Tests

Every test carries one `Trait("Req", "<id>")` for each item it verifies. The chaos tests carry NFR-58; the matrix and the page are inspected, not tagged.

- Smoke, nightly, on KeyDB and Redict (TECH-87; TECH-78 and TECH-79 from ST-082 keep holding).

- No Must keep holding items are listed. ST-054's conformance and chaos suites (TECH-105, NFR-57) stay green on the other stores.
- Not automated: the hosted services, which no Docker matrix can hold. ST-082 records their runs by hand (open question 4).
