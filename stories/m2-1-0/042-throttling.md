# ST-042 — Throttle claims with concurrency keys, rate limits, LongRunning limits and weighted queues

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-030, ST-037

## Context

Adds the throttles that REQ-123's claim guard already names: concurrency keys whose Max holds across all nodes (INV-108), rate limits per key over a fixed or sliding window (INV-109), a per-node limit for LongRunning jobs (INV-112), waiting without penalty while a key or rate limit blocks a job (REQ-156) and limits changed at runtime (REQ-158), plus the may items for key templates (REQ-157) and weighted round-robin queues (REQ-159). The store enforces all of it at claim time, with no lock service or lock library (TECH-51, hosting REQ-37).

Builds on ST-037 (M1 acceptance, so M1 is finished first), ST-030, ST-008, whose REQ-123 guard was built against what existed then (no key, rate limit or LongRunning limit) and is completed here, and ST-009, whose claim order keeps holding: strict queue priority stays the default beside REQ-159 (INV-110), and within a queue a job blocked by its key or rate limit is skipped in priority order (INV-111). It also keeps INV-123 holding: where [Concurrency] and a fluent AddBellhop setting both give a job's throttle metadata, the fluent value wins. The tool infers M1 for SCN-106, but concurrency keys are M2 under hosting REQ-36 ("unique and concurrency keys"), and the owner's decision of 2026-11-10 moved only uniqueness into M1, so the scenario stays with INV-108. ST-043 applies keys in Inline mode, ST-052 alerts when jobs wait on a throttle key (integrations REQ-406), and ST-070 adds the Throttles page (dashboard REQ-327), from which a limit is changed, and keeps REQ-158 holding.

Lives in the Bellhop core package, which TECH-112 says contains throttling, and in the claim of each store that exists, the in-memory store and Bellhop.PostgreSql (TECH-31). The concurrency key travels on EnqueueOptions (TECH-20), TECH-17 lists a [Concurrency] attribute without naming its members, and the LongRunning limit is a worker option on AddWorker (TECH-128's notes). How a Max, a rate limit, a LongRunning job, a key template and queue weights are declared, and the API that changes a limit, are not in the specs (open questions 1 to 4, 6 and 7). If a LongRunning job turns out to be marked by a tag, tags arrive in ST-044: build against what exists by writing the tag into the store directly.

## Acceptance criteria

### AC-1 · INV-108 · must

> The system shall never admit a claim that would make more jobs with the same concurrency key processing at once, across all nodes, than that key's Max at the time of the claim.
>
> *Notes:* Max = 1 is a distributed mutex; Max = N a semaphore. Resolved after refiner-model 2026-11-06 F-1 (recommended option): a rule about claims, not a state invariant, because lowering Max at runtime (REQ-158) leaves the current holders running above the new Max.

- Given jobs with key tenant:7 and Max = 1 and free workers on two nodes over one PostgreSQL store, then at most one of them is processing at any time (SCN-106); with Max = N, at most N.
- Given jobs with different keys, then each key is judged on its own: a held tenant:7 does not hold back a tenant:8 job.
- Given Max is lowered below the current number of holders (REQ-158), then they keep running and no claim with the key is admitted until fewer than the new Max hold it (REQ-158's notes).
- Concurrency: many jobs with one key are claimed by many worker slots on two nodes while handlers finish, fail, time out and lose leases at random. At every claim, the number of processing jobs with that key after the claim is at most the key's Max at that moment (the model's Prop_KeyMaxAtClaim). Whether anything else counts as a holder is open question 5.
- Inspection: on each store the key check is part of the claim's single store operation, and no external lock is used (TECH-51).

### AC-2 · INV-109 · must

> Where a rate limit of N executions per fixed or sliding window is set for a key, the system shall never start a job with that key when N jobs with that key have already started in the current window, across all nodes, counting every start including retries and recovery restarts.
>
> *Notes:* Decided by the owner on 2026-11-06: every start counts, because each one reaches the downstream system. Waiting is REQ-156. Resolved after refiner-model 2026-11-06 F-1 (recommended option): a rule about starts, so lowering N at runtime (REQ-158) does not retroactively violate it for starts already made in the window.

- Given a rate limit of N per fixed window on key k, when N jobs with k have started in the current window, then no further job with k starts on any node until the next window.
- Given a rate limit of N per sliding window on k, then no job with k starts while N starts with k lie within the window's length before that moment.
- Given a job with k is retried (REQ-130) or recovered after its lease expired (REQ-132), then its new start counts against the window like a first start (the owner's note).
- Given N is lowered during a window (REQ-158), then the starts already made are not undone, and later starts are judged against the new N.
- Concurrency: two nodes over PostgreSQL, with a fake TimeProvider (TECH-12) moving the windows; no window holds more than N starts with k.
- Where a fixed window starts and which clock judges it is open question 2.

### AC-3 · INV-112 · must

> Where a separate LongRunning limit is configured, the system shall never run more jobs tagged LongRunning at once on a node than that limit.

- Given a node whose LongRunning limit L is below its concurrency limit, when more than L LongRunning jobs are enqueued, then at most L of them are processing on that node at once, and the node's other slots still claim jobs that are not LongRunning (REQ-123).
- Given two nodes with limit L each, then each node is judged on its own.
- Given no separate LongRunning limit is configured, then LongRunning jobs are limited only by the node's concurrency limit (INV-106).
- Property: over random claims and finishes on one node, the number of processing LongRunning jobs on the node never exceeds L (the model's Inv_LongRunning).
- Handlers that run on after losing their claim are open question 5.

### AC-4 · REQ-156 · must

> While a job's concurrency key is held by Max processing jobs or its rate limit is used up for the current window, the system shall keep the job enqueued and never fail it, retry it or count an attempt for waiting.
>
> *Notes:* Decided by the owner on 2026-11-06: a job blocked by a rate limit waits like one blocked by a concurrency key, and a blocked job never stalls the queue: lower-priority jobs that are allowed to run proceed (INV-111).

- Given key k is held by Max processing jobs, when job j with k waits, then j stays enqueued, its attempt number is unchanged, it gets no retryAt and it is never failed or dead-lettered for waiting, however far the fake clock is advanced.
- Given j's rate limit is used up for the current window, then the same holds until the window lets it start.
- Given j is blocked, then lower-priority jobs in its queue that are admitted are claimed (the owner's note; INV-111).
- Given the holders finish, then j is claimed, and its attempt number counts that claim only (REQ-123).
- Property: over random sequences of claims, finishes, window ends and limit changes, a blocked job's state and attempt number do not change while it waits.

### AC-5 · REQ-157 · may

> Where a concurrency key is a template such as tenant:{TenantId}, the system shall fill the key from the job's payload properties at enqueue.

- Given a concurrency key template tenant:{TenantId} and a payload whose TenantId is 7, when the job is enqueued, then it is stored with the concurrency key tenant:7.
- Given two jobs with TenantId 7 and one with TenantId 8, then the first two share a key and are limited together (INV-108), and the third is not limited with them.
- A missing or null property is open question 6.

### AC-6 · REQ-158 · must

> When an operator changes a concurrency key's Max or a rate limit through the API or the Throttles page, the system shall apply the new limit to every following claim on every node without a redeploy, and leave jobs already running untouched.
>
> *Notes:* Decided by the owner on 2026-11-06: when Max is lowered below the current holders, they keep running and no new holder is admitted until the count drops below the new Max.

- Given Max = 2 with two holders on two nodes, when an operator lowers Max to 1 through the API, then both holders keep running, no claim with the key is admitted on either node until none holds it, and neither node restarts.
- Given Max is raised, then the next claim with the key on any node after the change has been made is judged against the new Max, without a redeploy.
- Given a rate limit is changed, then the next start with the key on any node is judged against the new limit (INV-109).
- Given jobs that are already running when a limit changes, then none of them is cancelled, released or restarted.
- The API's name, and whether a change survives a restart, are open question 4. The Throttles page is ST-070.

### AC-7 · REQ-159 · may

> Where a worker is configured for weighted round-robin, the system shall claim from its queues in proportion to their weights instead of strict order.

- Given a worker whose queues have weights and always have claimable jobs, then over many claims each queue's share of the claims approaches its weight's share of the total weight, and later queues are claimed from while earlier ones still have jobs (where INV-110 would not).
- Given weighted round-robin is not configured, then the worker claims in strict order (INV-110, the default).
- Within one queue, claims keep INV-111's order and the throttles above.
- How close the shares must be, over how many claims, and what a queue without claimable jobs does to the others' shares, are open question 7.

### AC-8 · SCN-106 · scenario

> **Concurrency key mutex blocks a second job**
>
> *Given:* Jobs j1 and j2 are enqueued with concurrency key tenant:7 and Max = 1; two free workers.
>
> 1. REQ-123 — j1 claimed
> 2. REQ-123 — j2 claim attempted while j1 processing
>
> *Impossible at step 2.*
