# ST-044 — Tag jobs and carry correlation ids

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-038, ST-033, ST-039, ST-043

## Context

Gives jobs tags and correlation ids. A tag set at enqueue, by an attribute on the job type, by enqueue middleware (IEnqueueMiddleware, TECH-29) or by the running handler is stored on the job and added to its secondary index (REQ-167), so the dashboard's tag filter (REQ-308) and bulk requeue by tag (REQ-142) find real jobs. Every enqueue captures a correlation id (REQ-168), and continuations and jobs enqueued from a handler take their parent's (INV-127), so one id finds a whole flow of jobs.

Builds on ST-004 (IJobIndex, TECH-32), ST-007 (the tags of EnqueueOptions, TECH-20), ST-010 (REQ-154 sets the parent of a job enqueued from a handler; TECH-30's parameters, through which its notes say correlation ids are stored, so TECH-30 is in this story's Must keep holding table), ST-033 (REQ-308's tag and correlation-id filters, tested so far with index entries written into the store directly) and ST-038 (continuations and chains). ST-020 built REQ-142's "by tag" the same way. ST-045 builds on it (NFR-56 puts CorrelationId on every handler log line), as do ST-070 (the tags page, REQ-325 and REQ-326) and ST-073 (the samples, NFR-27, including tag-restoring middleware). It also depends on ST-039 (batch-level continuations, REQ-181) and ST-043 (inline continuations, INV-132), because INV-127's "every continuation" covers both.

Lives in the Bellhop core package: IEnqueueMiddleware (TECH-29), the tags of EnqueueOptions (TECH-20), the tags and correlation id of JobContext (TECH-16) and the IJobIndex entries for tags and correlation ids (TECH-32). Tags and correlation ids are persisted and indexed on every store that exists at this point, in-memory and PostgreSQL (TECH-31). The tag attribute, the way a handler sets a tag, the middleware's member and the options for the correlation accessor and header are not named in the specs (open questions 1 and 4).

## Acceptance criteria

### AC-1 · INV-127 · must

> The system shall give every continuation and every job enqueued from a handler the correlation id of its parent.

- Given a running job P whose correlation id is c, when its handler enqueues or schedules a job, then the new job's correlation id is c and its parent is P (REQ-154).
- Given a job P whose correlation id is c, when a continuation of P is created, then the continuation's correlation id is c. In a chain (REQ-176) every later step carries the first step's correlation id, since each is a continuation of the one before.
- Property: over random trees of root enqueues, continuations, chains and enqueues from handlers, every job with a parent carries its parent's correlation id. Each root is enqueued under its own test Activity, and REQ-168 has nothing to capture where a child is created (no accessor, no header, and no current Activity, because nothing listens to the Bellhop ActivitySource): the case in which both readings of open question 5 agree.
- Concurrency: handlers of jobs with different correlation ids run at once on one node and each enqueues children; every child carries its own parent's correlation id, never that of a job running beside it.
- Which correlation id a child gets when REQ-168 also has a source is open question 5; batch-level continuations are open question 6.

### AC-2 · REQ-167 · must

> When a tag is set at enqueue, by an attribute on the job type, by enqueue middleware or by the running handler, the system shall store the tag on the job and add it to the job's secondary index.
>
> *Notes:* Tags are 'key' or 'key:value' strings.

- Given a tag set through the tags of EnqueueOptions (TECH-20), by an attribute on the job type, by an IEnqueueMiddleware (TECH-29) or by the handler, when the job is created, then the job carries the tag and a query of the job index by that tag (TECH-32) returns the job. Each of the four sources is tested on its own.
- Given a 'key' tag and a 'key:value' tag on one job (REQ-167's notes), then the job carries both, and a query for each of the two strings returns it.
- Given tags from several sources on one job, then the job carries every one of them.
- Given a handler that sets a tag and then succeeds, then once the job is Succeeded it carries the tag and the index query returns it. Whether the tag shows while the job still runs, and whether one set in a failed attempt is kept, is open question 3.
- Property: over random jobs with random tags from the four sources, on the in-memory and PostgreSQL stores, the jobs that a query by tag t returns, and the count CountAsync gives for t, are exactly the jobs that carry t.
- The shape of a tag on EnqueueOptions and what a malformed tag does are open question 2.

### AC-3 · REQ-168 · must

> When a job is enqueued, the system shall capture a correlation id from the configured accessor when one is set, otherwise from the configured header when one is set, otherwise from the current Activity.
>
> *Notes:* Decided by the owner on 2026-11-06: explicit configuration beats ambient context.

- Given an accessor and a header are configured and a current Activity exists, when a job is enqueued, then its correlation id is the accessor's value (the owner's notes: explicit configuration beats ambient context).
- Given only a header is configured and it carries h, with a current Activity, when a job is enqueued, then its correlation id is h.
- Given neither is configured, when a job is enqueued under a current Activity, then its correlation id is taken from that Activity, and two jobs enqueued under the same Activity get the same correlation id.
- Given a captured correlation id, then the handler sees it on JobContext (TECH-16), and a query of the job index by it returns the job (TECH-32, REQ-308).
- What a configured source that yields no value leads to, which value of the Activity is used, and what a job gets when there is no source at all, is open question 4.

### AC-4 · TECH-29 · should

> **Enqueue middleware** — The core package shall define IEnqueueMiddleware so applications can stamp tags, tenant ids or correlation data on every job created.

- Inspection: the Bellhop core package defines a public IEnqueueMiddleware under the root namespace Bellhop (TECH-124).
- Given an IEnqueueMiddleware registered in dependency injection that stamps a tag and a tenant id, when jobs are created through each creating method of IJobClient (EnqueueAsync, EnqueueManyAsync, ScheduleAsync, ContinueWithAsync, ChainAsync and CreateBatchAsync, TECH-19) and from a handler, then every job created carries the tag, indexed (REQ-167), and the tenant id as a typed parameter that the handler reads back (TECH-30, whose parameters are available to middleware at enqueue).
- Passing: the inspection holds and the test passes on the in-memory and PostgreSQL stores. The middleware's member, and whether it also runs for jobs the system creates, are open question 1.

## Open questions

1. **Decide in delivery** · REQ-167, TECH-29: the public names: the attribute that tags a job type (TECH-17's list has none), how a running handler sets a tag (TECH-16 lists tags on JobContext but no way to set one), and IEnqueueMiddleware's member and signature (TECH-29 names only the interface). Does the middleware also run for jobs the system creates, such as recurring occurrences (REQ-216), given TECH-29's "every job created"? All of these become public contracts that NFR-20 freezes.
2. **Decide in delivery** · REQ-167, TECH-20: what is a tag on EnqueueOptions? TECH-20 says "key/value tags", while REQ-167's notes say tags are 'key' or 'key:value' strings. What happens to a malformed tag (empty, or with more than one colon), and does a query by key find 'key:value' tags (REQ-308, REQ-142)?
3. **Decide in delivery** · REQ-167: when is a tag set by the running handler stored and indexed: at once, or with the attempt's outcome? Is it kept after a failed attempt? The criteria cover only a handler that succeeds.
4. **Decide in delivery** · REQ-168: what are the configured accessor and header: their option names, the accessor's type, and whose header it is? An HTTP request's header needs ASP.NET Core, which the core must not reference (TECH-9). Which value of the current Activity is captured (trace id, span id or a baggage item)? When a configured source yields no value, or there is no current Activity, does capture fall through to the next source or leave the job without a correlation id? NFR-56 needs a CorrelationId on every handler log line.
5. **Decide in delivery** · INV-127, REQ-168: for a job enqueued from a handler and for a continuation, which wins when REQ-168 also has a source (a configured accessor or header, or the handler's consumer span as the current Activity, NFR-54): the parent's correlation id or the captured one? INV-127 says "every"; REQ-168's notes say explicit configuration beats ambient context. The criteria hold only where REQ-168 has nothing to capture.
6. **Decide in delivery** · INV-127: what correlation id does a batch-level continuation get (REQ-181)? It waits on a batch, not a job, and a batch has no correlation id (the jobs Batch entity has a name and members only).
7. **Decide in delivery** · REQ-167, TECH-32: are a job's index entries removed when the job is deleted or removed by retention (REQ-144, REQ-145)? Neither names the index, and without it a query or a count by tag (REQ-308, REQ-325) includes jobs that no longer exist.
