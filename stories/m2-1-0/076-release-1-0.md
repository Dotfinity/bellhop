# ST-076 — Prepare the 1.0 release: API compatibility, upgrades, changelog and package audit

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-052, ST-053, ST-064, ST-063, ST-065, ST-067, ST-073, ST-074, ST-075

## Context

Prepares the 1.0 release, the first whose compatibility promises bind. It installs the checks that keep later minor and patch releases compatible, API-compatibility tooling and a schema diff (NFR-20), the upgrade test that runs jobs written by one version on the next (NFR-19), the rule that a removal needs an analyzer warning at least one minor release earlier (NFR-21), and the release checks for an upgrade guide and breaking-change list per major version (NFR-22) and a changelog entry per release (NFR-23). It also audits what 1.0 ships: the core package's contents (TECH-112), no runtime licence checks (NFR-38), no telemetry (NFR-39) and no paid tier (NFR-40). NFR-38 and NFR-39 are standing items that every story keeps holding; this story owns their audit at the release.

Builds on every M2 story through ST-052, ST-053 (the analyzers TECH-112 lists), ST-063, ST-064, ST-065, ST-067, ST-073 (docs), ST-074 (benchmarks) and ST-075 (query plans). It keeps ST-073's NFR-26 and NFR-2 holding over the final 1.0 option set, which includes options added after ST-073 that no other story re-inspects. ST-077, the M2 acceptance run, builds on it, and every later release keeps its checks green. NFR-20 is inferred M1; it is placed at 1.0 because REQ-36 calls M1 a preview and 1.0 is where the compatibility baseline is first published. That placement is a planning assumption, not a decision in the specs; open question 1 asks the owner whether these promises already cover the step from the preview to 1.0.

The checks run in the repository's CI and release process, over the packages the specs name for 1.0: Bellhop (TECH-112, TECH-124), Bellhop.Testing (TECH-102), Bellhop.Dashboard (TECH-88), Bellhop.PostgreSql (TECH-37), Bellhop.SqlServer (TECH-40), Bellhop.Sqlite (TECH-42), Bellhop.Redis (TECH-70), Bellhop.EntityFrameworkCore (TECH-49) and Bellhop.Storage.Conformance (TECH-105), all shipped at one version with exact-version dependencies on each other (TECH-50). Where the changelog, upgrade guides and breaking-change lists are published is open question 4.

## Acceptance criteria

### AC-1 · TECH-112 · must

> **Core package contents** — The Bellhop core package shall contain the abstractions, engine, hosting integration, in-memory store, analyzers, OpenTelemetry instrumentation, health check, throttling, notifications, HTTP jobs and IJobContextAccessor.

- Inspection of the built Bellhop package: it contains the abstractions, the engine, the hosting integration (TECH-11, TECH-128), the in-memory store, the analyzers (TECH-107 to TECH-111), the OpenTelemetry instrumentation (TECH-97, TECH-98), the health check (AddBellhopHealthCheck(), TECH-101), throttling, notifications (AddAlerts(), TECH-129), HTTP jobs (HttpRequestJob, TECH-114) and IJobContextAccessor (TECH-34). The reviewer records the package's contents in Notes.
- Test: a consumer project that references only the Bellhop package compiles and runs code that uses each of those parts against the in-memory store, and an analyzer from the package reports in it (TECH-107 on a job type without [JobName]).
- Given any listed part, then no other first-party package is needed to use it; in particular there is no separate Bellhop.Http package (TECH-112's source).
- With all of this inside, the core package still depends only on the BCL and Microsoft.Extensions.* (TECH-8) and on neither ASP.NET Core nor Entity Framework Core (TECH-9); ST-001's dependency audit stays green.

### AC-2 · NFR-19 · must

> **Job compatibility across versions** — The system shall run jobs enqueued by version N on version N+1.
>
> *Measure:* jobs of every state written by N are processed correctly by N+1 in the upgrade test · *Verification:* test

- Upgrade test, on each store that keeps jobs across a restart (PostgreSQL, SQL Server, SQLite and Redis): version N writes jobs in every state of the jobs module (Scheduled, Enqueued, Processing, Succeeded, Failed, DeadLettered, Cancelled, Awaiting, Unroutable), its nodes stop, and N+1 nodes start on the same store after N+1's migrations (TECH-127).
- Then every job is processed correctly by N+1: each unfinished job continues through the transitions the specs give its state, for example a scheduled job runs when due (jobs REQ-122) and a processing job is recovered once its lease has expired (jobs REQ-132); each finished job stays readable and is removed by retention (jobs REQ-145).
- Given a job that N+1 cannot read, drops, or runs again outside the at-least-once window (hosting REQ-10), then the test fails.
- N is the last published release and N+1 the build under test. Whether N may be the M1 preview at 1.0 is open question 1; if not, the test first runs for the first release after 1.0, against 1.0.

### AC-3 · NFR-20 · must

> **Semantic versioning** — The system shall follow strict SemVer, with no breaking change in a minor or patch release, including attribute shapes, option names, table layout, dashboard auth behaviour and the JSON API.
>
> *Measure:* 0 breaking changes in minor or patch releases, checked by API-compatibility tooling and the schema diff · *Verification:* inspection

- Inspection of the release gate: for a minor or patch release, CI compares the public API of every first-party package with the last release's, using API-compatibility tooling, and every SQL store's schema with the last release's (schema diff), and fails on a breaking change. The reviewer confirms both run on the release build and records their output in Notes. The measure is 0 breaking changes in minor and patch releases.
- Coverage: attribute shapes and option names through the API comparison, with option names also checked as configuration keys under the "Bellhop" section (TECH-10); table layout through the schema diff, which within a major version accepts only added or widened objects (TECH-127); the JSON API through a comparison of its OpenAPI document with the last release's (TECH-92). How dashboard auth behaviour and the Redis store's layout are checked is open question 2.
- Failure criteria, on a test branch: a removed public member, a renamed option, a changed attribute constructor, a dropped or narrowed column and a removed JSON API field each make the gate fail.
- At 1.0 the baseline is 1.0.0 itself. Whether the preview counts is open question 1.

### AC-4 · NFR-21 · must

> **Deprecation warnings** — The system shall flag every deprecated API with an analyzer warning at least one minor release before removing it.
>
> *Measure:* every removal has an analyzer warning shipped ≥ 1 minor earlier · *Verification:* inspection

- Inspection at each major release: the reviewer lists every API removed since the previous major, from NFR-20's API comparison, and for each the minor release, at least one minor before the removal, that shipped an analyzer warning on it. A removal without such a warning fails the measure. The list is recorded in Notes for that release.
- Given a deprecated API, when a project uses it, then the build reports a warning. Whether the compiler's warning on an obsolete-marked API counts is open question 3.
- At 1.0, the removals to list depend on open question 1.

### AC-5 · NFR-22 · must

> **Upgrade guides** — The project shall publish an upgrade guide and a breaking-change list for every major version.
>
> *Measure:* 1 guide and 1 breaking-change list per major release · *Verification:* inspection

- Inspection at each major release: the docs hold exactly one upgrade guide and one breaking-change list for it, and the release check refuses a major release without both. The reviewer compares the breaking-change list with NFR-20's API comparison and schema diff against the previous major and records the result in Notes.
- Whether 1.0 needs a guide and a list, from the preview, is open question 1.

### AC-6 · NFR-23 · must

> **Changelog** — The project shall publish a changelog entry for every release.
>
> *Measure:* 1 changelog entry per release · *Verification:* inspection

- Inspection at each release: the changelog has exactly one entry for it, and the release check refuses a release without one. At 1.0, the reviewer finds the 1.0 entry and records it in Notes.
- Where the changelog is published is open question 4.

### AC-7 · NFR-38 · must

> **No licence checks** — The system shall perform no runtime licence checks.
>
> *Measure:* 0 licence-check code paths · *Verification:* inspection

- Inspection: the reviewer searches the source of every first-party package for runtime licence checks, such as reading a licence key or file, calling a licence server, or an edition flag that turns a feature off, and finds none. The measure is 0 licence-check code paths, recorded in Notes.
- Given no licence key or file configured, then every feature works (NFR-40).

### AC-8 · NFR-39 · must

> **No telemetry** — The system shall send no telemetry to the project or any third party.
>
> *Measure:* 0 outbound calls other than those the application configures (store, notifications, HTTP jobs, its own OpenTelemetry exporters) · *Verification:* inspection

- Inspection: the reviewer lists every outbound network call site in the first-party packages and finds that each is one the application configures: the store's connection, a notification channel (TECH-115 to TECH-118), an HTTP job (TECH-113) or an OpenTelemetry exporter the application registered. The measure is 0 others, recorded in Notes.
- Supporting check: a host with the in-memory store, the worker and the dashboard, and no channel, HTTP job or exporter configured, opens no outbound connection while it runs jobs.
- The dashboard loads nothing from a CDN (TECH-91), so a browser on a dashboard page calls no third party.

### AC-9 · NFR-40 · must

> **No paid tier** — The project shall offer every feature, including continuations, chains, batches and throttling, without a paid tier.
>
> *Measure:* 0 features gated behind payment · *Verification:* inspection

- Inspection: every feature of the 1.0 packages, including continuations, chains, batches and throttling, works from the MIT-licensed packages (NFR-37) with no payment, licence key (NFR-38), paid package or edition, and the README and docs mention no paid tier. The measure is 0 features gated behind payment, recorded in Notes.
