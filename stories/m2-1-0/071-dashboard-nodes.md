# ST-071 — Sample node metrics and show the nodes page

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-034, ST-055, ST-056, ST-062

## Context

Every running node takes a metrics sample of itself every NodeSampleInterval and writes it in one batched store write (REQ-314); worker nodes delete samples older than NodeSampleRetention as one of their background duties (REQ-343); and the nodes page shows each node's heartbeat, concurrency and in-flight jobs with its process CPU, working set, GC heap, thread-pool queue length and worker utilisation, charted over 24 hours (REQ-313).

Builds on ST-034 (the dashboard's pages and actions so far), ST-012 (the registry of running worker nodes with their heartbeats, hosting REQ-60), ST-006 (the node lifecycle: hosting REQ-18 marks a node running), ST-007 (hosting REQ-40, under which a node without the worker runs no background duty; it names dashboard node-sample pruning, so this story keeps it holding) and ST-055, ST-056 and ST-062 (the SQL Server, SQLite and Redis stores, on which samples are stored like on the in-memory and PostgreSQL stores). It keeps TECH-105 holding, with conformance tests for writing and pruning samples. Built on by ST-081 (insights rollups and the insights page, M3) and ST-075 (NFR-16 for the nodes page's queries).

The nodes page lives in Bellhop.Dashboard (TECH-88). Sampling runs on every running node, including nodes that never reference the dashboard package, so it belongs with the node in the core package (TECH-112's hosting integration). Samples are the NodeSample entity (node, cpu, workingSet, gcHeap, threadPoolQueue, workerUtilisation, inFlight, takenAt) kept in the store, so the store contract grows on every store that exists by now: in-memory, PostgreSQL, SQL Server, SQLite and Redis (TECH-31). Pruning is a worker background duty beside retention cleanup (ST-021).

## Acceptance criteria

### AC-1 · REQ-313 · must

> The system shall show a nodes page with each node's heartbeat, concurrency and in-flight jobs, plus process CPU, working set, GC heap, thread-pool queue length and worker utilisation with a 24-hour history chart.

- Given two running worker nodes with different concurrency limits, in-flight jobs and samples, when a viewer opens the nodes page, then each node is shown with its last heartbeat, its concurrency, its in-flight jobs and its latest process CPU, working set, GC heap, thread-pool queue length and worker utilisation.
- Given samples of a node spanning the last 30 hours (fake `TimeProvider`, TECH-12), then its history chart covers the 24 hours before now and shows no sample older than that.
- Given a node's in-flight jobs change, then the page shows the change without a reload (REQ-315).
- The page needs view permission only (INV-301).
- Which nodes are listed, and what concurrency and worker utilisation show for a node without the worker, are open question 1.

### AC-2 · REQ-314 · must

> While a node is running, whether or not the worker is registered, the system shall take a metrics sample of that node every NodeSampleInterval, 15 s by default, and write it in one batched store write per interval.
>
> *Notes:* refiner-model 2026-11-06 F-8 (option 1): every running node samples itself, client-only and dashboard-only nodes included; sampling is not a background duty under hosting REQ-40. Pruning old samples moved to REQ-343, a worker duty.

- Given a running node and a fake `TimeProvider` (TECH-12), when the clock advances by four times NodeSampleInterval, 15 s by default, then four samples of that node are stored, and a spy on the store sees exactly one sample write per interval.
- Given NodeSampleInterval configured as 5 s, then the node writes one sample every 5 s.
- Given a node that registers only the client, only maps the dashboard, registers the worker, or registers none of them, then each takes and writes its own samples (REQ-314's notes: sampling is not a hosting REQ-40 duty).
- Given a node that is still starting, failed to start or has stopped, then it writes no sample.
- What happens when a sample's write fails is open question 2. Whether these writes count as store load under NFR-11 is open question 4.

### AC-3 · REQ-343 · must

> Where the worker is registered on a node, the system shall delete node samples older than NodeSampleRetention, 7 days by default, as one of that node's background duties.
>
> *Notes:* refiner-model 2026-11-06 F-8 (option 1): split from REQ-314. Pruning is retention cleanup, a worker duty under hosting REQ-40; samples are not pruned while no worker is alive.

- Given a worker node and samples taken 8 days ago, 6 days ago and an hour ago (fake `TimeProvider`), when its pruning duty runs, then the 8-day-old sample is deleted and the others are kept.
- Given NodeSampleRetention configured as 1 day, then the duty deletes the samples older than 1 day and keeps the hour-old one.
- Given no node with the worker registered, then no sample is deleted however old it is (hosting REQ-40, REQ-343's notes).
- Concurrency: two worker nodes run the duty at the same moment; afterwards no sample younger than NodeSampleRetention has been deleted, every older one has, and neither node logs an error.
- How often the duty runs, and whether it is paced like retention cleanup, is open question 3.

## Tests

Every test carries one `Trait("Req", "<id>")` for each item it verifies.

- Unit, with a fake `TimeProvider` (TECH-12): REQ-314's cadence (default and override) and REQ-343's age cut-off (default and override).
- Integration, on every store (in-memory, PostgreSQL, SQL Server, SQLite, Redis): REQ-314's one write per interval through a store spy; REQ-343's pruning on a worker node, none on a node without the worker, and two pruning nodes at once.

- HTTP, against the dashboard in an in-process test server: REQ-313 with two nodes and 30 hours of samples written into the store.
- Conformance: writing and pruning samples join the store conformance suite (TECH-105, ST-054) and run on every store.
- Must keep holding: hosting REQ-40 and TECH-105 tests stay green, extended with sample pruning absent on nodes without the worker. ST-030's idle-load test (NFR-10) is rerun with sampling on.
- Not automated: how the history chart reads is reviewed by hand in the browser; the data behind it is tested.
