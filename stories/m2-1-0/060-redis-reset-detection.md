# ST-060 — Detect a Redis flush or reset and pause while reconciling

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-059

## Context

Makes the Redis store notice that its data was lost or rolled back (FLUSHALL, a restore from an old snapshot, a failover to a lagging replica) and pause claims and recurring occurrences until running jobs have had one lease to re-assert themselves (REQ-507, REQ-526, REQ-509). It adds the whole life of the generation marker: the first marker on a new server, initialised without a report (REQ-528, SCN-503), the advance every RecurringReconcileInterval that makes a rollback visible (REQ-527, SCN-505), the silent join of the other workers (REQ-530), the periodic re-seeding of code-defined recurring jobs (REQ-510) and Degraded health while reconciling (REQ-508). Without it a flush silently stops recurring jobs and erases concurrency holds, so two runs could share a Max = 1 key (REQ-526's rationale).

Builds on ST-059 (server detection, REQ-529's reconnection, which resumes a reconciliation through REQ-530, and REQ-505, which refuses eviction so partial loss is excluded), ST-058 (the claim, heartbeat and completion scripts, TECH-57, TECH-62), ST-057 (the marker in the key layout, TECH-56), ST-022 (reconciling code-defined recurring jobs, recurring REQ-203), ST-026 (the trigger the pause stops and the misfire policy that handles instants missed meanwhile) and ST-015 (the health state machine). It must keep ST-059's REQ-529 holding while the store is Reconciling, so a lost connection or role change still marks it connecting and repeats detection, and its REQ-503 and REQ-504, which log only after a connection or reconnection, never when REQ-509 makes the store ready again (REQ-504's notes). ST-061 builds on it: the heartbeat's re-creation of a vanished run (REQ-522), the unique-key cancel (REQ-534), the reset record that REQ-507's script writes (REQ-523), the health rule that outlasts reconciliation (REQ-524), and TECH-130 as a whole, which it owns and verifies. REQ-509's wait exists so those re-creations land before claims resume; this story builds the wait and tests it with runs that heartbeat, and ST-061 adds what the heartbeat re-creates. ST-062, ST-064 (one marker per hash tag under ShardByQueue) and ST-077 (a Redis flush end to end) follow.

Lives in Bellhop.Redis (TECH-70). The claim, heartbeat, completion and recurring trigger scripts gain the marker checks and writes that REQ-507, REQ-526, REQ-528 and REQ-530 call for, and every other marker read a worker makes (REQ-527's advance, REQ-509's clear) goes through a script that does the same. Those scripts follow TECH-130, which ST-061 owns because its statement also requires the heartbeat's re-creation, the unique-key cancel and REQ-523's record that ST-061 builds. This story builds the default tagging, one hash tag per namespace (TECH-58); per-queue markers under ShardByQueue are ST-064's.

- redis A-25 (affects REQ-530, LIV-500): A node "has finished a value's reconciliation" once REQ-509 found the marker at that value, cleared or already unflagged (REQ-530 notes)
- redis A-31 (affects REQ-523, REQ-530): REQ-523's trigger, "this node replaces the generation marker under REQ-507", is `DetectReset` (and its store side in `ReplyLost`). `InitMarker` (REQ-528) and `Learn` (REQ-530) record nothing
- redis A-28 (affects REQ-526, REQ-522, REQ-521, REQ-523): A script's read and the node's response to it (REQ-507/528/530) are ordered response-first: the claim, heartbeat or completion takes effect only once no sentence applies. ## Acceptance criteria

### AC-1 · REQ-507 · must

> Where the worker is registered, while the store is ready or reconciling, when any read this node makes of the generation marker, including those of its claim, heartbeat and completion scripts, finds it missing, or with a value older than the last value this node saw, whether or not it is flagged as reconciling, if this node has seen a generation marker since it started, then the system shall replace the marker, in the same atomic step as the read that found it, with the Redis server's current time as both its value and its last-reset value, flagged as reconciling, log the ERROR event StoreWasReset, and start re-seeding the code-defined recurring jobs, the queue registry and this node's registration.
>
> *Transition:* RedisStore: Ready | Reconciling → Reconciling · *Actor:* system
>
> *Notes:* Causes: FLUSHALL, a restore from an old snapshot, a failover to a lagging replica (both bring back an older marker). Partial eviction is excluded by REQ-505. A run whose job record vanished re-creates it at its next heartbeat (REQ-522) or completion (REQ-521). Runtime-defined recurring jobs cannot be re-seeded; the loss is reported and health stays Degraded until an operator acknowledges it (REQ-523 to REQ-525). refiner-model 2026-11-06: F-2 option 1 (owner's decision: full protection) adds the 'older' test, with the marker advanced every RecurringReconcileInterval (REQ-527); a rollback to a state less than one interval old is not detected. F-3 (recommended): only a node that has seen a marker reports a reset; a new server is initialised by REQ-528. F-4 (recommended): detection and reconciliation are worker duties, matching hosting REQ-40. F-8 (recommended): the reconciling marker is written at detection, so a second flush during reconciliation removes it and is detected again. F-9 (recommended): exactly one node reports each reset and the others reconcile silently (a compare-and-set at first; since run 5 F-1 it follows from the atomic write). F-13 (recommended): the node registration is re-seeded too, so the orphan sweep (recurring REQ-205, REQ-207) does not act on the re-seeded jobs. Run 2: F-1 (recommended), a flagged marker is judged too, so the lowest-value first marker a late node writes after a flush (REQ-528) is still found older and reported. F-6 (recommended), values come from the server clock, which keeps moving across a flush, so no two nodes pick values that go backwards relative to each other and report a phantom reset; a failover to a server whose clock is behind looks like a rollback and is reported as a reset (NFR-31). F-5 (option 2, accepted): after a rollback to older data, jobs claimed since that copy may run again and their outcomes may be lost until a node detects it; this is at-least-once, like a lost lease, and is reported. Closing it fully is impossible, since a rollback within one RecurringReconcileInterval is not detected at all. Run 4 F-1 (recommended option): every marker read the node already makes is a detection point, not a separate look at some unspecified time. The claim script reads the marker every PollInterval and the heartbeat every HeartbeatInterval, so a node that is working sees a flush well within REQ-509's wait of one LeaseDuration, before REQ-527 can advance the lowest-value marker of REQ-528 away. Before, a node could claim and heartbeat under that marker without detecting it, and the flush stayed hidden with no node paused. Only a node that makes no read for the whole window misses it, and its runs have lost their lease; that is the case REQ-528's notes and NFR-31 accept. Run 5 F-1 (recommended option): the write is made in the same atomic step as the read that found the marker missing or older (the same script, TECH-130). Run 4 moved that read into the scripts, which left the compare-and-set as a later command, and it could lose to REQ-528's first marker or REQ-527's advance; neither reports, so the loser re-seeded silently and the flush went unreported although this node had read it. With the read and the write in one step nothing can land between them, the write always succeeds, and every other node finds the new flagged value and joins silently (REQ-530). F-9's 'exactly one node reports each reset' now follows from that, with no compare-and-set. Not chosen: retrying a lost compare-and-set (a second rule with a subtle last-reset test), or replacing REQ-528's lowest-value marker with an 'initialised without a report' mark (run 3 F-3 already declined a second detection trigger).

- Given worker node n1 whose store is ready and which has seen the generation marker, when someone runs FLUSHALL and n1's next claim, heartbeat or completion script reads the marker, then that same script replaces it with the server's current time as both its value and its last-reset value, flagged as reconciling (TECH-130); n1 logs the ERROR event StoreWasReset once, its store becomes Reconciling, and it starts re-seeding its code-defined recurring jobs, the queue registry and its registration.
- Given n1 last saw value v and the store now holds a marker older than v (a restore or failover, written into the store directly by the test), then the same happens, whether the older marker is flagged or not (SCN-505). An older flagged marker is what a late node writes after a flush (REQ-528); n1 reports it and does not join it (REQ-530).
- Given a marker equal to or newer than the last value n1 saw, then this rule does not apply: no replacement and no StoreWasReset.
- If the node has not seen a marker since it started, then this rule never applies to it; a missing marker is REQ-528's case.
- Given a node with the worker not registered, then it never replaces the marker, logs no StoreWasReset and re-seeds nothing (SCN-506, hosting REQ-40).
- Given n1 lost its connection (REQ-529) and FLUSHALL ran meanwhile, when it reconnects and its store is ready, then its first marker read applies this rule, because it has seen a marker since it started.
- Given n1 is already reconciling and a second FLUSHALL removes its flagged marker, then its next marker read detects the reset again, writes a new flagged value and starts re-seeding again, which restarts REQ-509's wait (SCN-509).
- Concurrency: given two worker nodes that both saw the marker, when FLUSHALL runs and both nodes' scripts read the marker at once, then exactly one script replaces it and exactly one StoreWasReset is logged; the other node finds the new flagged value and joins it silently (REQ-530).
- Property: over random sequences of advances (REQ-527), first markers (REQ-528), joins (REQ-530), clears (REQ-509), reconnections and node restarts with no flush and no rollback, no node logs StoreWasReset.
- Whether a replacement may carry a value older than one written meanwhile is open question 2.

### AC-3 · REQ-509 · must

> While the store is reconciling, when this node has re-seeded the code-defined recurring jobs, the queue registry and its registration, and LeaseDuration has passed since it last started re-seeding (REQ-507, REQ-528, REQ-530), the system shall clear the reconciling flag on the generation marker if it is still set on the value this reconciliation is for, and mark the store ready.
>
> *Transition:* RedisStore: Reconciling → Ready · *Actor:* system
>
> *Notes:* refiner-model 2026-11-06: F-8 (recommended) moves writing the new marker to detection (REQ-507), so this only clears the flag. F-1 option 1 (owner's decision: full protection): waiting HeartbeatInterval gives every live run one heartbeat to re-create its record and concurrency-key hold (REQ-522) before claims resume (REQ-526). Cost: claims pause for about 20 s after a reset. Run 2 F-3 (recommended option): the wait is a full LeaseDuration, measured from when this node's store became reconciling, which a reconnection restarts (REQ-529, REQ-530). The rule is that a detected flush ends every lease: the flag is never cleared less than one lease after it was set, so a run that could not re-assert its record in that time would have lost its lease without any reset (jobs REQ-132) and is treated the same way. Cost: claims pause for about 60 s after a reset, and for the same time when the first worker starts on a new server (REQ-528). Run 3 F-1 (recommended option): the wait restarts every time this node starts re-seeding, a second detection while already reconciling included. Measured from the store becoming reconciling, a second flush caught mid-reconciliation inherited a wait that was already over, so its flag was cleared at once beside a run that had kept its lease.

- Given a node reconciling value T, which it wrote or joined, when it has re-seeded the code-defined recurring jobs, the queue registry and its registration and LeaseDuration has passed since it last started re-seeding, then it clears the reconciling flag if the marker still holds T flagged, and its store becomes Ready.
- If LeaseDuration has not passed since it last started re-seeding, then the flag stays set and claims stay paused (REQ-526), even when re-seeding finished long before.
- If re-seeding has not finished, then the flag stays set, whatever time has passed.
- Given the wait was restarted by a second detection, a join or a reconnection while reconciling (REQ-507, REQ-530, REQ-529), then LeaseDuration counts from the last start, never from when the store first became reconciling (SCN-509).
- Given the marker now holds another value because another node replaced it, then this node leaves that value's flag alone, becomes Ready, and joins the new value through REQ-530 (REQ-528's notes).
- Given another node already cleared the flag on T, then this node changes nothing on the marker and becomes Ready.
- Given the clear's script finds the marker missing (a flush during the wait), then it applies REQ-507 instead of clearing (TECH-130, redis A-2).
- Given LeaseDuration is not configured, then the flag is never cleared less than 60 seconds after the last re-seeding started (jobs REQ-102); given LeaseDuration is lowered for a test, then the shorter wait applies (REQ-528's notes).
- These waits are checked in real time with the node's clock and the server's clock in step. Which clock times the wait when they differ is open question 4; no criterion is set there, and no test shortens the wait by moving a fake node clock.

### AC-4 · REQ-510 · must

> While the store is ready, when RecurringReconcileInterval, 5 minutes by default, has passed since the last reconciliation, the system shall reconcile the code-defined recurring jobs again so that a flush never silently stops them.
>
> *Transition:* RedisStore: Ready → Ready · *Actor:* system

- Given a worker node whose store is ready and RecurringReconcileInterval is not configured, when 5 minutes have passed since its last reconciliation, then it reconciles its code-defined recurring jobs again: a code-defined job whose definition the test removed from the store directly exists again (recurring REQ-203).
- Before 5 minutes have passed, then it has not reconciled again: the removed definition is still missing.
- Given RecurringReconcileInterval is configured as 1 minute, then both criteria hold with 1 minute in place of 5.
- While the store is reconciling, this rule does not run; the reconciliation's own re-seeding applies (REQ-509).
- Given a node with the worker not registered, then it never reconciles (hosting REQ-40 lists Redis recurring reconciliation as a worker duty).
- Given two worker nodes reconciling the same definitions at the same moment, then no definition is duplicated and neither reconciliation fails (recurring INV-200).
- The interval is checked in real time with the node's and the server's clocks in step; which clock times it when they differ is open question 4.

### AC-5 · REQ-527 · must

> Where the worker is registered, while the store is ready, when RecurringReconcileInterval has passed since the generation marker was last advanced, the system shall advance the unflagged generation marker to the Redis server's current time by compare-and-set, unless another node already did, and remember the value.
>
> *Transition:* RedisStore: Ready → Ready · *Actor:* system
>
> *Rationale:* A restore or failover brings back an older marker; only a marker that moves forward reveals the rollback (REQ-507).
>
> *Notes:* refiner-model 2026-11-06 F-2 option 1 (owner's decision on 2026-11-06: full protection). Part of the Redis recurring reconciliation duty, so worker nodes only (hosting REQ-40). Every node remembers the latest marker value it reads (lastSeenMarker). Cost: one write per interval. Run 2 F-6 (recommended option): the server clock, not the node's memory, makes every new value later than any written before; the last-reset value is left as it is.

- Given worker nodes whose stores are ready and an unflagged marker, when RecurringReconcileInterval has passed since the marker was last advanced (checked in real time with RecurringReconcileInterval lowered and the clocks in step), then the marker is advanced to the server's current time by compare-and-set, its last-reset value is unchanged, and the advancing node remembers the new value as the last value it saw.
- Property, over random interleavings of advances by several worker nodes with flags set and cleared: a flagged marker is never advanced, and each marker value is advanced at most once (one compare-and-set from a value wins; the other node writes nothing and remembers the value it finds).
- If this node's store is not ready, then this node advances nothing.
- Which clock times the interval, the node's or the server's, is open question 4; no criterion depends on it.
- Given a node with the worker not registered, then it never advances the marker (hosting REQ-40).
- Given a flush just before the advance, then the advance's script finds the marker missing and applies REQ-507, or REQ-528 for a node that has not seen a marker, instead (TECH-130).
- Given the marker was advanced to v and the store is then rolled back to a marker older than v, then the first marker read of a node that saw v reports the reset (REQ-507, SCN-505).
- A rollback to a state less than one RecurringReconcileInterval old is not detected (REQ-507's notes, NFR-31); no criterion asserts detection there.

### AC-6 · REQ-528 · must

> Where the worker is registered, while the store is ready, when any read this node makes of the generation marker, including those of its claim, heartbeat and completion scripts, finds it missing, if this node has not seen a generation marker since it started, then the system shall write the first generation marker at the lowest value, with the Redis server's current time as its last-reset value, flagged as reconciling, in the same atomic step as the read that found it missing, log at INFO that it initialised the store and that claims start when the reconciliation ends, and start re-seeding the code-defined recurring jobs, the queue registry and this node's registration without logging StoreWasReset or recording the reset as unacknowledged.
>
> *Transition:* RedisStore: Ready → Reconciling · *Actor:* system
>
> *Rationale:* An empty server and a flushed one look the same; a new installation must not be reported as a reset.
>
> *Notes:* refiner-model 2026-11-06 F-3 (recommended option). Same event as REQ-507 for a node that has not seen a marker. A flush that happens while every worker is down is still reported if a node that saw the old marker comes back: it finds this lowest-value marker older than the one it saw (REQ-507). It goes unreported if no running node saw a marker before, or if every node that did misses this marker until it is advanced (run 3 F-3). Run 2 F-1 (recommended option): a flushed server looks exactly like a new one, and the first node to look may be one that started moments after the flush while another node is still running a job. The first marker is therefore flagged and reconciled (REQ-509): claims stay paused for one lease, running jobs re-assert their holds, and a node that saw an earlier marker still finds this one older and reports the reset (REQ-507). Cost: on a new server the first claim waits one LeaseDuration (60 s); tests against a fresh Redis can lower LeaseDuration (NFR-31). If another node replaces the marker meanwhile, this node finishes its wait, then joins the new value through REQ-530. Run 3 F-3 (option 2): the first marker carries the server's current time as its last-reset value, so a run claimed under an earlier marker on a node that missed this whole reconciliation still has its outcome recorded (REQ-521, glossary resetSinceClaim). The flush itself is reported only if a node that saw the earlier marker reads this one before REQ-527 advances it; a node paused for that whole time (more than one LeaseDuration, so its runs are lease-lost anyway) does not report it, and NFR-31 says so. Not chosen: letting such a node detect it later, which needs every node to remember a second value and a third detection trigger, and would start a second cluster-wide pause when the paused node wakes. Run 4 F-1: 'reads this one' means any marker read, including the claim and heartbeat scripts (REQ-507), so 'paused' means making no marker read for the whole window. Run 5 F-1: the write is atomic with the read that found the marker missing, like REQ-507's, so 'only if none exists yet' holds by construction and no other write can land between them.

- Given worker node n1, which has not seen a marker since it started, and an empty server, when its first marker read finds the marker missing, then the same script writes the first marker at the lowest value, flagged as reconciling, with the server's current time as its last-reset value; n1 logs at INFO that it initialised the store and that claims start when the reconciliation ends, and starts re-seeding (SCN-503).
- Then n1 logs no StoreWasReset, and the store holds no unacknowledged reset record (REQ-523 is not triggered, redis A-31).
- Then nothing is claimed until REQ-509 clears the flag one LeaseDuration later (REQ-526).
- Concurrency: given two such nodes starting at once against an empty server, then one first marker is written; the other node finds it flagged and joins silently (REQ-530); neither logs StoreWasReset.
- If the node has seen a marker since it started, then a missing marker takes REQ-507's path and is reported.
- Given worker node n1 saw the marker before a flush and node n2 writes the first marker after it, when n1 next reads the marker, then it finds it older than the value it saw and reports the reset (REQ-507, SCN-507).
- Given a node with the worker not registered finds the marker missing, then it writes nothing; the marker stays missing until a worker node writes it (LIV-501).

### AC-7 · REQ-530 · must

> Where the worker is registered, while the store is ready, when any read this node makes of the generation marker, including those of its claim, heartbeat and completion scripts, finds it flagged as reconciling with a value whose reconciliation this node has not finished, if that value is not older than the last value this node saw, then the system shall start re-seeding the code-defined recurring jobs, the queue registry and this node's registration without logging StoreWasReset, and remember the value.
>
> *Transition:* RedisStore: Ready → Reconciling · *Actor:* system
>
> *Rationale:* Every worker re-seeds what its own code declares and its own registration; only the node that detected the reset reports it.
>
> *Notes:* refiner-model 2026-11-06 F-9 and F-13 (recommended options): the nodes other than the one that replaced the marker under REQ-507 reconcile silently. Also resumes a reconciliation interrupted by a reconnection (REQ-529, F-12). Run 2 F-4 (recommended option): a node has finished a value's reconciliation once it cleared the flag on it (REQ-509) or found the marker no longer flagged with it. Before, a reconnection after re-seeding but before the clear left the flag set for good and blocked every claim; re-seeding again is idempotent and costs little. Run 3 F-4 (recommended option): a flagged marker older than the last value this node saw is a reset this node must report (REQ-507), not a reconciliation to join. Without the guard both sentences applied, and joining silently made the node remember the lower value, so the flush was never reported. Run 4 F-1: the same marker reads as REQ-507 drive this sentence, so one check on every read covers REQ-507, REQ-528 and REQ-530. Run 5 F-1: REQ-507's write is atomic with its read, so no node loses it; the other nodes find the new flagged value and join here.

- Given worker node n2, which saw marker value v, when another node replaces the marker with a flagged value T later than v (REQ-507) and n2's next marker read finds T flagged, then n2 starts re-seeding its code-defined recurring jobs, the queue registry and its registration, its store becomes Reconciling, it remembers T as the last value it saw, and it logs no StoreWasReset. It then clears the flag or finds it cleared under REQ-509 after its own wait.
- If T is older than the last value n2 saw, then n2 does not join: REQ-507 applies and n2 reports the reset.
- If n2 has already finished T's reconciliation (it cleared the flag on T or found the marker no longer flagged with T, redis A-25), then reading T does not start re-seeding again. What that means for a flag that a rollback brings back is open question 1.
- Given n2 had re-seeded for T but not cleared when its connection dropped (REQ-529), when it reconnects and finds T still flagged, then it re-seeds again and its REQ-509 wait restarts (REQ-530's and REQ-529's notes).
- Given a node that has not seen any marker finds a flagged marker, then it joins it.
- Given a node with the worker not registered, then it never re-seeds.
- Property: over random interleavings of one flush with two or three worker nodes, with every script reply arriving, exactly one StoreWasReset is logged and every worker re-seeds.

### AC-8 · REQ-526 · must

> While the generation marker is missing or flagged as reconciling, the system shall claim no job and create no recurring occurrence.
>
> *Rationale:* Holds erased by a flush must be re-asserted (REQ-522) before new holders are admitted, or two jobs run under a Max = 1 concurrency key (jobs INV-107, INV-108, recurring INV-204).
>
> *Notes:* refiner-model 2026-11-06 F-1 option 1 (owner's decision on 2026-11-06: full protection). The claim script checks the marker itself, so claims stop the moment a flush removes it, before any node has detected the reset. A new server claims nothing until a worker node writes the first marker (REQ-528). A rollback that brings back an older marker is caught only when a node detects it (REQ-507). Run 2 F-2 (recommended in part): the scheduler creates no occurrence during the pause, because recurring overlap (INV-204) decides by looking for an unfinished job that the flush erased; instants that fall due meanwhile are handled by the misfire policy when the pause ends (recurring REQ-217 to REQ-219). Enqueues are not held, not even with a unique key; REQ-534 resolves a unique-key collision instead. A continuation added to a running job during the pause can be refused as having no parent (jobs INV-138) until the job re-asserts its record. F-5 (option 2, accepted): until a node detects a rollback, claims go on against the restored data, so jobs claimed since that copy may run again (NFR-31).

- Attack: a concurrency test with several worker nodes polling a queue of ready jobs and a due recurring job, while the test removes the marker (FLUSHALL, or deleting the marker key), sets its flag directly, or writes an older value. Observed in the store: no job moves to Processing and no recurring occurrence is created while the marker is missing or flagged; both resume after REQ-509 clears the flag.
- Given the marker is missing and no node has detected it yet, when a claim script runs, then it claims nothing; the script checks the marker itself (TECH-130), so claims stop the moment the marker is gone.
- Given a new server and only nodes without the worker, then nothing is claimed until a worker node writes the first marker and its reconciliation ends (REQ-528).
- Given the pause, when the application enqueues a job, with or without a unique key, then the enqueue is accepted, not held (REQ-526's notes); a unique-key collision is resolved by REQ-534 (ST-061).
- Given a recurring job falls due during the pause, then no occurrence is created during the pause, and when the pause ends its missed instants go through its misfire policy (recurring REQ-217 to REQ-219).
- Given a rollback brings back an older unflagged marker, then a node that saw a newer value stops claiming at its first marker read (REQ-507); until some node detects it, claims go on against the restored data (REQ-526's notes, accepted).
- What an operator's trigger-now gets during the pause is open question 3.

### AC-9 · LIV-500 · must

> While the generation marker is flagged as reconciling and a node with the worker registered is running, the system shall eventually re-seed every code-defined recurring job and clear the reconciling flag.
>
> *Notes:* refiner-model 2026-11-06 F-4 (recommended option): re-seeding is a worker duty (hosting REQ-40), so only a running worker node is obliged; a client-only node never starts a reconciliation (REQ-507). Clearing the flag matters because claims are paused while it is set (REQ-526).

- Given the marker is flagged and one worker node is running, when LeaseDuration (lowered for the test) has passed in real time and the node's scripts and re-seeding have run, then every code-defined recurring job that the running worker nodes declare exists and the flag is cleared; claims resume. A job that only a stopped node declares cannot come back until that node runs; amending LIV-500's wording to say so is open question 5.
- Given the node that detected the reset stops during its reconciliation and another worker node is running, then that node finds the flagged value at its next marker read, joins it (REQ-530) and clears the flag after its own wait.
- Given a worker's connection drops during its reconciliation and comes back (REQ-529), then the flag is still cleared, one LeaseDuration after its re-seeding restarted.
- Given a second flush during the reconciliation, then the flag is still cleared, one LeaseDuration after the last re-seeding started (SCN-509).
- Given only nodes without the worker are running, then nothing is required: the flag stays set until a worker node runs.
- A rollback to an image taken while the flag was set, after every running worker finished that value, is open question 1; no criterion is set for it.

### AC-10 · LIV-501 · must

> While the generation marker is missing and a node with the worker registered is running, the system shall eventually write a generation marker.
>
> *Rationale:* Claims are paused while the marker is missing (REQ-526), so a missing marker must not last.
>
> *Notes:* refiner-model 2026-11-06 F-1 and F-3 (owner's decision and recommended option).

- Given an idle running worker node and the marker missing (a flush, or a new server), when time is advanced by one PollInterval, then a marker exists, written under REQ-507 if the node had seen one and under REQ-528 otherwise; its claim script reads the marker every PollInterval (REQ-507's notes).
- Given every slot of the node is busy, then its heartbeat script writes the marker within one HeartbeatInterval (REQ-507's notes).
- Given only nodes without the worker are running, then nothing is required: the marker stays missing and nothing is claimed (REQ-526).

## Open questions

1. **Decide in delivery** · LIV-500, REQ-530, REQ-507, REQ-527: how does a rollback end that brings back a flagged marker? A restore or a failover to a lagging replica, to an image taken while value T was flagged, landing after every running worker finished T and before the next advance, leaves T flagged with no rule to clear it: REQ-530 does not apply (every node finished T), REQ-507 does not (T is not older than the last value seen), REQ-509 needs a reconciling store and REQ-527 advances only an unflagged marker. Claims then stay paused until a worker restarts, against LIV-500. The model's rollback liveness check (Redis_LivRestore.cfg) allows one loss only, so this shape was never checked.
2. **Decide in delivery** · TECH-56, TECH-130, TECH-59, REQ-507, REQ-528: is TECH-130's "read from the server's TIME" an exception to TECH-59's "never read TIME inside a script"? TECH-56 gives the marker a forward-only value, and the glossary says it only moves forward. Under TECH-59 a script takes the time from a TIME call made before it runs, so a REQ-507 write can carry a value earlier than one another node's REQ-527 advance wrote in between. A node that read that advance then finds the new marker older and reports the same flush a second time, against SCN-500's single StoreWasReset; redis A-24 assumes every new value is later than every earlier one.
3. **Decide in delivery** · REQ-526, recurring REQ-226: what does an operator's trigger-now get during the pause? REQ-226 allows it even for a paused job, REQ-526 creates no occurrence while the marker is missing or flagged, and neither says whether the caller of IRecurringJobManager (TECH-21) or the dashboard gets an error or the trigger is carried out when the pause ends.
4. **Decide in delivery** · REQ-509, REQ-510, REQ-527: which clock times LeaseDuration since re-seeding started, RecurringReconcileInterval since the last reconciliation, and RecurringReconcileInterval since the last advance: the node's TimeProvider (TECH-12) or the server's TIME? No item says. Marker values are the server's TIME (TECH-130), REQ-509's wait rests on lease expiry (its notes cite jobs REQ-132), and jobs INV-105 judges lease expiry on the database clock, so a node clock that runs ahead could clear the flag before a run's lease has expired.
5. **Decide in delivery** · LIV-500: may LIV-500 say "every code-defined recurring job that a running worker node declares"? A job that only a stopped node declares cannot be re-seeded until that node runs again (REQ-530's rationale: every worker re-seeds what its own code declares), so "every code-defined recurring job" cannot be met as written.
6. **Decide in delivery** · REQ-508, hosting REQ-35: what does a readiness probe answer while a node is Degraded by a reconciliation? REQ-508's notes say Degraded does not fail a readiness probe, while hosting REQ-35's notes say readiness waits HealthyAfterPasses check intervals after startup, which reads as readiness needing Healthy. A new server's first worker is Degraded for one LeaseDuration (REQ-528), so the answer decides whether it ever becomes ready in that time.

Answers go into the specs with refiner-requirements first. `stories.py scaffold --refresh ST-060` then re-quotes the changed items.
