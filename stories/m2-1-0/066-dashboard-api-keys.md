# ST-066 — Authenticate scripts with dashboard API keys

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-034, ST-055, ST-056, ST-062

## Context

Gives scripts and the CLI a way into the JSON API. With `RequireApiKey()` enabled, an operator creates a named key with view or operate scope in the dashboard, sees it once, and the system keeps only its hash; the key authenticates as "apikey:" plus its name until it is revoked or its expiresAt passes (REQ-305, REQ-337 to REQ-340). A key cannot create or revoke keys (INV-307), and a bad key is refused with 401 and never locked out (INV-308), so its strength rests on its entropy: at least 256 bits from a CSPRNG, the measure the owner decided on 2026-11-10 (NFR-62).

Builds on ST-031 (INV-301, which makes creating and revoking a key an operate action, the JSON API of TECH-92, and REQ-301's startup message, which already mentions `RequireApiKey()` and was built against what existed), ST-034 (the dashboard's operate actions, which key management joins), ST-006 (NFR-41, whose secret scan now also looks for keys) and ST-055, ST-056 and ST-062 (the SQL Server, SQLite and Redis stores, on which key records are implemented like on the in-memory and PostgreSQL stores). It keeps TECH-105 holding, so the conformance suite (ST-054) gains tests for the key-record operations, and REQ-300 and REQ-301 (ST-031), since `RequireApiKey()` changes neither the anonymous grant nor the startup failure, only REQ-301's message. Built on by ST-067 (basic auth, whose lockout must never touch a key, so it keeps REQ-305 holding), ST-068 (launches by key carry "apikey:<name>", REQ-320 to REQ-323), ST-086 (the CLI calls the JSON API with a key, TECH-122) and ST-087 (MCP uses the same API keys, TECH-121). NFR-62 is verified here although ST-067 builds REQ-304, which NFR-62 lists under Applies to: NFR-62 measures key generation only, and REQ-304 is listed because keys are never locked out (INV-308), which ST-067 keeps holding.

Lives in Bellhop.Dashboard (TECH-88): `RequireApiKey()` on the dashboard endpoint builder (REQ-305), key management in the dashboard UI and in the JSON API under the dashboard path (TECH-92). INV-308 holds on every node that serves the dashboard and nodes share state only through the store (hosting REQ-51's notes), so key records go through the store contract (TECH-31) and are implemented on every store that exists by now: in-memory, PostgreSQL, SQL Server, SQLite and Redis. The endpoints, how a request presents a key, the key's text form and the stored record are not in the specs (open questions 1 to 3).

## Acceptance criteria

### AC-1 · REQ-340 · must

> The system shall default an API key's expiry to ApiKeyDefaultExpiry, 90 days, and allow a key that never expires when the operator asks for one (ApiKeyDefaultExpiry).
>
> *Notes:* Decided by the owner on 2026-11-06.

- Given an operator creates a key without an expiry at instant t (fake `TimeProvider`, TECH-12), then its expiresAt is t plus 90 days: the key authenticates one second before that instant (REQ-305) and is answered 401 Unauthorized one second after it (INV-308).
- Given the operator asks for a key that never expires, then it has no expiresAt, still authenticates after the clock has been advanced far past 90 days, and REQ-339 never marks it expired.
- Given the operator gives an expiry, then that expiry is used instead of ApiKeyDefaultExpiry (REQ-337).
- Whether ApiKeyDefaultExpiry itself can be configured, and under which option name, is open question 4.

### AC-2 · REQ-337 · must

> When an operator creates an API key in the dashboard with a name, a scope of view or operate and an optional expiry, the system shall generate the key, show it once, and store only its hash with the name, scope, creator and expiry, using ApiKeyDefaultExpiry when no expiry is given.
>
> *Transition:* ApiKey: (new) → Active · *Actor:* Operator
>
> *Notes:* Decided by the owner on 2026-11-06. Creating a key is an operate action, so it needs operate permission and is refused on a ReadOnly dashboard (INV-302).

- Given `RequireApiKey()` and an operator with operate permission, when they create a key named n with scope view (and again with scope operate), then the key is Active, the creation response shows its value, and the stored record holds its hash, the name n, the scope, the creator and an expiresAt set by REQ-340.
- Given that creation, then the value appears in no later response (the key list, the key's details, any JSON API read, a reload of the page) and in no log line (NFR-41).
- Given the stored record, then no field of it contains the key's value; inspection confirms that only a one-way hash of it is kept, and the reviewer records the file and line in Notes.
- Given the new key, then it authenticates at once with its scope and the principal name "apikey:n" (REQ-305).
- Given an operator with view permission only, when they create a key, then the response is 403 Forbidden (INV-300) and no key is stored. Given a `ReadOnly()` dashboard, then creation is refused and no key is stored (INV-302); its response code is the one ST-031 settles (dashboard A-16).
- Given a request authenticated by an API key, then creation is refused under INV-307.
- Given an open Development dashboard (no authorization requirement, REQ-300), then an anonymous request can create a key (INV-307's notes).
- Invalid names, scopes and expiries are open question 5.

### AC-3 · REQ-338 · must

> When an operator revokes an API key in the dashboard, the system shall mark the key revoked.
>
> *Transition:* ApiKey: Active → Revoked · *Actor:* Operator
>
> *Notes:* Decided by the owner on 2026-11-06.

- Given an active key k, when an operator with operate permission revokes it, then the key list shows k as Revoked, and every later request with k is answered 401 Unauthorized (INV-308), on this node and on another node over the same store.
- Given several active keys, when one is revoked, then the others still authenticate with their own scopes (REQ-305's notes: rotation).
- Given an operator with view permission only, a `ReadOnly()` dashboard, or a request authenticated by an API key (INV-307), then the revoke is refused and k stays Active.
- Given a key that is Revoked or Expired, then it never becomes Active again and a revoke changes nothing (both are final states of ApiKey); the response to that revoke is open question 6.

### AC-4 · REQ-339 · must

> While an API key is active, when its expiresAt has passed, the system shall mark the key expired.
>
> *Transition:* ApiKey: Active → Expired · *Actor:* system
>
> *Notes:* Decided by the owner on 2026-11-06. refiner-model 2026-11-06 F-4 (option 1): this is bookkeeping for the key list; whether a key authenticates is decided from expiresAt at request time (REQ-305, INV-308), so the delay before this transition runs does not matter.

- Given an active key k with expiresAt e, when the fake clock passes e, then requests with k are answered 401 Unauthorized from that moment, whether or not k has been marked yet (INV-308), and k is then marked and shown as Expired in the key list.
- Given a key revoked before e, then it stays Revoked after e (REQ-339 applies only while a key is active).
- Given a key that never expires (REQ-340), then it is never marked expired.
- When, and on which node, the mark is made is open question 7.

### AC-5 · INV-307 · must

> If a request authenticated by an API key tries to create or revoke an API key, then the system shall respond 403 Forbidden and change nothing.
>
> *Notes:* Decided by the owner on 2026-11-06: only interactive users mint keys, so a leaked key cannot create more keys. This holds outside an open Development dashboard: there, with no scheme listed, anonymous requests have operate (REQ-300), which includes creating a key (INV-301), as accepted in run 2 F-2.

- Given `RequireApiKey()` and a request authenticated by an active operate-scope key, when it calls the create-key endpoint, then the response is 403 Forbidden and no key is created (SCN-306); when it revokes any key, its own included, then the response is 403 and the key is unchanged.
- Given a view-scope key, then both are answered 403 as well (INV-300 also requires it).
- Property: over random sequences of key creations and revocations by operators and by key-authenticated requests, interleaved with clock advances past expiresAt, the set of keys and their states change only through requests that were not authenticated by a key.
- Given an open Development dashboard (no authorization requirement, REQ-300), then a request that presents a valid key is still answered 403 when it creates or revokes a key, while a request without a key is anonymous with operate and can (INV-307's notes; the accepted check `Chk_ApiKeyNotBypassed` in the dashboard findings).

### AC-6 · INV-308 · must

> If a request presents an API key that is revoked, expired, past its expiresAt or unknown, then the system shall respond 401 Unauthorized.
>
> *Notes:* Decided by the owner on 2026-11-06 (key lifecycle). refiner-model 2026-11-06 F-2/F-3 (option 2, owner decision): failed key attempts are no longer counted as failed logins; API keys are never locked out (REQ-304) and brute-force resistance rests on key entropy (NFR). F-4 (option 1): a key past its expiresAt is refused even before REQ-339 marks it expired.

- Given `RequireApiKey()`, when a request presents a key that is revoked, marked expired, active but past its expiresAt, or unknown (never issued, or a random value of the same form), then the response is 401 Unauthorized and the request is not authenticated, for pages, JSON API reads and operate actions alike.
- Given a key revoked or expired on one node, then a request with it on another node over the same store is answered 401.
- Property over the key lifecycle: random sequences of create, revoke, clock advance past expiresAt and REQ-339's marking, with requests presenting each key; every request whose key is not active, or is past its expiresAt, is answered 401.
- Concurrency: a revoke racing requests that present the key; every request that starts after the revoke has committed is answered 401.
- Given many refused keys from one client address, then a valid key from that address is still authenticated: refused keys are not counted as failed logins and keys are never locked out (INV-308's notes). The basic-auth side of that rule is checked in ST-067.
- What a request that presents a key gets where `RequireApiKey()` is not enabled is open question 8.

### AC-7 · REQ-305 · must

> Where RequireApiKey() is enabled, when a script or the CLI calls the JSON API with an active API key whose expiresAt has not passed, the system shall authenticate it with the scope assigned to that key and the principal name "apikey:" followed by the key's name.
>
> *Notes:* Decided by the owner on 2026-11-06: keys are issued and revoked from the dashboard (REQ-337, REQ-338), stored hashed, scoped to view or operate, and expire after 90 days by default (REQ-340). Several keys can be active at once, which is how rotation works. refiner-model 2026-11-06 F-4 (option 1): expiry is decided at request time from expiresAt, so a key stops working at the instant it expires whatever REQ-339 has done. F-9 (option 1): the principal name makes key launches attributable (REQ-320, REQ-323). F-2 (owner decision): a key is never refused because of a basic-auth lockout (REQ-304). Run 2 F-2 (accepted, option 3): RequireApiKey() adds a way in for scripts and closes nothing. The dashboard UI is itself a client of the JSON API (TECH-92), so whatever REQ-300 or REQ-342 grant anonymous browsers, an anonymous script gets too; a 401 for keyless API calls would break the anonymous pages, and telling the UI's calls apart from a script's cannot be enforced. A keyless script in Development therefore has operate, like the open pages, and a production dashboard needs an authorization requirement or AllowAnonymous() for its pages even when only scripts use it (REQ-301 says so in its message).

- Given `RequireApiKey()` and an active view-scope key named "reports" whose expiresAt has not passed, when a script makes a JSON API read with it, then the request is served, authenticated with view and the principal name "apikey:reports"; an operate action with it is answered 403 Forbidden (INV-300).
- Given an active operate-scope key, then operate actions through the JSON API are performed and carry the principal name "apikey:" followed by the key's name.
- Given two active keys, then each authenticates with its own scope and name (REQ-305's notes: rotation).
- Given `RequireApiKey()` is not enabled, then no key authenticates a request (dashboard A-7).
- Given `RequireApiKey()`, then requests without a key keep what REQ-300 or REQ-342 grants them: operate in Development without an authorization requirement (the accepted check `Chk_ApiKeyNotBypassed`), view only with `AllowAnonymous()` elsewhere. Outside Development without either, the start fails and REQ-301's message says that API keys authenticate scripts but do not protect the pages.
- Property: the INV-308 lifecycle run also asserts that a request is authenticated by a key exactly when `RequireApiKey()` is enabled and the key is active and not past its expiresAt, with that key's scope.
- How a script presents its key is open question 1.

### AC-10 · NFR-62 · must

> **API key entropy** — The system shall generate every dashboard API key from a cryptographically secure random source with enough entropy that guessing a key without a lockout is infeasible.
>
> *Measure:* at least 256 bits of entropy per key, drawn from a cryptographically secure random number generator · *Verification:* inspection
>
> *Notes:* refiner-model 2026-11-06 dashboard F-2/F-3, owner's decision: API keys are never locked out and failed key attempts are not counted, so brute-force resistance rests on key entropy alone. Measure decided by the owner on 2026-11-10: 256 bits from a CSPRNG, as proposed.

- Inspection: the reviewer reads the code that generates a key and confirms that its random part comes from a cryptographically secure random number generator, that each key carries at least 256 bits (32 bytes) of that output, and that nothing (a fixed prefix, an encoding, a truncation) reduces it. The reviewer records the file and line in Notes.
- Supporting unit test: keys generated in a loop are all distinct and each carries at least 32 random bytes. It shows nothing is constant; the entropy itself is judged by the inspection.
