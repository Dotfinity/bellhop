# ST-075 — Prove every cleanup and dashboard query is indexed and paged

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-055, ST-056, ST-062, ST-068, ST-069, ST-070, ST-071, ST-072

## Context

Proves, from the query plans and commands of every store, that retention cleanup runs through an index in small paced batches (NFR-15) and that every dashboard list is paged and every dashboard query is backed by an index with 1M stored jobs (NFR-16), and fixes any query that falls short. It comes after the last M2 dashboard page, so the inventory of lists and queries is complete for 1.0. NFR-15 and NFR-16 are inferred M1, but both apply to the Redis store (TECH-66, TECH-67), which REQ-36 puts in M2, and NFR-16 covers every dashboard list, and REQ-36 puts the full dashboard in M2.

Builds on ST-055 (SQL Server), ST-056 (SQLite), ST-062 (Redis Tier 1) and the M2 dashboard pages of ST-068 to ST-072. The cleanup it inspects is ST-021's (jobs REQ-145, REQ-109), and the Redis mechanisms are ST-058's (TECH-66, TECH-67). ST-076 builds on it.

The queries live in the store packages, Bellhop.PostgreSql (TECH-37), Bellhop.SqlServer (TECH-40), Bellhop.Sqlite (TECH-42) and Bellhop.Redis (TECH-70), and the dashboard's lists in Bellhop.Dashboard (TECH-88), served through its JSON API (TECH-92) and, for tags and correlation ids, IJobIndex (TECH-32). An index added here goes into the store's migrations and only adds a schema object (TECH-127).

## Acceptance criteria

### AC-1 · NFR-15 · must

> **Cleanup I/O** — The system shall run retention cleanup through an index in small paced batches so that it never spikes I/O.
>
> *Measure:* every cleanup query uses an index (no table scan in the plan); batches ≤ CleanupBatchSize with a pause between them · *Verification:* inspection

- Inspection, on PostgreSQL, SQL Server and SQLite: with the store populated, the reviewer captures the plan the database reports for every cleanup query: the removal of succeeded, cancelled and dead-lettered jobs past their retention (jobs REQ-104, REQ-145), with its batch-membership exemption, and the removal of their state history, captured logs and parameters. The measure passes when no plan contains a table scan; one table scan fails it. NFR-15 gives no data size; the size used is recorded in Notes.
- Given more expired jobs than one batch holds, when cleanup runs, then each batch removes at most CleanupBatchSize rows, 500 by default (jobs REQ-109), and cleanup pauses between batches; with CleanupBatchSize configured lower, the batches follow it. REQ-109 says only "a short pause", so the pause's length is not judged.
- Inspection, on Redis: terminal jobs expire through a whole-hash EXPIRE, and the janitor trims the time-scored index sets with ZRANGEBYSCORE and ZREM, at most 500 entries per pass by default, with a pause between passes (TECH-67). Cleanup sends no KEYS or SCAN, which TECH-67's mechanism does not use.
- Which other removals count as cleanup is open question 1; the in-memory store is open question 2.

### AC-2 · NFR-16 · must

> **Dashboard query cost** — The system shall paginate every dashboard list and back every dashboard query by an index, never loading an entire table.
>
> *Measure:* 0 unpaginated lists; 0 table scans in dashboard query plans with 1M stored jobs · *Verification:* inspection

- Inventory: the reviewer lists every dashboard list and every query behind a dashboard page, JSON API read (TECH-92) or live update (REQ-315), and records it in Notes. It includes at least the overview's counts (REQ-307), the jobs list with each of its filters (REQ-308), the job detail (REQ-309), recurring jobs and their occurrence history (REQ-310, REQ-329), dead letters (REQ-311), queues (REQ-312), nodes (REQ-313), tags (REQ-325), throttles (REQ-327), recent launches (REQ-323) and the Notifications page (REQ-410).
- Given 1M stored jobs, when any list of the inventory is requested, as a page or through the JSON API, then it returns one page, never every row. This holds for lists that are short in practice, such as queues and nodes: the measure is 0 unpaginated lists, and one fails it.
- Given 1M stored jobs on PostgreSQL, SQL Server and SQLite, then no query of the inventory has a table scan in its plan, for each filter of REQ-308 alone and for each combination the jobs list lets a viewer set. One table scan fails the measure.
- Given 1M stored jobs on Redis, when the inventory's pages and API reads run, then the state, queue, name and tag filters are served from index sets with paging through ZRANGE ... LIMIT, and the server receives no KEYS or SCAN command during those requests (TECH-66), as its command statistics show.
- The page size, and whether a client can ask for a page large enough to hold a whole table, is open question 3.

## Tests

Every test carries one `Trait("Req", "<id>")` for each item it verifies.

- Inspection evidence, captured by a test per SQL store so it can be re-run: seed 1M jobs, run every cleanup query and every query of the NFR-16 inventory, collect the plans, and fail on a table scan. Tagged NFR-15 or NFR-16. The reviewer records the result in Notes.

- HTTP: every list endpoint of the JSON API returns one page with 1M stored jobs (NFR-16).
