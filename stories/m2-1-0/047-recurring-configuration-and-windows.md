# ST-047 — Define recurring jobs in configuration and limit them to a validity window

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-030, ST-037

## Context

Adds two things to recurring jobs. Jobs can be defined in configuration under Bellhop:RecurringJobs, read through IOptionsMonitor so that changes apply without a restart (TECH-120, REQ-232), and are reconciled, orphaned and protected exactly like code-defined jobs (INV-209); all three items are may. And a recurring job can have a validity window, outside which no occurrence is created on schedule (INV-202, must).

Builds on ST-022 (code-defined reconciliation, REQ-203 to REQ-207 and REQ-241, the origin REQ-202, the startup check REQ-210 and TECH-45's compare-and-set), ST-023 (REQ-211's edit protection, INV-206's removal refusal and REQ-236's name check), ST-026 (the scheduled trigger REQ-216 that INV-202 limits, with INV-201 and INV-212) ST-030 (PostgreSQL) and ST-037 (M1 accepted, so milestones are built in order). REQ-202, REQ-210 and REQ-236 already name configuration-defined jobs, and those stories built them against what existed; here they meet real configuration-defined jobs, which is why they are in this story's Must keep holding table. ST-072 builds on it (the recurring builder, and REQ-329's validity-window settings on the dashboard), and ST-054 puts it into the conformance suite.

The configuration is the Bellhop:RecurringJobs section (REQ-202) of the options that TECH-10 binds under "Bellhop", read through IOptionsMonitor (TECH-120), in the Bellhop core package. The validity window is a recurring job's activeFrom and activeUntil (the recurring RecurringJob entity), persisted with the definition on every store that exists at this point, in-memory and PostgreSQL (TECH-31). The format of a configuration entry and the way a validity window is set are not in the specs (open questions 1 and 5).

## Acceptance criteria

### AC-1 · REQ-232 · may

> Where recurring jobs are defined in configuration under Bellhop:RecurringJobs, when that configuration changes, the system shall apply the added and changed definitions without a restart.
>
> *Transition:* RecurringJob: Active | Paused → Active | Paused · *Actor:* system
>
> *Notes:* Decided by the owner on 2026-11-06: configuration-defined jobs are treated exactly like code-defined ones (INV-209): removed from configuration means orphaned once no live node declares it, read-only in the UI unless AllowRuntimeOverride, and hot reload reconciles like a start. Nodes with different configuration settle as in a rolling deploy.

- Given a running worker node whose Bellhop:RecurringJobs defines r1, when an entry r2 is added and the configuration reloads, then without a restart r2 is stored with origin configuration (REQ-202), active, with nextRunAt computed from now (REQ-203).
- Given r1 is stored, when its schedule changes in the configuration and the configuration reloads, then its stored definition and definitionHash match the new entry, its active or paused state is kept, nextRunAt is computed from now and no catch-up occurrence is created for the old schedule (REQ-204, REQ-227).
- Given r1 changes in something other than its schedule, such as its payload, then the stored definition is updated and nextRunAt does not move (REQ-204).
- Given a reload that leaves r1's entry unchanged, then nothing is written for r1, so a runtime edit made under AllowRuntimeOverride survives (REQ-204's notes).
- Given r1 is removed from the configuration of every live node, then once no live node declares it, it is orphaned and paused under orphanPolicy Orphan, or removed under Delete (REQ-205, REQ-207). While another live node still declares r1, it stays as it is.
- What a reload does with an invalid entry, or with a name that is already taken, is open question 2.

### AC-2 · INV-202 · must

> Where a recurring job has a validity window, the system shall never create an occurrence on schedule before ActiveFrom or after ActiveUntil.

- Given a recurring job that is active, with maintenance off, ActiveFrom F, ActiveUntil U and a schedule with instants before F, between F and U and after U, when the database clock is advanced past all of them with every trigger on time (a fake TimeProvider, TECH-12), then occurrences are created on schedule for the instants between F and U, and for none before F or after U.
- Property and concurrency: over random schedules, windows and misfire policies, with two nodes triggering at once and every trigger on time, so that an instant's due time and the time its occurrence is created coincide, no occurrence is created on schedule before ActiveFrom or after ActiveUntil.
- Given a recurring job without a validity window, then occurrences are created on schedule as REQ-216 says.
- Given now is outside the window, when an operator triggers the job now (REQ-226), then INV-202 does not stop the occurrence, since it covers only occurrences created on schedule.
- Late triggers, misfire catch-ups and the exact bounds are open question 5.

### AC-3 · INV-209 · may

> Where recurring jobs are defined in configuration under Bellhop:RecurringJobs, the system shall reconcile, orphan and protect them from runtime edits and removal exactly as code-defined jobs (REQ-203 to REQ-207, REQ-211, INV-206).
>
> *Notes:* Decided by the owner on 2026-11-06.

- Attack: a differential test runs the same random sequence of node starts and stops, configuration changes, operator edits, pauses and removals, and scheduler passes on two nodes, once with job r defined in code (AddRecurring, TECH-22) and once in configuration. Observed: r goes through the same states, stored definitions and nextRunAt values in both runs (REQ-203 to REQ-207); only the origin differs (REQ-202).
- Given a configuration-defined job that is not marked AllowRuntimeOverride, when an operator edits its definition through IRecurringJobManager or the dashboard, then the edit is rejected (REQ-211), while pause, resume and trigger now are allowed (REQ-211's notes). Given it is marked AllowRuntimeOverride, then the edit is accepted.
- Given a configuration-defined job that is not orphaned, when an operator removes it, then the removal is refused with INV-206's message. Once it is orphaned, removing it deletes it (REQ-213).
- Given a configuration-defined job with an invalid schedule, or with the name of a stored runtime-defined job, when a node starts, then the start fails with a message that names the job (REQ-210, REQ-236).
- The message of a rejected edit, and whether REQ-241 applies, are open questions 3 and 4.

### AC-4 · TECH-120 · may

> **Configuration-defined recurring jobs** — Configuration-defined recurring jobs shall be read through IOptionsMonitor so changes apply without a restart.

- Inspection: configuration-defined recurring jobs are read through IOptionsMonitor and its change notification, and nothing reads them only once at startup.
- Test: REQ-232's criteria pass with a configuration source that reloads while the host runs, without restarting the host.
- Passing: both hold.
