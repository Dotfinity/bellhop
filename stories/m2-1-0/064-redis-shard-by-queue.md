# ST-064 — Shard the Redis store by queue on a Cluster

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-061, ST-062

## Context

Adds the opt-in ShardByQueue mode for Redis Cluster: one hash tag per queue instead of one per namespace, so a namespace's queues can spread over several shards for higher throughput (TECH-65). In that mode unique keys are enforced per queue (INV-500, which narrows jobs INV-100), the dashboard builds its global views by aggregating across queues (INV-306), and the first page of the Redis store docs explains the trade-off (NFR-33).

Builds on ST-062 (the store proven on a Cluster), ST-061 and ST-060 (the reset rules; under ShardByQueue every hash tag carries its own generation marker, which the owner accepted on 2026-11-10, TECH-130's notes), ST-019 (jobs INV-100, whose per-queue scope this mode switches on), ST-057 (TECH-58's hash tags) and the dashboard pages of ST-032 to ST-034 that INV-306 aggregates. Because the mode moves the marker into every queue's hash tag, it must keep the reset rules holding: ST-057's TECH-56 (the marker, flag and last-reset value in every hash tag the claim scripts use), ST-060's REQ-507, REQ-509 and REQ-526, and ST-061's TECH-130 and REQ-523. No earlier story builds their per-tag form; this one does, to the extent TECH-56 and TECH-130's notes state it, and the rest of what they mean per tag is open question 6. ST-076 (the 1.0 release) builds on it, and ST-073 writes NFR-31's durability notes on the same first docs page.

Lives in Bellhop.Redis (TECH-70) for the key layout and scripts, in Bellhop.Dashboard (TECH-88) for INV-306, and in the docs site (NFR-28) for NFR-33. How the mode is switched on is not named (open question 4). Blocked: which hash slot holds REQ-523's reset record under ShardByQueue is still an open question in technical-specifications.md (open question 1), TECH-58 as written requires one hash tag per namespace, which contradicts TECH-65, while transitions that touch more than one queue have no single tag in this mode (open question 2), and the reset sentences say nothing about how they apply per tag (open question 6).

## Acceptance criteria

### AC-1 · INV-306 · must

> Where the Redis store runs in ShardByQueue mode, the system shall build global views by aggregating across queues.
>
> *Notes:* Uniqueness scope in that mode is INV-500 in the redis module.

- Attack: a property test that spreads random jobs without unique keys over several queues, states, names and tags, with ShardByQueue on a Cluster and in the default mode on the same jobs. Observed: every global view shows the same counts and the same set of jobs in both modes. Jobs with unique keys are left out because the modes keep different jobs (INV-500 against jobs INV-100); with them, each mode's views are compared with the jobs that mode stored.
- Given ShardByQueue with jobs in queues q1 and q2, when the overview (dashboard REQ-307) and the jobs list without a queue filter (dashboard REQ-308) are shown, then the counts are the sums over both queues and the list holds the matching jobs of both.
- The aggregation reads no keys with KEYS or SCAN at request time (TECH-66).
- Which views are global, and how a list merged from several queues is ordered and paged, is open question 3.
- dashboard A-5 concerns the outcomes of authorization rules and does not bear on this one.

### AC-2 · INV-500 · must

> Where ShardByQueue mode is on, the system shall enforce unique keys per queue rather than per namespace.
>
> *Notes:* This weakens INV-100: two active jobs with the same unique key can exist in different queues.

- Attack: a concurrency test that enqueues jobs with the same unique key from several nodes at once, into one queue and into several, with ShardByQueue on and off. Observed: with the mode on, at most one active job holds a key in each queue; with it off, at most one in the namespace (jobs INV-100).
- Given the mode on, when two nodes enqueue jobs with unique key k into queue q at once, then one active job holds k in q, and the other call is answered as jobs REQ-150 and REQ-152 say.
- Given the mode on, when jobs with key k are enqueued into q1 and into q2, then both are active (INV-500's notes).
- Given the mode off, then the second job with key k is treated as a duplicate whatever its queue (jobs INV-100).
- Given the mode on and a reset, then REQ-534 cancels another holder of the run's unique key only in the run's queue.

### AC-3 · TECH-65 · must

> **ShardByQueue mode** — The Redis store shall offer an opt-in ShardByQueue mode that uses one hash tag per queue for higher Cluster throughput.

- Given the mode not switched on, then the store keeps one hash tag per namespace (TECH-58, TECH-68), as before.
- Given the mode on, then different queues use different hash tags (TECH-65), and every script still declares all its keys in KEYS (TECH-58) and touches the keys of one queue's hash tag only, so no call fails with a cross-slot error. TECH-58's one tag per namespace contradicts this mode (open question 2).
- Given the mode on, then every queue's hash tag holds its own generation marker, reconciling flag and last-reset value (TECH-56: in every hash tag the claim scripts use; TECH-130's notes: every hash tag carries its own marker copy).
- Given a Cluster with queues on several shards, when one shard's primary is flushed, then the reset is detected per tag (TECH-130's notes, decided by the owner on 2026-11-10): the markers of the tags on that shard are replaced flagged as reconciling (REQ-507), and the markers of the tags on the other shards keep their values.
- The marker writes, REQ-523's record and REQ-527's advance are not atomic across the namespace in this mode (TECH-130's notes); no criterion asserts that they are. Which claims pause, whether the node is Degraded, and which last value seen applies per tag is open question 6; the record's slot is open question 1.
- Test on a Cluster: the conformance suite (TECH-105) passes in this mode with queues spread over several shards. Passing: green, with no cross-slot error.
- Inspection, recorded in Notes: for each script, the keys it declares and the hash tag they share.
- Not measured: the throughput gain; no item gives a measure.
- Which keys stay namespace-wide and how transitions across queues work is open question 2; the reset record's slot is open question 1; switching the mode on a store that holds data is open question 5.

## Open questions

1. **Blocks** · TECH-130, redis REQ-523: under ShardByQueue, which hash slot holds REQ-523's unacknowledged reset record? REQ-523 writes it in the same atomic step as REQ-507's replacement, which with one marker per hash tag happens in one queue's tag, while REQ-524, REQ-525 and REQ-532 read and write one record for the store (redis A-34). technical-specifications.md leaves the slot open. Owner to decide.
2. **Blocks** · TECH-58, TECH-65: which keys stay namespace-wide, and how does a transition that touches more than one queue stay one Cluster-safe script (TECH-57)? TECH-58 makes all keys of one namespace share one hash tag, while TECH-65 uses one per queue, so the two contradict in this mode. Under one tag per queue there is no single tag for a continuation or chain step in another queue, a batch with members in several queues, a concurrency key shared by jobs of different queues (jobs INV-108 counts across all nodes), a recurring trigger that creates an occurrence in a queue, or the node registry, queue registry and recurring definitions. Are these narrowed per queue, as INV-500 narrows uniqueness, or kept atomic some other way? Owner to decide.
3. **Decide in delivery** · INV-306: which dashboard views are global (the overview, the jobs list without a queue filter, dead letters, tag search), and how is a list merged from several queues ordered and paged, given that TECH-66 pages each index set with ZRANGE ... LIMIT?
4. **Decide in delivery** · TECH-65: what is the option that switches ShardByQueue on, and where is it set? It becomes a public option name under NFR-20.
5. **Decide in delivery** · TECH-65, TECH-56: what happens when the mode is switched on or off for a store that already holds data under the other tagging: refused at startup, migrated, or documented as needing an empty store? The key layout is documented and versioned (TECH-56).
6. **Blocks** · TECH-130, REQ-507, REQ-526: what do the reset sentences mean per hash tag? The owner accepted one marker per tag with detection per tag on 2026-11-10, but REQ-508 and REQ-509 speak of one reconciling store, REQ-507 and REQ-530 of one last value this node saw, and REQ-526 of one marker. Does a flush of one shard pause claims only in the queues whose tags lost their marker, is the node Degraded while any tag reconciles, and which tag do the recurring trigger and the re-seeding read? Neither ST-060 nor ST-061 builds the per-tag form, and no criterion beyond per-tag markers and detection can be written without the answer. Owner to decide.
