# ST-048 — Run HTTP jobs and guard outbound calls

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-030, ST-033, ST-038

## Context

Adds HTTP jobs, part of M2 under hosting REQ-36: the built-in HttpRequestJob payload (TECH-114), sent through a named HttpClient registration (REQ-420, TECH-113), whose response either succeeds the job with the response as its result (REQ-421) or fails the attempt like any handler failure (REQ-422). It also installs the rules every outbound call Bellhop makes obeys: a destination allowlist that is empty by default (INV-401), the private-address rule (INV-402), no redirect to another host and none at all unless MaxRedirects is raised (INV-403, REQ-416), credential headers only from named registrations (INV-404), checked when a job is created (INV-408), and masking of [Sensitive] headers (INV-405). A refused destination dead-letters the job at once instead of retrying a call that cannot succeed (REQ-434).

Builds on ST-030 (the job lifecycle on the in-memory and PostgreSQL stores; ST-011's retry policy decides between Failed and DeadLettered, jobs REQ-129 and REQ-131) ST-033 (the job detail page, where results and masked headers show) and ST-038 (continuations): a job that REQ-434 dead-letters is an ordinary dead-letter, so its OnFailure and OnCompletion continuations are enqueued, and this story keeps REQ-172 holding. It also uses result storage from ST-040 (jobs REQ-128), recurring definitions from code and configuration (ST-022, recurring REQ-202) and their hot reload (ST-047). ST-050 sends notification webhooks under the same rules and keeps INV-401, INV-402 and INV-403 holding; ST-068 adds the launch page and keeps INV-408 holding.

Lives in the Bellhop core package, which holds HTTP jobs (TECH-112). The payload is HttpRequestJob (TECH-114), and requests go through named HttpClient registrations from Microsoft.Extensions.Http (TECH-113); whether that package and a JSONPath evaluator fit TECH-8's core dependency rule is open question 10. Where the allowlist and MaxRedirects are configured, how a header is marked [Sensitive] and HttpRequestJob's property names are not in the specs (open questions 1, 9 and 4). INV-401 and TECH-113 also cover notification webhooks, and INV-408 the launch page; neither exists yet, so this story tests HTTP jobs created from code and configuration, and ST-050 and ST-068 add the tests for theirs.

## Acceptance criteria

### AC-1 · REQ-416 · must

> The system shall default MaxRedirects for outbound calls to 0 (MaxRedirects).
>
> *Notes:* Decided by the owner on 2026-11-06: redirects are not followed unless the application opts in.

- Given MaxRedirects is not configured, when an HTTP job's server answers 302 with a location on the same host, then no second request is sent and the 302 is the response: the attempt fails unless 302 is one of the job's accepted status codes, in which case the job succeeds (REQ-422 notes, REQ-421).
- Given the application raises MaxRedirects to 2, when the server redirects twice on the same host and then answers 200, then both redirects are followed and the 200 decides the job (INV-403).
- Where and at what scope the application raises it is open question 1.

### AC-2 · REQ-421 · must

> While an HTTP job is processing, when the response arrives, if its status is one of the accepted status codes and the success predicate, when one is set, holds for the body, then the system shall mark the job succeeded and store the status, headers and body truncated to the response capture limit as its result.
>
> *Transition:* jobs.Job: Processing → Succeeded · *Actor:* system
>
> *Notes:* Decided by the owner on 2026-11-06: the success predicate is a JSONPath with equals or exists (TECH-114).

- Given an HTTP job that accepts 200 and sets no success predicate, when the response is 200, then the job is Succeeded and its result, read by job id as jobs REQ-128 stores results, holds the response's status, headers and body.
- Given the predicate {"path": "$.status", "equals": "ok"} (TECH-114), when a 200 arrives whose body has `$.status` equal to "ok", then the job is Succeeded; given an exists predicate on a path the body contains, the same.
- Given a 3xx status that the job lists as accepted, when it arrives and is not followed (REQ-416), then the job is Succeeded (integrations A-6).
- Given a body longer than the job's response capture limit, then the stored body is no longer than that limit; a response within the limit is stored whole.
- The predicate is judged on the body as it arrived, not on the stored copy cut to the capture limit.
- If the status is not accepted, or a predicate is set and does not hold, then the job does not succeed: REQ-422 applies.
- Whether the limit cuts the body only or the stored result as a whole, the limit's default and unit, and how the result meets ResultSizeLimit (jobs REQ-185) are open questions 4 and 5.

### AC-3 · REQ-422 · must

> While an HTTP job is processing, if the response status is not accepted, the success predicate does not hold, the request times out, or no response arrives because the connection, name resolution or TLS handshake fails, then the system shall fail the attempt so the retry policy decides between Failed and DeadLettered, and store the response if there was one.
>
> *Transition:* jobs.Job: Processing → Failed | DeadLettered · *Actor:* system
>
> *Notes:* Reading confirmed by the owner on 2026-11-06: everything that is not an accepted response is an ordinary handler failure, so the retry policy decides between Failed and DeadLettered. With MaxRedirects 0 (REQ-416) a 3xx response is not followed and counts as not accepted unless listed. refiner-model 2026-11-06 F-7 option 1: transport errors are now in the sentence; a destination refused by the security rules is not a failure to retry but REQ-434.

- Given a job that accepts 200 and 204 with maxAttempts 5, when the server returns 503 on the first attempt, then the attempt fails, the job is Failed with a retry scheduled (jobs REQ-129), and the 503's status, headers and body are stored (SCN-402).
- Given the same response on the fifth attempt, then the job is DeadLettered (jobs REQ-131) and the response is stored.
- Given a 200 whose body does not satisfy the job's success predicate, or a body that is not JSON while a predicate is set, then the attempt fails and the response is stored.
- Given a server that does not answer within the job's timeout, a refused connection, a host name that does not resolve or a TLS handshake that fails, then the attempt fails and no response is stored.
- Given MaxRedirects 0 and a 3xx that the job does not list as accepted, then the attempt fails and the 3xx is stored (notes).
- Given a destination refused by INV-401 or INV-402, then this transition does not apply and no retry is scheduled: REQ-434 does.
- Where a failed attempt's response is kept, and whether a later attempt's response replaces it, is open question 5.

### AC-4 · REQ-434 · must

> While an HTTP job is processing, if its destination is refused by the destination allowlist or the private-address rule, then the system shall move the job to dead-lettered at once, without sending the request, with a reason that names the rule that refused it.
>
> *Transition:* jobs.Job: Processing → DeadLettered · *Actor:* system
>
> *Notes:* refiner-model 2026-11-06 F-7 option 1: retrying a host that is not allowed cannot succeed, so refusal is permanent. Before this, a refused job stayed Processing for ever because no requirement moved it on and the lease kept being renewed. Run 2 F-14 (recommended option): the redirect rules are no longer listed. INV-403 never follows a redirect to another host, so a followed redirect always lands on the already allowed host, and a redirect that is not followed is a response: accepted if its status is listed (REQ-421), otherwise an ordinary failure (REQ-422), as the owner decided in REQ-422's notes.

- Given an allowlist that holds only api.example.com, when an HTTP job for other.example.com is processed on its first attempt with attempts left, then the job is DeadLettered on that attempt, no request reaches any server, and the dead-letter reason names the allowlist rule.
- Given a host that the allowlist covers only through a wildcard entry and that resolves to a private-network or loopback address, then the job is DeadLettered at once in the same way, with a reason that names the private-address rule (INV-402).
- Given a host that is itself an entry on the allowlist and resolves to a public address, then the job is not refused and the request is sent (REQ-420).
- The check is made while the job is processing, so a host removed from the allowlist after the job was enqueued is refused.
- The reason's wording is open question 6.

### AC-5 · INV-401 · must

> The system shall never send an HTTP job request or a notification webhook to a host that is not on the configured destination allowlist, which is empty by default.

- Property: over random HTTP jobs with random hosts, allowlists (none configured included) and same-host redirect chains, every request a recording transport receives goes to a host on the allowlist as configured when the request is sent.
- Given no allowlist is configured, then no HTTP job sends any request, and each one is dead-lettered by REQ-434 (SCN-401's refusal, for any host).
- The notification-webhook half of this rule is tested when ST-050 adds webhook channels, which keeps it holding.

### AC-6 · INV-402 · must

> If the destination resolves to a private-network or loopback address and its host name is not itself an entry on the destination allowlist, then the system shall refuse to send the request.
>
> *Notes:* refiner-model 2026-11-06 F-8 option 1: the allowlist entry for the exact host name is the explicit permission; no wildcard entry covers a private address. Decided by the owner on 2026-11-06: the check is made on the host name and its resolution before the request, not on the address actually connected to. A name that resolves to a public address at check time and a private one at connect time (DNS rebinding) is therefore not caught; the allowlist (INV-401) is the main defence. Revisit if HTTP jobs ever take destinations from untrusted input.

- Given a host that the allowlist covers through a wildcard entry, when it resolves to a private-network or loopback address such as 10.0.0.5 or 127.0.0.1, then nothing is sent and REQ-434 dead-letters the job.
- Given the same host name added as an entry of its own, then the request is sent (notes: the exact entry is the explicit permission).
- Given a host covered by a wildcard entry that resolves to a public address, then the request is sent.
- Property: over random host names, resolutions and allowlists, a request is sent to a name that resolves to a private-network or loopback address only when that name is itself an entry.
- The check uses the host name and its resolution before the request (notes); a name that resolves differently at connect time is not caught, and no criterion is set for it.
- Which address ranges count, and how a name with several addresses is judged, is open question 2; the wildcard syntax is open question 1.

### AC-7 · INV-403 · must

> The system shall never follow a redirect to a different host and never follow more than MaxRedirects redirects.
>
> *Notes:* Decided by the owner on 2026-11-06: MaxRedirects is 0 by default (REQ-416), so redirects are not followed unless the application raises it, and then only to the same host.

- Given MaxRedirects 3 and a 302 to another host, even one on the allowlist, then the redirect is not followed and the 302 is the response under REQ-421 or REQ-422 (REQ-434 notes).
- Given MaxRedirects 2 and a chain of three same-host redirects, then two are followed and the third 3xx is the response.
- Given the named HttpClient is registered with AddHttpClient(name) and no handler configuration, then both limits above still hold, although that registration's default primary handler follows redirects on its own.
- Property: over random redirect chains, hosts and MaxRedirects values, no request follows more than MaxRedirects redirects and every followed request goes to the job's host.
- Whether another scheme or port is a different host, and a registration that is set to follow redirects itself, are open question 3.

### AC-8 · INV-404 · must

> The system shall take Authorization, Proxy-Authorization and Cookie headers and URL user information for outbound calls only from named HttpClient registrations, never from job payloads or configuration templates.
>
> *Notes:* Decided by the owner on 2026-11-06: enforced at creation by INV-408. refiner-model 2026-11-06 F-10 option 1: the sentence now names exactly what is enforced. Other secrets (for example an X-Api-Key header) belong on named HttpClient registrations; the docs say so, but a payload header with another name is not detected.

- Given a named HttpClient registration that adds an Authorization header, when an HTTP job referencing it runs, then the request carries that header.
- Given a job whose payload sets Authorization, Proxy-Authorization or Cookie, or whose URL carries user information, written into the store directly so that INV-408 never saw it, when it executes, then no request carries the payload's value or the user information. What the job does instead is open question 8.
- Property: over random payload headers in any letter case, no outbound request carries an Authorization, Proxy-Authorization or Cookie value, or URL user information, that came from a payload or from a configuration-defined job.
- A credential in a header with another name (for example X-Api-Key) is not detected (notes); no criterion is set for it.

### AC-9 · INV-405 · must

> Where a header is marked [Sensitive], the system shall mask its value in the dashboard and in logs.

- Given an HTTP job with a header marked [Sensitive], then its value appears on no dashboard page or JSON API response, the job detail page (REQ-309) included, and in no log line written while the job is enqueued, run, retried and dead-lettered; the values of unmarked headers still show.
- The NFR-41 scan of logs and dashboard responses (ST-006) finds none of those values either.
- How a header is marked, and whether response headers, traces and Microsoft.Extensions.Http's own logging are covered, is open question 9.

### AC-10 · INV-408 · must

> If an HTTP job is enqueued, scheduled or defined as recurring, from code, from the launch page or from configuration, with a payload that sets an Authorization, Proxy-Authorization or Cookie header or a URL that carries user information, then the system shall reject it with an error that points to named HttpClient registrations, and store nothing; a recurring definition from configuration is rejected when it is loaded.
>
> *Notes:* Decided by the owner on 2026-11-06. refiner-model 2026-11-06 F-9 option 1: the check covers every creation path listed in REQ-420's notes, not only application code; before this, a launch-page or configuration job could send an Authorization header from its payload.

- Given an HttpRequestJob that sets an Authorization, Proxy-Authorization or Cookie header, in any letter case, or a URL with user information, when it is enqueued or scheduled through IJobClient (TECH-19) or defined as recurring in code (TECH-22, TECH-21), then the call fails with an error that points to named HttpClient registrations, and afterwards the store holds no job and no definition for it.
- Given such a recurring definition in configuration (Bellhop:RecurringJobs, recurring REQ-202), when it is loaded, then it is rejected with an error that points to named HttpClient registrations, and nothing is stored for it.
- Given a payload with other headers only and a URL without user information, then it is accepted.
- Property: over random payloads, a job or definition is stored exactly when it carries none of the three headers and no URL user information.
- The launch-page path is tested in ST-068. What a rejection at load does to the host, which other creation paths are covered, and the error's wording are open questions 7 and 6.

### AC-11 · REQ-420 · must

> When an HTTP job executes, the system shall send the request described by its payload through the named HttpClient it references, with the job's request timeout.
>
> *Notes:* HTTP jobs can be enqueued, scheduled or made recurring from code, from the launch page and from configuration.

- Given a named HttpClient registration whose primary handler records requests, when an HTTP job that references that name executes, then one request reaches it with the payload's method, URL, headers, body and content type, after passing every handler of that registration.
- Property: over random payloads, the request received matches the payload field by field.
- Given a job whose timeout is shorter than the server's delay, then the request is cancelled when the timeout has passed and the attempt fails (REQ-422).
- Given a destination refused by INV-401 or INV-402, then nothing is sent (integrations A-7, SCN-401).
- A client name with no registration, and the defaults, are open question 4.
