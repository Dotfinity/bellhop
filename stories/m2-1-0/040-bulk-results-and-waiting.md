# ST-040 — Enqueue in bulk, store job results and wait for completion

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-030, ST-037

## Context

Gives three IJobClient methods that ST-007 declared (TECH-19) their behaviour: EnqueueManyAsync stores all of its jobs or none of them (INV-102) in a single store round-trip (NFR-17); a job's result is stored and read by job id (REQ-128), capped at ResultSizeLimit (REQ-185) and dropped with a warning when it is larger (REQ-184); and WaitForCompletionAsync returns when the job finishes or its timeout passes, whichever is first (REQ-155).

Builds on ST-037 (M1 acceptance, so M1 is finished first), ST-030 (the PostgreSQL store, on which NFR-17 is measured), ST-007 (TECH-19's methods, and TECH-33's capability set, whose result-storage part this story fills in), ST-008 (REQ-127, the success that REQ-128 and REQ-184 add consequences to) and ST-002 (result jobs and handlers, TECH-14, TECH-15). It keeps REQ-150 holding for a job inside an EnqueueManyAsync call whose unique key is held (open question 4). ST-054 puts the bulk and result rules in the conformance suite, ST-055, ST-056 and ST-058 keep NFR-17 holding on their stores, and ST-057 makes the Redis store report result storage (redis REQ-512).

Lives in the Bellhop core package (engine and in-memory store, TECH-112) and Bellhop.PostgreSql (TECH-37). A result and its dropped-for-size mark are new stored state, made on both stores that exist (TECH-31). The public methods are EnqueueManyAsync, GetResultAsync<T> and WaitForCompletionAsync (TECH-19); what they return outside the happy path is not in the specs (open questions 2 and 3). REQ-184's warning is logged with a stable EventId, as every log line is (NFR-51).

## Acceptance criteria

### AC-1 · REQ-185 · must

> The system shall cap stored job results at ResultSizeLimit, 1 MB by default (ResultSizeLimit).
>
> *Notes:* Decided by the owner on 2026-11-06.

- Given ResultSizeLimit is not configured, when a handler returns a result of exactly 1 MB, then the result is stored (REQ-128); when it returns a result one byte larger, the result is dropped (REQ-184).
- Given ResultSizeLimit is configured to another value, then both criteria hold at that value instead.
- How a result's size is measured, and how many bytes 1 MB is, is open question 1.

### AC-2 · REQ-128 · should

> While a job is processing, when its handler returns without an exception, if the job returns a result no larger than ResultSizeLimit, then the system shall store the result so it can be read by job id.
>
> *Transition:* Job: Processing → Succeeded · *Actor:* Handler
>
> *Notes:* Same event as REQ-127 with a second consequence. Decided by the owner on 2026-11-06: ResultSizeLimit is 1 MB (REQ-185); a larger result is REQ-184.

- Given a handler of a result job (TECH-14, TECH-15) returns a result no larger than ResultSizeLimit, when the job is marked succeeded (REQ-127), then GetResultAsync<T> with the job's id returns that result on any node, from the moment the job can be read as succeeded (the notes: the same event as REQ-127).
- Given the handler throws, then no result is stored.
- Given a run whose lease was taken over returns a result, then that result is not stored, because such a run cannot complete the job (REQ-127's notes).
- Given a result larger than ResultSizeLimit, then REQ-184 applies and nothing is stored.
- What a store without result storage does is open question 6; what happens to a result at retention and requeue is open question 7.

### AC-3 · REQ-184 · should

> While a job is processing, when its handler returns without an exception, if the job returns a result larger than ResultSizeLimit, then the system shall store no result, mark the result as dropped for size and log a warning with the size and the limit.
>
> *Transition:* Job: Processing → Succeeded · *Actor:* Handler
>
> *Notes:* Decided by the owner on 2026-11-06: the job still succeeds because the work was done; a truncated result would be invalid JSON. Same event as REQ-127 and REQ-128.

- Given a handler returns a result larger than ResultSizeLimit, then the job is marked succeeded (REQ-127), no part of the result is stored (the owner's note: a truncated result would be invalid JSON), the job is marked as dropped for size, and one warning is logged that gives the result's size and the limit.
- Given a result no larger than the limit, then there is no mark and no warning.
- Where the mark can be seen, and what GetResultAsync<T> returns for such a job, is open question 2.

### AC-4 · INV-102 · should

> When an application enqueues several jobs in one bulk call, the system shall store either all of them or none of them.

- Given EnqueueManyAsync with n jobs, when the call returns, then all n are stored as enqueued.
- Given one of the jobs has a payload larger than PayloadHardLimit (REQ-148) or a unique key held under the Error policy (REQ-152), then the call is rejected and none of the n is stored.
- Given the store write fails part way, by a fault injected after some jobs are written or a PostgreSQL connection dropped before the commit, then none of the n is stored and the call fails.
- Concurrency: workers on two nodes claim continuously while bulk calls run; no reader or worker sees part of a call's jobs.
- Property: over random bulk calls with random injected failures, every call's jobs are afterwards all stored or none stored, and every call that returned normally has all of its jobs stored.
- A call in which one job is ignored as a duplicate is open question 4.

### AC-5 · REQ-155 · should

> When an application waits for a job's completion with a timeout, the system shall return as soon as the job is succeeded, dead-lettered or cancelled, or when the timeout passes, whichever comes first.

- Given a processing job and a fake TimeProvider (TECH-12), when the application waits with timeout T and the job succeeds, is dead-lettered or is cancelled before T, then the wait returns at that outcome, before T passes.
- Given the job does not finish before T, then the wait returns when T passes, while the job is still unfinished.
- Given the job fails an attempt and will retry (REQ-129), then the wait does not return for that failure; it returns at the job's final outcome or at T.
- Given the job has already succeeded, been dead-lettered or been cancelled when the wait starts, then the wait returns at once.
- Given the job finishes on another node (two nodes over PostgreSQL), then the wait returns at that outcome too.
- Property: over random finishing times and timeouts under the fake clock, the wait returns at the earlier of the two.
- What the wait returns, and how soon "as soon as" must be, is open question 3.

### AC-6 · NFR-17 · should

> **Bulk enqueue round-trips** — When jobs are enqueued in bulk, the system shall use a single store round-trip per batch.
>
> *Measure:* 1 round-trip per EnqueueManyAsync call · *Verification:* test

- Test, on PostgreSQL: count the round-trips to the database during each EnqueueManyAsync call, by wrapping the connection or by the driver's command diagnostics, for a call of one job and for a large call. Pass: exactly one round-trip per call, the transaction's begin and commit included.
- The in-memory store makes no round-trips and is not measured. The largest call the test must cover is open question 5.
