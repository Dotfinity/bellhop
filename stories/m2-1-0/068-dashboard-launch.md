# ST-068 — Launch jobs from the dashboard

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-048, ST-066, ST-055, ST-056, ST-062

## Context

Adds the launch page: an operator picks any registered job type, fills a form generated from its payload record (TECH-95), and runs it now, schedules it for an instant in a chosen time zone, or makes it recurring; the operator's principal name is stored on what is created, and recent launches list who launched what and when (REQ-319 to REQ-323, INV-304). Launching works on a node that only maps the dashboard, because the dashboard writes through the store (INV-309).

Builds on ST-031 (INV-301 and INV-302: launching is an operate action and `ReadOnly()` refuses it; REQ-300 and REQ-342 give anonymous requests their level and name), ST-066 (a key-authenticated launch carries "apikey:<name>", REQ-305), ST-048 (HTTP jobs, whose credential check INV-408 covers the launch page), ST-023 (REQ-208 creates the runtime-defined recurring job; REQ-209 rejects an invalid schedule), ST-010 (TECH-30's parameters, through which launch principals are stored) and ST-055, ST-056 and ST-062 (the SQL Server, SQLite and Redis stores, on which launches are stored like on the in-memory and PostgreSQL stores). It keeps TECH-105 holding, with conformance tests for any store operation that launches add, and REQ-300 (ST-031), whose principal name "anonymous" first shows on launches here. Built on by ST-070 and ST-072, which keep INV-309 holding for the operate actions they add (bulk actions by tag and the limit change; schedule building, where ST-072's preview also covers Make recurring, REQ-328), and ST-075 (NFR-16 for the launch page's queries). INV-309 covers every operate action: the ones that exist now are tested here.

Lives in Bellhop.Dashboard (TECH-88): the launch page in the React front end (TECH-93) and its JSON API (TECH-92). Forms come from a JSON schema derived from the payload record and its DataAnnotations (TECH-95); job types are the ones registered through AddBellhop (TECH-22). The principal name is stored through the job's parameters (TECH-30's notes). Its parameter key, where it is kept on a recurring job, how launches are recorded for the list, and how a custom editor is registered (REQ-324) are not in the specs (open questions 3, 4 and 6).

## Acceptance criteria

### AC-1 · REQ-320 · must

> When an operator submits a valid launch form with Run now, the system shall enqueue the job with the form's payload and store the operator's principal name on it.
>
> *Transition:* jobs.Job: (new) → Enqueued · *Actor:* Operator

- Given registered job type T, an operator with operate permission and a form whose values pass T's validation rules, when they submit with Run now, then exactly one T job is stored as Enqueued with a payload holding the values entered, and the operator's principal name is stored on it (SCN-302).
- Given the submitting request was authenticated by an API key, then the name stored is "apikey:" followed by the key's name (REQ-305); given an anonymous request on a Development dashboard without an authorization requirement, it is "anonymous" (REQ-300). Which name a user of the host's scheme gets is open question 4.
- Given a user with view permission only, then the response is 403 Forbidden (INV-300) and no job is stored (SCN-303). Given a `ReadOnly()` dashboard, then the launch is refused and no job is stored (INV-302, SCN-304). Given an anonymous viewer outside Development, then the launch is refused and no job is stored (REQ-342, SCN-309). The response codes of the last two refusals are the ones ST-031 settles (dashboard A-16).
- Given an HTTP job whose payload sets an Authorization, Proxy-Authorization or Cookie header or whose URL carries user information, then the launch is rejected with an error that points to named HttpClient registrations and nothing is stored (INV-408).
- Invalid values are REQ-319.

### AC-2 · REQ-321 · must

> When an operator submits a valid launch form with Schedule for and a date, time and time zone, the system shall schedule the job for that instant with the form's payload and store the operator's principal name on it.
>
> *Transition:* jobs.Job: (new) → Scheduled · *Actor:* Operator

- Given a valid form with Schedule for and a date, time and time zone that name an instant in the future, when an operator with operate permission submits it, then exactly one job is stored as Scheduled for that instant, with the form's payload and the operator's principal name on it.
- Given the same wall-clock instant entered in two zones (09:00 in Europe/Berlin and 08:00 in UTC on a winter day), then both jobs are scheduled for the same instant.
- Given the refusals and the HTTP-job rejection listed under REQ-320, then they apply to Schedule for in the same way, and nothing is stored.
- An instant that is not in the future, and a local time that the zone skips or repeats at a daylight-saving change, are open question 5.

### AC-3 · REQ-322 · must

> When an operator submits a valid launch form with Make recurring and a schedule, the system shall create a runtime-defined recurring job with the form's payload and store the operator's principal name on it.
>
> *Transition:* recurring.RecurringJob: (new) → Active · *Actor:* Operator
>
> *Notes:* refiner-model 2026-11-06 F-9 (option 1): recurring launches are attributed like Run now and Schedule, so REQ-323 can list who launched them.

- Given a valid form with Make recurring and a valid schedule, when an operator with operate permission submits it, then a runtime-defined recurring job (origin runtime, recurring REQ-202) is created Active with the form's payload and nextRunAt computed from now (REQ-208), and the operator's principal name is stored on it.
- Given an invalid schedule expression, or time mode Local without a valid IANA time zone, then the submission is rejected with an error that says what is wrong and nothing is stored (recurring REQ-209).
- Given the refusals and the HTTP-job rejection listed under REQ-320, then they apply to Make recurring in the same way (INV-408 names recurring definitions from the launch page), and nothing is stored.
- The recurring job's name, its time mode, zone and policies, and a name that is already taken are open question 2.

### AC-4 · INV-304 · must

> The system shall offer every registered job type for launch.
>
> *Notes:* Decided by the owner on 2026-11-06: DSH-12 wins over BLT-8 and the §9 Q9 proposal. There is no opt-in attribute (TECH-96 retired); launching still needs operate permission (INV-301) and is refused on a ReadOnly dashboard (INV-302).

- Given job types registered with `AddJob<TJob, THandler>()` and with `AddJobsFromAssemblyContaining<T>()` over two assemblies (TECH-22), none carrying any attribute or switch, when an operator opens the launch page, then every one of them is offered.
- Property: over random sets of registered job types, the launch page offers every registered type.
- Whether "registered" means registered on the node that serves the dashboard or declared by any running worker node is open question 1.

### AC-5 · INV-309 · must

> The system shall offer and perform launches and other operate actions on a node that maps the dashboard whether or not the client or the worker is registered on that node.
>
> *Notes:* refiner-model 2026-11-06 F-12 (option 1): the dashboard writes through the store, so an ops portal that maps only the dashboard can launch, requeue, cancel and trigger. Permission and ReadOnly() rules still apply (INV-301, INV-302).

- Given a node that maps the dashboard and registers neither the client nor the worker (TECH-128), when an operator with operate permission launches with Run now, Schedule for and Make recurring, then the page offers all three, each job or recurring job is stored, and a worker node on the same store runs the launched job.
- Given the same node, then every other operate action that exists by now (INV-301's list) is offered and performed through the store.
- Given the four registrations of a dashboard node (dashboard only, with the client, with the worker, with both), then the launches and their results are the same.
- Given such a node, then permission and `ReadOnly()` still apply (INV-301, INV-302).

### AC-6 · REQ-319 · must

> If a launch form is submitted with values that fail the payload's validation rules, then the system shall show the validation errors and enqueue, schedule or create nothing.
>
> *Notes:* Fields, labels and rules come from the payload record and its DataAnnotations (TECH-95).

- Given a payload record with `[Required]`, `[Range]` and `[StringLength]` properties (TECH-95), when a form that breaks any of those rules is submitted with Run now, Schedule for or Make recurring, then the page shows the validation errors for the failing fields, and no job and no recurring job is created (SCN-305).
- Given the same invalid values posted straight to the JSON API, bypassing the page's own checks, then nothing is created and the response carries the validation errors: the UI is itself a client of the JSON API (TECH-92), so the rules are applied there.
- Property: over random payload records and random values, a submission creates something only when every value passes the payload's validation rules, and the store is unchanged after every submission that does not.
- The JSON API's status code and error shape for an invalid launch are open question 7.

### AC-7 · REQ-323 · must

> The system shall list recent launches with who launched which job and when.

- Given launches by a user, by an API key and, on a Development dashboard without an authorization requirement, by an anonymous request, then the recent launches list shows each with the principal name stored on it (REQ-320 to REQ-322), the job or recurring job it created, and when (SCN-302).
- Given a launch made on another node over the same store, then it is listed too.
- Given a submission that was refused or rejected (REQ-319, INV-408, a permission refusal), then no entry names a job for it, since none was created.
- What "recent" covers, and how long an entry outlives its job, is open question 3.

### AC-8 · REQ-324 · may

> Where a custom editor is registered for a payload type in dashboard options, the system shall use it instead of the generated form for that type.

- Given a custom editor registered in dashboard options for payload type P, when an operator opens the launch form for P, then the custom editor is shown instead of the generated form, and types without one still get the generated form (TECH-95).
- Given no custom editor is registered, then every type uses the generated form.
- How an editor is registered, what it is, and whether its submissions are still checked against the payload's validation rules (REQ-319) are open question 6.

- Conformance test over a set of payload records that uses every listed annotation (`[Display]`, `[Required]`, `[Range]`, `[StringLength]`, `[DataType]`) and an enum, a date with time zone, a nullable field, a nested record and a collection: the generated JSON schema carries each field with the label from `[Display]`, the rules from the other annotations, the enum's values, nullability and nesting, and the rendered form shows those fields with those labels.

3. **Decide in delivery** · REQ-323: what does "recent" cover (a number of launches or an age), where are launches recorded so that every node lists the same ones, and does an entry stay once its job is deleted or removed by retention (jobs REQ-144, REQ-145)?
