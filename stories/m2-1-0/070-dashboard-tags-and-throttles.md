# ST-070 — Show the tags and throttles pages

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-044, ST-042, ST-068, ST-055, ST-056, ST-062

## Context

Adds the tags page, with the number of jobs per tag, per-tag success and failure counts and click-through to the matching jobs (REQ-325); bulk requeue, cancel and delete by tag, applied job by job to the jobs that had the tag when the action started (REQ-326); and the throttles page, with each key's limit, current holders, waiting count and recent waits, where an operator can change a limit (REQ-327).

Builds on ST-044 (tags stored on jobs and added to the secondary index, REQ-167, over IJobIndex, TECH-32), ST-042 (concurrency keys, rate limits and the runtime limit change of REQ-158, which names the Throttles page), ST-018 (cancelling, REQ-134 and REQ-135), ST-020 (requeue and delete, REQ-141, REQ-143, REQ-144, INV-129 and INV-130, and the bulk requeue REQ-142 that REQ-326 mirrors), ST-034 (the dashboard's operate actions), ST-068 (INV-309, which this story keeps holding: its bulk actions and limit change are offered and performed on a node that only maps the dashboard) and ST-055, ST-056 and ST-062 (the SQL Server, SQLite and Redis stores, on which the new reads are implemented). The bulk actions and the limit change are operate actions, so INV-301 and INV-302 apply. It keeps TECH-105 holding, with conformance tests for any store operation it adds. Built on by ST-075 (NFR-16 for these queries).

Lives in Bellhop.Dashboard (TECH-88) and its JSON API (TECH-92). The tags page reads through IJobIndex (TECH-32), whose operations as listed cannot enumerate the tags in use or count a tag's jobs by outcome (open question 2); the throttles page reads each key's holders and waiting jobs from the store. Where the store contract grows for either, it grows on every store that exists by now: in-memory, PostgreSQL, SQL Server, SQLite and Redis (TECH-31).

## Acceptance criteria

### AC-1 · REQ-325 · must

> The system shall show a tags page with the number of jobs per tag, per-tag success and failure counts, and click-through to the matching jobs.

- Given three jobs tagged t1 and two tagged t2, one job carrying both, when a viewer opens the tags page, then t1 shows 3 jobs and t2 shows 2.
- Given t1's jobs include a succeeded job and a dead-lettered job, then the succeeded job counts towards t1's success count and not its failure count, and the dead-lettered job towards its failure count and not its success count.
- Given a tag set by the running handler (REQ-167), then it appears on the page with its job.
- When the viewer clicks t1, then the jobs list filtered by tag t1 (REQ-308) shows exactly the jobs that carry t1.
- The page needs view permission only (INV-301).
- Which other states count as failures, whether counts cover only jobs still stored, and how "key:value" tags are grouped are open question 1.

### AC-2 · REQ-326 · must

> When an operator runs a bulk requeue, cancel or delete by tag, the system shall apply the action to each job that has the tag when the action starts, in its own atomic step, where the action is allowed in the job's state at that step, and return how many jobs were changed and how many were skipped.
>
> *Notes:* Allowed states: jobs REQ-134, REQ-135, REQ-141, REQ-143, REQ-144. refiner-model 2026-11-06 F-11 (option 1): mirrors jobs REQ-142, so jobs tagged after the action starts are not included and a job whose state changed meanwhile is skipped and counted.

- Given jobs tagged t in every state, when an operator with operate permission runs a bulk requeue by t, then each dead-lettered, succeeded or cancelled job with t is enqueued again with its attempt number reset to zero and its cancellation request cleared (jobs REQ-141, REQ-143), every other job is left unchanged and counted as skipped, and the result reports how many were changed and how many skipped.
- Given the same jobs and a bulk cancel by t, then scheduled, enqueued, awaiting, failed and unroutable jobs are cancelled (REQ-134), processing jobs have their cancellation recorded and their token signalled (REQ-135) and count as changed, and finished jobs are skipped.
- Given the same jobs and a bulk delete by t, then every job that is not processing is removed with its history, captured logs and parameters, and each removal is logged (REQ-144); processing jobs are left unchanged and counted as skipped (INV-130).
- Given a job that gets tag t after the action has started, then the action neither touches nor counts it.
- Given a job whose state changes between the start of the action and its own step so that the action is no longer allowed, then it is left unchanged and counted as skipped.
- Concurrency: each bulk action runs while worker nodes claim, finish and fail the tagged jobs and handlers tag new jobs with t. Afterwards no job was changed twice or left half-changed, every job that had t when the action started is counted exactly once in the result, and no job tagged later was touched.
- Given a requeue of a job whose unique key is held by another active job, then the job is left unchanged (INV-129); which count it goes into is open question 3.
- Given an operator with view permission only, then the response is 403 Forbidden (INV-300) and nothing changes. Given a `ReadOnly()` dashboard, then the action is refused and nothing changes (INV-302).
- How the call ends for a large tag, or when it is cut off midway, is open question 4.

### AC-3 · REQ-327 · must

> The system shall show a throttles page with each key's limit, current holders, waiting count and recent waits, and let an operator change a limit.

- Given concurrency key k with Max 2, two processing jobs holding it and three enqueued jobs waiting for it (REQ-156), when a viewer opens the throttles page, then k is shown with limit 2, its two holders, a waiting count of 3 and its recent waits.
- Given a rate limit of N starts per window on key r (INV-109), then the page shows r with that limit.
- Given an operator with operate permission raises k's Max from 2 to 3, then the next claim on any node admits a third holder and the running holders are untouched (REQ-158).
- Given the operator lowers k's Max to 1 while two jobs hold it, then both keep running and no new holder is admitted until the number of holders drops below the new Max (REQ-158's notes).
- Given an operator with view permission only, then a limit change is answered 403 Forbidden (INV-300) and the limit is unchanged. Given a `ReadOnly()` dashboard, then it is refused and the limit is unchanged (INV-302).
- What "recent waits" shows, which keys are listed, which values a limit may take, and whether a changed limit lasts are open question 5.

## Open questions

1. **Decide in delivery** · REQ-325: which jobs count as failures (dead-lettered only, or also failed jobs awaiting a retry, cancelled jobs, or each failed attempt)? Are the counts over the jobs still stored, so that retention lowers them (jobs REQ-145), or kept as counters? Are "key:value" tags (REQ-167's notes) listed per full tag or grouped by key?
2. **Decide in delivery** · REQ-325, TECH-32: IJobIndex as TECH-32 lists it (AddAsync, RemoveAsync, QueryAsync, CountAsync) cannot list the tags in use or count a tag's jobs by state. Does TECH-32 grow, as a public store contract under NFR-20, on every store?
3. **Decide in delivery** · REQ-326: does a requeue refused because the job's unique key is held (INV-129) count as skipped, or get a count of its own as in jobs REQ-142? REQ-326 names two counts and REQ-142 three.
4. **Decide in delivery** · REQ-326: does the call return only after every job has been processed, and what happens to the rest of the jobs when the request is cut off or the node stops midway? Each job has its own atomic step, so a partial result is possible, and no limit is given on how many jobs one action touches.
5. **Decide in delivery** · REQ-327: what are "recent waits" (which jobs, how long they waited, over what period), which keys are listed (configured keys only, or every key filled from a template, jobs REQ-157), which values may a limit take, and does a limit changed here survive a restart or a redeploy that sets another value in code? Redis REQ-523 already treats runtime throttle limits as state that a reset can lose.
