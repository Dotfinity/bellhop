# ST-045 — Capture job logs and progress, and mask sensitive values

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-044

## Context

Captures what a handler logs and reports. Lines written through the job-scoped logger at or above the capture level are stored on the job with their timestamp, level, category and structured properties (REQ-165), by an ILoggerProvider scoped by job id so that every other logging provider keeps working (TECH-100); the stored log never exceeds CapturedLogLimit and marks where it was cut (INV-126). The latest progress report is stored (REQ-166), every log line written during a handler carries JobId, JobName, Attempt, Queue and CorrelationId (NFR-56), and payload properties marked [Sensitive] are masked in the dashboard, captured logs and traces (INV-124).

Builds on ST-044 (the correlation id that NFR-56 attaches), ST-008 (JobContext's job-scoped ILogger and ReportProgressAsync(double, string?), TECH-16, which this story makes work), ST-009 (REQ-108: capture at Information and above and CapturedLogLimit = 256 KB as option defaults), ST-013 (INV-128 refuses a progress write from a stale run, which this story must keep holding), ST-021 (INV-119 keeps captured logs as long as the job), ST-028 (the Bellhop ActivitySource, TECH-97, whose spans INV-124 masks) and ST-033 (REQ-309's job detail page, tested so far with logs and progress written into the store directly). ST-069 builds on it (live log streaming and the progress bar, REQ-316) and keeps INV-124 holding on its pages; ST-054 puts captured logs and progress into the conformance suite.

Lives in the Bellhop core package: the capture provider (an ILoggerProvider, TECH-100), JobContext's logger and ReportProgressAsync (TECH-16), and the [Sensitive] attribute that INV-124 names, beside the other job abstractions (TECH-112). Masking also reaches Bellhop.Dashboard (TECH-88), whose job pages and JSON API (TECH-92) show payloads. Captured lines and progress are persisted on every store that exists at this point, in-memory and PostgreSQL (TECH-31). The switches that turn capture off, the truncation mark and the mask are not given by the specs (open questions 1, 3 and 5).

## Acceptance criteria

### AC-1 · REQ-166 · must

> While a job is processing, when its handler reports progress with a fraction and an optional message, the system shall store the latest progress on the job.
>
> *Transition:* Job: Processing → Processing · *Actor:* Handler

- Given a processing job, when its handler calls ReportProgressAsync with 0.5 and a message (TECH-16), then the job stays Processing and its stored progress is 0.5 with that message, which the job detail page shows (REQ-309).
- Given that progress, when the handler reports 0.8, then the stored fraction is 0.8: the latest report is the job's progress. Whether a report without a message clears the earlier message is open question 4.
- Given a run whose lease token is no longer the job's current one, or whose job is no longer processing, when it reports progress, then the write is refused and the job is unchanged (INV-128).
- What a fraction outside 0 to 1 does is open question 4.

### AC-2 · INV-124 · should

> Where a payload property is marked [Sensitive], the system shall mask its value in the dashboard, captured logs and traces.

- Given a payload type with a property marked [Sensitive] that holds s, when a job of that type is enqueued, run and opened on the dashboard, then s appears in no dashboard page or JSON API response for the job (REQ-309, TECH-92), in none of its captured log lines, and in no span, span attribute or event of the Bellhop ActivitySource (TECH-97); a mask stands in its place.
- Given the handler logs the payload object as a structured property through the job-scoped logger, then the captured line keeps the other properties and does not contain s.
- Given the same job, then its handler receives s as enqueued: INV-124 masks the three outputs it names, not the payload the job runs with.
- Given a payload type with no [Sensitive] property, then the dashboard shows its values as they are.
- Property: over random payload types with [Sensitive] properties and random values, a scan of the dashboard responses, the captured logs and the exported spans, with the scan that NFR-41 uses (ST-006), finds none of the values.
- The mask itself, nested types, and a value the handler logs as a plain argument are open question 5.

### AC-3 · INV-126 · must

> The system shall never store more than CapturedLogLimit of captured log lines per job, and mark the point where the log was truncated.

- Attack: a handler writes lines totalling several times CapturedLogLimit, within one attempt, across several attempts of one job (the limit is per job) and from several tasks at once. Observed: the stored captured log never exceeds CapturedLogLimit, and a truncation mark is stored at the point where lines were dropped.
- Given lines totalling less than CapturedLogLimit, then every line is stored and there is no truncation mark.
- Given CapturedLogLimit configured below its default (REQ-108), then the cap is the configured value.
- Under every reading of open question 3, the stored lines are an unbroken run of the written lines, in the order written, with the mark at the cut.
- How size is counted, which end is kept and what the mark looks like are open question 3.

### AC-4 · REQ-165 · must

> While a job is processing, when its handler writes a log line through the job-scoped logger at or above the capture level, the system shall store the line with its timestamp, level, category and structured properties on the job, unless capture is disabled globally or for that job type.
>
> *Notes:* Decided by the owner on 2026-11-06: capture is on by default at Information and above, as BLT-1 says; DSH-6's 'opt-in' is superseded. It can be disabled globally or per job type, is capped per job (INV-126) and is removed with the job (INV-119).

- Given a processing job with capture on, as it is by default (REQ-108), when its handler writes an Information line with structured properties through the job-scoped logger (TECH-16), then the line is stored on the job with its timestamp, level, category and structured properties, and the job detail page shows it (REQ-309).
- Given the default capture level, then Warning and Error lines are stored and a Debug line is not. Given the capture level set to Warning, then an Information line is not stored.
- Given capture disabled globally, then no line is stored for any job. Given it disabled for job type T, then no line is stored for T's jobs, while jobs of other types still capture.
- Concurrency: jobs running at once on one node each write lines; every stored line is on the job whose handler wrote it.
- Given two Bellhop instances in one process on different stores (NFR-53), then each captures its own jobs' lines into its own store.
- Whether lines written through loggers other than the job-scoped one are captured is open question 2.

### AC-5 · TECH-100 · must

> **Log capture provider** — Job log capture shall be an ILoggerProvider scoped by job id, so Serilog, NLog and every other logging provider keep working and no special console API exists.

- Inspection: capture is an ILoggerProvider of Microsoft.Extensions.Logging that files lines by job id, and no Bellhop public API offers a console to write to; JobContext's logger is an ILogger (TECH-16).
- Given another logging provider registered beside it, when a handler writes lines through the job-scoped logger, then that provider receives every line and the job's captured log stores them too.
- Passing: the inspection holds and the test passes.

### AC-6 · NFR-56 · must

> **Job-scoped log context** — The system shall attach JobId, JobName, Attempt, Queue and CorrelationId to every log line written during a handler.
>
> *Measure:* 100% of handler log lines carry the five scope properties in the test logger · *Verification:* test

- Measurement: a test logger provider records the scope properties of every line. Handlers write lines through the job-scoped logger and through an ILogger<T> injected into them, for several jobs running at once on one node with different names, queues and correlation ids, one of them on its second attempt.
- Passing: 100% of the lines written during a handler carry JobId, JobName, Attempt, Queue and CorrelationId, each with the values of the job whose handler wrote the line.
- What CorrelationId carries for a job without a correlation id is open question 6.

## Open questions

1. **Decide in delivery** · REQ-165, TECH-100: the option names for the capture level and for turning capture off globally and per job type, the category given to the job-scoped logger's lines, and whether AddBellhop registers the capture provider or the application does. All become public contracts that NFR-20 freezes.
2. **Decide in delivery** · REQ-165, TECH-100, NFR-56: are lines written during a handler through other loggers (an ILogger<T> injected into the handler or its services) captured too? REQ-165 names only the job-scoped logger, while a provider scoped by job id (TECH-100) sees both, and NFR-56 scopes every line written during a handler.
3. **Decide in delivery** · INV-126: how is a line's size counted against CapturedLogLimit (the message text, or the line with its properties)? Which lines are kept once the limit is reached, the first or the latest? What happens to one line larger than the limit, and what does the truncation mark look like in the store and on the job page?
4. **Decide in delivery** · REQ-166: what does a fraction below 0, above 1 or NaN do, and does a report without a message clear the previous message? TECH-16 gives only ReportProgressAsync(double, string?).
5. **Decide in delivery** · INV-124: what replaces a masked value? Are [Sensitive] properties of nested types and of collection elements covered? Must a value the handler logs as a plain argument be masked in captured logs, although the system can recognise it only when the payload object itself is logged?
6. **Decide in delivery** · NFR-56: what does CorrelationId carry on a line of a job without a correlation id? That depends on ST-044's open question on REQ-168 when no source yields a value.
