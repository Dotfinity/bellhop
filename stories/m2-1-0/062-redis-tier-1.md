# ST-062 — Prove the Redis store on Tier 1 servers and topologies

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-061

## Context

Proves that the Redis store works on the Tier 1 servers and hosted services that 1.0 supports: Valkey 8.1, 9.0 and 9.1 (TECH-71), Redis 7.2 and 8.x without Redis 8's modules or Redis-8-only commands (TECH-73), AWS ElastiCache for Valkey including serverless (TECH-80), AWS MemoryDB (TECH-81) and GCP Memorystore for Valkey (TECH-82), standalone, with Sentinel and as a Cluster, with TLS and ACL users (TECH-64), and that it never refuses one of those topologies (REQ-511). The behaviour exists already; this story runs it against each target and fixes what breaks.

Builds on ST-061 and the Redis stories before it (ST-057 to ST-060: key layout, scripts, server detection, reset handling) and on the store conformance suite (TECH-105, ST-054), the test it runs everywhere. ST-064 (ShardByQueue on a Cluster), ST-073 (docs), ST-074 (benchmarks), ST-075 (query plans) and ST-082 (Tier 2 and 3 servers) build on it. The CI matrix that keeps these servers tested on every commit is TECH-87, and the requirement to pass conformance and chaos tests on every server is NFR-58, both owned by ST-084 in M3.

Lives in Bellhop.Redis (TECH-70) and its test projects; fixes go where the failures are, and no public API is added. The hosted services need cloud accounts, and how and how often they are tested is not in the specs (open question 2).

## Acceptance criteria

### AC-1 · REQ-511 · must

> Where the server runs standalone, as primary and replica with Sentinel, or as a Cluster, the system shall start and run without refusing the topology.
>
> *Rationale:* Correctness comes from one atomic script per transition (TECH-57), not from refusing to start.

- Attack: start nodes against each topology and run the conformance suite (TECH-105) with work in flight: a standalone server, a primary with replicas under Sentinel, and a Cluster, then force a Sentinel failover during the run. Observed: every node reaches Running (hosting REQ-18), the suite passes, and no node stops or refuses to start because of the topology.
- Given replicas, then the store logs that replication is asynchronous (REQ-504) and keeps running; the notice is not a refusal.
- Given a Sentinel failover while jobs run, then each node marks its store connecting, repeats detection on the new primary (REQ-529, TECH-69) and goes on processing.
- If the server has no EVAL (REQ-502) or an eviction policy other than noeviction (REQ-505), then the start fails for that reason on every topology; nothing else refuses a start.

### AC-2 · TECH-64 · must

> **Redis topologies** — The Redis store shall support standalone servers, primary/replica with Sentinel and Cluster, with TLS and ACL users.
>
> *Notes:* The default tagging bounds one namespace to one shard; the trade-off is documented (NFR-33).

- Test: the conformance suite (TECH-105) passes against a standalone server, a primary/replica set with Sentinel and a Cluster, each with TLS on and the store connected as an ACL user other than the default user. Passing: green on all three, with the topology, the TLS setting and the ACL user recorded with the run.
- Given the Cluster, then the run passes with each namespace's keys on one hash tag (TECH-58); the capacity trade-off this gives is documented by NFR-33 (ST-064).
- Which commands an ACL user must be granted is open question 1.

### AC-3 · TECH-71 · must

> **Valkey** — The Redis store shall support Valkey as a Tier 1 server, tested standalone, with Sentinel and as a Cluster.
>
> *Version:* 8.1, 9.0, 9.1
>
> *Notes:* Valkey's INFO reports redis_version 7.2.4, so detection uses HELLO (TECH-69). The docs recommend Valkey as the default open-source choice (NFR-34).

- Test: the conformance suite passes against Valkey 8.1, 9.0 and 9.1 standalone, and against Valkey with Sentinel and as a Cluster. Passing: green on each.
- Given Valkey, then the startup summary names Valkey and its version, not the redis_version 7.2.4 that its INFO reports (REQ-500, TECH-69).
- Which version runs in which topology is open question 3.

### AC-4 · TECH-73 · must

> **Redis** — The Redis store shall support Redis as a Tier 1 server without relying on Redis 8 built-in modules or Redis-8-only commands such as XACKDEL, HGETDEL or MSETEX.
>
> *Version:* 7.2 and 8.x

- Test: the conformance suite passes against Redis 7.2 and Redis 8.x. Passing: green on both. A green run on 7.2, which has none of Redis 8's modules or Redis-8-only commands, shows that the paths it covers do not rely on them.
- Inspection, recorded in Notes: no command the store sends and no script calls a Redis 8 built-in module or a Redis-8-only command such as XACKDEL, HGETDEL or MSETEX, and every command is one TECH-54, TECH-59 or TECH-69 names (TECH-55 already excludes modules). Passing: none found.

### AC-5 · TECH-80 · must

> **AWS ElastiCache for Valkey** — The Redis store shall support AWS ElastiCache for Valkey as a Tier 1 hosted service, including serverless, which runs in cluster mode.
>
> *Notes:* Synchronous durability on Valkey 9 node-based clusters is called out in the docs (NFR-31).

- Test: the conformance suite passes against an ElastiCache for Valkey node-based cluster and an ElastiCache Serverless cache for Valkey, which runs in cluster mode, both with TLS (TECH-64). Passing: green on both.
- If the service's eviction policy is not noeviction and cannot be changed, then REQ-505 refuses it at startup; that conflict is open question 4.

### AC-6 · TECH-81 · must

> **AWS MemoryDB** — The Redis store shall support AWS MemoryDB as a Tier 1 hosted service.

- Test: the conformance suite passes against an AWS MemoryDB cluster with TLS (TECH-64). Passing: green.
- The eviction-policy conflict of open question 4 applies here too.

### AC-7 · TECH-82 · must

> **GCP Memorystore for Valkey** — The Redis store shall support Google Cloud Memorystore for Valkey as a Tier 1 hosted service.

- Test: the conformance suite passes against a GCP Memorystore for Valkey instance with TLS (TECH-64). Passing: green.
- The eviction-policy conflict of open question 4 applies here too.

## Tests

- Conformance (TECH-105) against each self-hosted target in containers: Valkey 8.1, 9.0 and 9.1, Redis 7.2 and 8.x, a Sentinel set, a Valkey cluster, with TLS and an ACL user (REQ-511, TECH-64, TECH-71, TECH-73). Each run is tagged with the server item it proves.

- Not automated here: the per-commit matrix, the compatibility page and the chaos tests that kill the primary mid-job (TECH-87, NFR-35, NFR-58, ST-084); this story runs the targets but does not install the matrix.

## Open questions

1. **Decide in delivery** · TECH-64, TECH-54: which commands must an ACL user be granted? TECH-54 lists the only commands the store uses, but TIME (TECH-59), HELLO and INFO (TECH-69) are not on it, and an operator needs the full list to create the user; the list is also a documentation contract.
2. **Decide in delivery** · TECH-80, TECH-81, TECH-82: how and how often is support for the hosted services verified (every commit, nightly, before each release), and who provides the accounts? TECH-87's matrix holds Docker images only, while its source says Tier 1 runs in CI on every commit.
3. **Decide in delivery** · TECH-71, TECH-87: which Valkey version runs in which topology? TECH-71 lists 8.1, 9.0 and 9.1, tested standalone, with Sentinel and as a Cluster; TECH-87 runs valkey:8.1 and one valkey:9 image with a Valkey cluster and a Redis Sentinel set, so only one of 9.0 and 9.1, and no Valkey Sentinel set, is in it.
4. **Decide in delivery** · TECH-80, TECH-81, TECH-82, REQ-505: if a hosted service runs with an eviction policy other than noeviction and does not let it be changed, or does not let the store read it, REQ-505 refuses it at startup while these items say it is supported. REQ-505's notes accept refusing servers whose policy cannot be changed; which wins for these services? The first run against each service will show whether the case arises.
