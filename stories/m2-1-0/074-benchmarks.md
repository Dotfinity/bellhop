# ST-074 — Benchmark enqueue, scheduling, throughput and cron punctuality

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** should · **Depends on:** ST-055, ST-062

## Context

Adds the public benchmark harness that actually executes jobs on every system it compares (TECH-123), and measures with it the performance goals for 1.0: enqueue latency on PostgreSQL (NFR-5), schedule-to-start lag with and without notifications (NFR-6), throughput of no-op jobs (NFR-7), punctuality of a 1-second cron schedule (NFR-8) and enqueue-to-start latency on Redis (NFR-9). REQ-36 lists the benchmark in M2. Every measurement runs on the reference machine, 2 vCPU and 8 GB RAM, which the owner set for every performance goal on 2026-11-06 (NFR-5's notes); that is also the "modest hardware" of NFR-7.

Builds on ST-055 and ST-062, after which every 1.0 store exists: PostgreSQL with LISTEN/NOTIFY (TECH-38, ST-030), SQL Server, and Redis with its pub/sub wake-ups (TECH-63, ST-058) on the Tier 1 servers (ST-062). The behaviour it measures comes from ST-007 (enqueue and promotion, REQ-120, REQ-122), ST-008 (claims, REQ-123) and ST-026 (the recurring trigger, REQ-216). ST-076 builds on it. NFR-6 is inferred M1, but its measure names Redis pub/sub, which arrives with the Redis store in M2 (TECH-70's notes), and the harness that measures it is M2 (REQ-36; TECH-123's source).

The harness lives in the repository and is public (TECH-123). It drives Bellhop as an application does, through IJobClient (TECH-19) and job registration on AddBellhop (TECH-22), and adds nothing to the packages. The 1-second schedule of NFR-8 needs the 6-field cron form (TECH-23). Which systems it compares is open question 1.

## Acceptance criteria

### AC-1 · TECH-123 · should

> **Benchmark harness** — The repository shall include a public benchmark harness that actually executes jobs on every compared system.

- Inspection: the harness is in the public repository, and for each system it compares, a result comes only from a run in which the jobs were executed by handlers, not only stored: the run counts the handler executions and checks them against the jobs it enqueued, and reports both.
- Given a run in which fewer jobs were executed than enqueued, then the harness reports that run as incomplete rather than as a result.
- Given the harness, then it produces the measurements of NFR-5 to NFR-8 (its Applies to) and NFR-9 for Bellhop.
- Which systems it compares is open question 1.

### AC-2 · NFR-5 · should

> **Enqueue latency** — When a job is enqueued on PostgreSQL, the system shall return within 2 ms at the median.
>
> *Measure:* enqueue p50 < 2 ms, PostgreSQL store, one node, on the reference machine (2 vCPU, 8 GB RAM) · *Verification:* test
>
> *Notes:* Decided by the owner on 2026-11-06: the reference machine for every performance goal is 2 vCPU and 8 GB RAM, the size of a standard GitHub-hosted runner, so anyone can reproduce the numbers.

- Measurement test: on the reference machine, with the PostgreSQL store (TECH-37) and one node, the harness enqueues jobs through IJobClient (REQ-120) and times each call from its start to its return. The measure passes when the median is below 2 ms; a median of 2 ms or more fails it.
- The run records its sample count, warm-up, PostgreSQL version and where the server ran, with the median, in the harness output and in Notes. Where the server runs and which version are open question 2.

### AC-3 · NFR-6 · should

> **Schedule-to-start lag** — When a job becomes due, the system shall start it within 100 ms at the median where notifications are available and within PollInterval otherwise, on any node.
>
> *Measure:* schedule-to-start lag p50 < 100 ms with notifications (PostgreSQL LISTEN/NOTIFY, Redis pub/sub), < PollInterval without; one node, PostgreSQL · *Verification:* test
>
> *Notes:* EXE-8 (MUST) also requires the enqueuing node to wake its own workers immediately and adaptive polling otherwise; those are behaviour and implementation, measured here.

- Measurement test, with notifications: on the reference machine, PostgreSQL store, one node, LISTEN/NOTIFY available (TECH-38). Jobs are scheduled for known instants, and each job's lag is its handler's start minus its due instant. The measure passes when the median lag is below 100 ms.
- Measurement test, without notifications: the same set-up with notifications unavailable to the node. The measure passes when the median lag is below PollInterval, 1 s by default (REQ-103), or the PollInterval configured for the run.
- The one-node run with notifications also measures the enqueuing node waking its own workers, which NFR-6's notes say is measured here.
- A median at or above either bound fails the measure. Whether "on any node" needs a two-node run, and whether the Redis lag is measured under NFR-6 too, is open question 3.

### AC-4 · NFR-7 · should

> **Throughput** — The system shall process at least 1,000 no-op jobs per second per node.
>
> *Measure:* ≥ 1,000 no-op jobs/s per node, PostgreSQL store, modest hardware · *Verification:* test

- Measurement test: on the reference machine, with the PostgreSQL store and one node, the harness runs no-op jobs and counts handler completions per second over the steady part of the run. The measure passes at 1,000 jobs per second or more; below that it fails.
- The run records its options, its length and the job count in Notes. Whether the options are the defaults is open question 4.

### AC-5 · NFR-8 · should

> **Cron punctuality** — The system shall start recurring occurrences on time.
>
> *Measure:* ≥ 99% of occurrences of a 1-second cron schedule start less than 1 s after their due instant, on the reference machine with no other load · *Verification:* test
>
> *Notes:* Decided by the owner on 2026-11-06: measured from the due instant to handler start.

- Measurement test: on the reference machine with no other load, a recurring job on a 1-second cron schedule (6-field form, TECH-23); each occurrence's lag is its handler's start minus its due instant (NFR-8's notes). The measure passes when at least 99% of the occurrences due during the run have a lag below 1 s.
- Given a due instant during the run for which no occurrence started, then it counts as not on time: a skipped or missing occurrence stays in the count.
- The run records the number of occurrences and the store in Notes. Which store, as NFR-8 names none, is open question 5.

### AC-6 · NFR-9 · should

> **Redis enqueue-to-start latency** — When a job is enqueued on the Redis store, the system shall start it within 20 ms at the median.
>
> *Measure:* enqueue-to-start p50 < 20 ms against a local server with pub/sub wake-ups · *Verification:* test

- Measurement test: on the reference machine (NFR-5's notes), the Redis store against a local server with pub/sub wake-ups (TECH-63); each job's lag is its handler's start minus the start of its enqueue call. The measure passes when the median lag is below 20 ms; a median of 20 ms or more fails it.
- The run records the server and its version in Notes. Which Tier 1 server is open question 2.
