# ST-055 — Store jobs in SQL Server

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-054

## Context

Adds the Bellhop.SqlServer package, a job store on Microsoft SQL Server for teams whose database is SQL Server, Azure SQL Database or Azure SQL Managed Instance (TECH-40). Its claims use READPAST and UPDLOCK, so concurrent workers skip a row that another claim has locked instead of queueing behind it (TECH-41). The tool infers TECH-41 for M1 from INV-103, but hosting REQ-36 puts the SQL Server store in M2 and TECH-37's notes say SQL Server follows PostgreSQL in M2, so the claim rule ships with the store.

Builds on ST-054 (the conformance suite, TECH-105, which this store must pass), ST-029 and ST-030 (the rules every SQL store follows: TECH-36, TECH-44, TECH-46, TECH-47, TECH-126, TECH-127), ST-008 (claims, INV-103), ST-041 (transactional enqueue, INV-101), ST-040 (a bulk enqueue takes one store round-trip per batch, NFR-17), ST-054 (library versions N and N+1 both read and write schema N, NFR-18) and ST-036 (memory proportional to in-flight jobs, NFR-13, and due recurring jobs found by one indexed range query per poll, NFR-14), all of which must now hold on SQL Server too. ST-073 (docs and the Testcontainers sample, TECH-106), ST-074 (benchmarks), ST-075 (query plans, NFR-15, NFR-16) and ST-086 (the CLI) build on it.

Lives in the Bellhop.SqlServer package (TECH-40, TECH-124). It owns a bellhop schema created by embedded migrations (TECH-46), serialises them with sp_getapplock (TECH-126) and gives BellhopSchema.GetScript its SQL Server output (TECH-47). The registration method and its options, the ADO.NET provider package and the capability set the store reports (TECH-33) are not in the specs (open questions 1 to 3).

## Acceptance criteria

### AC-1 · TECH-40 · must

> **SQL Server store** — The Bellhop.SqlServer package shall use Microsoft SQL Server as a job store.
>
> *Version:* the three most recent major versions at each Bellhop release
>
> *Notes:* Decided by the owner on 2026-11-06: the last three major versions. Azure SQL Database and Azure SQL Managed Instance are supported too and join the CI matrix (Managed Instance nightly).

- CI: the conformance suite (TECH-105) runs against Bellhop.SqlServer on each of the three most recent major versions of SQL Server and on Azure SQL Database, and nightly on Azure SQL Managed Instance (TECH-40's notes). The item passes when the suite is green on every one of them.
- At each Bellhop release the matrix holds the three most recent major versions as of that release, and the release records which they are. An older version is not tested; whether the store refuses one is open question 4.
- Given a host configured with the SQL Server store, AutoMigrate on and an empty database, when it starts, then the embedded migrations create the bellhop schema (TECH-46, hosting REQ-22) and the node reaches Running (hosting REQ-18).
- Dependency audit: Bellhop.SqlServer references neither EF Core nor Dapper (TECH-36) and needs no DbContext (TECH-48).
- Given any startup or connection failure, then neither the logs nor the startup summary contain the connection string or its password (NFR-41).

### AC-2 · TECH-41 · must

> **SQL Server claims** — The SQL Server store shall claim jobs with READPAST and UPDLOCK hints.

- Inspection: the statement that picks the job to claim reads the jobs table with both the READPAST and the UPDLOCK hint, and that read and the write that records the claim run in one statement or one transaction. The reviewer records the file and line in Notes.
- Given one claim holds a job's row locked in a transaction that the test keeps open, when a second worker claims from the same queue, then it gets the next eligible job without waiting for that transaction, or no job if there is none.
- Concurrency: many workers on several store instances claim from one queue at once, on every server in the TECH-40 matrix; no job is ever held by two workers with unexpired claims (INV-103), and every eligible job is claimed.
- The claim keeps queue order and priority (jobs INV-111) and the guards of jobs REQ-123: the conformance suite's claim tests pass.

## Tests

Every test carries one `Trait("Req", "<id>")` for each item it verifies.

- Conformance: the TECH-105 suite against Bellhop.SqlServer on every server in the TECH-40 matrix (TECH-40; INV-103 through its claim tests).
- Concurrency, against a SQL Server container: TECH-41's locked-row test and its many-worker claim test, also tagged INV-103.
- Integration: migrations from an empty database and from each earlier schema version (TECH-46, TECH-127), two nodes starting at once with only one migrating under sp_getapplock (TECH-126, hosting REQ-42), GetScript output compared with the schema the migrations produce (TECH-47), concurrent enqueues with one unique key turned away by the unique index (TECH-44), and the transactional-enqueue tests (INV-101) if open question 3 gives the store that capability.
- Inspection, recorded in Notes: TECH-41's claim statement and TECH-36's dependency audit.
- Must keep holding: the tests of TECH-36, TECH-44, TECH-46, TECH-47, TECH-126, TECH-127, TECH-105 and INV-101 stay green on the PostgreSQL and in-memory stores. On SQL Server as well: NFR-17 (round-trips counted for a bulk enqueue), NFR-18 (the suite's mixed-version run on schema N), NFR-13 (node memory with a large stored history) and NFR-14 (one indexed range query per poll for due recurring jobs, checked in the query plan).
- Not automated: that the matrix holds the three most recent major versions is checked when a release is cut and recorded with it (ST-076 for 1.0). Managed Instance runs nightly, not on every commit.

## Open questions

1. **Decide in delivery** · TECH-40: what are the SQL Server store's registration method and option names (connection string, schema name)? No item names them, and they become public API that NFR-20 freezes.
2. **Decide in delivery** · TECH-36, TECH-40: which ADO.NET provider package does Bellhop.SqlServer depend on? TECH-36 requires plain ADO.NET but names no provider, and the dependency is visible to every application that installs the package.
3. **Decide in delivery** · TECH-33, INV-101: which capabilities does the SQL Server store report: transactional enqueue, push notifications, result storage? The specs give them only for Redis (REQ-512) and the in-memory store (jobs REQ-153's notes). NFR-32 sends Redis users to the SQL stores for transactional enqueue, and the plan lists INV-101 for this story, which suggests SQL Server reports it.
4. **Decide in delivery** · TECH-40: on a SQL Server version older than the three supported ones, does the store refuse to start, or is it only untested? The item gives the supported range, not what happens outside it.
