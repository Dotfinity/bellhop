# ST-067 — Sign in to the dashboard with basic authentication

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-066

## Context

Adds `RequireBasicAuth()` so a team without an identity provider can protect the dashboard with users and password hashes kept in configuration (REQ-303, TECH-94). A plain-text password stops the host at startup (REQ-334), and repeated failures lock out a user or a client address for LoginLockoutWindow (REQ-304), while API keys keep working (SCN-310).

Builds on ST-006 (the startup sequence: hosting REQ-12 runs REQ-334 among the checks that need no store, and hosting REQ-18 marks the node running only after it), ST-031 (the view and operate permissions every dashboard request is judged by, INV-301, and the startup checks REQ-300, REQ-301 and REQ-342, which name RequireBasicAuth, were built against what existed, and which this story keeps holding) and ST-066 (API keys, which a lockout must not touch: REQ-305). Built on by ST-086, whose CLI generates the hashes (TECH-122), and ST-076, where NFR-20 freezes dashboard auth behaviour for 1.0.

Lives in the Bellhop.Dashboard package (TECH-88). It adds `RequireBasicAuth()` (REQ-303, TECH-94) and the password-hash helper that TECH-94 mentions. The helper's name and the configuration shape of a user are not in the specs (open question 5).

## Acceptance criteria

### AC-1 · REQ-335 · must

> The system shall default MaxFailedLogins to 5 (MaxFailedLogins).
>
> *Notes:* Decided by the owner on 2026-11-06.

- Given basic authentication is enabled and MaxFailedLogins is not configured, when a user fails basic authentication 5 times within LoginLockoutWindow, then the user's next attempt is rejected (REQ-304); after 4 failures it is not.
- Given MaxFailedLogins is configured as 3, when a user fails 3 times within LoginLockoutWindow, then the user's next attempt is rejected.

### AC-2 · REQ-336 · must

> The system shall default LoginLockoutWindow to 15 minutes (LoginLockoutWindow).
>
> *Notes:* Decided by the owner on 2026-11-06.

- Given basic authentication is enabled and LoginLockoutWindow is not configured, when a user fails 5 times within one minute, then a correct password is still rejected while less than 15 minutes have passed since the first of those failures.
- Given the same lockout, when more than 15 minutes have passed since the fifth failure with no attempt in between, then a correct password is accepted again.
- Given LoginLockoutWindow is configured as 5 minutes, then both criteria above hold with 5 minutes in place of 15.
- Between those two instants the readings of "within LoginLockoutWindow" differ (open question 3); no criterion is set there.

### AC-3 · REQ-334 · must

> While a node is starting, if basic authentication is enabled and a configured password is not a supported salted hash, then the system shall fail the host's start with a message that names the user and shows how to produce the hash.
>
> *Transition:* hosting.Node: Starting → StartupFailed · *Actor:* system
>
> *Notes:* Decided by the owner on 2026-11-06. refiner-model 2026-11-06 F-5: hosting REQ-18/REQ-19 name this check as a startup check, so it always runs before the node is marked running.

- Given `RequireBasicAuth()` and a configured user whose password is plain text, when the host starts, then the start fails, the node never reaches Running (hosting REQ-18), and the failure message names that user and says how to produce the hash.
- Given the same configuration and a store that cannot be reached, then the start fails with this message before the store is contacted, and nothing is migrated or written (hosting REQ-12 runs REQ-334 with the checks that need no store).
- Given that failure, then neither the message nor any log line contains the configured password (NFR-41).
- Given a configured password stored as an Argon2 hash, or as a salted PBKDF2-HMAC-SHA1 hash, then the start fails in the same way: PBKDF2-HMAC-SHA256 is the only supported hash (REQ-303's notes, TECH-94).
- Given every configured password is a supported salted hash, then this check does not fail the start.
- Given basic authentication is not enabled, then this check does not run, whatever passwords are configured.

### AC-4 · REQ-303 · must

> Where basic authentication is enabled with RequireBasicAuth(), the system shall accept only users from configuration whose passwords are stored as salted PBKDF2 hashes.
>
> *Notes:* Decided by the owner on 2026-11-06: a plain-text password fails startup (REQ-334), and PBKDF2 is the only supported hash; Argon2 from BLT-2 is not offered (TECH-94). Constant-time comparison is NFR-43.

- Given a configured user with a salted PBKDF2 hash, when they sign in with the right password from an address that is not locked out, then the request is authenticated (dashboard A-4), with the permission that open question 1 settles.
- Given a user name that is not in configuration, when a request signs in with it, then the request is not authenticated, and the attempt counts as a failure from that address (REQ-304).
- Given a configured user, when a request signs in with a wrong password, then the request is not authenticated, and the failure counts for that user and that address (REQ-304).
- Property: over random sequences of sign-ins with configured and unknown users and right and wrong passwords, a request is authenticated only when its user is in configuration and the password matches that user's hash.
- Given `RequireBasicAuth()` is the only authorization requirement, then in Development anonymous requests are not given operate (REQ-300 does not fire) and outside Development the host starts without `AllowAnonymous()` (REQ-301 does not fire), since it is one of the authorization requirements (glossary `authorizationRequirement`).
- What the dashboard answers to a request that is not authenticated is open question 2.

### AC-5 · REQ-304 · must

> Where basic authentication is enabled with RequireBasicAuth(), if a user, or a client address, has failed basic authentication MaxFailedLogins times within LoginLockoutWindow, then the system shall reject further basic-authentication attempts for that user or from that address until the window has passed, even with the right password.
>
> *Notes:* Decided by the owner on 2026-11-06: 5 failures in 15 minutes, counted both per user and per client address, so one address cannot try many users and many addresses cannot hammer one user. refiner-model 2026-11-06 F-2/F-3 (option 2, owner decision): the lockout covers basic authentication only. API keys are never locked out and failed key attempts are not counted (INV-308), so a noisy neighbour cannot block a CI script; brute-force resistance for keys rests on key entropy (NFR).

- Given the defaults, when user u fails basic authentication 5 times within 15 minutes from address a1, then u's next attempt is rejected even with the right password, from a1 and from any other address.
- Given the defaults, when address a fails 5 times within 15 minutes, once each for five different users, then the next attempt from a is rejected for every user even with the right password, and each of those users can still sign in from another address.
- Given a user or address locked out by 5 failures, when more than LoginLockoutWindow has passed since the fifth failure with no attempt in between, then the right password is accepted again.
- Given user u fails 4 times, then more than LoginLockoutWindow passes with no attempt, then u fails once more, then u's next attempt with the right password is accepted. The same holds for an address that fails 4 times, waits, and fails once more. This holds under every reading in open question 3.
- Given failed API-key attempts from an address, then they do not count towards MaxFailedLogins, and a basic-auth lockout of that address does not affect requests that present an API key (SCN-310, INV-308).
- The response to a rejected attempt is open question 2. Counting across nodes is open question 4.

### AC-6 · SCN-310 · scenario

> **A basic-auth lockout does not block API keys**
>
> *Given:* RequireBasicAuth() and RequireApiKey() are enabled; the office address has failed basic authentication MaxFailedLogins times within LoginLockoutWindow; the CI script behind the same address holds an active operate-scope key k1 whose expiresAt has not passed.
>
> 1. REQ-304 — a correct basic-auth password from the office address is rejected
> 2. REQ-305 — the CI script calls the JSON API with k1
>
> *Then:* The basic-auth attempt was rejected, and the CI request is authenticated with operate scope and principal name apikey:k1.

### AC-7 · TECH-94 · must

> **Basic-auth password hashing** — RequireBasicAuth() shall verify passwords against salted PBKDF2-HMAC-SHA256 hashes with at least 600,000 iterations, computed with the BCL's Rfc2898DeriveBytes.Pbkdf2, which a helper and the CLI generate.
>
> *Notes:* Decided by the owner on 2026-11-06: PBKDF2 only, so the dashboard takes no third-party dependency; Argon2 is not offered. 600,000 iterations follows the OWASP recommendation for PBKDF2-HMAC-SHA256.

- Given a password, when the helper hashes it, then the result is a salted PBKDF2-HMAC-SHA256 hash with at least 600,000 iterations, computed with `Rfc2898DeriveBytes.Pbkdf2`. Hashing the same password twice gives two different hashes, and both verify.
- Given a configured hash produced by the helper, then signing in with its password succeeds (REQ-303) and signing in with any other password fails.
- Inspection: verification calls `Rfc2898DeriveBytes.Pbkdf2` with SHA-256, and Bellhop.Dashboard references no third-party cryptography package (TECH-94's notes).
- Whether a weaker hash counts as unsupported is open question 6.

### AC-8 · NFR-43 · must

> **Constant-time password comparison** — When basic authentication checks a password, the system shall compare hashes in constant time.
>
> *Measure:* comparison uses a fixed-time equality primitive · *Verification:* inspection

- Inspection: the code that compares the derived hash with the stored one uses a fixed-time equality primitive, and nothing compares hash bytes in a way that can stop at the first difference. The reviewer records the file and line in Notes.

## Open questions

1. **Blocks** · REQ-303: which permission does an authenticated basic-auth user get, view or operate, and what principal name do their actions carry? No item says, while anonymous access (REQ-300, REQ-342) and API keys (REQ-305) both do. Owner to decide.
2. **Decide in delivery** · REQ-303, REQ-304: what does the dashboard answer to a wrong basic-auth credential and to a locked-out attempt? INV-300 and INV-308 cover neither, and dashboard A-16 leaves it open.
3. **Decide in delivery** · REQ-304, REQ-336: does LoginLockoutWindow count from the first failure or over a sliding window, and does an attempt rejected during a lockout count as a failure? The criteria hold under every reading; the boundary between the readings needs the answer. The LoginLockoutWindow glossary entry and the LoginAttempt entity's lockedUntil attribute do not settle it.
4. **Decide in delivery** · REQ-304: are failures counted per node or shared by every node through the store? With per-node counts, N dashboard nodes allow N × MaxFailedLogins attempts.
5. **Decide in delivery** · REQ-334, TECH-94: the configuration shape of a user, the text format of a stored hash, and the helper's name. All three become public contracts that NFR-20 then freezes.
6. **Decide in delivery** · TECH-94, REQ-334: is a PBKDF2-HMAC-SHA256 hash with fewer than 600,000 iterations "not a supported salted hash", so that startup fails? TECH-94's "at least 600,000 iterations" may bind verification, or only the hashes the helper and the CLI generate.
7. **Decide in delivery** · TECH-94, TECH-122: TECH-94 (must) has hashes generated by "a helper and the CLI", but the CLI is may and M3 (TECH-122, ST-086). Should TECH-94 name only the helper for 1.0? The owner decides the wording.
