# ST-041 — Enqueue inside the application's database transaction

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-030, ST-037

## Context

Lets an application enqueue a job inside its own database transaction, so that the job runs only if the transaction commits (INV-101, SCN-113). It works through the explicit database transaction on EnqueueOptions (TECH-20) and, in the new optional Bellhop.EntityFrameworkCore package, through dbContext.EnqueueAsync(job) when the job store shares the application's database (REQ-431, TECH-49). The PostgreSQL store becomes the first store whose capability set reports transactional enqueue (TECH-33).

Builds on ST-037 (M1 acceptance, so M1 is finished first), ST-030 (the PostgreSQL store) and ST-007, which put the transaction on EnqueueOptions and made a store without the capability reject it (REQ-153); the in-memory store keeps rejecting it (REQ-153's notes). The tool infers M1 for SCN-113, but the scenario exercises INV-101, which is tagged M2 and which hosting REQ-36 places in M2 as "EF Core enqueue" (TECH-49's notes: transactional enqueue is MUST and M2), so it stays with INV-101. TECH-49's outbox table and relay are ST-078 (M3), which builds on this story and keeps TECH-49 and REQ-431 holding; owning TECH-49 here is fine because the package is the contract ST-078 extends. ST-055 and ST-056 keep INV-101 holding on SQL Server and SQLite, ST-073 publishes the transactional-enqueue sample (NFR-27) and ST-054 puts INV-101 in the conformance suite.

Lives in Bellhop.PostgreSql (TECH-37), which writes the job through the application's transaction with plain ADO.NET (TECH-36), and in Bellhop.EntityFrameworkCore (TECH-49), the only package that references Entity Framework Core: the core stays free of it (TECH-9) and no store requires a DbContext (TECH-48). The EnqueueOptions member that carries the transaction and the full signature of dbContext.EnqueueAsync are not in the specs (open questions 1 and 6). Outbox mode does not exist before ST-078, so REQ-431's "outbox mode is not configured" always holds in this story.

## Acceptance criteria

### AC-1 · INV-101 · must

> Where the store supports transactional enqueue, when an application enqueues a job inside its open database transaction, the system shall make the job visible to workers only if that transaction commits.

- Given the PostgreSQL store and an open application transaction on the store's database, when the application enqueues a job with that transaction on EnqueueOptions (TECH-20) and then commits, then the job is enqueued and a worker claims it (REQ-123).
- Given the same, when the application rolls the transaction back instead, then the job is not stored and no worker ever claims it (SCN-113).
- Given the transaction is still open, then no worker on any node claims the job.
- Given the in-memory store, which reports no transactional enqueue, then a call that passes a transaction is rejected as REQ-153 says.
- Concurrency: two worker nodes claim continuously while the application runs many transactions that each enqueue a job and then commit or roll back at random. Observed: every claimed job belongs to a committed transaction, and every committed job is claimed.
- Inspection: the PostgreSQL store's capability set reports transactional enqueue (TECH-33).

### AC-2 · REQ-431 · should

> Where the job store shares the application's database and outbox mode is not configured, when an application calls dbContext.EnqueueAsync, the system shall enqueue directly in the context's current transaction.
>
> *Notes:* The choice between the direct path and the outbox is made by configuration.

- Given the PostgreSQL store on the application's database and a DbContext with a current transaction, when the application saves an entity, calls dbContext.EnqueueAsync(job) and commits, then both the entity and the job are stored, and a worker claims the job.
- Given the same, when the transaction rolls back, then neither the entity nor the job is stored, and no worker claims the job.
- Given the transaction is still open, then no worker claims the job.
- Property, with concurrent claimers: over random commits and rollbacks, the job exists exactly when the entity saved in the same transaction does.
- A context with no current transaction, and a store that does not share the database, are open questions 4 and 5.

### AC-3 · SCN-113 · scenario

> **Rolled-back transactional enqueue never runs**
>
> *Given:* PostgreSQL store sharing the application database; app enqueues j inside its transaction and then rolls the transaction back.
>
> 1. REQ-120 — enqueue inside the transaction
> 2. REQ-123 — a worker tries to claim j after the rollback
>
> *Impossible at step 2.*

### AC-4 · TECH-49 · must

> **EF Core package** — The optional Bellhop.EntityFrameworkCore package shall use Entity Framework Core to provide dbContext.EnqueueAsync(job) and the outbox table and relay.
>
> *Notes:* The outbox part is SHOULD and M3 (BLT-17); transactional enqueue is MUST and M2.

- Build check: Bellhop.EntityFrameworkCore builds for net8.0 and net10.0 (TECH-1), references Entity Framework Core, and ships with the same version as the other first-party packages and exact-version dependencies on them (TECH-50).
- Dependency audit: neither the core package nor Bellhop.PostgreSql references Entity Framework Core or Bellhop.EntityFrameworkCore (TECH-9, TECH-48), and an application that does not reference the package runs unchanged.
- Test: once the package is referenced, dbContext.EnqueueAsync(job) is available on a DbContext and behaves as REQ-431 says. Pass means both checks above are green and REQ-431's tests pass; the outbox table and relay are checked in ST-078.

## Open questions

1. **Decide in delivery** · INV-101, TECH-20: which EnqueueOptions member carries the transaction and what is its type (ADO.NET's DbTransaction, or a store-specific type), and which IJobClient calls accept it: EnqueueAsync only, or also ScheduleAsync, EnqueueManyAsync, ChainAsync and CreateBatchAsync? TECH-20 says only "an explicit database transaction".
2. **Decide in delivery** · INV-101, REQ-153: what happens when the transaction passed is no longer open, or belongs to a connection to a database other than the store's? INV-101 assumes "its open database transaction", and REQ-153 covers only a store without the capability.
3. **Decide in delivery** · INV-101, REQ-169: when are the IJobEvents handlers called for a job enqueued in the application's transaction, which Bellhop does not commit itself? REQ-169 calls them "after the store write has committed", so a job whose transaction rolls back must raise none.
4. **Decide in delivery** · REQ-431: what does dbContext.EnqueueAsync do when the context has no current transaction (enqueue at once, wait for SaveChanges, or reject), and how is it established that the job store shares the application's database (by configuration, or by comparing connections)? Neither is stated.
5. **Decide in delivery** · REQ-431, integrations REQ-437: in M2, what does dbContext.EnqueueAsync do when the job store does not share the application's database? REQ-437 rejects the call, but it is tagged M3 with the outbox, and its notes say that enqueueing outside the transaction would lose atomicity silently. Owner to decide whether REQ-437 moves to M2.
6. **Decide in delivery** · TECH-49: the signature of dbContext.EnqueueAsync (its options and return value) and the Entity Framework Core versions the package depends on for net8.0 and net10.0 (TECH-1). Both become public contracts.
