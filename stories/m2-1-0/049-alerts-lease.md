# ST-049 — Load alert rules and hold the notification lease on alerts nodes

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-030, ST-032, ST-037

## Context

Adds AddAlerts() on the AddBellhop builder (TECH-129, as the owner decided on 2026-11-10), the alerts registration that runs notification checks on any node, apart from the client and the worker, so that a node-lost alert still fires when the last worker is down (REQ-59 notes). Nodes without it run no check (REQ-59). Among the nodes that have it, one takes a store-side notification lease (REQ-438), and rules are evaluated and deliveries created and sent only on the holder, with the lease checked in the same store write (INV-411). Rules are loaded from configuration and code, code winning, and listed on the Notifications page (REQ-410), so this story adds that page to the dashboard.

Builds on ST-037 (M1's acceptance, so the milestones are built in order), ST-030 (the in-memory and PostgreSQL stores, where the lease lives, TECH-51) and ST-032 (the dashboard shell the Notifications page joins), and on ST-005 and ST-006, whose REQ-52 and REQ-54 already name the alerts registration and were built against what existed; this story keeps them and REQ-40 holding, and keeps REQ-19 (ST-006) holding now that its startup summary can name the alerts registration. ST-050 (channels, sending and 'send test' on this page), ST-051 (cooldowns and the dead-letter rule) and ST-052 (the other rules; it keeps INV-411 holding) build on it.

AddAlerts() is in the Bellhop core package, which holds notifications (TECH-112), and the Notifications page is in Bellhop.Dashboard (TECH-88), backed by the JSON API (TECH-92). The lease and the lease-checked delivery write change the store contract (TECH-31), so they are implemented on the in-memory and PostgreSQL stores. INV-411 covers creating and sending deliveries, which first happen in ST-050 and ST-051; this story builds the lease-checked write and tests it by writing deliveries through the store directly. The rule's configuration section and shape, and the code API for rules, are not in the specs (open question 1).

### Modeling assumptions

Decisions the model took where the sentences were silent. Build to them, or raise an open question.

- integrations A-9 (affects INV-409, INV-411): In the cooldown model, delivery creation is serialised, which is what INV-411's fenced write gives. The lease itself is modeled in `IntegrationsAlerts.tla`.
- integrations A-15 (affects INV-411, INV-412, INV-413): `IntegrationsAlertEvents` has one alerts node holding the lease throughout, and each store write is one step (the find and the conditional write coincide). Handovers and writes split into a read and a later write are in `IntegrationsAlerts`. Rule evaluation, including INV-413's first evaluation, is fair (it happens if it stays possible) but has no deadline.
- integrations A-21 (affects INV-411, INV-412, INV-413): In `IntegrationsAlerts` every INV-412 and INV-413 write is two steps: a read that decides it, and a write that checks the lease and its condition when it lands and, if either fails, changes nothing (the next evaluation reads again). The read takes an event that is neither delivered for the name nor before the start of the version the node runs. The write checks "not yet delivered for that name", as INV-412 says, and under run 6's wording also the version's start marks. A crash forgets a pending write. The node-memory counterfactuals keep a one-step write.
- hosting A-20 (affects REQ-59): A node with the alerts registration starts its notification checks when it is marked running (integrations INV-411/REQ-438), and stops them when it stops. REQ-59 therefore holds by construction
- integrations A-10 (affects LIV-400, REQ-435, REQ-438): At most one crash per behaviour (relay node, or alerts node).
- integrations A-11 (affects REQ-432, REQ-435, REQ-438, INV-412, INV-413): At most one lease expiry under a running holder (a missed renewal, e.g. a long pause). The relay's row delete is not fenced (REQ-432 does not say), but it is idempotent.
- integrations A-12 (affects REQ-438, INV-412, INV-413): A crashed node is restarted by its host (fair) as a new instance that does not inherit its old lease. The old lease must expire first. A paused node that is still running may take the lease again once it is free.

## Acceptance criteria

### AC-1 · INV-411 · must

> The system shall evaluate notification rules, create their deliveries and send deliveries only on a running node that has the alerts registration and holds the notification lease, checking the lease in the same store write that creates or updates the delivery.
>
> *Notes:* refiner-model 2026-11-06 F-6, decided by the owner: alerting is its own registration, independent of the client and the worker, so it can run on a worker node, a client or dashboard node, or a node that only does alerts; it keeps working when no worker is alive. The notification check is no longer a worker duty (hosting REQ-40). The lease, fenced in the store write, makes one node the detector, so two nodes noticing the same breach create one delivery (closes modeling assumption A-11). Test deliveries (REQ-409) can be requested from any dashboard node but are sent by the lease holder.

- Concurrency, on the in-memory and PostgreSQL stores: two and three nodes with AddAlerts() and rules configured, a fake TimeProvider, a holder that pauses past LeaseDuration and resumes, a holder that crashes and is restarted, and every node trying to create and update deliveries at random moments. Observed: every delivery write the store accepts came from the node that held the unexpired notification lease when the write landed; every other write changes nothing.
- Given a1 holds the lease, when a2, running with the alerts registration, writes a delivery, then the write fails and the store is unchanged (SCN-405 in ST-051 builds on this).
- Given a holder whose lease expired during a pause and was taken by another node, when it lands a write it prepared before the pause, then the write fails (integrations A-21).
- Given a node with the alerts registration that is still starting, then it evaluates no rule and takes no lease (hosting A-20: the checks start when the node is marked running).
- Given an alerts-only node and no worker running, then it holds the lease and evaluates the rules (notes).
- A node without the alerts registration is REQ-59.

### AC-2 · REQ-59 · must

> While a node does not have the alerts registration, the system shall run no notification check on that node, whether or not the worker is registered.
>
> *Notes:* Decided by the owner on 2026-11-06 (refiner-model, integrations F-6): alerting is a separate registration that can live on a worker node, a client or dashboard node, or a node that does only alerts, so the node-lost alert still fires when the last worker is down. The checks themselves, and how several alerts nodes share them, are in the integrations module.

- Given rules are configured and nodes registered with every combination of AddClient(), AddWorker(...) and MapBellhopDashboard but without AddAlerts(), then over the whole run none of them takes the notification lease, evaluates a rule or creates a delivery, whether or not the worker is registered.
- Given AddAlerts() is added to one of them, then that node takes the lease (REQ-438) and the others still run no check.
- Given a node with AddAlerts() and no worker, then it runs no background duty of the worker (hosting REQ-40).

### AC-3 · REQ-410 · must

> The system shall load rules from configuration and from code, use the code definition when a rule with the same name exists in both, and list every rule on the Notifications page.
>
> *Notes:* Decided by the owner on 2026-11-06: code wins, the same precedence as options (hosting REQ-17).

- Given a rule defined only in configuration and another only in code, then both are loaded and both are listed on the Notifications page.
- Given a rule with the same name in configuration and in code, with different settings, then the code definition is the one evaluated, and the page lists that rule once, with the code's settings.
- Given a request without view or operate permission, then the Notifications page is not served (dashboard INV-301).
- Whether "code wins" replaces the whole rule or each field, and which node's rules the page lists in a deployment with several nodes, are open questions 2 and 3.

### AC-4 · REQ-438 · must

> Where notification rules are configured, when no running node with the alerts registration holds an unexpired notification lease, the system shall let one running node with the alerts registration take the notification lease for LeaseDuration and renew it every HeartbeatInterval while it runs.
>
> *Notes:* refiner-model 2026-11-06 F-6: the same kind of lease as the outbox relay (REQ-435) and the cleanup lease (jobs REQ-164), with the job lease's length and heartbeat (jobs REQ-102) so no new constant is needed.

- Given rules are configured, two running nodes with the alerts registration and no lease held, then exactly one of them takes the notification lease for LeaseDuration (60 s by default, jobs REQ-102) and renews it every HeartbeatInterval (20 s) while it runs; the other does not take it while that lease is unexpired.
- Given the holder crashes, when LeaseDuration has passed since its last renewal (fake clock), then the other node takes the lease, and not before.
- Given LeaseDuration is configured as 30 s, then the notification lease lasts 30 s and is renewed every 10 s (notes: the job lease's length and heartbeat).
- Given no notification rules are configured, then no node takes the lease.
- Given running nodes none of which has the alerts registration, then no node takes the lease (REQ-59).
- Concurrency, on the in-memory and PostgreSQL stores: many nodes race for a free lease; at no instant do two nodes hold an unexpired lease.

### AC-5 · TECH-129 · must

> **Alerts registration** — The AddBellhop builder shall offer AddAlerts(), an alerts registration separate from AddClient() and AddWorker(), that can be combined with them and with MapBellhopDashboard on one node or used alone on an alerts-only node.
>
> *Notes:* Decided by the owner on 2026-11-06 (integrations findings F-6): alerting must keep working when the last worker is down. Decided by the owner on 2026-11-10: AddAlerts() on the AddBellhop builder, in the style of TECH-128, because a hosted background duty is registered on the service collection; app.UseBellhopAlerts(), suggested earlier, is not offered.

- Build check: AddBellhop(...).AddAlerts() compiles alone and chained with AddClient() and AddWorker(...), on a host that also calls MapBellhopDashboard.
- Test: a host with AddBellhop(...).AddAlerts() and nothing else starts and is marked running without hosting REQ-54's "will do nothing" warning, runs no background duty of the worker (hosting REQ-40), names the alerts registration in its startup summary (hosting REQ-19) and, with rules configured, takes the notification lease (REQ-438).
- Test: every combination of AddClient(), AddWorker(...), AddAlerts() and MapBellhopDashboard, none included, starts as hosting REQ-52 says.
- Inspection of the public API: AddAlerts() is on the AddBellhop builder in the style of TECH-128, and there is no app.UseBellhopAlerts() (notes). The reviewer records it in Notes.
