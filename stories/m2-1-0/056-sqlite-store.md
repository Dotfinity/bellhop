# ST-056 — Store jobs in SQLite for a single node

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-054

## Context

Adds the Bellhop.Sqlite package, a job store on SQLite for development and small deployments that run a single node (TECH-42). It follows the same SQL-store rules as PostgreSQL and SQL Server and passes the conformance suite. By the owner's decision, two nodes pointed at one SQLite file are unsupported and undefined: the docs say so, and the store does not check for it (TECH-42's notes).

Builds on ST-054 (the conformance suite, TECH-105), ST-029 and ST-030 (the SQL-store rules TECH-36, TECH-44, TECH-46, TECH-47, TECH-126, TECH-127), ST-008 (claims), ST-040 (a bulk enqueue takes one store round-trip per batch, NFR-17), ST-054 (library versions N and N+1 both read and write schema N, NFR-18; on a single node, open question 1), ST-036 (memory proportional to in-flight jobs, NFR-13, and due recurring jobs found by one indexed range query per poll, NFR-14) and ST-041 (a job enqueued in a transaction runs only if it commits, INV-101, where the store supports transactional enqueue; open question 3). ST-075 (query plans, NFR-15, NFR-16) and ST-086 (the CLI) build on it.

Lives in the Bellhop.Sqlite package (TECH-42, TECH-124). Migrations are serialised by a SQLite write transaction (TECH-126), and BellhopSchema.GetScript gives its SQLite output (TECH-47). Not in the specs: the form the default "bellhop" takes on a database without schemas, the capability set, what the database clock is, and the registration method, options and ADO.NET provider package (open questions 2 to 5).

## Acceptance criteria

### AC-1 · TECH-42 · must

> **SQLite store** — The Bellhop.Sqlite package shall use SQLite as a single-node job store for development and small deployments.
>
> *Notes:* Decided by the owner on 2026-11-06: pointing two nodes at one SQLite file is unsupported and undefined; the docs say so and the store does not check for it.

- Given one node with several workers on one SQLite file, when the conformance suite (TECH-105) runs, then it is green, including its concurrency tests for claims, uniqueness and recurring triggers run inside that node. Which tests that use more than one node apply is open question 1.
- Given a host configured with the SQLite store, AutoMigrate on and a new database file, when it starts, then the embedded migrations create the schema under the default name bellhop (TECH-46; its SQLite form is open question 2) and the node reaches Running (hosting REQ-18).
- Dependency audit: Bellhop.Sqlite references neither EF Core nor Dapper (TECH-36) and needs no DbContext (TECH-48).
- Inspection: the store has no check for another node on the same file (TECH-42's notes), and no test asserts any behaviour for two nodes on one file, which is undefined.
- Inspection: the SQLite store's documentation says it is meant for development and small deployments on a single node, and that pointing two nodes at one file is unsupported and undefined. The reviewer records the page in Notes.

## Tests

Every test carries one `Trait("Req", "<id>")` for each item it verifies.

- Conformance: the TECH-105 suite against Bellhop.Sqlite on a single node (TECH-42).
- Integration: migrations from a new file and from each earlier schema version (TECH-46, TECH-127), two migration attempts on one file at the same time with only one applying them inside its write transaction (TECH-126, hosting REQ-42), GetScript output compared with the schema the migrations produce (TECH-47), and concurrent enqueues with one unique key turned away by the unique index (TECH-44).
- Inspection, recorded in Notes: TECH-36's dependency audit, the absence of a check for other nodes, and the documentation statement (TECH-42).
- Must keep holding: the tests of TECH-36, TECH-44, TECH-46, TECH-47, TECH-126, TECH-127, TECH-105 and INV-101 stay green on the other stores. On SQLite as well: NFR-17 (round-trips counted for a bulk enqueue), NFR-18 (version N+1 reading and writing schema N, one node at a time unless open question 1 says otherwise), NFR-13 (node memory with a large stored history), NFR-14 (one indexed range query per poll for due recurring jobs, checked in the query plan) and, if open question 3 gives SQLite transactional enqueue, INV-101 (a rolled-back transaction leaves no job to run).
- Not automated: TECH-42 gives no measure for development and small deployments; the documentation statement is checked by inspection.

## Out of scope

- Several nodes sharing one store: SQL Server (ST-055) and PostgreSQL (ST-029, ST-030); on SQLite it is unsupported by the owner's decision in TECH-42's notes.
- Index use by cleanup and dashboard queries: NFR-15 and NFR-16 (ST-075).
- Waking nodes through Redis instead of polling: REQ-516 (ST-063).
- First-party MySQL or MongoDB stores: hosting REQ-8 (non-goal); community stores are ST-089 (NFR-59).
- The CLI: TECH-122 (ST-086).

## Open questions

1. **Decide in delivery** · TECH-42, TECH-105, NFR-18: may a single-node store skip the conformance tests that run two store instances (two nodes) against one database, or must SQLite pass them, and is NFR-18 met on SQLite by running version N+1 on schema N one node at a time? TECH-105 does not say, NFR-18's measure runs mixed N and N+1 nodes side by side, and TECH-42's notes make two nodes on one file undefined.
2. **Decide in delivery** · TECH-46: SQLite has no schemas; does the configurable bellhop name become a table-name prefix, and in what form? The table names are a persisted format that NFR-20 then freezes.
3. **Decide in delivery** · TECH-33, INV-101: does the SQLite store support transactional enqueue, so that INV-101 applies to it, and which other capabilities (push notifications, result storage) does it report? The specs give the capability set only for Redis (REQ-512) and the in-memory store (jobs REQ-153's notes). NFR-32 sends Redis users to the SQL stores for transactional enqueue, and TECH-36 counts SQLite among them.
4. **Decide in delivery** · jobs INV-105, TECH-12: what is the database clock on SQLite, which runs inside the node's process? SQLite's own current time reads the machine clock and cannot follow a FakeTimeProvider (TECH-103), while the node's TimeProvider is the node clock that INV-105 rules out.
5. **Decide in delivery** · TECH-42, TECH-36: what are the SQLite store's registration method and option names, and which ADO.NET provider package does it depend on? No item names them, and both are visible to applications (NFR-20).
