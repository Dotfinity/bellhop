# ST-063 — Wake SQL-store nodes through Redis notifications

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** may · **Depends on:** ST-058, ST-055

## Context

Lets a team that keeps its jobs in a SQL store add Redis only to wake nodes sooner. With UseRedisNotifications(), an enqueue publishes a wake-up signal on Redis so other nodes pick the job up before their next poll (REQ-516), job state is never read from Redis (INV-501), and while Redis is down the nodes poll the SQL store at PollInterval as they would without it (REQ-517, SCN-502). Every item is may.

Builds on ST-058 (the Redis store's per-queue wake-up channel and subscription, TECH-63) and the Redis client of ST-057 (TECH-52, TECH-53), and on the SQL stores: PostgreSQL (ST-029, ST-030), and SQL Server (ST-055), a direct dependency because SCN-502 runs on it. ST-076 (the 1.0 release) builds on it.

Nothing in the SQL stores' data changes: the SQL store stays the only source of truth (TECH-37, TECH-40, TECH-42). REQ-516 names the call UseRedisNotifications(), but no item says which package offers it, on which builder, or how it gets its Redis connection (open question 1).

## Acceptance criteria

### AC-1 · INV-501 · may

> Where UseRedisNotifications() pairs a SQL store with Redis, the system shall never read job state from Redis; the SQL store is the only source of truth.

- Attack: a run of enqueues, claims, retries, completions and dashboard reads on two nodes with UseRedisNotifications(), while the test records every command the nodes send to Redis and publishes signals of its own: duplicated, dropped, and naming jobs that do not exist. Observed: no command reads a key from Redis, every job's state and history equals what the SQL store holds, and a signal for a job that does not exist changes nothing.
- Given the Redis server also holds job data under Bellhop's key prefix (TECH-68), for example that of a Bellhop installation using the Redis store, then the nodes never read it.
- Given a signal arrives, then the node claims through the SQL store exactly as when it polls (jobs REQ-103).
- Property: over random signal streams (duplicates, drops, unknown ids), every job's history equals that of the same run with no Redis at all.

### AC-2 · REQ-516 · may

> Where UseRedisNotifications() pairs a SQL store with Redis, when a job is enqueued, the system shall publish a wake-up signal on Redis so other nodes pick up work without waiting for the next poll.

- Given two idle nodes A and B with UseRedisNotifications() and a PollInterval longer than the test waits, when A enqueues a job through IJobClient, then a signal is published on Redis and B claims the job before its next poll.
- Given a node without UseRedisNotifications(), then it publishes nothing on Redis.
- Given Redis came back after an outage (REQ-517), then a later enqueue wakes B again without restarting either node.
- Which other moves into Enqueued publish, and when an enqueue inside the application's transaction publishes, is open question 2.

### AC-3 · REQ-517 · may

> Where UseRedisNotifications() pairs a SQL store with Redis, if Redis is unavailable, then the system shall keep processing by polling the SQL store at PollInterval.

- Given UseRedisNotifications() and Redis stopped, when a job is enqueued on A, then it is stored in the SQL store and B picks it up within PollInterval by polling (SCN-502); no node stops processing.
- Given PollInterval is not configured, then that poll runs every 1 second (jobs REQ-103).
- Given Redis stays unavailable for many PollIntervals, then every job enqueued meanwhile is picked up within PollInterval of being stored.
- What a node reports while Redis is down, whether it starts when Redis is unavailable at startup, and how long an enqueue waits for its publish are open question 3.

### AC-4 · SCN-502 · scenario

> **Hybrid notifications survive a Redis outage**
>
> *Given:* SQL Server store with UseRedisNotifications(); Redis goes down; a job is enqueued on node A.
>
> 1. REQ-517
>
> *Then:* Node B picks up the job within PollInterval by polling SQL Server, and no job state was read from Redis.

## Open questions

1. **Decide in delivery** · REQ-516, REQ-517, INV-501: which package and builder offer UseRedisNotifications(), and how does it get its connection? TECH-53's connection string or shared IConnectionMultiplexer is a rule for the Redis store, not this mode. The channel and message format, and how namespaces keep their signals apart (TECH-68's prefix), become a contract between nodes of different versions. No item names any of it.
2. **Decide in delivery** · REQ-516: which enqueues publish? Only an IJobClient enqueue, or every move into Enqueued (a scheduled or retry job promoted, a requeue, a continuation released)? And for an enqueue inside the application's own database transaction (INV-101, ST-041), Bellhop does not see the commit: is the signal sent at the call, before other nodes can see the job, or after the commit?
3. **Decide in delivery** · REQ-517: while Redis is unavailable, what does the node report (health, a log line), does an unavailable Redis at startup stop the host (hosting REQ-12 lists no such check), and how long may an enqueue wait for its publish before going on?
