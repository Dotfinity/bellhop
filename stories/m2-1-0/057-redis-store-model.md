# ST-057 — Connect the Redis store and lay out its data model and scripts

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-054

## Context

Lays the foundation of the Bellhop.Redis package, which ships in 1.0 with the Tier 1 servers (TECH-70's notes, hosting REQ-36): the StackExchange.Redis connection (TECH-52, TECH-53), the documented, versioned key layout with its prefix and hash tags (TECH-56, TECH-58, TECH-68), and the rules every Redis script follows: the command baseline and the features never used (TECH-54, TECH-55), the time passed in by the caller (TECH-59), the Lua subset (TECH-60) and loading by EVALSHA (TECH-61). It also sets the store's capability set and its lower default payload limit (REQ-512, REQ-513). The store is built on sorted sets, lists, hashes and Lua rather than Streams (hosting REQ-38).

Builds on ST-054 (the conformance suite), ST-004 (IJobStore, TECH-31), ST-007 (the capability set TECH-33, the payload limits of jobs REQ-105 and REQ-148, and the refusal of a transaction, jobs REQ-153), ST-046 (namespaces, jobs INV-125, which TECH-68 maps to prefixes), ST-029 (migrations serialised by a lock native to the store, which on Redis is a key set with NX and an expiry, TECH-126) and ST-006 (the schema rules at startup: migrating an older version with AutoMigrate on, hosting REQ-22; failing a start more than one version behind with AutoMigrate off, hosting REQ-23; failing a start on a newer version, hosting REQ-43). In this plan the Redis store's schema is its versioned key layout (TECH-56), so those four rules apply to the layout version; how is open question 7. ST-058 writes the job-lifecycle scripts against this layout and these rules, ST-059 adds server detection, ST-060 writes the generation marker and reconciling flag laid out here (it lists TECH-56 under Must keep holding), ST-061 the unacknowledged-reset record, ST-062 runs the store on the Tier 1 servers and topologies, and ST-064 changes the hash tags for ShardByQueue (it lists TECH-58). TECH-70 and the script contracts TECH-56 and TECH-58 to TECH-61 are owned here, before any story builds the Redis behaviour they apply to, so that every script from ST-058 on is written and checked against them; hosting REQ-36 puts all of them in M2. TECH-70's same semantics as the SQL stores can only be shown by the full conformance run, which needs ST-058's scripts; ST-058 lists TECH-70 and the script rules TECH-54, TECH-55 and TECH-58 to TECH-61 under Must keep holding.

Lives in the Bellhop.Redis package (TECH-70, TECH-124), which depends on StackExchange.Redis 3.4.20 or later (TECH-52); the capability set is IJobStore's (TECH-33). The registration method and its options (connection string, multiplexer, key prefix) and the composed key format are not in the specs (open questions 3 and 4). The marker, its flag and last-reset value and the reset record are laid out here but first written by ST-060 and ST-061 (TECH-130); this story's layout test covers them once those stories write them.

## Acceptance criteria

### AC-1 · REQ-512 · must

> The system shall report in the Redis store's capability set no transactional enqueue, while offering push notifications and result storage.
>
> *Notes:* Decided by the owner on 2026-11-06: free-text payload search is dropped from Bellhop altogether as overkill; tag filters (BLT-9) cover looking jobs up by business key. Checked against current Redis: pub/sub gives push notifications and hashes with TTLs give result storage on every supported server, while no Redis server can join the application's SQL transaction. Redis 8 does ship a query engine with full-text search, but it is not used (RDV-2).

- Given the Redis store, when the capability set is read (TECH-33), then transactional enqueue is reported missing and push notifications and result storage are reported present.
- Given the Redis store, when an application passes a database transaction in EnqueueOptions (TECH-20), then the call is rejected with an error that names the transactional-enqueue capability and the store, and no key is written (jobs REQ-153).
- No option changes these values; the sentence offers no override.
- Push notifications and result storage are delivered by ST-058's scripts (TECH-63, REQ-514), whose conformance run shows that the store does what it reports.

### AC-2 · REQ-513 · must

> The system shall lower the default payload hard limit to 256 KB on the Redis store.

- Given the Redis store and PayloadHardLimit not configured, when an application enqueues a job whose payload is just over 256 KB, then the call is rejected with an exception that names the size and the limit, and no key is written (jobs REQ-148); a payload of exactly 256 KB is stored, with the soft-limit warning of jobs REQ-147.
- Given the Redis store and PayloadHardLimit configured, then the configured value applies in place of 256 KB.
- Given any other store and PayloadHardLimit not configured, then the default stays 1 MB (jobs REQ-105).

### AC-3 · TECH-52 · must

> **Redis client** — The Redis store shall use StackExchange.Redis as its client.
>
> *Version:* >= 3.4.20

- Dependency audit in CI: Bellhop.Redis declares StackExchange.Redis with a lower bound of 3.4.20 or higher, the restored version is at least 3.4.20, and the store reaches the server through no other client library. Passing: the audit is green on every build.
- The audit is installed here and runs for every later Redis story; another client (TECH-72) is deferred.

### AC-4 · TECH-53 · must

> **Shared multiplexer** — The Redis store shall accept a connection string or an IConnectionMultiplexer, and shall reuse the application's multiplexer from DI when one is registered rather than opening a second one.

- Given only a connection string, when the store starts, then it connects with a multiplexer of its own.
- Given an IConnectionMultiplexer passed to the store, then it uses that one, and the server's client list shows no connection from the store beyond that multiplexer's.
- Given the application has registered an IConnectionMultiplexer in DI, when the store starts, then it reuses that multiplexer and opens no second one: the server's client list shows the same connections with and without the store.
- Which one is used when a connection string is given and a multiplexer is registered too, and whether the store may dispose a multiplexer it reused, are open question 3.

### AC-5 · TECH-54 · must

> **Redis command baseline** — The Redis store shall use only strings (SET NX PX, GET, DEL, INCR/DECR, EXPIRE/PTTL), hashes (HSET/HGET/HMGET/HGETALL/HINCRBY/HDEL, whole-hash EXPIRE), lists (LPUSH/RPUSH/RPOP/LMOVE/LREM/LRANGE/LLEN), sorted sets (ZADD/ZREM/ZSCORE/ZCARD/ZRANGEBYSCORE ... LIMIT/ZREMRANGEBYSCORE/ZPOPMIN/ZRANK), sets (SADD/SREM/SMEMBERS/SISMEMBER), PUBLISH/SUBSCRIBE, EVAL/EVALSHA/SCRIPT LOAD and MULTI/EXEC without EVAL inside, on database 0 only.
>
> *Rationale:* This baseline is what keeps every server in TECH-71 to TECH-86 usable.

- CI check installed here: a test server records every command it receives during the Redis test runs, the conformance suite included from ST-058 on, and marks the commands run inside scripts. Passing: every command the store sends, directly or inside a script, is in TECH-54's list or among the commands open question 1 settles (TECH-59's TIME and TECH-69's HELLO and INFO among them).
- The same recording shows no EVAL or EVALSHA between MULTI and EXEC, and every command runs on database 0.
- A static check lists the commands each script calls (redis.call, redis.pcall) and fails the build on one outside the list.
- A connection string that names another database is open question 2.

### AC-6 · TECH-55 · must

> **Redis features never used** — The Redis store shall not depend on modules, FUNCTION/FCALL, Streams, keyspace notifications, hash-field TTL (HEXPIRE), CLIENT TRACKING, KEYS, ZRANGEBYLEX, SELECT, WAIT, atomic MSET or any Redis-8-only command.

- The command recording of TECH-54 contains none of FUNCTION or FCALL, any Streams command, a hash-field TTL command (HEXPIRE or its family), CLIENT TRACKING, KEYS, ZRANGEBYLEX, SELECT, WAIT or MSET, no subscription to a keyspace-notification channel and no change to the notify-keyspace-events setting. Passing: none appears in any run.
- The Redis tests pass on Redis 7.2 and Valkey 8.1 (the Tier 1 versions of TECH-73 and TECH-71) with no modules loaded, which shows that the store needs no module and no Redis-8-only command.
- The static script check of TECH-54 rejects the same commands inside scripts.

### AC-7 · TECH-56 · must

> **Redis data model** — The Redis store shall keep each job as a hash, per-queue ready and working lists, scheduled, retry and lease sorted sets scored by time, index sorted sets per state, queue and name, tag index sets, recurring definitions as hashes with a sorted set scored by NextRunAt, a node registry sorted set scored by heartbeat, unique keys as SET NX PX and concurrency counters as integers maintained inside scripts, in a documented and versioned key layout, plus a generation marker with a forward-only value taken from the server clock, a reconciling flag and the last-reset value in every hash tag the claim scripts use, and an unacknowledged-reset record.

- Inspection: the key-layout document is in the repository, carries a version, and lists for each structure named in TECH-56 its key pattern, its Redis type and, for a sorted set, what the score is. The reviewer records the document and its version in Notes.
- Layout test installed here: after each Redis test run, every key on the server matches a pattern in the document and has the documented type: job hashes, per-queue ready and working lists, scheduled, retry and lease sorted sets scored by time, index sorted sets per state, queue and name, tag index sets, recurring hashes with their sorted set scored by NextRunAt, the node registry sorted set scored by heartbeat, unique keys as strings and concurrency counters as integers. Passing: no key outside the document.
- The command recording of TECH-54 shows unique keys written only with SET NX PX, and concurrency counters changed only by commands run inside scripts.
- The document puts a generation marker, its reconciling flag and its last-reset value in every hash tag the claim scripts use, and one unacknowledged-reset record. ST-060 and ST-061 write them (TECH-130), and the layout test covers them from then on. Which hash slot holds the record under ShardByQueue is TECH-130's open question (ST-064).

### AC-8 · TECH-58 · must

> **Declared keys and hash tags** — Every Redis script shall declare all the keys it touches in KEYS, and all keys of one namespace shall share one hash tag so scripts are Cluster-safe.
>
> *Notes:* Declared keys also avoid Dragonfly's global script lock (RDV-4).

- Test guard installed here: every script call in the Redis test runs fails the test if the script touches a key that is not in its KEYS. Passing: no failure over the whole run.
- Given two namespaces (jobs INV-125) in the default mode, when the tests have run, then all keys of one namespace hash to one Cluster slot through one shared hash tag, and the two namespaces have different hash tags (TECH-68).
- Running the scripts on a Cluster without a cross-slot error is shown in ST-062 (TECH-64); ShardByQueue's tag per queue is ST-064 (TECH-65).

### AC-9 · TECH-59 · must

> **Script time from the caller** — Redis scripts shall receive the current time in ARGV, taken from a TIME call to the same server once per store call, never read TIME inside a script or use a node's clock, and shall be deterministic and short.
>
> *Notes:* Decided by the owner on 2026-11-06: the client reads the server clock with TIME and passes it in, so scripts stay deterministic and claims and due checks use the Redis clock as INV-105 requires. The extra round trip can be pipelined with the script call.

- Static check: no script calls TIME.
- The command recording of TECH-54 shows, for every store call that runs a script, exactly one TIME sent to the server that runs the script, and the script receives that value in ARGV; the TIME call may be pipelined with the script call (the item's notes).
- Given the node's clock (a FakeTimeProvider, TECH-103) set hours away from the server's, when jobs are scheduled, claimed and their leases renewed, then due checks, claims and lease deadlines follow the server's clock and not the node's (jobs INV-105).
- Determinism: each script run twice on the same data with the same KEYS and ARGV makes the same writes and returns the same reply.
- What makes a script short is open question 5.

### AC-10 · TECH-60 · must

> **Lua subset** — Redis scripts shall be written in the common subset of Lua 5.1 and 5.4, without the bit library, cjson, cmsgpack, redis.replicate_commands or redis.setresp, and with numbers passed as strings.
>
> *Version:* Lua 5.1 and 5.4 common subset
>
> *Rationale:* Keeps Dragonfly (Lua 5.4) and Garnet (opt-in Lua) supported (ADR-2).

- CI check installed here: every script compiles under a Lua 5.1 and a Lua 5.4 interpreter, and the build fails on any use of the bit library, cjson, cmsgpack, redis.replicate_commands or redis.setresp, or of syntax only one of the two versions accepts.
- Inspection: every number the store passes to a script is a string in ARGV. Whether numbers a script stores and returns must be strings too is open question 6.
- The scripts run on Redis and Valkey (Lua 5.1) in every Redis test run; Dragonfly (Lua 5.4) and Garnet join in ST-082.

### AC-11 · TECH-61 · must

> **Script loading** — The Redis store shall load each script once and invoke it with EVALSHA, falling back on NOSCRIPT.

- The command recording of TECH-54 shows each script loaded once and then called with EVALSHA on every later call, and never loaded again unless the server answered NOSCRIPT.
- Given the server's script cache is emptied (SCRIPT FLUSH by the test, or a server restart), when the next store call runs a script, then the server answers NOSCRIPT, the store loads the script again and the call succeeds, with no error reaching the caller.

### AC-12 · TECH-68 · must

> **Redis key prefix** — The Redis store shall prefix its keys with a configurable prefix, "bellhop:" by default, mapping each namespace to a distinct prefix and hash tag.

- Given no prefix configured, when the Redis tests run, then every key the store writes starts with bellhop: and nothing else.
- Given a prefix configured, then every key starts with that prefix and none with bellhop:.
- Given two namespaces, then their keys are disjoint, each with a distinct prefix and a distinct hash tag, and a job of one namespace is never visible through the other (jobs INV-125).
- The prefix option's name, how prefix, namespace and hash tag compose, and whether a prefix containing a brace is refused, are open questions 3 and 4.

### AC-13 · TECH-70 · must

> **Redis store package** — The Bellhop.Redis package shall use Redis and Redis-compatible servers as a job store with the same semantics as the SQL stores.
>
> *Notes:* Decided by the owner on 2026-11-06 (§9 Q7): the Redis store ships in 1.0 (M2) with the Tier 1 servers.

- Build: Bellhop.Redis builds for the target frameworks (TECH-1) at the same version as the other packages (TECH-50), and implements IJobStore as its only store interface (TECH-31), together with IJobIndex (TECH-32).
- Given a host configured with the Redis store, when it starts against Redis 7.2 or Valkey 8.1, then the store connects and the conformance suite (TECH-105) runs against it in CI. In this story the tests that need no lifecycle script pass: the capability set, the payload limits and the refused transaction.
- The pass condition, the full suite green on the Tier 1 servers, needs ST-058's scripts: ST-058 makes it green and keeps it so (TECH-70 and TECH-105 are in its Must keep holding), and ST-062 runs it on every Tier 1 server and topology.

## Open questions

1. **Decide in delivery** · TECH-54, TECH-59, TECH-63, TECH-66, TECH-69: what may the store send beyond TECH-54's list, which says "only"? TIME (TECH-59) and HELLO and INFO (TECH-69) are required elsewhere, TECH-66 pages with ZRANGE ... LIMIT while the list has ZRANGEBYSCORE ... LIMIT, TECH-63 allows BLMOVE, and StackExchange.Redis sends its own handshake, keep-alive and topology-discovery commands. Under the literal reading the command check cannot pass together with TECH-59 and TECH-69.
2. **Decide in delivery** · TECH-54: what does the store do with a connection string that names a database other than 0: fail the start under hosting REQ-9, ignore it, or something else? TECH-54 allows database 0 only and TECH-55 forbids SELECT, but no item says how a configured database is treated.
3. **Decide in delivery** · TECH-53, TECH-68: what are the store's registration method and option names (connection string, multiplexer, key prefix)? When a connection string is given and a multiplexer is registered in DI as well, which one is used, and may the store dispose a multiplexer it reused when the host stops? None of this is in the specs, and all of it becomes public API that NFR-20 freezes.
4. **Decide in delivery** · TECH-56, TECH-58, TECH-68: how do prefix, namespace and hash tag compose into a key name, and does option validation (hosting REQ-9) refuse a prefix containing { or }, which would change the hash tag every key of a namespace shares? The layout is a persisted format that NFR-20 freezes once it is published.
5. **Decide in delivery** · TECH-59: what makes a script short: a bound on the entries one call may touch, or a time budget? No figure is given; the only one nearby is TECH-67's 500 entries per janitor pass.
6. **Decide in delivery** · TECH-60: does passing numbers as strings also cover the numbers a script stores and returns? Lua 5.4 formats a float differently from 5.1, so a number written by a script could differ between Dragonfly and Redis.
7. **Decide in delivery** · TECH-56, TECH-126, hosting REQ-22, hosting REQ-23, hosting REQ-43: the plan treats the key-layout version as the Redis store's schema version, which REQ-22, REQ-23 and REQ-43 read and TECH-126's Redis lock serialises, but no item says so. Nor do the specs say where the version is stored, what an embedded migration is on Redis (TECH-46 covers the SQL stores only), how long the lock key's expiry is, or what path REQ-23's message gives when there is no migration script.
