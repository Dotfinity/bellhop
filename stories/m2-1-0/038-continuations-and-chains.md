# ST-038 — Continue jobs after their parent, and chain them

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-030, ST-037

## Context

Adds continuations and chains, which hosting REQ-36 puts in M2. An application adds a continuation to a parent with OnSuccess, OnFailure or OnCompletion (REQ-170); the parent's outcome enqueues or cancels it (REQ-171 to REQ-174), a continuation added to a parent that has already finished is resolved at once (REQ-175), and one added to a parent that does not exist is rejected (INV-138). A chain is a run of OnSuccess continuations created in one store transaction (REQ-176). An awaiting continuation is meant never to hang (LIV-102), except behind a parent that stays Unroutable or Failed, which the owner accepted.

Builds on ST-037 (M1 acceptance, so M1 is finished first) and ST-030 and, through them, the M1 job lifecycle: success (REQ-127, ST-008), dead-lettering (REQ-131, ST-011; REQ-133, ST-013; the timeout's REQ-186, ST-014), cancellation (REQ-134, REQ-136, REQ-190, ST-018), requeue and delete (REQ-141, REQ-143, REQ-144, ST-020), retention (REQ-145, ST-021), unique keys (REQ-150, REQ-152, ST-019) and the event hooks (REQ-169, ST-010). ST-007 declared ContinueWithAsync and ChainAsync on IJobClient (TECH-19); they get their behaviour here. ST-039 builds batches on this story and adds REQ-188, which cancels a continuation whose parent is deleted or removed; it sits there because it depends on REQ-192, so until ST-039 an OnSuccess continuation of a dead-lettered parent that is then deleted or removed is left awaiting. ST-043 runs continuations inline (INV-132), ST-048 keeps REQ-172 holding when it dead-letters a refused HTTP job (integrations REQ-434), ST-044 gives them their parent's correlation id (INV-127), ST-069 draws the parent and child graph (dashboard REQ-317) and ST-054 puts these rules in the conformance suite.

Lives in the Bellhop core package (abstractions, engine and in-memory store, TECH-112) and in Bellhop.PostgreSql (TECH-37). A job's parentId and continuation condition are new stored state, so the change is made on both stores that exist, as TECH-31 requires of every store. The entry points are IJobClient's ContinueWithAsync and ChainAsync (TECH-19); their signatures, their return values and the error that INV-138 raises are not in the specs (open question 3). The criteria build to jobs A-10: a continuation is resolved in the same store write as its parent's outcome.

## Acceptance criteria

### AC-1 · REQ-170 · must

> When an application adds a continuation to a parent job with the condition OnSuccess, OnFailure or OnCompletion, the system shall store the continuation as awaiting, with its parentId and condition.
>
> *Transition:* Job: (new) → Awaiting · *Actor:* Application

- Given a parent p that is scheduled, enqueued, processing, failed, awaiting or unroutable, when the application adds a continuation c to p with OnSuccess, OnFailure or OnCompletion, then c is stored as awaiting with parentId p and that condition, and no worker claims it while it awaits (REQ-123 claims only enqueued jobs).
- Given c is later released and runs, then its JobContext gives p as its parent id (TECH-16).
- Given p has already succeeded, been dead-lettered or been cancelled, then REQ-175 decides c's state instead of this rule.
- Given a parent id that does not exist, then the call is rejected and nothing is stored (INV-138).
- Given c carries a unique key that an active job holds, then REQ-150 and REQ-152 apply to the call as to any call that creates a job.

### AC-2 · REQ-171 · must

> While a continuation is awaiting, when its parent succeeds, if the condition is OnSuccess or OnCompletion, then the system shall enqueue the continuation.
>
> *Transition:* Job: Awaiting → Enqueued · *Actor:* system

- Given c is awaiting with OnSuccess or OnCompletion, when p succeeds (REQ-127), then c is enqueued in the same store write as p's success (jobs A-10), so no reader sees p succeeded while c still awaits.
- Given c is awaiting with OnFailure, when p succeeds, then c is not enqueued (REQ-174 cancels it).
- Given p fails an attempt and will retry (REQ-129), then c stays awaiting.
- Given c is no longer awaiting, because an operator cancelled it (REQ-134), when p succeeds, then c stays cancelled.
- Given c was enqueued by p's success, when p is requeued (REQ-143) and succeeds again, then c is not enqueued a second time.
- Given p's run has lost its lease, when that run returns, then c stays awaiting, because such a run cannot complete p (REQ-127's notes).

### AC-3 · REQ-172 · must

> While a continuation is awaiting, when its parent is dead-lettered, if the condition is OnFailure or OnCompletion, then the system shall enqueue the continuation.
>
> *Transition:* Job: Awaiting → Enqueued · *Actor:* system
>
> *Notes:* Decided by the owner on 2026-11-06 (reading confirmed): Failed (will retry) is not terminal, so OnFailure and OnCompletion fire on dead-lettering, not on each failed attempt.

- Given c is awaiting with OnFailure or OnCompletion, when p is dead-lettered by any path (REQ-131; REQ-133 at its last attempt; REQ-186, with reason Timeout), then c is enqueued in the store write that dead-letters p (jobs A-10).
- Given p fails an attempt and will retry (REQ-129), then c stays awaiting, however many attempts fail before the last (the owner's note: Failed is not terminal).
- Given c is awaiting with OnSuccess, when p is dead-lettered (REQ-131, REQ-133 or REQ-186), then c is neither enqueued nor cancelled and stays awaiting (REQ-174's notes; SCN-109).
- Given c was enqueued by p's dead-lettering, when p is requeued (REQ-141) and dead-lettered again, then c is not enqueued again.

### AC-4 · REQ-173 · must

> While a continuation is awaiting, when its parent is cancelled, the system shall cancel the continuation, whatever its condition.
>
> *Transition:* Job: Awaiting → Cancelled · *Actor:* system
>
> *Notes:* Decided by the owner on 2026-11-06: cancelling a parent cancels all its continuations, so 'completion' (REQ-171, REQ-172) means succeeded or dead-lettered, never cancelled. The cascade repeats down a chain.

- Given c is awaiting with any of the three conditions, when p is cancelled, whether while scheduled, enqueued, awaiting, failed or unroutable (REQ-134) or while processing (REQ-136, REQ-190), then c is cancelled in the same store write and is never enqueued (SCN-118).
- Given awaiting continuations below c, down a chain or a tree, then every one of them is cancelled in that same write (the owner's note; jobs A-10).
- Given a continuation of p that was already enqueued, when p is requeued (REQ-143) and then cancelled, then that continuation is unchanged.
- Given c was cancelled with p, when p is requeued (REQ-143), then c stays cancelled (REQ-143's notes).
- The reason recorded for this cancellation is open question 1.

### AC-5 · REQ-174 · must

> While a continuation is awaiting, when its parent succeeds, if the condition is OnFailure, then the system shall cancel the continuation with reason ConditionNotMet.
>
> *Transition:* Job: Awaiting → Cancelled · *Actor:* system
>
> *Notes:* Decided by the owner on 2026-11-06: a continuation whose condition does not match resolves to Cancelled; the reason tells it apart from an operator cancel. Resolved after refiner-model 2026-11-06 F-9 (recommended option 1): a continuation whose parent is dead-lettered and whose condition does not match stays awaiting, because the parent can still be requeued (REQ-141) and succeed, as batches already allow (REQ-179). It is cancelled when the parent is cancelled (REQ-173), deleted or removed by retention (REQ-188). Same event as REQ-171 with the complementary guard.

- Given c is awaiting with OnFailure, when p succeeds, then c is cancelled in the same store write as p's success, its state history records the reason ConditionNotMet (INV-116), and c's own awaiting continuations are cancelled with it (REQ-173).
- Given an operator cancels an awaiting continuation (REQ-134), then the reason recorded is not ConditionNotMet (the owner's note: the reason tells the two apart).
- Given c is awaiting with OnSuccess or OnCompletion, when p succeeds, then c is not cancelled (REQ-171 enqueues it).
- Given c is awaiting with OnSuccess, when p is dead-lettered (REQ-131, REQ-133 or REQ-186), then c stays awaiting; when p is then requeued (REQ-141) and succeeds, c is enqueued (REQ-171; SCN-121).

### AC-6 · REQ-175 · must

> When an application adds a continuation to a parent that has already succeeded, been dead-lettered or been cancelled, the system shall resolve the continuation as if the parent had just finished (REQ-171 to REQ-174), and store it as awaiting only when none of those rules applies.
>
> *Transition:* Job: (new) → Enqueued | Cancelled | Awaiting · *Actor:* Application
>
> *Notes:* Decided by the owner on 2026-11-06 (reading confirmed): without this, a continuation added after its parent finished would wait for an event that already happened and hang, violating LIV-102. refiner-model 2026-11-06 run 2 F-3 (recommended option): since run-1 F-9 a non-matching continuation of a dead-lettered parent stays awaiting (REQ-174), so one added after the parent was dead-lettered waits for a requeue too, exactly like one added before.

- Given p has succeeded, when the application adds c, then c is stored as enqueued for OnSuccess or OnCompletion, and as cancelled with reason ConditionNotMet for OnFailure.
- Given p has been dead-lettered, then c is stored as enqueued for OnFailure or OnCompletion, and as awaiting for OnSuccess; that awaiting c is enqueued once p is requeued (REQ-141) and succeeds.
- Given p has been cancelled, then c is stored as cancelled, whatever its condition.
- Given p has not finished, then c is stored as awaiting (REQ-170).
- Concurrency: when the add races p's success, dead-lettering or cancellation on another node, then afterwards c is never awaiting behind a parent that is succeeded or cancelled, nor behind a dead-lettered parent when its condition is OnFailure or OnCompletion (the model's Inv_AwaitingOnlyWhenNoRule).

### AC-7 · INV-138 · must

> If an application adds a continuation to a parent job id that does not exist, then the system shall reject the call with an error that names the parent id, and store nothing.
>
> *Notes:* Resolved after refiner-model 2026-11-06 F-11 (recommended option): a parent that was deleted or removed by retention falls between REQ-170, REQ-175 and REQ-188 and would leave the continuation awaiting for ever.

- Given an id that no job has ever had, when the application adds a continuation to it, then the call is rejected with an error that names that id, and no job is stored.
- Given a parent that was deleted (REQ-144) or removed by retention (REQ-145; SCN-123), then the same.
- Concurrency, on PostgreSQL with two nodes: adds race the parent's deletion and its removal by retention. Every call either is rejected with nothing stored, or returns with the continuation stored while its parent still existed; no call is rejected after storing anything. What then happens to a stored continuation whose parent goes is REQ-188 (ST-039).
- The error's type is open question 3.

### AC-8 · REQ-176 · must

> When an application creates a chain of jobs, the system shall store the first job as enqueued and each later job as an OnSuccess continuation of the one before it, all in one store transaction, so that either the whole chain exists or none of it does.
>
> *Notes:* Decided by the owner on 2026-11-06 (reading confirmed): OnSuccess, so a dead-lettered step cancels the rest of the chain (REQ-174) and a cancelled step cancels it too (REQ-173). Resolved after refiner-model 2026-11-06 F-9: a dead-lettered step now keeps the rest of the chain awaiting; requeuing the step and its success revives the chain (REQ-171). Cancelling, deleting or removing the step cancels the rest.

- Given a chain of jobs a, b and c, when the application creates it, then a is stored as enqueued, b as an awaiting OnSuccess continuation of a, and c as an awaiting OnSuccess continuation of b.
- Given one step is rejected, because its unique key is held and its policy is Error, then the call fails and no step is stored (REQ-152, whose notes say rejecting the call creates none of its jobs).
- Given the store write fails part way, by a fault injected after the first step is written or a PostgreSQL connection dropped before the commit, then no step is stored.
- Concurrency: while chains are created, workers on two nodes claim continuously; no first step is claimed before the later steps of its chain are stored, and no reader sees part of a chain.
- Given a step is dead-lettered, then the later steps stay awaiting, and requeuing that step (REQ-141) and its success revive the chain (SCN-121). Given a step is cancelled, then every later step is cancelled (REQ-173). Deleting or removing a step is REQ-188 (ST-039).
- What a chain does when one step is ignored as a duplicate is open question 2.

### AC-9 · LIV-102 · should

> While a continuation is awaiting, the system shall eventually enqueue or cancel it.
>
> *Notes:* Expected to fail as written when the parent stays Unroutable or Failed for ever, and for an OnBatchSucceeded continuation of a batch that stays Completed (REQ-181). Deleting a parent now cancels its continuations (REQ-188), and retention only removes finished parents, whose continuations were already resolved. These are the findings we want the model to report. Confirmed by the model 2026-11-06 (F-13) behind an Unroutable parent and a Completed batch, and accepted; an operator can cancel the continuation (REQ-134). Since F-9 a continuation also waits behind a dead-lettered parent until it is requeued, cancelled, deleted or removed, so LIV-102 is a should. refiner-model run 3: since REQ-192 and REQ-188 an OnBatchSucceeded continuation of a batch that stays Completed is cancelled when the batch is removed, and the model shows it holds; the acceptance now covers only a parent that stays Unroutable or Failed.

- Given an awaiting continuation whose parent succeeds, is dead-lettered or is cancelled, then by the time that outcome can be read the continuation is enqueued or cancelled (jobs A-10), unless it is an OnSuccess continuation of a dead-lettered parent.
- Given a parent that fails and retries, with a fake TimeProvider (TECH-12) advanced past each retryAt until the parent succeeds or is dead-lettered, then the continuation is resolved at that outcome as above.
- Given an OnSuccess continuation of a dead-lettered parent, then it is enqueued once the parent is requeued (REQ-141) and succeeds, cancelled once the requeued parent is cancelled (REQ-173), and cancellable by an operator at any time (REQ-134). Its cancellation when the parent is deleted or removed is REQ-188 (ST-039).
- Accepted by the owner (LIV-102's notes): given a parent that stays Unroutable (REQ-124), or stays Failed because its retry is never promoted while no node with a worker runs (hosting REQ-40), then the continuation keeps awaiting however far the fake clock is advanced, and an operator cancel (REQ-134) resolves it.
- Property: over random sequences of adds, chain creations, parent outcomes, cancels and requeues, after every step no continuation awaits a parent that is succeeded or cancelled, or a dead-lettered parent when its condition is OnFailure or OnCompletion.

### AC-10 · SCN-108 · scenario

> **OnFailure continuation runs after dead-letter**
>

> 2. REQ-170 — c added, awaiting
> 3. REQ-123 — p claimed
> 4. REQ-131 — p throws, dead-lettered

### AC-12 · SCN-118 · scenario

> **Cancelling a parent cancels its OnCompletion continuation**
>
> *Given:* Parent p is scheduled for tomorrow; continuation c is OnCompletion of p.
>
> 1. REQ-121 — p scheduled
> 2. REQ-170 — c added, awaiting
> 3. REQ-134 — app cancels p
> 4. REQ-173 — c cancelled
>

### AC-13 · SCN-121 · scenario

> **Requeuing a dead-lettered chain step revives the chain**
>
> *Given:* A chain import then report; import has maxAttempts = 1 and its handler throws once, then succeeds.
>
> 1. REQ-176 — chain created: import enqueued, report awaiting
> 2. REQ-123 — import claimed
> 3. REQ-131 — import throws and is dead-lettered; report stays awaiting
> 4. REQ-141 — operator requeues import
> 5. REQ-123 — import claimed again
> 6. REQ-127 — import succeeds
> 7. REQ-171 — report enqueued
>
> *Then:* report is Enqueued and the chain continues without the operator touching report.

> **A continuation of a missing parent is rejected**
>
> *Given:* Job j1 succeeded and was removed by retention.
>
> 1. REQ-170 — the app adds an OnSuccess continuation to j1's id
>
> *Impossible at step 1.*

## Tests

Every test carries one `Trait("Req", "<id>")` for each item it verifies.

- Unit, core engine over the in-memory store (TECH-43): REQ-170 to REQ-175 as a table of parent state against condition, with a row for each dead-letter path (REQ-131, REQ-133, and REQ-186's timeout with reason Timeout), INV-138 for an unknown, a deleted and a retention-removed parent, and REQ-176's shape for a three-step chain.
- Property, in-memory store with a fake TimeProvider: random sequences of adds, chains, parent outcomes, cancels, requeues, deletes and retention passes. After every step it asserts the LIV-102 and REQ-175 conditions above, that an OnSuccess continuation is released only by a parent that has succeeded (SCN-109), and that no continuation is enqueued twice (REQ-171, REQ-172).
- Concurrency, on PostgreSQL with two worker nodes: REQ-175 (an add racing the parent's outcome), INV-138 (an add racing delete and retention) and REQ-176 (creation with concurrent claimers and an injected failure before the commit).
- Scenario, on both stores: SCN-108, SCN-109, SCN-118, SCN-121 and SCN-123, one test each.
- Must keep holding, green on both stores: REQ-150 (a continuation or chain step whose unique key is held), REQ-169 (one event per enqueued or cancelled continuation, after the commit, on the node that made the parent's transition), REQ-134 (cancelling an awaiting continuation, which now cascades under REQ-173), REQ-145 (retention of finished parents), REQ-152 (a chain step rejected under the Error policy stores no step), REQ-143 (a requeued cancelled parent leaves its cancelled continuations cancelled, and a requeued succeeded parent does not release its continuations again) and TECH-19 (the methods are on IJobClient and nothing is static).
- Not automated: LIV-102 is an eventuality. The tests check it at bounded points, after each outcome and after the fake clock is advanced, and the Unroutable and Failed cases are checked as the owner accepted them: still awaiting, and cancellable.
