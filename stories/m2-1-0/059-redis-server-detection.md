# ST-059 — Detect the Redis server and disclose its durability

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-058

## Context

Makes the Redis store tell the operator what it is connected to. On every connection it identifies the server family and version with HELLO and INFO and probes EVAL with a trivial script (TECH-69, REQ-500, REQ-501), and it does so again after a lost connection or a role change (REQ-529). A starting node refuses a server without scripting or with an evicting maxmemory-policy (REQ-502, REQ-505, SCN-501). After each connection the store warns about weak persistence and asynchronous replication, and a running node logs an ERROR on an evicting server (REQ-503, REQ-504, REQ-531). The health check reports the persistence mode and memory use and turns Degraded near maxmemory (REQ-506, REQ-519, REQ-520).

Builds on ST-058 (a working Redis store), ST-057 (the connection, TECH-53), ST-006 (the startup sequence: REQ-502 and REQ-505 join the connect step of hosting REQ-12, and the family and version go into the startup summary of hosting REQ-19) and ST-015 (the health check, TECH-101, whose precedence rules hosting REQ-31, REQ-35 and REQ-58 this story's memory rule fits into). ST-060 builds on it and lists REQ-529, REQ-503 and REQ-504 under Must keep holding: REQ-529 also takes a reconciling store back to connecting, and REQ-503 and REQ-504 are not logged when reconciliation makes the store ready again (REQ-509). The Reconciling state comes from ST-060, so those criteria are tested by putting the store into it directly. ST-062 runs detection on every Tier 1 server and topology, and ST-082 adds the Tier 2 families.

Lives in the Bellhop.Redis package (TECH-70); the health information goes through AddBellhopHealthCheck() (TECH-101). Messages and logs follow NFR-41 (no connection string or password) and NFR-51 (stable event ids). The names and format of the health data and of the RedisMemoryDegradedShare option are not in the specs (open question 8).

## Acceptance criteria

### AC-1 · REQ-520 · must

> The system shall default RedisMemoryDegradedShare to 80% (RedisMemoryDegradedShare).
>
> *Notes:* Decided by the owner on 2026-11-06.

- Given RedisMemoryDegradedShare not configured and no check that reports Unhealthy failing, when the health check runs with used_memory just above 80% of maxmemory, then the node reports Degraded (REQ-519); at 80% or below, this rule does not.
- Given RedisMemoryDegradedShare configured, then the configured share applies in place of 80%.
- The option's name, and whether it is written as a fraction or a percentage, are open question 8.

### AC-2 · REQ-500 · must

> While the store is connecting, when the connection is established and a trivial EVAL script succeeds, the system shall identify the server family and version from HELLO and INFO, apply that family's adjustments if the family is recognised, mark the store ready and show the family and version in the startup summary.
>
> *Transition:* RedisStore: Connecting → Ready · *Actor:* system
>
> *Notes:* Valkey reports redis_version 7.2.4 in INFO, so detection must use HELLO (RDV-1). Families: Redis, Valkey, Garnet, Dragonfly, Kvrocks, KeyDB, Redict, unknown. refiner-model 2026-11-06 F-12 (recommended option): this runs on every connection, including a reconnection after REQ-529, so a failover re-checks the new primary; an unrecognised family gets no adjustments (REQ-501).

- Given Redis 7.2, when the store connects and the trivial EVAL succeeds, then the store is ready and the startup summary (hosting REQ-19) shows the family Redis and the server's version.
- Given Valkey 8.1, then the summary shows Valkey and its Valkey version, not the redis_version 7.2.4 that its INFO reports (the item's notes).
- Given a recognised family, then that family's adjustments are applied (what they are is open question 3); given an unrecognised family, none are (REQ-501).
- Given a reconnection (REQ-529), then detection runs again before the store is ready, and a new primary of another family or version is the one detected.
- Given the trivial EVAL fails, then the store is not marked ready: a starting node fails under REQ-502, and a running node is open question 2.
- Given a starting node, then it is not marked running before the store is ready (redis A-1, hosting REQ-18).
- The summary contains no connection string or password (NFR-41).

### AC-3 · REQ-501 · must

> While the store is connecting, when the connection is established and a trivial EVAL script succeeds, if the server family is not recognised, then the system shall log a warning that names what was detected and continue.
>
> *Transition:* RedisStore: Connecting → Ready · *Actor:* system
>
> *Notes:* Same event as REQ-500 with an extra consequence.

- Given a server whose HELLO and INFO name none of the families Redis, Valkey, Garnet, Dragonfly, Kvrocks, KeyDB and Redict (a test server that reports another name), when the connection is established and the trivial EVAL succeeds, then a warning names the server name and version that were detected, no family adjustments are applied, and the store becomes ready; the node starts if its other checks pass.
- Given a recognised family, then no such warning is logged.
- Given a reconnection to an unrecognised server (REQ-529), then the warning is logged again.

### AC-4 · REQ-502 · must

> While a node using the Redis store is starting, if the server does not support EVAL, then the system shall fail the host's start with a message that names the server flag that enables scripting, such as --lua on Garnet.
>
> *Transition:* hosting.Node: Starting → StartupFailed · *Actor:* system

- Given Garnet started without --lua (SCN-501), when a node using the Redis store starts, then the host's start fails, the node never reaches Running (hosting REQ-18), and the message names --lua.
- Given that failure, then no migration ran and no Bellhop key was written to the server, because the connection checks come first (hosting REQ-12), and neither the message nor the logs contain the connection string or a password (NFR-41).
- Given a server on which the trivial EVAL succeeds, then this check does not fail the start.
- Which EVAL failures count as a server that does not support EVAL, and which flag the message names on other servers, is open question 1.

### AC-5 · REQ-503 · must

> When the store becomes ready after a connection to the server, if INFO persistence shows that AOF is off, or the server persists by snapshot only, then the system shall log a warning that acknowledged jobs can be lost in a crash, naming the server's durability flag where one exists, such as --aof-commit-wait on Garnet.
>
> *Transition:* RedisStore: Ready → Ready · *Actor:* system
>
> *Notes:* If INFO persistence is not available on the server, the source says 'where available'; what to log then is open. refiner-model 2026-11-06 F-12 (recommended option): logged after every connection or reconnection (REQ-500, REQ-529), not when reconciliation makes the store ready again (REQ-509).

- Given a server with AOF off, whether it persists by snapshot only or not at all, when the store becomes ready after a connection, then a warning says that acknowledged jobs can be lost in a crash.
- Given Garnet with AOF off, then the warning names --aof-commit-wait.
- Given AOF on, then no such warning is logged.
- Given a reconnection (REQ-529), then the check runs again and logs again if it still applies; given the store becomes ready again through reconciliation (REQ-509, ST-060), then nothing is logged.
- What to log when INFO persistence is not available, and which flag the warning names on Redis and Valkey, are open question 4.

### AC-6 · REQ-504 · must

> When the store becomes ready after a connection to the server, if INFO replication shows replicas, then the system shall log a notice that replication is asynchronous and a failover can drop acknowledged writes.
>
> *Transition:* RedisStore: Ready → Ready · *Actor:* system
>
> *Notes:* refiner-model 2026-11-06 F-12 (recommended option): logged after every connection or reconnection (REQ-500, REQ-529), not when reconciliation makes the store ready again (REQ-509).

- Given a primary with at least one connected replica, when the store becomes ready after a connection, then a notice says that replication is asynchronous and that a failover can drop acknowledged writes.
- Given a server with no replicas, then no notice is logged.
- Given a reconnection (REQ-529), then the notice is logged again if replicas are still shown; given the store becomes ready again through reconciliation (REQ-509, ST-060), then it is not.
- The log level of a notice is open question 5.

### AC-7 · REQ-505 · must

> While a node using the Redis store is starting, if maxmemory-policy is anything other than noeviction, then the system shall fail the host's start with a message that eviction can silently delete job data without any reset being detected, naming the maxmemory-policy setting.
>
> *Transition:* hosting.Node: Starting → StartupFailed · *Actor:* system
>
> *Notes:* refiner-model 2026-11-06 F-2 option 1 (owner's decision on 2026-11-06: full protection): was a warning. Eviction removes keys one at a time and leaves the generation marker in place, so it can lose outcomes and recurring definitions with no reset ever detected. Cost: servers whose eviction policy cannot be changed are refused. A failover to a server with another policy is reported by REQ-531.

- Given maxmemory-policy allkeys-lru, and separately volatile-lru, when a node using the Redis store starts, then the host's start fails, the node never reaches Running (hosting REQ-18), and the message says that eviction can silently delete job data without any reset being detected and names maxmemory-policy.
- Given that failure, then no migration ran and no Bellhop key was written (hosting REQ-12), and the message contains no connection string or password (NFR-41).
- Given noeviction, then this check does not fail the start.
- Given a running node that reconnects to an evicting server, then the host is not stopped; REQ-531 applies instead.
- A server that does not report its policy is open question 6.

### AC-8 · REQ-519 · must

> When the health check runs, if no check that reports Unhealthy fails and the Redis server's used_memory is above RedisMemoryDegradedShare of its maxmemory, then the system shall report the node Degraded.
>
> *Transition:* hosting.Health: Healthy | Unhealthy → Degraded · *Actor:* system
>
> *Notes:* Decided by the owner on 2026-11-06: an eviction is a store reset in disguise, so warn early. refiner-model 2026-11-06 F-5 and F-6 (recommended option): Unhealthy takes precedence on the same run, and a node recovering from Unhealthy drops to Degraded.

- Given used_memory above RedisMemoryDegradedShare of maxmemory and no check that reports Unhealthy failing, when the health check runs, then the node reports Degraded, both from Healthy and from Unhealthy (a recovering node drops to Degraded: the item's notes and hosting REQ-58).
- Given the same memory use and a failing check that reports Unhealthy (the store unreachable, hosting REQ-31), then the node reports Unhealthy.
- Given used_memory at or below the share, then this rule reports nothing, and the node returns to Healthy only through hosting REQ-35.
- A server with no maxmemory set is open question 7.

### AC-9 · REQ-529 · must

> When the connection to the server is lost or the server's role changes, the system shall mark the store connecting and repeat server detection when it reconnects.
>
> *Transition:* RedisStore: Ready | Reconciling → Connecting · *Actor:* system
>
> *Rationale:* After a failover the new primary's family, persistence and eviction settings must be checked again (REQ-500 to REQ-504, REQ-531).
>
> *Notes:* refiner-model 2026-11-06 F-12 (recommended option). A node that was reconciling resumes through REQ-530 after reconnecting, because the marker is still flagged. Run 2 F-3/F-4: it rejoins even if it had already re-seeded for that value, and its wait in REQ-509 starts again from the reconnection.

- Given a ready store, when the test kills the store's connection or restarts the server, then the store is marked connecting and, on reconnection, runs detection again (HELLO, INFO and the trivial EVAL, TECH-69) before it is ready, and REQ-503, REQ-504 and REQ-531 are checked again.
- Given a role change (the primary demoted with REPLICAOF, or a Sentinel failover), then the same happens against the new primary, and the family, persistence and eviction settings reported are the new primary's.
- Given a reconciling store (put into that state directly; ST-060 produces it), when the connection is lost, then it is marked connecting too; its return through REQ-530 is ST-060's.
- A running node whose reconnection finds EVAL failing is open question 2.

### AC-10 · REQ-531 · must

> While the node is running, when the store becomes ready after a connection to the server, if maxmemory-policy is anything other than noeviction, then the system shall log an ERROR that the server may evict job data and that resets caused by eviction are not detected.
>
> *Transition:* RedisStore: Ready → Ready · *Actor:* system
>
> *Rationale:* REQ-505 refuses such a server at startup; a failover can still land a running node on one.
>
> *Notes:* refiner-model 2026-11-06 F-2 option 1 and F-12 (recommended option). Same event as REQ-503 and REQ-504.

- Given a running node, when its store becomes ready after a connection to a server whose maxmemory-policy is not noeviction (set by the test with CONFIG SET before a reconnection, or a failover to a replica configured that way), then an ERROR says that the server may evict job data and that resets caused by eviction are not detected, and the node keeps running.
- Given noeviction, then no such ERROR is logged.
- Given a starting node on such a server, then REQ-505 fails the start instead.
- Whether health should change as well is open question 9.

### AC-11 · REQ-506 · must

> The system shall include the persistence mode in the health check and report used_memory against maxmemory.
>
> *Notes:* used_memory reporting is SHOULD (RED-13); the persistence mode is MUST (RED-7). Decided by the owner on 2026-11-06: the check turns Degraded above 80% of maxmemory (REQ-519, REQ-520).

- Property, over random sequences of health-check runs, persistence changes (CONFIG SET appendonly), memory growth, reconnections and failovers (REQ-529): every health-check result taken while the server is reachable includes the persistence mode and used_memory against maxmemory, and the values are those of the server the store is connected to, read no earlier than its last connection.
- Given a failover to a server with other persistence settings, then the next result shows the new server's mode.
- The names and format of these values in the health result (TECH-101) are open question 8.
