# ST-043 — Run continuations, unique keys and concurrency keys inline

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-038, ST-042, ST-039

## Context

Extends ST-027's Inline execution mode (REQ-146) to the M2 features, so code that uses them behaves under test as it does in production: the continuations a job's outcome releases run inline before the enqueue call returns (INV-132), unique keys and concurrency keys apply as in the normal mode (INV-134), and a job whose concurrency key is held is stored and run on the holder's thread as soon as the holder finishes, rather than failed or blocked, so a handler that enqueues a job with its own key does not deadlock (INV-137).

Builds on ST-027 (the Inline mode with REQ-146, INV-131 and INV-133, and Bellhop.Testing, TECH-102), ST-038 (continuations and chains), ST-039 (batches, whose creation INV-137's notes cover), ST-042 (concurrency keys, INV-108) and ST-019 (unique keys, REQ-150 to REQ-152). INV-137's notes also cover recurring trigger-now (recurring REQ-226, ST-024). ST-054's conformance suite comes after it; nothing else builds on it.

Lives where ST-027 puts the Inline mode; the specs name neither the package nor the option that selects it, which is ST-027's question. Nothing here changes a store. "On the caller's thread" and "before the call returns" are checked the way ST-027 checks them for REQ-146.

## Acceptance criteria

### AC-1 · INV-132 · must

> Where the execution mode is Inline, when a job with continuations finishes, the system shall run the continuations that its outcome releases on the caller's thread before the enqueue call returns.
>
> *Notes:* Decided by the owner on 2026-11-06.

- Given Inline mode and a chain a, b, c (REQ-176), when the application creates it, then a, b and c have all run, in that order, when the call returns.
- Given a running inline job that adds an OnSuccess and an OnFailure continuation to itself (REQ-170), when it returns normally, then the OnSuccess continuation has run when the enqueue call returns, and the OnFailure one has not run (REQ-174 cancels it).
- Given the first step of an inline chain throws, then the later steps, which are OnSuccess continuations (REQ-176), have not run when the call returns.
- Exceptions, and continuations released by other calls, are open questions 1 and 2.

### AC-2 · INV-134 · must

> Where the execution mode is Inline, the system shall apply unique keys and concurrency keys as in the normal execution mode.
>
> *Notes:* Decided by the owner on 2026-11-06. A job whose concurrency key is held is deferred, not failed or blocked (INV-137).

- Given Inline mode and a scheduled job with unique key u (stored without running, INV-133), when the application enqueues another job with u under Ignore, then no job is created or run and the call returns the scheduled job's id with WasDuplicate set to true (REQ-150); under Error the call is rejected (REQ-152); a schedule call under ReplaceSchedule moves the scheduled job's time (REQ-151).
- Given a running inline job that holds u, when its handler enqueues a job with u, then the same rules apply, because a processing job is active for uniqueness (REQ-107).
- Given the job that held u has finished, then a new job with u is created and run.
- Given two test threads enqueue jobs with u at once, then one job is created and the other call gets it as a duplicate (INV-100).
- Given Inline mode and a concurrency key held by fewer than its Max, then a new job with the key runs at once on its own call (REQ-146); at its Max, the new job is deferred (INV-137) and never runs beside the holders.
- Differential: the same sequence of calls in Inline mode and in the normal mode (Bellhop.Testing's harness, TECH-102) gives the same WasDuplicate answers and creates the same jobs.
- Rate limits and the LongRunning limit are open question 4.

### AC-3 · INV-137 · must

> Where the execution mode is Inline, if a job is created while its concurrency key is held by Max running jobs, then the system shall store the job as enqueued and run it inline on the thread of a job holding the key as soon as that job finishes, before the call that started the holding job returns.
>
> *Notes:* Decided by the owner on 2026-11-06. Applies to every call that creates a job (EnqueueAsync, EnqueueManyAsync, ContinueWithAsync, ChainAsync, batch creation, recurring trigger-now). Failing would make code that works in production fail under test, and blocking deadlocks when a handler enqueues a job with its own key. Example: handler A (key tenant:7, Max 1) enqueues B with the same key; B is stored and runs right after A, before the outer EnqueueAsync(A) returns. When two test threads collide, the second thread's call returns before its job has run, and that job runs on the first thread.

- Given Inline mode and handler A, which holds tenant:7 with Max 1, when A enqueues B with tenant:7, then B is stored as enqueued, B's EnqueueAsync returns before B runs, and B runs after A finishes and before the outer EnqueueAsync(A) returns (the notes' example).
- Given two test threads, thread 1 running A with tenant:7, when thread 2 enqueues C with tenant:7, then thread 2's call returns before C has run, and C runs on thread 1 after A, before thread 1's call returns (the notes).
- Given the key is held by fewer than Max running jobs, then the new job is not deferred; REQ-146 runs it on its own call.
- Given each job-creating call that the notes list (EnqueueAsync, EnqueueManyAsync, ContinueWithAsync, ChainAsync, batch creation, recurring trigger-now), then a job it creates with a held key is deferred in the same way.
- Given a deferred job, then it is never failed, never retried for waiting, and no call blocks waiting for it; a test with a deadline fails on a deadlock.
- Given several jobs deferred behind one holder, then all of them have run before the holder's call returns. Their order, and the fate of a deferred job's exception, are open question 3.

## Open questions

1. **Decide in delivery** · INV-132, REQ-146, INV-131: which exception does the caller see when an inline job or a continuation it releases throws, and do the released continuations run before the job's exception is rethrown? INV-131 says a throwing job is not retried but not which state it ends in, so whether its OnFailure and OnCompletion continuations run inline (REQ-172 needs dead-lettered) needs the same answer.
2. **Decide in delivery** · INV-132, REQ-175, REQ-181: does a continuation released by a call other than the parent's own run, such as ContinueWithAsync on a finished parent (REQ-175) or a batch-level continuation released when a batch succeeds or completes (REQ-181), run inline before that call returns? INV-132 speaks only of a job with continuations finishing and of "the enqueue call".
3. **Decide in delivery** · INV-137, REQ-146: when a deferred job throws on the holder's thread, where does its exception go, now that the call that created it has returned? And in which order do several jobs deferred behind one holder run?
4. **Decide in delivery** · INV-134: do rate limits (INV-109) and the LongRunning limit (INV-112) apply in Inline mode? INV-134 names unique keys and concurrency keys only.
