# ST-053 — Ship Roslyn analyzers for job names, handlers, payloads and cron literals

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-003, ST-012, ST-037

## Context

Ships five Roslyn analyzers in the core package, so that mistakes the runtime would find only later show up at build time: a job type without an explicit [JobName], whose rename would orphan its stored jobs (TECH-107, REQ-101); a job type with no handler (TECH-108), whose jobs would wait until they are marked unroutable (REQ-124); a handler whose job type is not registered (TECH-109); a payload type that System.Text.Json cannot serialize (TECH-110, TECH-5); and an invalid cron literal in [Recurring] (TECH-111), which would fail the start (REQ-210).

Builds on ST-002 (what the analyzers inspect: IJob and IJobHandler<TJob>, TECH-14; [JobName], TECH-18; [Recurring], TECH-17; the registration API, TECH-22), ST-003 (the schedule syntax, and the parser that decides whether a cron literal is valid, TECH-23) ST-012 (the handler names that nodes declare, REQ-124) and ST-037 (M1 accepted, so milestones are built in order). ST-076 builds on it: TECH-112 lists the analyzers among the core package's contents. The tool infers M1 for TECH-108 to TECH-111 from what they apply to, but hosting REQ-36 puts analyzers in M2, where TECH-107's own source also places it.

Lives in the Bellhop core package (TECH-107 to TECH-111, TECH-112), whose dependencies stay the BCL and Microsoft.Extensions.* abstractions (TECH-8): the analyzers travel inside the package and add no package dependency to it. Diagnostic ids, messages and severities are not in the specs (open question 1).

## Acceptance criteria

### AC-1 · TECH-107 · must

> **Analyzer: missing job name** — The core package shall ship a Roslyn analyzer that warns when a job type has no explicit [JobName].

- Test, compiling source with the analyzer: a type implementing IJob or IJob<TResult> (TECH-14) without [JobName] gets a warning at its declaration; the same type with [JobName("…")] gets none, and a type that implements neither gets none.
- Package check: a project that references only the packed Bellhop package and declares such a job type gets the warning when it builds.
- Passing: both hold, and the diagnostic has warning severity, as "warns" says.

### AC-2 · TECH-108 · should

> **Analyzer: job without handler** — The core package shall ship a Roslyn analyzer that flags a job type with no handler.

- Test: in a single-project application, a job type for which a class implements IJobHandler<TJob> (TECH-14) gets no diagnostic, and a job type with no such class in the project or its references is flagged at its declaration.
- Package check as for TECH-107.
- Passing: both hold. Solutions with several projects are open question 2.

### AC-3 · TECH-109 · should

> **Analyzer: handler without job** — The core package shall ship a Roslyn analyzer that flags a handler whose job type is not registered.

- Test: in a single-project application, a handler whose job type AddBellhop registers, through AddJob<TJob, THandler>() or through AddJobsFromAssemblyContaining<T>() over the handler's assembly (TECH-22), gets no diagnostic; a handler whose job type no registration in the project adds is flagged.
- Package check as for TECH-107.
- Passing: both hold. Registrations made in other projects are open question 2.

### AC-4 · TECH-110 · should

> **Analyzer: unserializable payload** — The core package shall ship a Roslyn analyzer that flags payload types that System.Text.Json cannot serialize.

- Test with an oracle: for a corpus of payload types, a type is flagged when serializing an instance with the default payload serializer, System.Text.Json without type names (TECH-5), throws, and a type that serializes and deserializes back to an equal value is not flagged.
- Passing: no type that round-trips is flagged, and every corpus type that fails to serialize is flagged. The corpus covers each kind of type the analyzer claims to detect; the list is recorded in Notes.
- Which types count, and under which serializer options, is open question 3.

### AC-5 · TECH-111 · should

> **Analyzer: invalid cron literal** — The core package shall ship a Roslyn analyzer that flags invalid cron literals in [Recurring].

- Property, against ST-003's schedule parser: for random strings and mutations of valid 5- and 6-field cron expressions (TECH-23) placed in [Recurring], the analyzer flags a literal exactly when the parser rejects it. A literal the build accepts therefore never fails the start under REQ-210, and a flagged one always would.
- Passing: the verdicts agree on every generated literal and on a fixed list of valid and invalid examples kept with the tests.

## Open questions

1. **Decide in delivery** · TECH-107, TECH-108, TECH-109, TECH-110, TECH-111: the diagnostic ids, titles and messages, and the default severity of TECH-108 to TECH-111, which "flag" where TECH-107 "warns". Ids and severities are public contracts (NFR-20): applications suppress and configure diagnostics by id.
2. **Decide in delivery** · TECH-108, TECH-109: what do "no handler" and "not registered" mean in a solution with several projects? An analyzer sees one compilation, while a handler can live in another assembly and AddJobsFromAssemblyContaining works across several (TECH-22), so a job type in a shared contracts project would be flagged although another project handles it. The criteria cover a single-project application only.
3. **Decide in delivery** · TECH-110: does "cannot serialize" also take in types that serialize but cannot be deserialized (no usable constructor)? Is it judged with the default options or with the application's JsonSerializerOptions or JsonSerializerContext (TECH-6)? Does the analyzer stay on when IJobSerializer replaces System.Text.Json (TECH-7)? Converters registered at run time are invisible to it.
