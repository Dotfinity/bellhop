# ST-054 — Publish the store conformance suite

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-039, ST-040, ST-041, ST-043, ST-045, ST-046, ST-047, ST-052

## Context

Publishes Bellhop.Storage.Conformance, an xUnit suite that store authors run to prove their store correct, with concurrency tests for claims, uniqueness and recurring triggers and tests for IJobIndex and typed parameters (TECH-105). The same suite proves rolling-deploy compatibility by passing with nodes on library versions N and N+1 against schema N (NFR-18), and the project runs concurrency and chaos tests in CI: nodes killed mid-job, clock skew and duplicate starts (NFR-57).

Builds on the M2 stories that change the store, so that the suite covers them: ST-039, ST-040, ST-041, ST-043, ST-045, ST-046, ST-047 and ST-052, and on the store-level tests that ST-029 and ST-030 ran against PostgreSQL. SQL Server (ST-055), SQLite (ST-056) and Redis (ST-057, ST-058) are built against it; ST-084 runs it on every Redis server (NFR-58), and ST-089 lists a community store only once it passes (NFR-59). The tool infers M1 for TECH-105 and NFR-57, but hosting REQ-36 puts the conformance suite in M2, and NFR-57 applies to the suite (TECH-105); ST-037 already ran the same deliberate failures by hand for M1. The owner split the nightly multi-node soak out of NFR-57 on 2026-11-06 (NFR-61, ST-088, M3).

Lives in the Bellhop.Storage.Conformance package (TECH-105), which references xUnit. In this repository it runs in CI against every store that exists at this point: the in-memory store (TECH-43) and PostgreSQL (TECH-37). NFR-18's run needs a published version N beside the current build, with AutoMigrate off on the N+1 nodes so that the schema stays at N (hosting REQ-22, REQ-23). How a store author plugs a store into the suite is not in the specs (open question 1).

## Acceptance criteria

### AC-1 · TECH-105 · must

> **Store conformance suite** — The Bellhop.Storage.Conformance package shall use xUnit to give store authors a test suite that proves correctness, including concurrency tests for claims, uniqueness and recurring triggers, and tests for IJobIndex and typed parameters.

- Check: the Bellhop.Storage.Conformance package references xUnit and contains tests for concurrent claims (never two unexpired claims on one job, INV-103), concurrent enqueues with one unique key (INV-100), recurring triggers on several nodes at once (one occurrence per due instant, SCN-200, through the compare-and-set of INV-212 and TECH-45), IJobIndex's AddAsync, RemoveAsync, paged QueryAsync and CountAsync (TECH-32), and typed parameters set and read back with the job (TECH-30).
- Given each method of IJobStore and the semantics its documentation states (TECH-31), then at least one test of the suite exercises it.
- Given the in-memory and PostgreSQL stores, when CI runs the suite against each, consuming it as a package rather than from source, then every test passes.
- Mutation: for each of the five areas above, a store deliberately broken in that area (a claim without its atomic guard, a unique check made by reading first, a trigger without the compare-and-set, an index that loses entries, parameters that are not persisted) fails at least one test of the suite.
- Passing: all four hold.

### AC-2 · NFR-18 · must

> **Rolling-deploy schema compatibility** — The system shall let library versions N and N+1 both read and write schema version N, so that nodes on two adjacent versions can run side by side.
>
> *Measure:* conformance suite passes with mixed N / N+1 nodes on schema N · *Verification:* test

- Measurement, on PostgreSQL: a store at schema version N, created by library version N; nodes on N and on N+1 run side by side against it, the N+1 nodes with AutoMigrate off, since hosting REQ-23 accepts a schema one version older. Each version enqueues jobs that the other claims and completes.
- Passing: the conformance suite passes with mixed N and N+1 nodes, and the stored schema version is still N afterwards.
- Which versions N and N+1 are is open question 2.

### AC-3 · NFR-57 · should

> **Concurrency and soak testing** — The project shall run concurrency and chaos tests (nodes killed mid-job, clock skew, duplicate starts) in CI.
>
> *Measure:* suites present and green on main · *Verification:* inspection
>
> *Notes:* Decided by the owner on 2026-11-06: the nightly soak test that the source lists here is split out to NFR-61 and deferred.

- Inspection: the CI workflow that runs on main runs TECH-105's concurrency tests and chaos tests that kill a node mid-job, skew a node's clock against the database clock and make duplicate starts, and its latest runs on main are green. The reviewer records the workflow file and the run in Notes.
- What the chaos tests check, from the items they exercise: a job whose node was killed mid-job returns to enqueued with reason Interrupted and runs again, or is dead-lettered at maxAttempts (REQ-132, REQ-133), within the at-least-once window (hosting REQ-10); on a skewed node, claims, lease expiry and due times still follow the database clock (INV-105) and the node logs the skew (hosting REQ-26); with duplicate starts, no job has two unexpired claims (INV-103) and migrations are serialised (hosting REQ-42).
- Which duplicate starts are meant, and how large the skew is, are open question 3.

## Tests

Every test carries one `Trait("Req", "<id>")` for each item it verifies; a test of the suite carries TECH-105 and the ids of the behaviour it checks (INV-103, INV-100, INV-212, TECH-32, TECH-30 and so on).

- Conformance: the suite against the in-memory and PostgreSQL stores (TECH-105). It is where TECH-31, TECH-32 and TECH-45, which this story must keep holding, are checked for every store.
- Mutation: the broken-store variants (TECH-105).
- Mixed versions: NFR-18 on PostgreSQL.
- Chaos, in CI on PostgreSQL: NFR-57 (a killed node, clock skew, duplicate starts).
- Inspection, recorded in Notes: NFR-57's workflow and its green runs on main.
- Not automated: NFR-57's verification is the inspection above; nothing else.

## Out of scope

- SQL Server, SQLite and Redis passing the suite: ST-055, ST-056, ST-057 and ST-058; every Redis server and topology: ST-084 (NFR-58).
- The nightly multi-node soak: NFR-61 (ST-088).
- Listing community stores: ST-089 (NFR-59). First-party MongoDB or MySQL stores are not shipped in v1 (hosting REQ-8).
- Exactly-once execution: not offered (hosting REQ-7); the chaos tests accept a second start within the duplicate window (hosting REQ-10).
- Jobs written by version N processed by N+1 in the upgrade test: NFR-19 (ST-076).
- The Testcontainers sample: TECH-106 (ST-073).

## Open questions

1. **Decide in delivery** · TECH-105: the suite's public shape: how a store author plugs a store in (a base class, a fixture or a factory), which xUnit major version it targets (an author's test project must match it), and whether NFR-57's chaos tests ship in the package or stay in this repository's CI. It becomes a public contract that NFR-20 freezes.
2. **Decide in delivery** · NFR-18: which versions are N and N+1 when the suite first runs, before 1.0 is published? M1 is a preview (hosting REQ-36) and TECH-127's additive rule holds within one major version, so the M1 preview beside a 1.0 build may not be what is meant.
3. **Decide in delivery** · NFR-57: do "duplicate starts" mean two nodes starting at once against one store (hosting REQ-42) or one job started twice (hosting REQ-10)? How large a clock skew must the tests use, against ClockSkewThreshold (hosting REQ-26)?
