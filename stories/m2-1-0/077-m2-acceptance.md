# ST-077 — Accept M2: run 1.0 end to end on every store

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** – · **Depends on:** ST-076 · **Kind:** acceptance

## Context

Accepts M2, Bellhop 1.0 as REQ-36 lists it (SQL Server, SQLite and Redis stores, continuations, chains and batches, unique and concurrency keys, the full dashboard, BLT-1 to BLT-12, EF Core enqueue, analyzers, conformance suite, docs, benchmark), by running it end to end on real infrastructure on every store, in-memory, PostgreSQL, SQL Server, SQLite and Redis, with deliberate failures, and recording what happened. It owns no item. It records the full-dashboard demonstrations of NFR-48 (themes) and NFR-49 (responsive layout), which ST-032 owns and ST-037 recorded for the M1 dashboard, and the manual keyboard pass that NFR-50's measure asks for before each release.

Builds on ST-076, the 1.0 release, and through it on every M2 story; ST-037 did the same for M1 on PostgreSQL. ST-085 (Native AOT), ST-088 (soak tests) and ST-089 (community stores) build on it. A finding where the specs are wrong or silent goes to refiner-requirements first; a finding where the build is wrong becomes a new story with the next free number, and the steps it touched are run again once that story is done.

No package code. The run uses the 1.0 packages from ST-076 in hosts built from ST-073's web app and worker service samples (NFR-27), with the stores on real servers: PostgreSQL (TECH-37), SQL Server (TECH-40), SQLite (TECH-42) on one node, since two nodes on one file are unsupported (TECH-42's notes), and Redis on Tier 1 servers (TECH-71, TECH-73; which ones is open question 1). The record goes into this story's Notes.

## Tests

Every test carries one `Trait("Req", "<id>")` for each item it verifies. The run is mostly a recorded walk-through; any script written for it that asserts an outcome carries the tags of the items whose behaviour it checks.

- **Set-up, per store.** Start from the §3 Program.cs (NFR-1) with that store. Run two or more worker nodes, a dashboard node and an alerts node (TECH-129) on every store except SQLite and the in-memory store, which run one node.
- **Happy path, per store.** Fire-and-forget, delayed and recurring jobs; continuations and chains (ST-038), batches (ST-039), bulk enqueue and results (ST-040); unique keys (SCN-105), concurrency keys (SCN-106) and throttling (ST-042); tags and correlation ids (ST-044), captured logs and progress (ST-045), namespaces (ST-046); configuration-defined recurring jobs and validity windows (ST-047); HTTP jobs (ST-048); alerts through each channel (ST-049 to ST-052); every dashboard page, with roles, API keys, basic authentication and launches (ST-065 to ST-072); the analyzers in a sample project (ST-053); and the conformance suite green against that store (ST-054). On the SQL stores a rolled-back transactional enqueue never runs (SCN-113); on Redis and in-memory a transaction is rejected (jobs REQ-153).
- **Deliberate failures, each with the behaviour expected:**
  - kill a worker node mid-job: another node recovers it once its lease expires (SCN-102), and the killed run cannot complete it afterwards (SCN-117);
  - start a node while the store is unreachable: the host stays up and Unhealthy and claims nothing until the store returns (SCN-6, hosting REQ-25, REQ-31);
  - start two nodes at the same instant: one recurring definition (SCN-207) and one occurrence per due instant (SCN-200);
  - skew one node's clock: claims, leases and due times follow the store's clock (jobs INV-105; on Redis, TECH-59), so nothing runs early and no lease ends early;
  - stop a node gracefully under load: its unfinished jobs go to another node (SCN-115);
  - on Redis: FLUSHALL under load is detected and recurring jobs come back (SCN-500), claims pause (redis REQ-526), a unique-key duplicate created during the pause is cancelled (SCN-508), and an operator acknowledges the reset on the dashboard (redis REQ-525); a restore from an older snapshot is detected (SCN-505); a new empty server is initialised, not reported (SCN-503); a server whose maxmemory-policy is not noeviction is refused at start (redis REQ-505);
  - on the dashboard: a production dashboard without authorization refuses to start (SCN-300), a basic-auth lockout does not block API keys (SCN-310), an expired key is rejected (SCN-307) and a viewer cannot launch (SCN-303);
  - stop the last worker: the node-lost alert fires (SCN-404); move the notification lease mid-run: no alert is repeated or lost (SCN-406);
  - an HTTP job to a host off the allowlist is refused (SCN-401); an oversized payload is rejected (SCN-116), at 256 KB on Redis (redis REQ-513).
- **Demonstrations.** NFR-48: dark, light and system themes on every page. NFR-49: every page and action at 360, 768, 1024 and 1440 px. NFR-50: the manual keyboard pass over every page and action.
- **Recorded in Notes**, per store and per step: the Bellhop, server and OS versions; what was done; the item whose behaviour was expected; what was observed (logs with their EventIds, NFR-51; health; the dashboard); and pass, or the finding and where it went (refiner-requirements, or the new story's id). For the demonstrations, per page: each theme, each width and the keyboard pass.
- Not automated: the run itself, apart from the scripted failure injections. A second run of a job within the lease window is the at-least-once window (hosting REQ-10, recurring REQ-238), not a finding.
