# ST-061 — Keep runs, unique keys and the reset record consistent across a Redis reset

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-060, ST-034

## Context

Keeps what a Redis reset erased from turning into wrong behaviour once claims resume. A run whose job record vanished re-creates it at its next heartbeat or progress write, with its lease and holds, so no second job is admitted beside it (REQ-522, SCN-504, SCN-507, SCN-509, SCN-510); a job that took the run's unique key during the pause is cancelled with reason DuplicateAfterReset in the same write (REQ-534, SCN-508); and a run that finishes without a record still leaves its outcome (REQ-521). The reset itself is recorded in the store as unacknowledged by the script that replaced the marker, re-written by a node that remembers it if a later loss erases it, and keeps every node Degraded until an operator acknowledges it on the dashboard (REQ-523, REQ-532, REQ-524, REQ-525, SCN-500).

Builds on ST-060 (the generation marker, REQ-507's replacement inside the claim, heartbeat and completion scripts, the pause of REQ-526 and REQ-509's wait, which exists so these re-creations land before claims resume) and ST-034 (dashboard operate actions; acknowledging a store reset is one, dashboard INV-301 from ST-031). It also relies on ST-015 (health), ST-019 (unique keys, jobs INV-100, which it must keep holding), ST-042 (concurrency keys), ST-024 (recurring overlap) and ST-045 (progress writes, jobs REQ-166). It owns TECH-130: ST-060 built the claim and trigger refusals, the marker writes and what each script returns for REQ-507, REQ-526, REQ-528 and REQ-530; this story adds the heartbeat's re-creation, the unique-key cancel and REQ-523's record, and verifies TECH-130 as a whole. ST-062 and ST-064 build on it, ST-073 documents its windows (NFR-31), and ST-077 runs a Redis flush end to end with an operator acknowledging it.

Lives in Bellhop.Redis (TECH-70): the heartbeat, progress and completion scripts, and REQ-507's replacement script from ST-060, which now also writes the record (TECH-130). The tool infers M1 for TECH-130 (the first milestone of what it applies to), but it applies only to the Redis store, which hosting REQ-36 puts in M2 (TECH-70's notes, the owner's decision of 2026-11-06). TECH-130's open question, the hash slot of REQ-523's record under ShardByQueue, does not touch this story, which builds the default tagging with one hash tag per namespace (TECH-58); it is raised here as Decide in delivery (open question 6) and blocks ST-064. The acknowledgement lives in Bellhop.Dashboard (TECH-88) and its JSON API (TECH-92); which page shows a reset and the API's shape are not in the specs (open question 2).

### Modeling assumptions

Decisions the model took where the sentences were silent. Build to them, or raise an open question.

- redis A-28 (affects REQ-526, REQ-522, REQ-521, REQ-523): A script's read and the node's response to it (REQ-507/528/530) are ordered response-first: the claim, heartbeat or completion takes effect only once no sentence applies. When the reply arrives, the script's REQ-507/528 write and the node's response are one step. With `LostReply`, the write can happen without the response (A-32)
- redis A-31 (affects REQ-523, REQ-530): REQ-523's trigger, "this node replaces the generation marker under REQ-507", is `DetectReset` (and its store side in `ReplyLost`). `InitMarker` (REQ-528) and `Learn` (REQ-530) record nothing
- redis A-32 (affects REQ-523, REQ-532, probes): `LostReply`: a connection drop (REQ-529) can come between the server running the script that makes REQ-507's write and the node receiving its reply. The write stands, unacknowledged record included (REQ-523, TECH-130). The node learns nothing: it logs neither ERROR, remembers nothing, its store is connecting and its last-seen value is unchanged. This is an environment event, not fair, at most `MaxDrops` per run, and it is on only in `Redis_*ReplyLost*.cfg`, `Redis_SCN500LostReply.cfg` and the probes (not P2b, P5b). A client-side timeout has the same effect but is not modeled
- redis A-34 (affects REQ-523, REQ-525, REQ-532, `Inv_RecordUntilAck`, `Liv_RecordRestored`): The store holds one reset record (`resetRec`: none, unacknowledged or acknowledged), not one per reset. A later detection overwrites it, and REQ-532's "record of that reset" is that record. An acknowledgement covers every reset recorded before it (`owed` ends). With one record per reset, a detected later loss writes its own record rather than restoring the lost-reply one, and in P1 REQ-532 re-writes the earlier reset's record. Health and acknowledgement are the same either way
- redis A-37 (affects REQ-531, REQ-523, REQ-532, P5): *(new, probe only)* `Redis.tla`'s eviction (`EvictJob`) removes job records only, never the marker or the reset record. P5 adds `EvictRecord` in `RedisProbe10` (`Spec10`): on an evicting server, the record's key is removed, which is not a pending (detectable) loss (REQ-531). Eviction of the marker key is not added: the next read finds it missing, which REQ-507 reports
- redis A-35 (affects REQ-532, P1): `RewriteRecord` (REQ-532) requires the node to be running and the server reachable, but not the node's own connection, so it can fire while that node is reconnecting. That makes a re-write earlier, never adds or removes one. No result above depends on it. Tighten the guard (`rs[n] # "Connecting"`) the next time the model changes

## Acceptance criteria

### AC-1 · REQ-524 · must

> When the health check runs, if no check that reports Unhealthy fails and a store reset has not been acknowledged, then the system shall report the node Degraded.
>
> *Transition:* hosting.Health: Healthy | Unhealthy → Degraded · *Actor:* system
>
> *Notes:* Decided by the owner on 2026-11-06. Lasts beyond reconciliation (REQ-508), until an operator acknowledges the reset (REQ-525). refiner-model 2026-11-06 F-5 and F-6 (recommended option): Unhealthy takes precedence on the same run, and a node recovering from Unhealthy drops to Degraded.

- Given an unacknowledged reset recorded in the store (REQ-523), when the health check runs on any node that uses the store and no check that reports Unhealthy fails, then the node reports Degraded, including after the reconciliation has ended and REQ-508 no longer applies.
- If a check that reports Unhealthy fails on the same run (the store unreachable, hosting REQ-31), then the node reports Unhealthy; when the store is back and the reset is still unacknowledged, the next run reports Degraded (hosting REQ-58).
- Given the reset is acknowledged (REQ-525) and no other check fails, then the node returns to Healthy after HealthyAfterPasses runs (hosting REQ-35).
- Given the detecting script's reply was lost, so no node logged StoreWasReset or REQ-523's ERROR and no node remembers the reset, then the record alone keeps every node Degraded until it is acknowledged (REQ-523's notes).
- Given a new server initialised under REQ-528, then no reset is recorded and this rule does not hold the node Degraded after the reconciliation (SCN-503).

### AC-2 · REQ-534 · must

> When a run's job record is re-created after a store reset (REQ-522) with a unique key that another active job holds, the system shall cancel that other job with reason DuplicateAfterReset in the same write that re-creates the record.
>
> *Transition:* jobs.Job: Scheduled | Enqueued | Awaiting | Unroutable → Cancelled · *Actor:* system
>
> *Rationale:* A flush erases a running job's unique-key lock, so an enqueue with the same key succeeds before the run's next heartbeat re-creates its record, leaving two active jobs with one key (jobs INV-100).
>
> *Notes:* refiner-model 2026-11-06 run 2 F-2, chosen instead of the recommended hold on unique-key enqueues. Holding would make every enqueue with a unique key block for up to a lease and then fail during a reset, and on a new server with no worker running yet, where nothing can collide. Before the flush the key belonged to the running job, so the other holder was created during the pause, and claims are paused (REQ-526), so it has never run. Cancelling it gives the state the store would have had without the flush; the caller was told the job was enqueued, and its cancel reason says why.

- Given j1 processing on n1 with unique key invoice:7, a FLUSHALL, and j2 enqueued with invoice:7 during the pause and accepted (REQ-526's notes), when j1's heartbeat re-creates j1's record (REQ-522), then the same script cancels j2 with reason DuplicateAfterReset and j1 holds invoice:7 (SCN-508).
- Then j2 goes to Cancelled from whichever of Scheduled, Enqueued, Awaiting or Unroutable it was in, it was never claimed (REQ-526), and the job shows the reason DuplicateAfterReset to whoever enqueued it.
- Property: every read made while heartbeats run finds either j1's record missing and j2 holding invoice:7, or j1 Processing with invoice:7 and j2 Cancelled; never two active jobs holding invoice:7 (jobs INV-100).
- If no other active job holds the run's unique key, then nothing is cancelled. If the other job with that key is already terminal, then it is not active and is left as it is.
- If the run's record is not re-created (its lease expired or the reconciliation is over, REQ-522), then nothing is cancelled and the other job keeps the key.

### AC-3 · REQ-521 · must

> When a run completes or fails, its job's record no longer exists and the store was reset since the claim, the system shall write a minimal job record with the job's id, name, outcome and node, marked as recreated after a store reset, and log a warning.
>
> *Notes:* Decided by the owner on 2026-11-06 so the outcome is not lost from history. This is not a stale token in the sense of jobs INV-128: there is no current record to protect. A record missing for any other reason is still refused. refiner-model 2026-11-06 F-2 option 1 (owner's decision: full protection): 'the store was reset since the claim' is defined in the glossary (resetSinceClaim) and now also covers a marker older than at the claim and a reset detected in between, so a second flush or a rollback no longer loses the outcome. Runs that heartbeat before completing have already re-created their record (REQ-522). Run 2 F-3: the marker's last-reset value (REQ-507) also covers a run on a node that missed the whole reconciliation, for example behind an outage, so its outcome is recorded rather than lost. Run 3 F-3: REQ-528's first marker has a last-reset value too, so this also covers a run that missed a reconciliation a late node started. Run 4 F-2 (recommended option): the glossary compares the marker's last-reset value with the last-reset value read at the claim, not with the marker value. REQ-528's first marker has a value (the lowest) older than its last-reset time, so the old comparison counted every job claimed under it as reset since the claim, and a deleted job could come back here with a reset logged that never happened.

- Attack: a property test over random sequences of claims, FLUSHALLs, rollbacks written directly, detections and joins (REQ-507, REQ-528, REQ-530), heartbeats, operator deletes, and completions and failures. Observed: when a run completes or fails and its record is missing, a minimal record with the job's id, name, outcome and node, marked as recreated after a store reset, is written and a warning logged exactly when the store was reset since the claim (glossary resetSinceClaim); otherwise the write is refused as under jobs INV-128 and nothing is written.
- Each case of resetSinceClaim gives the minimal record on its own: the marker missing; flagged; older than the value read at the claim; its last-reset value later than the one read at the claim (kept by the claim, TECH-130); this node detected or learned of a reset since the claim.
- Given a job claimed under REQ-528's first marker and then deleted by an operator, when its run completes, then nothing is written and the completion is refused: the last-reset value is the one read at the claim (REQ-521's notes).
- Given a run on a node that missed a whole reconciliation behind an outage, when it completes after the flag was cleared, then its outcome is recorded, because the last-reset value moved.
- Given a run whose lease expired during the reconciliation without re-asserting (SCN-510), when it completes, then its outcome is recorded (REQ-522's notes).
- Given a run whose heartbeat re-created its record (REQ-522), then it completes as usual and no minimal record is written.
- What the minimal record shows and what happens to it afterwards is open question 1.

### AC-4 · REQ-522 · must

> While the generation marker is missing or flagged as reconciling, if a heartbeat or progress write finds its job's record missing, the store was reset since the claim, and the run's leaseExpiresAt has not passed according to the database clock, then the system shall re-create the job's record as processing with the run's claiming node, leaseToken, leaseExpiresAt, queue, concurrency key, unique key and recurring occurrence, so that queue limits, concurrency keys, unique keys and recurring overlap count the run again, and let the run continue.
>
> *Notes:* Decided by the owner on 2026-11-06 that the run continues; the result is recorded at completion (REQ-521). refiner-model 2026-11-06 F-1 option 1 (owner's decision: full protection): the heartbeat re-creates the record instead of being ignored, so a second job with the same concurrency key, queue limit or recurring job is not admitted beside the old run (jobs INV-107, INV-108, recurring INV-204). Claims stay paused until every live run has had one heartbeat (REQ-509, REQ-526). Run 2: F-2, the unique key is re-created too, and a job that took it during the pause is cancelled (REQ-534). F-3, the record is re-created only while the reconciliation lasts. After it, a run that never re-asserted is treated like any run whose lease expired: its heartbeat re-creates nothing, so it never becomes a second holder beside a job claimed after the pause, and its outcome is still recorded when it finishes (REQ-521). Run 3 F-2 (recommended option): the run's own lease decides, not only the marker's state. A run whose lease expired during one reconciliation was excluded only because the flag was no longer set; a later flush set it again and the run came back as a second Processing occurrence or a second holder of a unique key. With the test, a run that could not re-assert in time stays expired at every later reset, as under jobs REQ-132, and its outcome is still recorded (REQ-521).

- Attack: concurrency tests with runs on two worker nodes holding a queue limit, a concurrency key with Max = 1, a unique key and an occurrence of a recurring job with overlap Skip, a FLUSHALL during the runs, and jobs with the same keys enqueued during the pause; and a property test over the order of heartbeats, flushes, REQ-509's clear and lease expiry. Observed: after the pause no second job holds the concurrency key, the queue slot or the occurrence beside a run that kept its lease (jobs INV-107, INV-108, recurring INV-204; SCN-504, SCN-507, SCN-509).
- Given the marker missing or flagged, a run's record missing, the store reset since the claim, and the run's leaseExpiresAt not passed by the database clock (the server's TIME, jobs INV-105), when its heartbeat or progress write runs, then the record is re-created as processing with the run's claiming node, leaseToken, leaseExpiresAt, queue, concurrency key, unique key and recurring occurrence, and the run goes on to complete.
- If the marker is present and unflagged (the reconciliation is over), then a heartbeat that finds its record missing re-creates nothing; the run's outcome is recorded at completion (REQ-521).
- If the run's leaseExpiresAt has passed, then nothing is re-created, even when a later flush flags the marker again (SCN-510).
- If the store was not reset since the claim (an operator or retention removed the record), then nothing is re-created and the write is refused as under jobs INV-128.
- Given a progress write (jobs REQ-166) in place of a heartbeat, then all of the above hold the same way.
- Given the re-created record's unique key is held by another active job, then REQ-534 applies in the same write.

### AC-5 · REQ-523 · must

> When this node replaces the generation marker under REQ-507, the system shall record the reset as unacknowledged in the store in the same atomic step as that replacement, log an ERROR saying that runtime-defined recurring jobs, the maintenance pause, queue pauses, runtime throttle limits and recurring-job pauses may have been lost and are back at their defaults, and remember the reset until it finds it acknowledged.
>
> *Notes:* Decided by the owner on 2026-11-06: report only; nodes do not cache runtime definitions. refiner-model 2026-11-06: F-7 (recommended) lists every piece of operator state that falls back to its default; a paused code-defined recurring job is re-seeded as Active. F-8 (recommended): the record is kept in the store and re-written by REQ-532 if a later flush erases it. F-9 (recommended): only the node that makes REQ-507's replacement reports the reset. Run 3 F-5 (recommended option): the trigger names REQ-507, because REQ-528's first write also writes a reconciling marker and must not report a reset (SCN-503). Run 6 F-1: REQ-507 has had no compare-and-set since run 5 F-1, so the trigger names the event it has now, its replacement of the marker in the same atomic step as the read that found it. Every such replacement succeeds and exactly one node makes it per reset, so exactly one node records the reset, as F-9 intended. Run 7 F-1 (recommended option): the record is written by the same script as REQ-507's replacement (TECH-130), so it does not depend on the script's reply. If the connection drops or the call times out after the script ran, both ERROR log lines (StoreWasReset and this one) and this node's memory are lost but the record is not, and health stays Degraded (REQ-524) until an operator acknowledges it, unless the store loses it in a way no node detects (run 8 and run 9 F-1). Before, a lost reply left no trace: every node, the writer included, joined the new marker silently through REQ-530. Run 8 and run 9 F-1 (recommended option): the record lives in the store, so a later loss of store data that no node detects as a reset (the unreported late-join flush or an undetected rollback, NFR-31) takes the record with it. A node that remembers the reset writes it back (REQ-532), but after a lost reply no node remembers it, and health then returns to Healthy without an acknowledgement. These notes name that class rather than counting its cases. Not chosen: having every worker that finds an unacknowledged record remember it, which narrows the window but cannot close it (no node may read between the two flushes).

- Attack: concurrency tests with two and three worker nodes and one or two FLUSHALLs, and fault injection that drops the connection after the server ran the detecting script (redis A-32). Observed in the store and the logs: every replacement under REQ-507 leaves an unacknowledged record written by the same script (TECH-130), and nothing else writes one.
- Given n1 replaces the marker under REQ-507 and the reply arrives, then the store holds the reset as unacknowledged, n1 logs one ERROR saying that runtime-defined recurring jobs, the maintenance pause, queue pauses, runtime throttle limits and recurring-job pauses may have been lost and are back at their defaults, beside its StoreWasReset (SCN-500), and n1 remembers the reset.
- Given other nodes join under REQ-530, or a node writes the first marker under REQ-528, then they write no record and log no such ERROR (redis A-31, SCN-503).
- Given the reply is lost, then the record is in the store although neither ERROR line was logged and no node remembers the reset, and health is Degraded (REQ-524).
- Given a code-defined recurring job was paused before the flush, then after the reconciliation it is Active again (REQ-523's notes).
- Given the reset is acknowledged (REQ-525), when n1 next reads the record, then it forgets the reset: if the test then deletes the record, n1 does not re-write it (REQ-532).
- Given a second detected reset before any acknowledgement, then the store holds one unacknowledged record (redis A-34).
- A loss that no node detects can take the record with it, and health then returns to Healthy without an acknowledgement (REQ-523's notes, NFR-31); no criterion asserts that the record survives such a loss.

### AC-6 · REQ-525 · must

> When an operator acknowledges a store reset on the dashboard, the system shall record the reset as acknowledged.

> *Notes:* Decided by the owner on 2026-11-06. Acknowledging is an operate action (dashboard INV-301).

### AC-7 · REQ-532 · must

> While this node remembers an unacknowledged store reset, if the store holds no record of that reset, then the system shall re-write the record as unacknowledged.
>
> *Rationale:* A later flush must not erase the only trace of an unacknowledged reset.
>
> *Notes:* refiner-model 2026-11-06 F-8 (recommended option). A node forgets the reset once it finds it acknowledged (REQ-523, REQ-525). The record does not survive a flush while every node that remembers it is down. Run 8 and run 9 F-1: a record written by a script whose reply was lost (REQ-523) has no node that remembers it, so this sentence cannot restore it. A later reset that is detected is recorded in turn (REQ-523); a later loss that no node detects (NFR-31) removes it unless some node still remembers an earlier unacknowledged reset.

- Attack: tests that remove the record without a detectable reset (deleting its key directly, as an undetected loss or an eviction would, redis A-37) while some nodes do and some do not remember the reset. Observed: the record is back as unacknowledged whenever a running node remembers it.
- Given n1 remembers an unacknowledged reset and the record is deleted, when time is advanced, then n1 re-writes it as unacknowledged and health stays Degraded (REQ-524).
- If no running node remembers it (after a lost reply, after every node found it acknowledged, or after the remembering node stopped), then nothing re-writes it.
- Given a later flush that a node detects, then that node records the new reset itself (REQ-523); this rule adds nothing.
- How soon the record comes back is open question 4.

### AC-8 · SCN-500 · scenario

> **FLUSHALL is detected and recurring jobs come back**
>
> *Given:* Worker node n1 runs against the ready Redis store, has seen its generation marker, and code-defined recurring job nightly-cleanup exists; someone runs FLUSHALL.
>
> 1. REQ-507 — marker missing; n1 writes the reconciling marker and logs StoreWasReset
> 2. REQ-523 — ERROR listing what may have been lost; reset recorded as unacknowledged
> 3. REQ-508 — health Degraded
> 4. REQ-509 — re-seeded; after LeaseDuration the reconciling flag is cleared
>
> *Then:* nightly-cleanup exists again, the generation marker is present without the reconciling flag, the store is Ready, one ERROR StoreWasReset event and one ERROR listing what may have been lost were logged, no job was claimed while the marker was missing or flagged, and health stays Degraded until an operator acknowledges the reset.

### AC-11 · SCN-508 · scenario

> **A unique-key duplicate created during the pause is cancelled**
