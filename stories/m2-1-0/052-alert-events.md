# ST-052 — Alert on failures, failure rates, late recurring jobs, lost nodes, deep queues and waiting throttles

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-051, ST-042

## Context

Adds the remaining triggers: the Nth failed attempt of a job (REQ-401), the failure rate of a job name (REQ-402), recurring occurrences that are missed, late or not started (REQ-403), lost nodes (REQ-404), deep queues (REQ-405) and jobs waiting on a throttle key (REQ-406). Each creates a delivery that INV-409 makes Pending or Suppressed. It also makes once-only events (dead-letters, Nth failures, missed or late occurrences) reliable: they are found from what the job store records and marked delivered per rule name in the same conditional write that creates the delivery (INV-412), and a rule with a new name or new event settings starts at the store's present (INV-413). Lease handovers, rolling deploys and rule edits then neither repeat an event nor skip one after a version's start.

Builds on ST-051 (cooldowns, the cap and REQ-400's dead-letter trigger) and ST-042 (throttle keys, jobs REQ-156), and on ST-049 (the lease, INV-411), ST-012 (node heartbeats and NodeLostAfter, hosting REQ-60), ST-026 (recurring REQ-242's stored record of missed instants), ST-008 (each job's state history, jobs INV-116) and ST-020 (requeues, jobs REQ-141 and REQ-143). It keeps INV-409, INV-411 and REQ-400 holding: INV-412 changes how REQ-400's dead-letters are found, so ST-051's REQ-400, SCN-400 and SCN-405 tests must stay green. INV-412 and INV-413 stay here rather than in ST-051 because INV-412 also governs the events of REQ-401 and REQ-403. SCN-406's steps are owned by ST-049 and ST-051, but it is placed here because its outcome, neither repeating nor losing an alert, is INV-412. ST-054's conformance suite then covers the store contract this story adds.

Part of the notification engine in the Bellhop core package (TECH-112). The rule records, the 'delivered' marks per rule name and the 'before the start' marks per name and event settings change the store contract (TECH-31), so they are implemented on the in-memory and PostgreSQL stores; how the store records them is an implementation choice (INV-412 notes). How a rule sets its threshold, window and tolerance is ST-049's open question 1.

- integrations A-24 (affects REQ-403, recurring REQ-242, REQ-234): A pause, orphaning or removal of the active recurring job with an overdue instant is one action, `PauseMissed`: it writes a REQ-242 record and no last outcome, and stops triggers. - integrations A-3 (affects INV-400, INV-407, INV-410, REQ-414, REQ-436, INV-412, INV-413): Cooldowns, NodeLostAfter, tolerance, MisfireThreshold, retention and LeaseDuration end as nondeterministic events. In `IntegrationsAlertEvents`, the settings are the trigger (`watch`) and a version bit (`ver`) that stands for a threshold or tolerance. A trigger edit moves the rule to other events, a widened trigger adds events, a settings edit keeps the same events, and a rename (a name bit `nm`) gives it a new name. Records are added, never replaced. "Delivered" is kept per name and "before the start" per name and event settings, as written. The node-memory counterfactuals keep a one-step write.

## Acceptance criteria

### AC-1 · REQ-401 · must

> Where a rule watches repeated failures with threshold N, when an attempt of a job ends with an exception or a timeout and the job's attempt number is N, whether the job becomes failed or dead-lettered, the system shall create a delivery for that rule with the job as subject.
>
> *Transition:* Delivery: (new) → Pending | Suppressed · *Actor:* system
>
> *Notes:* refiner-model 2026-11-06 F-5, option 1: failed attempts are counted, including the final one that dead-letters the job. A lease-expiry interruption (jobs REQ-132) is not a failure and does not count. The count is the job's attempt number, so an operator requeue (jobs REQ-141) starts it again.

- Given a rule that watches repeated failures with threshold 3 and a job with maxAttempts 5, when the job's third attempt ends with an exception, then one delivery for the rule with the job as subject is created; its first, second, fourth and fifth failed attempts create none for this rule.
- Given threshold 3 and maxAttempts 3, when the third attempt fails and the job is dead-lettered (jobs REQ-131), then the delivery is created (notes: the final attempt counts).
- Given the third attempt ends with a timeout (jobs REQ-138, REQ-186), then the delivery is created.
- Given the third attempt is interrupted by lease expiry (jobs REQ-132, REQ-133) or released at shutdown (jobs REQ-140), then no delivery is created (notes: an interruption is not a failure).
- Given the job failed its third attempt, was dead-lettered and is requeued by an operator (jobs REQ-141), when its third attempt fails again, then a second delivery is created (notes; INV-412).
- Given threshold 6 and maxAttempts 5, then the rule never fires for that job.

### AC-2 · REQ-402 · must

> Where a rule watches the failure rate, when the failure rate of a job name in the rule's window rises above its threshold, the system shall create a delivery for that rule with the job name as subject.
>
> *Transition:* Delivery: (new) → Pending | Suppressed · *Actor:* system
>
> *Notes:* Decided by the owner on 2026-11-06: the rate is always computed per job name, and each job name is its own subject for the cooldown (INV-400).

- Given a rule that watches the failure rate with threshold T and window W, when the failure rate of job name n within W rises above T, then one delivery with n as subject is created.
- Given n's rate within W reaches T but does not exceed it, then no delivery is created.
- Given n1's rate is above T and n2's is not, then only n1 gets a delivery; given both are above T, each gets its own delivery with its own subject (notes), and INV-400 judges them apart.
- Given failures that lie outside W, then they do not count towards the rate.
- What the rate is, and whether the rule fires again while the rate stays above T, are open questions 1 and 2.

### AC-3 · REQ-403 · must

> Where a rule watches recurring jobs, when a recurring job's occurrence is missed, starts later than the rule's tolerance after its due time, or has not started when the rule's tolerance after its due time has passed, the system shall create a delivery for that rule with the recurring job as subject.
>
> *Transition:* Delivery: (new) → Pending | Suppressed · *Actor:* system
>
> *Notes:* Missed occurrences are read from the record recurring REQ-242 keeps in the store (INV-412), not from REQ-220's in-memory event, so a miss caught by the trigger is alerted even after the next occurrence has finished. refiner-model 2026-11-06 F-6, decided by the owner: notification checks run on nodes with the alerts registration (INV-411), not on workers, so an occurrence that never fired because no worker is alive is still reported, from the stored nextRunAt, by the 'has not started' branch. Run 4 (recurring F-1): instants dropped by a schedule change are recorded by REQ-242 too, so they are alerted as missed. Recurring run 5 F-1: so are instants already missed when a job is paused, orphaned or removed.

- Given a rule that watches recurring jobs with tolerance τ, when recurring REQ-242 records missed instants of job r (written by a trigger, a schedule change, a pause, an orphaning or a removal), then a delivery with r as subject is created, one per record however many instants it covers (integrations A-20).
- Given an occurrence of r that starts more than τ after its due time, then a delivery is created; given one that starts within τ, none.
- Given no worker is running and r's stored nextRunAt lies more than τ in the past, then an alerts-only node creates a delivery with r as subject (notes: the 'has not started' branch).
- Given a miss caught by the trigger and the next occurrence already finished, then the miss is still alerted (notes: read from REQ-242's record, not from recurring REQ-220's event).
- Given instants that fell due while r was paused, then no delivery is created for them (recurring REQ-234; integrations A-24).
- Whether one occurrence can give several deliveries is open question 5.

### AC-4 · REQ-404 · must

> Where a rule watches nodes, when a node has sent no heartbeat for NodeLostAfter, the system shall create a delivery for that rule with the node as subject.
>
> *Transition:* Delivery: (new) → Pending | Suppressed · *Actor:* system
>
> *Notes:* Decided by the owner on 2026-11-06: NodeLostAfter is 5 minutes (hosting REQ-60), longer than the 60 s lease, so jobs of a lost node are recovered well before the alert; fewer false alarms during long pauses and deploys. refiner-model 2026-11-06 F-6, decided by the owner (instead of accepting the gap): the check runs on a node with the alerts registration (INV-411, REQ-438), which can be a worker node, a client or dashboard node, or a node that only does alerts, so the last worker going down is still reported as long as an alerts node runs.

- Given a rule that watches nodes, when a node has sent no heartbeat for NodeLostAfter (5 minutes by default, hosting REQ-60), then a delivery with that node as subject is created; while less than NodeLostAfter has passed, none.
- Given NodeLostAfter is configured as 2 minutes, then the delivery is created once 2 minutes have passed.
- Given the only worker crashed and the alerts registration runs on a client node with no worker, then the delivery is still created (SCN-404, TECH-129).
- Given a node that keeps sending heartbeats, then no delivery is created for it.
- Which nodes can be reported, a node that stopped cleanly, and repeats while a node stays lost are open questions 3 and 2.

### AC-5 · REQ-405 · must

> Where a rule watches queue depth, when a queue's depth rises above the rule's threshold, the system shall create a delivery for that rule with the queue as subject.
>
> *Transition:* Delivery: (new) → Pending | Suppressed · *Actor:* system

- Given a rule that watches queue depth with threshold D, when queue q's depth rises above D, then a delivery with q as subject is created; at a depth of D, none.
- Given queues q1 and q2 both above D, then each gets its own delivery with its own subject.
- What counts towards a queue's depth, and repeats, are open questions 4 and 2.

### AC-6 · REQ-406 · must

> Where a rule watches throttles, when jobs have waited on a throttle key for longer than the rule's threshold, the system shall create a delivery for that rule with the key as subject.
>
> *Transition:* Delivery: (new) → Pending | Suppressed · *Actor:* system
>
> *Notes:* Reading confirmed by the owner on 2026-11-06: 'throttle key starved' means jobs have waited on the key for longer than the rule's threshold.

- Given a rule that watches throttles with threshold T, when jobs have waited on throttle key k, held back by its concurrency key or rate limit (jobs REQ-156), for longer than T, then a delivery with k as subject is created; for T or less, none.
- Given jobs held back by something other than their throttle key (a paused queue, no worker running), then this rule creates no delivery for them.
- Given two keys whose jobs have waited longer than T, then each key gets its own delivery with its own subject.
- From when a wait is measured, and repeats, are open questions 4 and 2.

### AC-7 · INV-412 · must

> Where a rule watches an event that is a single recorded state change: a job dead-lettered (REQ-400), an attempt that makes the Nth failure (REQ-401), or a recurring occurrence missed or late (REQ-403); a job that is requeued (jobs REQ-141, REQ-143) can produce such an event again, the system shall find those events from what the job store records and, for each one that is neither delivered for the rule's name nor before the start of its name and event settings (INV-413), create its delivery and mark the event delivered for the rule's name in one store write that succeeds only if the event is not yet marked delivered for that name, so that neither a node that takes over the notification lease nor a version of the rule that takes over from another alerts an event again or skips one after its start (INV-413).
>
> *Rationale:* The lease decides which node writes, but these events happen on worker nodes. If the lease holder remembered what it reported in its own memory, a handover would alert an event twice or not at all.
>
> *Notes:* refiner-model 2026-11-06 run 2 F-15 (recommended option; the model shows one delivery per event and no event lost with this rule, against a duplicate or a loss with node-local memory). Events that happen while no node holds the lease, or while no alerts node runs at all, are alerted when a holder next runs, for rules the store already records; events before a rule's first evaluation are not (INV-413); the subject cooldown and the cap (INV-409) keep a backlog from flooding the channel. An event is no longer alerted once retention has removed the job it belongs to (jobs REQ-145). State-based rules (REQ-402, REQ-404, REQ-405) need nothing like this: any holder sees the condition, and the subject cooldown handles repeats. How the store records events and the marks, for example a per-rule position in a store-assigned sequence of state changes, is an implementation choice. Run 3 F-17 (recommended option): a missed occurrence is found from the record recurring REQ-242 keeps; the last outcome alone is overwritten by the next occurrence, and RunOnce left no trace. Run 3 F-19 (recommended option): each recorded state change is its own event, so a job that is requeued and then dead-lettered again, or reaches attempt N again, is alerted again (REQ-401 notes); a handled mark kept on the job row would hide the second one. Run 3 F-18: where a new rule starts is INV-413. Run 4 F-20 (recommended option): the write is conditional on what was read, like recurring REQ-216's compare-and-set, because INV-411's lease check also passes for a node that paused past LeaseDuration and then took the lease back, and that node's old write would alert the event a second time. Run 5 F-23: 'handled for that rule' means for its name and event settings, as INV-413 records it. Run 6 F-24 (recommended option): run 5's one mark per version also hid from each version what the other had delivered, so a rollback, or a lease that moved between versions during a rolling deploy, alerted the same event again whenever both versions watch it, which is the case for every threshold or tolerance edit. There are now two marks: 'delivered' is kept per rule name, the rule's identity for users and for the subject cooldown (REQ-410, INV-400), so a name alerts each event at most once whichever version or node does it; 'before the start' is kept per name and event settings (INV-413), so one version's start does not hide what another still owes (F-23 stays resolved).

- Concurrency, on the in-memory and PostgreSQL stores with two alerts nodes, a fake TimeProvider and injected crashes, restarts and pauses past LeaseDuration, as IntegrationsAlerts.tla's configurations do: dead-letters, Nth failures and missed or late occurrences happen on worker nodes at random moments while the lease moves. Observed: no event gets two deliveries for one rule name (Inv_OneDeliveryPerEvent), and every event a version of the rule watches after that version's start gets its delivery once the lease stays with a node that runs that version (integrations A-30).
- Given a holder that read an event as due, paused past LeaseDuration, and lands its write after the new holder delivered that event, then the write fails and nothing is created (notes: run 4 F-20).
- Given a1 and a2 run two versions of one rule name that watch the same events (a threshold edit during a rolling deploy) and the lease moves between them, then no event is delivered twice for that name (notes: run 6 F-24).
- Given a job dead-lettered, requeued (jobs REQ-141 or REQ-143) and dead-lettered again, then each dead-letter gets its own delivery.
- Given events that happen while no node holds the lease, or while no alerts node runs, then they are delivered when a holder next runs, for rule versions the store records (notes; integrations A-26, A-31). SCN-406 is the handover case.
- Given a job that retention removed (jobs REQ-145) before any holder found its event, then that event is not alerted (notes).
- Given INV-409 creates the delivery Suppressed, then the event is still marked delivered for the name and is not delivered again.
- Given the conditional write fails, then neither the delivery nor the mark exists afterwards.

### AC-8 · INV-413 · must

> Where a rule watches an event that is a single recorded state change (INV-412), when the notification lease holder evaluates a rule whose name and event settings (trigger, threshold and tolerance) the job store has no record of, the system shall in one store write that checks the notification lease and succeeds only if the store still has no record of them, record the rule's name and event settings and mark every such event the store records as before the start of that name and those event settings, without creating deliveries for them.
>
> *Rationale:* Without it, deploying a new rule alerts every once-only event still stored, up to 30 days of dead-letters (jobs REQ-104), or alerts none of them, depending on the implementation.
>
> *Notes:* refiner-model 2026-11-06 run 3 F-18 (recommended option): a rule starts at the store's present the first time its name is seen. Its records and start marks are kept per name and event settings even while no node loads the rule, so removing and re-adding it, or a rolling deploy in which the lease moves between nodes with and without it, continues where it stopped and skips nothing. A renamed rule is a new rule. Run 4 F-22 (recommended option): so is a rule whose trigger, threshold or tolerance is edited, because those decide which events are its own; without this, lowering a threshold or pointing a rule at another trigger alerted the stored backlog that this sentence exists to prevent. Changing its channel, template, window or cooldown is not a new rule. Run 4 F-20 (recommended option): the write checks the lease and is conditional on the store still having no record, so a holder that paused past LeaseDuration cannot land a stale write that marks an event a newer holder owes an alert. Run 4 F-21 (recommended option, accepted): a rule starts at its first evaluation by a lease holder, not at its deploy. On a new system, events before the first alerts node takes the notification lease are not alerted; run the alerts registration with the first deployment to avoid the gap. Starting every rule at the beginning on a store with no rule names was not chosen: the first upgrade of an existing installation would alert up to 30 days of stored dead-letters. Run 5 F-23 (recommended option): handled marks belong to a version of a rule (its name and event settings), like its record. Kept per name, an edited rule's first evaluation marked the events the previous version still owed, and a rollback, or a rolling deploy that moved the lease back to a node with the previous version, never alerted them. Now that version continues where it stopped and skips nothing; like a re-add, it also alerts its events from the time the edit was live. Run 6 F-24 (recommended option): the mark this sentence writes is 'before the start' of this version only, and the mark INV-412 writes, 'delivered', belongs to the rule's name. A version that is rolled back, or that takes the lease back in a rolling deploy, therefore alerts what it still owes but not what another version of the same name already delivered. Run 7 F-25 (recommended option): INV-412's 'skips none' is about the events after a version's start. An event recorded between the last evaluation of one version and the first evaluation of the next (an edit that is not rolled back, or a rename) is before the next version's start and is alerted by neither, unless the previous version comes back. Keeping an alerts node running through the deploy keeps that window to about one evaluation interval. Starting a new version where its name last stopped was not chosen: it needs a per-name evaluation point and alerts a slice of the new trigger's backlog (run 4 F-22). Run 7 F-26 (recommended option): a renamed rule is a new rule for both marks. When a rename is rolled back, or a rolling deploy moves the lease between nodes with the old and the new name, the old name alerts what happened while it was away, including events the new name already delivered, and the subject cooldown, kept per rule (INV-400), does not suppress the repeat. Rules that should share deliveries keep one name.

- Given dead-letters stored before a rule with a new name exists, when the lease holder first evaluates that rule, then it records the rule's name and event settings, creates no delivery for those dead-letters, and alerts a dead-letter that happens after that evaluation.
- Given a holder that read "no record", paused past LeaseDuration, and lands its write after another holder recorded the rule, then the write fails and the start the other holder recorded stands (notes: run 4 F-20).
- Given a rule's trigger, threshold or tolerance is edited, then the edited rule starts anew: events stored before its first evaluation are not alerted by it. Given only its channel, template, window or cooldown is edited, then it does not start anew (notes: run 4 F-22).
- Given a rule removed and added back with the same name and event settings, then it continues where it stopped and alerts what happened while it was away (notes).
- Given an edit that is rolled back, or a rolling deploy that moves the lease back to a node with the previous version, then that version alerts what it still owes after its start, but not what another version of the same name already delivered (notes: run 6 F-24).
- Given a rename, then the new name is a new rule for both marks; when the rename is rolled back, the old name alerts what happened while it was away, including events the new name delivered (notes: run 7 F-26, accepted).
- Given an edit that is not rolled back, or a rename, then an event between the old version's last evaluation and the new version's first is alerted by neither; on a new system, events before the first holder's first evaluation are not alerted (notes: run 7 F-25 and run 4 F-21, accepted).
