# ST-073 — Publish the 1.0 option reference, guides and samples

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-035, ST-041, ST-044, ST-055, ST-061, ST-062

## Context

Publishes the documentation 1.0 needs beyond the getting-started, concepts and recipe pages of ST-035: an option reference that lists every public option with its default (NFR-26) and says for each when to change it (NFR-2), samples for a web app, a worker service, multi-tenancy, transactional enqueue and tests (NFR-27), an integration-test sample for PostgreSQL and SQL Server on Testcontainers (TECH-106), the guide for migrating from Hangfire's expression-based API (NFR-30), and the Redis store's first page, which states its data-loss windows plainly (NFR-31) and says that transactional enqueue is not available, pointing to the SQL stores (NFR-32). REQ-36 lists docs in M2, and the 1.0 release (ST-076) depends on these pages.

Builds on ST-035 (the docs site, versioned with the code, with every snippet compiled in CI: NFR-28, which every page and sample here keeps holding), ST-041 (transactional enqueue, which its sample shows), ST-044 (tags, which the multi-tenancy sample's middleware reads), ST-055 (the SQL Server store that the Testcontainers sample runs against) and ST-061 and ST-062 (Redis reset recovery and the Tier 1 servers, whose behaviour NFR-31 describes). ST-076 and ST-078 build on it; ST-078 keeps NFR-32 holding and adds the pointer to the outbox relay sample. NFR-27 is inferred M1, but two of its samples show M2 features, transactional enqueue (INV-101, tagged M2) and tags (REQ-167, tagged M2), and REQ-36 puts docs in M2. NFR-32 is inferred M3 and is verified here before ST-078 builds the outbox it may point to. Its "or the SQL stores" lets 1.0 meet it without the outbox, and the Redis store and its first page ship in 1.0 (REQ-36; TECH-70's notes), where the store already reports no transactional enqueue (redis REQ-512, tagged M2).

The pages live in the repository's documentation (NFR-28). The option reference is generated from, or checked against, the options types (NFR-26): at least the options bound from the "Bellhop" configuration section (TECH-10) and those of AddWorker(options) (TECH-128); what else counts is open question 1. The multi-tenancy sample's middleware is an IJobMiddleware (TECH-28) that reads a tag set on the job (REQ-167). The transactional-enqueue sample uses what ST-041 built: dbContext.EnqueueAsync(job) from Bellhop.EntityFrameworkCore (TECH-49) or the explicit database transaction on EnqueueOptions (TECH-20). Where the samples live is open question 4. No package code changes here.

### Terms

### Modeling assumptions

Decisions the model took where the sentences were silent. Build to them, or raise an open question.

- redis A-21 (affects `Liv_LossReported`, P2, NFR-31): Only a rollback to an older marker value counts as a detectable loss in `Liv_LossReported`; same-value rollbacks and runtime evictions are documented as undetected (NFR-31, REQ-531). A rollback is also undetectable when its marker is older than the current one but no node has seen anything newer, as after a lost reply (P2). `Hidden` covers both. *(run 10)* Without a clock the model cannot check NFR-31's "less than one RecurringReconcileInterval old" for either kind
- redis A-27 (affects REQ-528, NFR-31): "Paused" in NFR-31 and the REQ-528 notes means the node makes no marker read between the flush and the advance (`readInWindow`). A node whose store is connecting makes no reads, so it counts as paused

3. **Decide in delivery** · NFR-27, TECH-106: is the Testcontainers sample (TECH-106) NFR-27's "tests" sample or a second one? Must CI build it and run its tests, and must the docs link to it? And must the NFR-27 samples' tests pass in CI, or only build? 5. **Decide in delivery** · NFR-31: should the page say an undetected loss "can also remove" the earlier reset's record, which the redis findings (Notes to correct) give as exact, since a rollback removes it only when its image is older than the record? 6. **Decide in delivery** · NFR-31: the page names Kvrocks as an option for durability-critical workloads, but Kvrocks is a Tier 2 server (TECH-77), which REQ-36 and TECH-87's notes put in M3 (ST-082). Should the 1.0 page say that Kvrocks support comes in 1.x?
