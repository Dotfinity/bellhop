# ST-058 — Run the job lifecycle on Redis with one script per transition

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-057

## Context

Runs the whole job lifecycle on the Redis store, every state transition as one Lua script (TECH-57): claims that move a job from the ready list to the node's working list under a lease (TECH-62), per-queue pub/sub wake-ups with polling as the fallback (TECH-63), dashboard filters served from the index sets (TECH-66), and retention by whole-hash EXPIRE and a janitor (TECH-67). It adds the Redis rules for captured logs and results, which expire with their job (REQ-514), and removes the registration of a node that has stopped heartbeating (REQ-515, REQ-533). With it the conformance suite runs green on Redis. The tool infers TECH-62, TECH-63, TECH-66 and TECH-67 for M1 from the M1 rules they implement, but the Redis store is M2 (hosting REQ-36; TECH-70's notes), so they ship with it.

Builds on ST-057: its key layout; the Redis store package with the same semantics as the SQL stores (TECH-70), which the full conformance run here first shows; and its script rules, which every script here must pass: the command baseline (TECH-54), the features never used (TECH-55), declared keys and one hash tag per namespace (TECH-58), the time passed in from one TIME call (TECH-59), the Lua subset (TECH-60) and loading with EVALSHA and the NOSCRIPT fallback (TECH-61). It also builds on the stories whose transitions the scripts carry out: ST-007 (enqueue), ST-008 (claims, INV-103), ST-011 (retries), ST-012 (the node registry that jobs REQ-124 reads), ST-013 (heartbeats and recovery), ST-018 (cancellation), ST-019 (unique keys, INV-100), ST-021 (retention, jobs REQ-145), ST-022 and ST-026 (recurring writes, TECH-45), ST-040 (results, and a bulk enqueue in one store round-trip per batch, NFR-17), ST-042 (concurrency admission), ST-045 (log capture), ST-004 (IJobIndex, TECH-32), ST-054 (the suite, TECH-105, and library versions N and N+1 both reading and writing schema N, NFR-18) and ST-036 (memory proportional to in-flight jobs, NFR-13, and due recurring jobs found by one indexed range query per poll, NFR-14), all of which must now hold on Redis. ST-059 adds server detection, ST-060 adds the reset checks to the claim, heartbeat and trigger scripts (it lists TECH-62 under Must keep holding), ST-063 wakes SQL-store nodes over this pub/sub, ST-074 measures Redis latency (NFR-9) and ST-075 inspects the queries of TECH-66 and TECH-67 (NFR-15, NFR-16).

Lives in the Bellhop.Redis package (TECH-70), in scripts that pass ST-057's checks (TECH-54, TECH-55, TECH-58 to TECH-61). The claim, heartbeat and trigger scripts are written here without the generation-marker checks that ST-060 adds (TECH-130). The option names for StaleNodeAge and the janitor's batch size are not in the specs (open questions 5 and 8); the channel names belong to the key layout (ST-057's open question 4).

## Acceptance criteria

### AC-1 · REQ-533 · must

> The system shall default StaleNodeAge to 3 × HeartbeatInterval, 60 seconds (StaleNodeAge).
>
> *Notes:* refiner-model 2026-11-06 F-14 (recommended option). HeartbeatInterval is jobs REQ-102 (20 s). The owner may prefer another value; note that jobs REQ-124 and recurring REQ-205 act on a node as soon as its registration is gone, while integrations NodeLostAfter (5 minutes) is longer.

- Given LeaseDuration and StaleNodeAge not configured (HeartbeatInterval 20 s, jobs REQ-102), when a node's last heartbeat is more than 60 seconds old by the server's clock, then its registration is removed (REQ-515); at 60 seconds or less it is kept.
- Given StaleNodeAge configured, then the configured age applies in place of 60 seconds.
- Whether StaleNodeAge follows a configured LeaseDuration, and the option's name, are open question 5.

### AC-2 · REQ-515 · must

> When a node has not sent a heartbeat for longer than StaleNodeAge, the system shall remove its node registration.
>
> *Transition:* hosting.Node: Starting | Running | Draining → (removed) · *Actor:* system
>
> *Notes:* refiner-model 2026-11-06 F-14 (recommended option): an event that removes the node from the store's view, so a transition rather than an invariant; the age is the new assumption REQ-533. Jobs REQ-124 (Unroutable) and recurring REQ-205 (Orphaned) count running worker nodes from these registrations.

- Given a node registered in the node registry sorted set (TECH-56), when it sends no heartbeat for longer than StaleNodeAge, then its registration is removed, and from then on it does not count as a running worker node for jobs REQ-124 or recurring REQ-205.
- Given a node whose heartbeats keep arriving within StaleNodeAge, then its registration is never removed, whether it is Starting, Running or Draining.
- Given a stale node in any of those three states, then it is removed all the same.
- Given the clock of the node that removes registrations set far ahead of the server's (a FakeTimeProvider), then a node that heartbeats on time is not removed: the age is measured on the server's clock (TECH-59).
- Which nodes do the removal, and whether a node removed during a long pause registers again at its next heartbeat, is open question 6. What the node-lost rules read once a registration is gone is open question 7.

### AC-3 · REQ-514 · should

> The system shall cap the size of captured logs and job results and give them the same TTL as their job's record, renewed whenever the job changes state.
>
> *Notes:* refiner-model 2026-11-06 F-11 (recommended option): a fixed TTL could expire logs before a long-kept job, such as a dead letter kept 30 days (jobs REQ-104), against jobs INV-119.

- Property, over random sequences of enqueue, claim, heartbeat, log writes, completion with a result, failure, retry, dead-lettering, cancellation, requeue, deletion and expiry: after every step a job's captured logs and result have the same TTL as its job hash (none while the hash has none, the same expiry once it has one), and no logs or result remain for a job whose hash is gone (jobs INV-119).
- Given a job dead-lettered and kept for RetentionDeadLettered (30 days by default, jobs REQ-104), then its captured logs expire with it and not earlier (the item's notes).
- Given a job changes state, then the TTL of its logs and result is set again together with its hash's, in the same script (TECH-67).
- Given a handler logs more than CapturedLogLimit, then the stored log stops there with the truncation mark (jobs INV-126); given a result larger than ResultSizeLimit, then no result is stored and the result is marked dropped for size (jobs REQ-184).
- Whether the caps are those jobs-wide limits or lower Redis defaults is open question 4; the TTL after a requeue out of a terminal state is open question 3.

### AC-4 · TECH-57 · must

> **One script per transition** — The Redis store shall perform every state transition (enqueue, claim, heartbeat, complete, fail, retry, cancel, recover, recurring trigger, unique check, concurrency admission) as exactly one Lua script.

- The command recording of TECH-54 shows, for each transition (enqueue, claim, heartbeat, complete, fail, retry, cancel, recover, recurring trigger, unique check, concurrency admission), exactly one script call (EVALSHA, or the reload after NOSCRIPT of TECH-61) besides the TIME of TECH-59, and no write command outside that script. Passing: no transition with two scripts or with a write outside its script.
- Fault injection: with the connection dropped at random points around script calls, every job is afterwards in exactly the structures its state calls for (one ready, working, scheduled or retry structure, the lease set only while processing, the index sets of its state, queue and name), never in a mix of before and after.
- The conformance suite's concurrency tests for unique keys (INV-100), concurrency keys (jobs INV-108) and recurring triggers pass on Redis; the recurring trigger is one compare-and-set script that also requires the maintenance pause to be off (TECH-45).

### AC-5 · TECH-62 · must

> **Redis claims and leases** — The Redis claim script shall move a job from the ready list to the node's working list and add it to the lease sorted set with its deadline; heartbeats update that score and recovery scans the set for deadlines in the past.

- Given a job in a queue's ready list, when a worker claims it, then the job is no longer in the ready list, is in that node's working list, and is in the lease sorted set scored by its lease deadline, the claim's server time plus LeaseDuration (jobs REQ-102).
- Given a heartbeat (jobs REQ-126), then the job's score in the lease set becomes its new deadline.
- Given recovery runs, then it takes only entries whose deadline has passed by the server's clock and returns those jobs as jobs REQ-132 says; a job whose deadline has not passed is left alone.
- Concurrency: many workers on several nodes claim from one ready list at once; no job is ever in two working lists or held by two workers with unexpired claims (INV-103).
- How a claim from a list keeps priority order and skips the jobs it may not take is open question 1.

### AC-6 · TECH-63 · must

> **Redis wake-ups** — The Redis store shall publish on a per-queue pub/sub channel at enqueue and have workers subscribe, with polling at PollInterval as the fallback; blocking pops (BLMOVE) may be used but shall not be required.

- Given an idle worker on node B that serves queue q, with PollInterval set far longer than the test, when node A enqueues a job to q, then A publishes on q's channel and B claims the job without waiting for its next poll.
- Given the wake-up is lost (B's subscription connection dropped, or the message never sent), then B still claims the job within PollInterval (jobs REQ-103).
- Given an enqueue to queue q, then nothing is published on another queue's channel.
- Given a server user that may not run blocking pops (an ACL that denies BLMOVE), then the conformance suite still passes: blocking pops are not required.
- The channel names are part of the documented layout (TECH-56; ST-057's open question 4).

### AC-7 · TECH-66 · must

> **Redis dashboard queries** — The Redis store shall serve state, queue, name and tag filters from its index sets with paging via ZRANGE ... LIMIT, and shall never use KEYS or SCAN at request time.

- The command recording of TECH-54, taken while lists filtered by state, queue, name and tag are paged through the store and IJobIndex (TECH-32), shows only reads of index sets bounded by the page (ZRANGE ... LIMIT) and reads of the page's job hashes, and never KEYS, SCAN or another SCAN-family command.
- Given many more jobs in one state than fit on a page, then a page request reads one page of index entries, however many jobs there are.
- How tag index sets, which TECH-56 calls sets, are paged with ZRANGE, and how two filters combine, is open question 2.

### AC-8 · TECH-67 · must

> **Redis retention mechanism** — The Redis store shall give terminal jobs a whole-hash EXPIRE and trim time-scored index sets with a janitor using ZRANGEBYSCORE and ZREM, 500 entries per pass by default, never using hash-field TTL, and shall give captured logs and results the same EXPIRE as their job hash, re-applied on every state change.

- Given a job reaches Succeeded, Cancelled or DeadLettered, then the transition's script gives its job hash an EXPIRE of that state's retention (jobs REQ-104), and no hash-field TTL command is used (TECH-55).
- Given a terminal job that is a member of a batch that is open or completed, then it is not removed while that holds (jobs REQ-145).
- Given index entries whose job hashes have expired, when the janitor runs, then it finds them with ZRANGEBYSCORE and removes them with ZREM, at most 500 per pass by default and the configured number otherwise; given more than 500 such entries, one pass removes 500 and the next pass goes on.
- Given a node without the worker registered, then it runs no janitor pass (hosting REQ-40).
- Given a job changes state, then its captured logs and result get the same EXPIRE as its hash again (REQ-514).
- Whether the 500 is jobs CleanupBatchSize is open question 8; the pause between batches and index use are NFR-15 (ST-075).
