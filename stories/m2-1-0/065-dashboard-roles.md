# ST-065 — Grant dashboard permissions by role or claim

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** must · **Depends on:** ST-031, ST-037

## Context

Lets a host grant dashboard view or operate by the principal's role or claim with `RequireRole(...)` and `RequireClaim(...)`, so a team that already signs its staff in can give some of them read-only access and others operate without writing policies (REQ-306). Both are authorization requirements in the sense of the startup checks (glossary `authorizationRequirement`), so using one keeps a Development dashboard from opening to anonymous operators (REQ-300) and a production dashboard from failing to start (REQ-301).

Builds on ST-037, the M1 acceptance gate after which M2 work starts (hosting REQ-36), and on ST-031, which mounts the dashboard, judges every page, JSON API read and operate action by view and operate (INV-301), grants levels by separate policies (REQ-302), and whose startup checks (REQ-300, REQ-301, REQ-342) already name RequireRole and RequireClaim; they were built against what existed then, this story makes them see the real methods, and it keeps REQ-300, REQ-301 and REQ-342 holding. Built on by ST-087, whose MCP server uses the same permissions (TECH-121), and ST-076, where NFR-20 freezes dashboard auth behaviour for 1.0.

Lives in Bellhop.Dashboard (TECH-88), on the endpoint convention builder that `app.MapBellhopDashboard("/path")` returns. REQ-306 names `RequireRole(...)` and `RequireClaim(...)`; their parameters and how a role or claim is tied to view or to operate are not in the specs (open question 1). Authentication stays the host's own scheme (dashboard A-7); this story only maps the principal it produces to a level.

## Acceptance criteria

### AC-1 · REQ-306 · must

> Where RequireRole(...) or RequireClaim(...) is used, the system shall grant view or operate to principals with that role or claim as configured.

- Given `RequireRole(...)` configured so that role R grants view, when an authenticated principal whose only configured role is R opens a page or makes a JSON API read, then it is served (INV-301); when it tries any operate action, then the response is 403 Forbidden (INV-300) and nothing changes.
- Given role R2 configured to grant operate, when a principal with R2 opens a page, makes a read or performs an operate action, then each is served or performed (operate includes view, glossary), except that a `ReadOnly()` dashboard still refuses the operate actions (INV-302).
- Given `RequireClaim(...)` configured for a claim, then the two criteria above hold with that claim in place of the role.
- Given an authenticated principal that holds none of the configured roles or claims, then every page, read and operate action is answered 403 Forbidden (INV-300).
- Given a principal that holds both a role granting view and a role or claim granting operate, then it has operate.
- Property: over random principals (random sets of configured and unconfigured roles and claims) and random requests (each page, JSON API reads, each operate action that exists by now), with `ReadOnly()` on and off, a request is served only when its principal holds a role or claim configured for the level the request needs, and every refusal of an authenticated principal is 403 (INV-300, INV-301, INV-302).
- Given `RequireRole(...)` or `RequireClaim(...)` is the only authorization requirement, then in Development anonymous requests are not given operate and no notice is logged (REQ-300 does not fire), and outside Development without `AllowAnonymous()` the host starts (REQ-301 does not fire).
- What an unauthenticated request is answered is not set here: INV-300 covers authenticated requests only, dashboard A-16 leaves the rest open, and ST-031 owns it. How these grants combine with `RequireAuthorization` or separate policies is open question 2.
