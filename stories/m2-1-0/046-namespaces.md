# ST-046 — Share one store between applications with namespaces

**Milestone:** M2 · **Epic:** m2-1-0 · **Priority:** should · **Depends on:** ST-030, ST-037

## Context

Lets several applications share one store, each under its own namespace, and guarantees that a worker never sees or claims a job of another namespace (INV-125). The multi-app shared store is one of the popular Hangfire add-ons that Bellhop covers with a feature of its own (hosting REQ-39).

Builds on ST-037 (M1 accepted, so milestones are built in order), ST-030 (the M1 behaviour proven on PostgreSQL) and, through them, on ST-008's claim (REQ-123, with at most one unexpired claim per job, INV-103) and ST-004's store contract. INV-100 (ST-019) already keeps unique keys per namespace; until now there was only one namespace, so this is where that scope first has two values, and INV-100 and TECH-44 (ST-030's unique index, which must now cover the namespace) are in this story's Must keep holding table. ST-054 builds on it (the conformance suite, which tests namespaces on every store), and ST-057 maps each namespace to its own Redis key prefix and hash tag (TECH-68).

The namespace is the job's namespace attribute (the jobs Job entity). The work is in the Bellhop core package's claim path and in every store that exists at this point, in-memory and PostgreSQL, whose claims and reads change (TECH-31); a PostgreSQL schema change stays additive (TECH-127). How an application sets its namespace, and the default, are not in the specs (open question 1).

## Acceptance criteria

### AC-1 · INV-125 · should

> Where several applications share one store under different namespaces, the system shall never let a worker see or claim a job from another namespace.

- Given applications A and B on one store under namespaces a and b, each with a handler for job name n on queue q, when both enqueue jobs of n on q and their workers run, then every job A's workers claim was enqueued by A, and every job B's workers claim was enqueued by B.
- Given B has no running node and jobs of b wait on q, when A's workers poll q while idle, then A claims none of them and none is returned to A's polling; they are claimed once a node of b runs.
- Concurrency: nodes of a and b, several per namespace, claim from the same queue name at once against one store, over random interleavings. No claim crosses namespaces, and no job has two unexpired claims (INV-103).
- Given two Bellhop instances in one process on the same store under a and b (NFR-53), then the same holds.
- Where one application uses the store alone, as in every earlier story, then claims behave as before.
- What a namespace scopes besides a worker's view and its claims is open questions 2 and 3.

## Open questions

1. **Decide in delivery** · INV-125: how does an application set its namespace (the option name and configuration key), which namespace does a job get when none is set, and which namespace do jobs stored before this story belong to? How the namespace is stored is a schema contract (TECH-127).
2. **Decide in delivery** · INV-125: what store-wide work is per namespace besides a worker's view and its claims? Nodes also recover expired leases (REQ-132), mark jobs unroutable by the handlers that running nodes list (REQ-124) and apply retention (REQ-145). The recurring scheduler would trigger another application's recurring jobs, and orphan them while that application's nodes are down (REQ-205), because a recurring job has no namespace and REQ-236 and INV-211 judge names across the store. Queues, their pauses and maintenance (REQ-160, REQ-162) have no namespace either. On Redis each namespace has its own key prefix (TECH-68), which separates all of this; the other stores have no rule.
3. **Decide in delivery** · INV-125: does a dashboard, or IJobClient's calls by job id (TECH-19), show or act on another namespace's jobs? INV-125 restricts only workers.
