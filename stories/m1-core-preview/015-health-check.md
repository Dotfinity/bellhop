# ST-015 — Report node health

**Milestone:** M1 · **Epic:** m1-core-preview · **Priority:** must · **Depends on:** ST-011, ST-012

## Context

Delivers the Bellhop health check, AddBellhopHealthCheck() (TECH-101). A node reports Unhealthy while an internal error stalls processing, the store is unreachable, the schema is outside the accepted range, its worker loop is not alive or too few worker nodes are alive (REQ-30 to REQ-33, REQ-44). It reports Degraded when scheduling lag, dead-letter growth or failures pass their thresholds (REQ-34, REQ-46 to REQ-48), and Healthy only after HealthyAfterPasses passing runs in a row (REQ-35, REQ-50), recovering from Unhealthy through Degraded (REQ-58). Health starts Unhealthy (REQ-35's notes), so readiness waits for those passes after startup, and the status does not flap near a threshold.

Builds on ST-011 (failed attempts and dead letters, which REQ-34's thresholds count) and ST-012 (worker heartbeats within NodeLostAfter, REQ-60, which REQ-44 counts); the expected and stored schema versions come from ST-006 (REQ-23, REQ-43). Built on by ST-016 (a node that cannot reach the store at startup reports Unhealthy, SCN-6) and ST-032 (the dashboard shell). The Redis store adds its own health rules in ST-059 to ST-061 (redis REQ-508, REQ-519, REQ-524).

Lives in the core package (TECH-112, TECH-101) on Microsoft.Extensions.Diagnostics.HealthChecks, whose Healthy, Degraded and Unhealthy statuses the check reports. What a "run" is, the registration's name and tags, and where the thresholds are configured are not in the specs (open question 1); the package's place in the core dependency audit is open question 5.

### Terms

- **DeadLetterGrowthThreshold** (hosting): Dead-letter growth above which the node reports Degraded; 100 in 15 min by default (REQ-47).

## Acceptance criteria

### AC-1 · REQ-46 · must

> The system shall default SchedulingLagThreshold to 60 seconds (SchedulingLagThreshold).
>
> *Notes:* Decided by the owner on 2026-11-06; the source says the thresholds are configurable but gives no defaults.

- Given SchedulingLagThreshold is not configured and no check that reports Unhealthy fails, when the health check runs with scheduling lag above 60 seconds, then the node reports Degraded (REQ-34); with lag of 60 seconds or less, the lag alone does not make it Degraded.
- Given SchedulingLagThreshold is configured as 10 seconds, then the same holds with 10 seconds.
- What scheduling lag measures is open question 2.

### AC-2 · REQ-47 · must

> The system shall default DeadLetterGrowthThreshold to 100 dead-lettered jobs in 15 minutes (DeadLetterGrowthThreshold).
>
> *Notes:* Decided by the owner on 2026-11-06.

- Given DeadLetterGrowthThreshold is not configured, when more than 100 jobs were dead-lettered in the last 15 minutes and no check that reports Unhealthy fails, then the node reports Degraded (REQ-34); 100 or fewer do not make it Degraded.
- Given the threshold is configured as 10 jobs in 5 minutes, then the same holds with those values.

### AC-3 · REQ-48 · must

> The system shall default FailureThreshold to 50 failed attempts in 5 minutes (FailureThreshold).
>
> *Notes:* Decided by the owner on 2026-11-06.

- Given FailureThreshold is not configured, when more than 50 attempts failed in the last 5 minutes and no check that reports Unhealthy fails, then the node reports Degraded (REQ-34); 50 or fewer do not.
- Given the threshold is configured as 5 in 1 minute, then the same holds with those values.
- What counts as a failed attempt, and whose attempts are counted, is open question 3.

### AC-4 · REQ-49 · must

> The system shall default MinNodesAlive to 1 (MinNodesAlive).
>
> *Notes:* Decided by the owner on 2026-11-06. Only worker nodes evaluate REQ-44 and a reporting worker node is itself alive, so the default never fires; applications opt in by raising it.

- Given MinNodesAlive is not configured, then REQ-44 never reports a worker node Unhealthy, because the reporting worker node is itself alive (REQ-49's notes).
- Given MinNodesAlive is configured as 2 and only one worker node has sent a heartbeat within NodeLostAfter, then that worker node reports Unhealthy (REQ-44).

### AC-5 · REQ-50 · must

> The system shall default HealthyAfterPasses to 3 (HealthyAfterPasses).
>
> *Notes:* Decided by the owner on 2026-11-06.

- Given HealthyAfterPasses is not configured and a node that has just started (Unhealthy), when every check passes on three runs in a row, then it reports Healthy on the third, counting the run that took it to Degraded (REQ-58, hosting A-15), and not before.
- Given a check fails on the second of those runs, then the count starts again.
- Given HealthyAfterPasses is configured as 5, then five passing runs in a row are needed.

### AC-6 · REQ-30 · must

> When the health check runs, if an internal error (store error, scheduler error, serialization error or recovery error) is stalling processing, then the system shall report the node Unhealthy.
>
> *Transition:* Health: Healthy | Degraded → Unhealthy · *Actor:* system
>
> *Notes:* Turned into a health check (refiner-model 2026-11-06 F-3, recommended option) so that REQ-35's 'every check has passed' covers it and the node cannot report Healthy while the stall lasts. Same health-check event as REQ-31 to REQ-35, REQ-44 and REQ-58.

- Given the worker loop's claims, the promotion of due jobs or lease recovery keep failing with a store, scheduler, serialization or recovery error so that no job progresses, when the health check runs, then the node reports Unhealthy, from Healthy or Degraded.
- Given the stall lasts, then every run reports Unhealthy, never Degraded or Healthy.
- Given the error stops stalling processing, then the next run reports Degraded (REQ-58).
- Each such error is logged with a stable EventId (NFR-51). When an error counts as stalling is open question 4.

### AC-7 · REQ-31 · must

> When the health check runs, if the store is unreachable, then the system shall report the node Unhealthy.
>
> *Transition:* Health: Healthy | Degraded → Unhealthy · *Actor:* system

- Given the store becomes unreachable, when the health check runs, then the node reports Unhealthy, also while the node is still Starting (SCN-6).
- Given the store is reachable again, then the next run reports Degraded (REQ-58).

### AC-8 · REQ-32 · must

> When the health check runs, if the stored schema version is neither the expected version nor one version older, then the system shall report the node Unhealthy.
>
> *Transition:* Health: Healthy | Degraded → Unhealthy · *Actor:* system
>
> *Notes:* Follows from the accepted range (REQ-23): once the first N+1 node migrates during a rolling deploy, nodes still on N see a newer schema and report Unhealthy until they are replaced. They keep working meanwhile because migrations are additive (TECH-127).

- Given the stored schema version is the expected version or one older, then this check passes.
- Given it is newer than the expected version (a node on the next version migrated) or more than one version older, when the health check runs, then the node reports Unhealthy, and its worker keeps working (REQ-32's notes, TECH-127). Tests put the store into that schema state directly, as ST-006's schema tests do.

### AC-9 · REQ-33 · must

> Where the worker is registered, when the health check runs, if the node's worker loop is not alive, then the system shall report the node Unhealthy.
>
> *Transition:* Health: Healthy | Degraded → Unhealthy · *Actor:* system
>
> *Notes:* Decided by the owner on 2026-11-06: only nodes with a worker have a worker loop; a client- or dashboard-only process is not reported Unhealthy for lacking one.

- Given the worker is registered and its loop has ended or faulted, when the health check runs, then the node reports Unhealthy.
- Given the worker is not registered (a client- or dashboard-only process), then this check never fails (REQ-33's notes).
- Whether a loop that hangs without ending is "not alive" is open question 4.

### AC-10 · REQ-34 · must

> When the health check runs, if no check that reports Unhealthy fails, and scheduling lag exceeds SchedulingLagThreshold, dead-letter growth exceeds DeadLetterGrowthThreshold or failures in the window exceed FailureThreshold, then the system shall report the node Degraded.
>
> *Transition:* Health: Healthy → Degraded · *Actor:* system
>
> *Notes:* Decided by the owner on 2026-11-06: backlog and failure checks give Degraded; MinNodesAlive gives Unhealthy (REQ-44). Recovery from Unhealthy now always goes through Degraded by REQ-58, backlog or not (refiner-model 2026-11-06 F-8, recommended option), so this rule no longer needs `from: Unhealthy`.

- Given a Healthy node, no check that reports Unhealthy failing and one of the three thresholds exceeded, when the health check runs, then the node reports Degraded.
- Given a check that reports Unhealthy fails as well, then the node reports Unhealthy, not Degraded.
- Given a Degraded node and a threshold still exceeded, then it stays Degraded and the run does not count as a pass (REQ-35).
- Given no threshold is exceeded, then this rule does not apply.

### AC-11 · REQ-35 · must

> When the health check runs, if every check has passed on the last HealthyAfterPasses runs in a row, then the system shall report the node Healthy.
>
> *Transition:* Health: Degraded → Healthy · *Actor:* system
>
> *Notes:* Decided by the owner on 2026-11-06: recovery needs consecutive passes so the status does not flap near a threshold. The source only implies recovery. Only from Degraded: an Unhealthy node first drops to Degraded by REQ-58 (refiner-model 2026-11-06 F-8). Health starts Unhealthy (entity `initial`, refiner-model 2026-11-06 F-11, recommended option), so this rule is the only route to Healthy and readiness waits HealthyAfterPasses check intervals after startup.

- Given a Degraded node, when every check passes on HealthyAfterPasses runs in a row, then it reports Healthy; any run with a failing check, Unhealthy or Degraded, starts the count again.
- Given a node that has just started, then it reports Unhealthy until its checks pass, and never goes from Unhealthy to Healthy in one run (REQ-58).
- Property: over random sequences of check outcomes, a node reports Healthy only after HealthyAfterPasses passing runs in a row, and Unhealthy is never directly followed by Healthy (`Prop_NoUnhealthyToHealthy`).

### AC-12 · REQ-44 · must

> Where the worker is registered, when the health check runs, if fewer than MinNodesAlive nodes with the worker registered have sent a heartbeat within NodeLostAfter, then the system shall report the node Unhealthy.
>
> *Transition:* Health: Healthy | Degraded → Unhealthy · *Actor:* system
>
> *Notes:* Decided by the owner on 2026-11-06. Every node reports this at the same moment, so an orchestrator that restarts on Unhealthy restarts the whole cluster together; the docs should say so. 'Alive' is defined as in the dashboard's no-worker banner (refiner-model 2026-11-06 F-9, recommended option); NodeLostAfter is defined in REQ-60. Client-only processes do not evaluate it, so a down worker never takes a web API out of readiness; they get the dashboard banner instead.

- Given MinNodesAlive is configured as 3 and only 2 worker nodes have sent a heartbeat within NodeLostAfter, when the health check runs on a worker node, then it reports Unhealthy, on every worker node.
- Given a third worker node starts sending heartbeats, then the next run reports Degraded (REQ-58).
- Given a node without the worker registered, then this check is not evaluated there, so a down worker never makes a client-only process Unhealthy (REQ-44's notes); nodes without the worker do not count towards MinNodesAlive.

### AC-13 · REQ-58 · must

> While the node is Unhealthy, when the health check runs, if no check that reports Unhealthy fails, then the system shall report the node Degraded.
>
> *Transition:* Health: Unhealthy → Degraded · *Actor:* system
>
> *Notes:* Added by refiner-model 2026-11-06 F-8 (recommended option): recovery always goes Unhealthy → Degraded → Healthy after HealthyAfterPasses passes (REQ-35), so a recovering node with a backlog never reports better than one without. Same health-check event as REQ-30 to REQ-35 and REQ-44.

- Given an Unhealthy node, when the health check runs and no check that reports Unhealthy fails, then it reports Degraded, whether or not a threshold is exceeded.
- Given a check that reports Unhealthy still fails, then the node stays Unhealthy.

### AC-14 · TECH-101 · must

> **Health check** — The core package shall provide AddBellhopHealthCheck() on Microsoft.Extensions.Diagnostics.HealthChecks.

- Test: a host that registers AddBellhopHealthCheck() has a check that the health check service runs and that reports the node's status as Healthy, Degraded or Unhealthy.
- Inspection: the check is built on Microsoft.Extensions.Diagnostics.HealthChecks, and the core package takes no ASP.NET Core dependency for it (TECH-9), so a worker service without ASP.NET Core can register it.

## Open questions

1. **Decide in delivery** · TECH-101, REQ-35, REQ-46–REQ-50: what is a "run": each call of the check by the health check service (every probe), or a check Bellhop makes at an interval whose last result the check reports? REQ-35's notes speak of "check intervals" but no interval is given, and with one run per probe, two probes count passes twice as fast. Also the registration's name and tags, and whether the thresholds are options of AddBellhopHealthCheck() or Bellhop options (TECH-10).
2. **Decide in delivery** · REQ-34, REQ-46: what is scheduling lag (how late due jobs are promoted, how long the oldest enqueued job has waited, or another measure), and is it measured for the node or the cluster? Neither the glossary nor any item defines it.
3. **Decide in delivery** · REQ-34, REQ-47, REQ-48: are dead letters and failed attempts counted across the cluster or for the node's own runs, are the windows sliding or fixed, and do failed attempts include timeouts and the attempt that dead-letters but not lease-expiry interruptions, as integrations REQ-401's notes count them for alerts?
4. **Decide in delivery** · REQ-30, REQ-33: when does an internal error "stall processing" (how many failures in a row or for how long, and does one job's serialization error count), and is a worker loop that hangs without ending "not alive"?
5. **Decide in delivery** · TECH-101, TECH-8: an extension on the health checks builder needs the Microsoft.Extensions.Diagnostics.HealthChecks package itself, not only its Abstractions package, while TECH-8 allows the core only the BCL and Microsoft.Extensions.* abstractions. Confirm the package is allowed, so that ST-001's dependency audit passes.
