# ST-016 — Survive store outages, migration races and clock skew

**Milestone:** M1 · **Epic:** m1-core-preview · **Priority:** must · **Depends on:** ST-006, ST-015

## Context

Keeps a node safe when the store or the cluster misbehaves at startup. An unreachable store is retried with backoff without stopping the host and without claiming any job (REQ-25, SCN-6). Nodes starting together against an older schema migrate once, under the store's migration lock (REQ-42), which a node holds only while starting and releases before it leaves starting for any reason (REQ-56). Applying an applied migration again changes nothing (REQ-24). A node on library version N+1 with AutoMigrate off runs on schema N (SCN-5). A running node warns when its clock drifts from the database clock by more than ClockSkewThreshold (REQ-26, REQ-45).

Builds on ST-006: the startup sequence (REQ-12), the transition to running (REQ-18) and migration under AutoMigrate (REQ-22), which must keep holding, and the schema checks (REQ-23, REQ-43). Builds on ST-015 for the Unhealthy report while the store is unreachable (REQ-31, SCN-6), and reads the database clock that INV-105 decides by (ST-007). Built on by ST-017 (a host stop while the node is still retrying, REQ-55) and ST-029 (PostgreSQL's migrations and advisory lock, TECH-46, TECH-126, which keep REQ-24, REQ-42 and REQ-56 holding). The migration lock and the schema state are generic over the store here; tests put the store into the needed state directly, as ST-006's schema tests do.

Lives in the core package's hosting integration (TECH-112, TECH-11) and the store contract (TECH-31). The store members for the schema version, migrations and the lock are not named (open question 4), nor is where ClockSkewThreshold is configured beyond the "Bellhop" section (TECH-10). Connection failures are logged with a stable EventId (NFR-51) and never with the connection string (NFR-41).

## Acceptance criteria

### AC-1 · REQ-45 · must

> The system shall default ClockSkewThreshold to 5 seconds (ClockSkewThreshold).
>
> *Notes:* Decided by the owner on 2026-11-06; the source asks for a threshold but gives no value.

- Given ClockSkewThreshold is not configured, then a running node whose clock is 6 seconds ahead of the database clock logs the warning (REQ-26), and one that is 5 seconds or less ahead or behind does not.
- Given ClockSkewThreshold is configured as 1 second, then the same holds with 1 second.

### AC-2 · REQ-25 · must

> While a node is starting, if the store is unreachable, then the system shall keep retrying the connection with backoff without stopping the host, and claim no job until the store is reachable.
>
> *Transition:* Node: Starting → Starting · *Actor:* Host
>
> *Notes:* Decided by the owner on 2026-11-06: Bellhop runs inside the application's host, so a database outage must not take the web application down. The health check reports Unhealthy meanwhile (REQ-31). The docs should advise mapping Bellhop health to readiness, not liveness, or the orchestrator restarts the pod in a loop.

- Given the store is unreachable when the host starts, then the node stays Starting, the host is not stopped, and the connection is tried again and again with growing intervals between attempts rather than given up.
- Given that state, then no job is claimed and neither the worker nor its background duties are started (REQ-18), and the node reports Unhealthy (REQ-31, SCN-6).
- Given the store becomes reachable, then the node continues the startup sequence (REQ-12) and, when every check passes, is marked running and starts claiming (REQ-18).
- Given the failing attempts, then each is logged with a stable EventId (NFR-51), and no log line contains the connection string (NFR-41).
- Whether the host's start completes meanwhile is open question 1; the backoff's schedule is open question 5.

### AC-3 · REQ-26 · must

> While a node is running, if the node's clock differs from the database clock by more than ClockSkewThreshold, then the system shall log a warning that names the measured skew.
>
> *Transition:* Node: Running → Running · *Actor:* system

- Given a running node whose clock differs from the database clock by more than ClockSkewThreshold, ahead or behind, then it logs a warning that names the measured skew.
- Given a difference of ClockSkewThreshold or less, then no skew warning is logged.
- Given a skew above the threshold, then claims, lease expiry and due times still follow the database clock (INV-105).
- How often the skew is measured, and how often a lasting skew is logged, is open question 2.

### AC-4 · REQ-24 · must

> When a migration that is already applied is applied again, the system shall leave the schema unchanged.

- Given a store at the expected schema version, when the migration to that version is applied again, then the schema objects and the stored version are the same before and after.
- Property: applying the embedded migrations in order, each of them any number of times, gives the same schema as applying each once (`Prop_MigrationIdempotent`).
- The PostgreSQL migrations themselves are TECH-46 (ST-029), which keeps this holding.

### AC-5 · REQ-42 · must

> Where AutoMigrate is on, when several nodes start at the same time against a store whose schema is older than expected, the system shall let only the node holding the store's migration lock apply migrations, and have the others wait for the lock and then re-read the schema version.
>
> *Notes:* Decided by the owner on 2026-11-06. The lock lives in the store (TECH-126), consistent with ADR-1 and TECH-51.

- Concurrency test: given AutoMigrate on and several nodes starting at once against a store one or more versions older than expected, then only the node holding the migration lock applies migrations, each migration is applied once, the other nodes wait for the lock, re-read the schema version, find it current and apply nothing, and every node is marked running on the expected version (REQ-18).
- Given the lock holder fails during its migration and leaves starting, then a waiting node takes the lock, re-reads the version and applies the migrations still missing (REQ-56, REQ-24).
- Property: over random interleavings of starts, lock acquisitions, migrations, failures and host stops of two or more nodes, no node applies a migration without holding the lock (`Prop_MigrateOnlyUnderLock`).
- Given AutoMigrate off, then no node applies a migration (REQ-22, SCN-5).
- How long a node waits for the lock is open question 3.

### AC-6 · REQ-56 · must

> While a node holds the store's migration lock, the system shall keep that node starting, and have a node that leaves starting for any reason release the lock first.
>
> *Notes:* Added by refiner-model 2026-11-06 F-4 (recommended option): a node that failed startup while holding the lock left the other nodes waiting under REQ-42. With StartupFailed failing the host's start (REQ-9, F-10), process exit releases a store-native lock (TECH-126).

- Property: over random startup paths of two or more nodes (the migration succeeds, a migration fails, the host stops while the node waits for or holds the lock, REQ-55), a node that holds the lock is always Starting, and a node that becomes Running, StartupFailed or Stopped has released the lock before that state is visible (`Inv_LockHolderStarting`).
- Given the holder's process exits while holding the lock, then the lock is freed for the waiting nodes (REQ-56's notes). That needs a lock native to the store and is verified on PostgreSQL in ST-029 (TECH-126).
- What a node does when a migration fails is open question 3.

### AC-7 · SCN-5 · scenario

> **Rolling deploy: new node runs on the previous schema**
>
> *Given:* Library version N+1 starts with AutoMigrate off against a store on schema version N; the store is reachable and options are valid.
>
> 1. REQ-12
> 2. REQ-18 — schema N is accepted
>
> *Then:* The node is Running on schema N and no migration was applied.

### AC-8 · SCN-6 · scenario

> **Store down at startup keeps the host up**
>
> *Given:* A node starts while the database is unreachable.
>
> 1. REQ-12
> 2. REQ-25 — retry with backoff
> 3. REQ-31 — health check runs
>
> *Then:* The host is still running, the node is Starting and reports Unhealthy, and no job was claimed.

## Open questions

1. **Decide in delivery** · REQ-25, REQ-23, REQ-43: does the host's start complete while the node keeps retrying the store, so that the application's other hosted services and endpoints run? REQ-25's notes say an outage "must not take the web application down". If it does, what does "fail the host's start" (REQ-23, REQ-43) mean when the store comes back with a schema the node rejects after the host has started?
2. **Decide in delivery** · REQ-26: how often does a running node measure its skew, and does a lasting skew log a warning at every measurement or once until it clears? Neither is stated, and both decide how loud the log gets.
3. **Decide in delivery** · REQ-42, REQ-56: how long does a node wait for the migration lock, and what does a node do when applying a migration fails: fail the host's start, as REQ-9 does for invalid options, or retry, as REQ-25 does for an unreachable store? REQ-56 says only that the lock is released first.
4. **Decide in delivery** · REQ-24, REQ-42, REQ-56: which IJobStore members read the schema version, apply migrations and take and release the migration lock? They are part of the public store contract every store implements (TECH-31), and TECH-126 names the native locks of four stores but not the in-memory store's.
5. **Decide in delivery** · REQ-25: which backoff, and what longest interval, do the connection retries use? The longest interval bounds how long a node stays Starting after the store comes back.
