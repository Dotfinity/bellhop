# ST-023 — Manage recurring jobs at runtime

**Milestone:** M1 · **Epic:** m1-core-preview · **Priority:** must · **Depends on:** ST-022

## Context

Gives operators and application code IRecurringJobManager (TECH-21) to manage recurring jobs at runtime: add (REQ-208), update (REQ-212), remove (REQ-213), pause (REQ-214), resume (REQ-215) and preview the next N occurrences (REQ-230). The same story adds the refusals that keep the stored jobs safe. Invalid schedules are rejected (REQ-209). Code-defined jobs cannot be edited without AllowRuntimeOverride (REQ-211) and cannot be removed unless orphaned (INV-206). Names are unique across origins, both for an add (INV-211) and for a starting node (REQ-236).

Builds on ST-022: the stored definitions, their origin, TECH-45's compare-and-set (every write here uses it, and this story constrains TECH-45) and REQ-227, which an operator's schedule edit now triggers (also constrained). REQ-236 runs inside ST-006's hosting REQ-12 sequence, among the checks that read stored data, before migration. It keeps TECH-128 (ST-005) holding, because AddClient() and AddWorker() now register IRecurringJobManager. These stories build on it: ST-024 (trigger now, REQ-226, on this interface), ST-025 (REQ-237 skips waiting occurrences when a job is paused or removed; last outcome, REQ-231), and ST-026, which adds REQ-242's record to the pause, removal and schedule-change writes and attacks every write here under INV-212. On the dashboard side: ST-034 (the recurring page's actions, dashboard REQ-310), ST-068 (the launch form's Make recurring, dashboard REQ-322, which constrains REQ-208), ST-072 (the schedule builder) and ST-047 (configuration-defined jobs, which constrains REQ-236).

Lives in the Bellhop core package (TECH-112). IRecurringJobManager is registered by AddClient(), and so also by AddWorker(), which registers the client (TECH-128). "The API" in REQ-209, REQ-211 and REQ-214 is this interface. The dashboard reaches the same rules through its JSON API (TECH-92, ST-031) in the dashboard stories above. The specs give neither the method names and signatures nor how a refusal reaches the caller (open questions 1 and 2). INV-206 and REQ-236 also name configuration-defined jobs, which ST-047 adds. Here they are built against what exists: tests write a configuration-origin record into the store directly.

### Modeling assumptions

Decisions the model took where the sentences were silent. Build to them, or raise an open question.

- recurring A-8 (affects REQ-203, REQ-204, REQ-208, INV-200, INV-211, SCN-207, REQ-242, INV-212): At node start, REQ-203 and REQ-204 (and REQ-242's schedule-change record) are applied together for every declared name. The store is keyed by name, so INV-200 and SCN-207 hold by construction. Creating a job, by either branch of REQ-203 or by REQ-208, is an insert that fails if the name exists.
- recurring A-9 (affects REQ-205, REQ-207, REQ-212, REQ-221–REQ-225): Overlap, misfire and orphan policies are fixed per job for a whole run.
- recurring A-13 (affects REQ-204, REQ-206, REQ-212, REQ-241, REQ-227): *(changed)* definitionHash is the hash of the code definition last applied. A runtime edit under AllowRuntimeOverride changes the stored definition but not the hash, so REQ-241 never fires because of a runtime edit. In `Recurring.tla` and in race cfgs with `SchedOn = FALSE` the definition has no schedule content: "the schedule changed" is a nondeterministic choice. The `…Sch` race cfgs give it content (A-32). A runtime edit is one value, "edited". A restore whose node's code has the stored hash keeps the stored definition, an edit included, and one whose node's code has another hash takes that code (REQ-206, run 10).
- recurring A-32 (affects REQ-204, REQ-206, REQ-212, REQ-227, REQ-241, INV-212): *(changed)* Schedule content (`SchedOn = TRUE`): two schedules, s1 and s2. Release v1's and v3's code use s1, and release v2's code uses s1 or s2, chosen per behaviour, so that two declaring releases can have the same or different schedules. A runtime job is added with s1, and an operator update sets either. A definition write "changes the schedule" when the schedule it sets differs from the stored one, judged against what its read saw (as written the two agree, because a write that lands saw the stored definition). A restore that keeps the stored definition keeps its schedule, and nextRunAt is computed from that schedule (run 10).
- recurring A-1 (affects REQ-215, REQ-216, REQ-227, REQ-204, REQ-206, REQ-241, INV-210, REQ-242): No clock. Each job keeps a count of due instants passed since nextRunAt was set (0, 1, "2 or more"), and time passing is a nondeterministic step. "nextRunAt computed from now" resets the count to 0.
- hosting A-23 (affects REQ-12, recurring REQ-236): The schema check and REQ-236 are one step. Between them, another node can only migrate the schema forward. REQ-236 reads name and origin only, and migrations only add (TECH-127), so a split step would read the same answer
- recurring A-14 (affects INV-209, REQ-232, REQ-236): Configuration-defined jobs are not modeled (INV-209 and REQ-232 are `may`), so REQ-236 is checked for code-defined names only.
- recurring A-16 (affects REQ-236): REQ-236's and REQ-210's "fail the host's start" is abstracted as the node staying down. The hosting module owns the node's states.
- recurring A-24 (affects REQ-236): Schemas are not modeled. The initial store holds no recurring job, which is what REQ-236 says a store without a Bellhop schema holds.

## Acceptance criteria

### AC-1 · REQ-208 · must

> When an operator adds a recurring job through IRecurringJobManager or the dashboard and no definition with its name exists, the system shall create a runtime-defined recurring job with nextRunAt computed from now.
>
> *Transition:* RecurringJob: (new) → Active · *Actor:* Operator

- Given no definition named tenant-7-export, when an operator adds it through IRecurringJobManager with a valid schedule and a payload, then it is stored Active with origin runtime (REQ-202), that payload, and nextRunAt equal to the schedule's next occurrence after now by the database clock (TECH-25, jobs INV-105).
- Given no misfire or overlap policy in the call, then RunOnce and Skip are stored (REQ-201).
- Given two jobs of the same job type added with different names and payloads, then both are stored, each with its own payload (REQ-221's notes, one per tenant).
- Given a definition with that name already exists, of any origin, then nothing is created (INV-211). Given the schedule is invalid, nothing is created either (REQ-209).
- Concurrency: given two adds of the same new name at once, then exactly one definition is stored and the other call gets INV-211's error (an insert keyed by name, recurring A-8). The same holds for an add racing a node start that creates the name (REQ-203): one definition, and the loser stores nothing.
- The dashboard's add is dashboard REQ-322 (ST-068).

### AC-2 · REQ-212 · must

> When an operator updates a runtime-defined recurring job, or a code-defined one marked AllowRuntimeOverride, the system shall store the new definition.
>
> *Transition:* RecurringJob: Active | Paused → Active | Paused · *Actor:* Operator

- Given a runtime-defined Active job, when an operator updates its payload and policies, then the new definition is stored, the job stays Active and nextRunAt is unchanged.
- Given the update changes the schedule, then nextRunAt becomes the new schedule's next occurrence after now, and no catch-up occurrence is created for the old schedule (REQ-227).
- Given the job is Paused, then it stays Paused after the update.
- Given a code-defined job marked AllowRuntimeOverride, then the update is stored and definitionHash is unchanged (REQ-241's notes). A later node start with unchanged code keeps the edit (REQ-204), and so does REQ-241.
- Given a code-defined job not marked AllowRuntimeOverride, then the update is rejected (REQ-211, SCN-205). Given an invalid schedule, the update is rejected and the stored definition is unchanged (REQ-209).
- Given the update's compare-and-set loses to another write (TECH-45), then nothing is changed by that write. INV-212 (ST-026) covers the reread.
- What an update of an Orphaned job returns is open question 3. What happens to waiting occurrences when the overlap policy or its maximum changes is open question 4.

### AC-3 · REQ-213 · must

> When an operator removes a runtime-defined recurring job, or an orphaned one of any origin, the system shall delete the definition.
>
> *Transition:* RecurringJob: Active | Paused | Orphaned → (removed) · *Actor:* Operator
>
> *Notes:* Decided by the owner on 2026-11-06: a code- or configuration-defined job that is not orphaned cannot be removed, because the next start would re-create it (INV-206).

- Given a runtime-defined job that is Active, and another that is Paused, when an operator removes each, then each definition is deleted and no longer listed.
- Given an Orphaned code-defined job, and an Orphaned configuration-origin job (written into the store directly), when an operator removes each, then each is deleted. If a node that declares the code-defined one runs later, the scheduler creates it again (REQ-203, ST-022).
- Given a code- or configuration-defined job that is Active or Paused, then the removal is refused (INV-206, SCN-212).
- Given the removal's compare-and-set loses to another write, then it deletes nothing (TECH-45).
- What removing a name that is not stored returns is open question 3. Waiting occurrences skipped with reason Removed: REQ-237 (ST-025).

### AC-4 · REQ-214 · must

> When an operator pauses a recurring job through the API or the dashboard, the system shall mark the job paused.
>
> *Transition:* RecurringJob: Active → Paused · *Actor:* Operator

- Given an Active job, when an operator pauses it through IRecurringJobManager, then it is Paused and nextRunAt is unchanged (SCN-217's step 1: a pause leaves nextRunAt unchanged).
- Given a code-defined job, then the pause is allowed (REQ-211's notes). A later node start keeps it Paused, with changed code (REQ-204) or unchanged code.
- Given the pause's compare-and-set loses to another write, then the job is not paused by that write. INV-212 (ST-026) covers the reread, which ends with the job Paused (SCN-216).
- Pausing a Paused or Orphaned job is open question 3. No occurrence on schedule while paused: INV-201 (ST-026). Waiting occurrences skipped with reason Paused: REQ-237 (ST-025). Missed instants recorded: REQ-242 (ST-026).

### AC-5 · REQ-215 · must

> When an operator resumes a paused recurring job, the system shall mark the job active and compute nextRunAt from now.
>
> *Transition:* RecurringJob: Paused → Active · *Actor:* Operator
>
> *Notes:* Decided by the owner on 2026-11-06: instants missed while paused are dropped, not caught up; 'from now' is confirmed. Maintenance is different: instants that fall due during maintenance go through the misfire policy (INV-210). refiner-model run 5 F-1: instants already missed when the job was paused are recorded by the pause (REQ-242); only those that fall due while it is paused are dropped without a record.

- Given an hourly job paused at 01:10 and resumed at 04:30, then it is Active, nextRunAt is 05:00, and no occurrence is created for 02:00, 03:00 or 04:00. The instants that fell due while it was paused are dropped, not caught up.
- Given the maintenance pause is on (ST-009) when the job is resumed, then it is still marked Active with nextRunAt from now (INV-210's notes).
- Given the resume's compare-and-set loses to another write, then the job is not resumed by that write (TECH-45).
- Resuming an Active or Orphaned job is open question 3.

### AC-6 · REQ-236 · must

> While a node is starting, if a code-defined or configuration-defined recurring job has the name of a stored runtime-defined recurring job, judged by each stored recurring job's name and origin only, with none stored where the store has no Bellhop schema yet, then the system shall fail the host's start with a message that names the job and says it is already defined at runtime.
>
> *Transition:* hosting.Node: Starting → StartupFailed · *Actor:* Host
>
> *Notes:* refiner-model 2026-11-06 F-6, decided by the owner on 2026-11-06: recurring job names are unique across origins, and a collision is an error on both sides (INV-211 for the API). Like REQ-210. hosting run 3 F-1 (recommended option): the check runs before the migration (hosting REQ-12), so it must work on whatever schema is stored. Name and origin are stored by every schema version, because migrations only add (TECH-127); a new database has no Bellhop tables and so no runtime-defined jobs, which must not fail the first start.

- Given a stored runtime-defined job nightly-export, Active or Paused, when a node starts whose code declares nightly-export, then the start fails, the node never reaches Running (hosting REQ-18), and the message names nightly-export and says it is already defined at runtime. Nothing is migrated or reconciled first (hosting REQ-12).
- Given the stored nightly-export is code-defined, then this check passes, and REQ-204 applies instead.
- Given a store with no Bellhop schema, then this check finds no stored jobs and passes, so the first start on a new database is not failed by it.
- Given a store at a schema version older than the node's that holds a runtime-defined job with a declared name (put into that state directly), then the check reads it and fails the start before migrating (hosting REQ-12; name and origin are stored by every schema version, TECH-127).
- Given a configuration-defined job with a stored runtime job's name, then the start fails the same way. ST-047 loads such jobs and keeps REQ-236 holding.
- Whether a node without the worker runs this check is open question 6.

### AC-7 · INV-206 · must

> If an operator removes a code-defined or configuration-defined recurring job that is not orphaned, then the system shall refuse with a message that the job would be re-created at the next start.
>
> *Notes:* Decided by the owner on 2026-11-06.

- Given nightly-cleanup is code-defined and Active, or Paused, when an operator removes it, then the call is refused with a message that the job would be re-created at the next start. Its state, nextRunAt and definition are unchanged (SCN-212).
- Given a configuration-origin job that is not orphaned (written into the store directly), then the removal is refused the same way.
- Property: over random sequences of removals, pauses, resumes, orphanings and restores across jobs of all three origins, a removal deletes a job only when the job is runtime-defined or Orphaned, and every other removal is refused with this message.
- Concurrency: given a removal that read the job as Orphaned, and a restore (REQ-206) that lands before the removal's write, then the removal's compare-and-set changes nothing (TECH-45). When the remover reads again it finds an Active or Paused code-defined job, and the removal is refused (INV-212, ST-026).

### AC-8 · INV-211 · must

> If an operator adds a recurring job through IRecurringJobManager or the dashboard with a name that is already stored, then the system shall reject the call with an error that names the existing job and its origin, and store nothing.
>
> *Notes:* refiner-model 2026-11-06 F-6, decided by the owner on 2026-11-06: names are unique across origins and a collision is an error on both sides (REQ-236 for starting nodes).

- Given nightly-export is stored as a code-defined job, when an operator adds a runtime job named nightly-export, then the call is rejected with an error that names nightly-export and its origin, code, and nothing is stored or changed (SCN-214). The same holds for a stored configuration-origin job (written into the store directly).
- Given nightly-export is stored as a runtime-defined job, and the call is an add, then it is rejected naming the runtime origin. Whether IRecurringJobManager's add-or-update counts such a call as an add or as an update (REQ-212) is open question 1.
- Concurrency: given several adds of one name at once, and an add racing a node start's create (REQ-203), then one definition is stored. Every losing add gets this error, and a losing create stores nothing (recurring A-8).
- Property: over random sequences of adds, removals and node starts, no add ever replaces or changes a stored job.

### AC-9 · REQ-209 · must

> If a schedule expression given through the API or the dashboard is invalid, or its time mode is Local without a valid IANA time zone, then the system shall reject the call with an error that says what is wrong and store nothing.

- Given an add through IRecurringJobManager with a schedule expression that TECH-23 does not accept, then the call is rejected with an error that says what is wrong with the expression, and no job is stored.
- Given time mode Local with no time zone, or with an id that is not a valid IANA time zone (TECH-24), then the call is rejected and the error says the zone is the problem.
- Given an update of a stored job with either fault, then the call is rejected and the stored definition, state and nextRunAt are unchanged.
- Given time mode Utc and no zone, then the call is accepted (REQ-200).
- Property: over random adds and updates with valid and invalid schedules and zones, every call that is accepted leaves a schedule that ST-003 can evaluate, and every rejected call leaves the store unchanged.
- The dashboard's forms reach this rule through ST-034, ST-068 and ST-072.

### AC-10 · REQ-211 · must

> If an operator edits a code-defined recurring job through the API or the dashboard and the job is not marked AllowRuntimeOverride, then the system shall reject the edit with a message saying the job is defined in code.
>
> *Notes:* Decided by the owner on 2026-11-06: 'edit' means changing the definition (schedule, time mode and zone, policies, payload). Pause, resume and trigger now are allowed on code-defined jobs; remove is refused (INV-206).

- Given nightly-cleanup is code-defined without AllowRuntimeOverride, when an operator changes its schedule through IRecurringJobManager, then the edit is rejected with a message saying the job is defined in code, and the stored definition, hash, state and nextRunAt are unchanged (SCN-205).
- The same holds for an edit of only the time mode and zone, only a policy, or only the payload.
- Given the same job, then pause and resume are accepted (REQ-214, REQ-215). Trigger now is accepted too (REQ-226, ST-024).
- Given the job is marked AllowRuntimeOverride, then the edit is stored (REQ-212).
- Property: over random edits of jobs of every origin, with and without AllowRuntimeOverride, a code-defined job's definition changes only through an edit of a job marked AllowRuntimeOverride, or through reconciliation (REQ-204, REQ-206, REQ-241).

### AC-11 · REQ-230 · must

> When an operator asks for a recurring job's next N occurrences, the system shall compute them from its schedule in its own time zone.

- Given an Active job whose schedule is daily at 03:00 in Local time mode with zone Europe/Berlin, and whose nextRunAt is in the future, when an operator asks for its next 3 occurrences, then they are 03:00 Berlin time on three consecutive days, as instants, and the first is nextRunAt.
- Given the same schedule in Utc time mode, then the occurrences are 03:00 UTC.
- Given the next occurrences cross a daylight-saving change, then they follow REQ-228 and REQ-229 (ST-003).
- Given a runtime edit of the schedule (REQ-212), then the next occurrences follow the stored, edited schedule.
- Property: for random schedules, zones and N, the list has N strictly increasing instants, each the schedule's next occurrence after the one before (TECH-25).
- Whether the list counts from now or from nextRunAt, which differ when nextRunAt has passed or the job is paused or orphaned, is open question 5.

INV-211 rejects an add whose name is stored, of any origin, and REQ-212 updates a stored runtime job, or a code-defined one marked AllowRuntimeOverride. The criteria hold for a new name, and for a code-defined name without AllowRuntimeOverride, which both rules reject. For a stored runtime-defined name, or a code-defined one with AllowRuntimeOverride, one reading updates and the other rejects. SCN-214 does not say whether nightly-export has AllowRuntimeOverride.
2. **Decide in delivery** · TECH-21, INV-206, INV-211, REQ-209, REQ-211: the method names and signatures, what list, next N occurrences and last outcome return, and how a refusal reaches the caller: an exception type or a result. Message wording beyond what the items require is not given either. All of these become public API that NFR-20 freezes.
3. **Decide in delivery** · REQ-212, REQ-213, REQ-214, REQ-215: what does a call return when the job is in a state its transition does not start from? That covers an update or resume of an Orphaned job, a pause of a Paused or Orphaned job, a resume of an Active job, and any call naming a job that is not stored. The transitions give only their from-states.
4. **Decide in delivery** · REQ-212, REQ-233, REQ-235: when an update changes the overlap policy, or lowers Queue's maximum below the number of occurrences now waiting, what happens to the waiting occurrences? REQ-211's notes let an edit change the policies, but the model fixes them for a whole run (recurring A-9), so this was never checked.
5. **Decide in delivery** · REQ-230: are the next N occurrences counted from now or from nextRunAt? And what is returned for a Paused or Orphaned job? The two readings differ when nextRunAt has passed, for example during maintenance (INV-210), or when the job is not active.
6. **Decide in delivery** · REQ-236: does a node without the worker run this check? Hosting REQ-12 runs it on every starting node, while REQ-203's notes say such a node does not declare recurring jobs. The same question is raised for REQ-210 in ST-022.
