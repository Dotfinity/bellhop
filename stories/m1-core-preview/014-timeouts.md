# ST-014 — Time out handlers that run too long

**Milestone:** M1 · **Epic:** m1-core-preview · **Priority:** must · **Depends on:** ST-013

## Context

Gives every job a timeout, DefaultJobTimeout (5 minutes) unless one is set by attribute, fluently or per enqueue (REQ-189). When a run lasts longer, the handler's cancellation token is signalled (REQ-137). A handler that is still running TimeoutGracePeriod later (REQ-187), or that throws OperationCanceledException within it, is abandoned if still running, and the attempt counts as an ordinary failure with reason Timeout: retried with backoff (REQ-138), or dead-lettered when attempts or the retry policy run out (REQ-186). REQ-189's notes record why: a job that ran silently for an hour under another library now times out.

Builds on ST-013: an abandoned handler keeps running in the process, and lease fencing (INV-128) makes its late result harmless; INV-128 must keep holding. Uses ST-011's retry policy and backoff, and keeps REQ-129 holding: an OperationCanceledException thrown after the timeout signal is a timeout, not REQ-129's failure (jobs A-5). For the same reason it keeps ST-011's REQ-131 holding: such an exception at the last attempt is dead-lettered by REQ-186 with reason Timeout, not by REQ-131. The timeout's precedence of attribute, fluent and per-enqueue values keeps ST-002's INV-123 holding. "Its cancellation was not requested" is built against what exists: ST-018 adds cancellation (REQ-136, REQ-190) and keeps REQ-138 holding; ST-017 keeps it holding at shutdown, where an OperationCanceledException thrown after both signals is a timeout (REQ-140's notes). Built on by ST-017 (the drain waits for a timed-out handler, hosting REQ-29) and ST-028 (spans and metrics). Recording an abandoned handler is REQ-191 (ST-018).

Lives in the core package's engine (TECH-112). The timeout is set with [Timeout] (TECH-17, ST-002), fluently (INV-123) or with EnqueueOptions' timeout (TECH-20, ST-007). Where DefaultJobTimeout and TimeoutGracePeriod are configured is open question 1.

## Acceptance criteria

### AC-1 · REQ-187 · must

> The system shall give a handler TimeoutGracePeriod, 30 seconds by default, after its timeout token is signalled before abandoning it (TimeoutGracePeriod).
>
> *Notes:* Decided by the owner on 2026-11-06.

- Given TimeoutGracePeriod is not configured and a handler ignores its token, when its timeout token is signalled, then the handler is not abandoned before 30 seconds have passed and is abandoned once they have (REQ-138, REQ-186).
- Given TimeoutGracePeriod is configured as 5 seconds, then the same holds with 5 seconds.

### AC-2 · REQ-189 · must

> The system shall give every job a timeout of DefaultJobTimeout, 5 minutes, unless one is set by attribute, fluently or per enqueue (DefaultJobTimeout).
>
> *Notes:* Decided by the owner on 2026-11-06. The source gave no default. A handler that ignores its token is abandoned TimeoutGracePeriod later (REQ-138, REQ-186). The docs must say so prominently, because a job that silently ran for an hour under another library will now time out.

- Given a job type with no [Timeout], no fluent timeout and no per-enqueue timeout, then its handler's token is signalled once a run has lasted longer than 5 minutes (REQ-137), and not before.
- Given [Timeout] on the job type, then that timeout is used; given a fluent timeout as well, the fluent one (INV-123); given a per-enqueue timeout, it is used over both (INV-123's notes).
- Whether DefaultJobTimeout itself can be changed is open question 1; zero, negative and infinite timeouts are open question 2.

### AC-3 · REQ-137 · must

> While a job is processing, when it has run for longer than its timeout, the system shall signal the handler's cancellation token.
>
> *Transition:* Job: Processing → Processing · *Actor:* system
>
> *Notes:* Decided by the owner on 2026-11-06: every job has a timeout, 5 minutes unless one is set (REQ-189). Long-running jobs must set a longer one.

- Given a job with a 1-minute timeout is processing, when its run has lasted longer than 1 minute by the fake clock, then the cancellation token passed to its handler (TECH-15) is signalled, the job is still Processing, and its lease is still renewed (REQ-126).
- Given the run has not lasted longer than its timeout, then the token is not signalled.
- Given a later attempt of the same job, then its timeout counts from that attempt's claim (`SignalTimeout` in `Jobs.tla` is per run).

### AC-4 · REQ-138 · must

> While a job is processing, its timeout token was signalled and its cancellation was not requested, if the handler is still running TimeoutGracePeriod later or throws OperationCanceledException within it, and the attempt number is below maxAttempts and the retry policy allows another attempt, then the system shall abandon the handler if it is still running, mark the job failed with reason Timeout and set retryAt from the backoff.
>
> *Transition:* Job: Processing → Failed · *Actor:* system
>
> *Notes:* Decided by the owner on 2026-11-06: TimeoutGracePeriod is 30 s (REQ-187) and a timeout is an ordinary failed attempt: it is retried, or dead-lettered when attempts run out (REQ-186). An abandoned handler keeps running in the process; lease fencing (INV-128) makes its eventual result harmless. Resolved after refiner-model 2026-11-06 F-6 (recommended option): a job whose cancellation was requested is never retried; REQ-136 or REQ-190 marks it cancelled.

- Given attempt 1 of 5 and a handler that ignores its token, when TimeoutGracePeriod passes after the timeout signal, then the job is Failed with reason Timeout and retryAt from the backoff (REQ-100), and the handler is abandoned: it keeps running in the process, holds no claim, and its node may claim another job in its place (INV-106).
- Given the handler throws OperationCanceledException within the grace period, then the job is Failed with reason Timeout and retryAt from the backoff, with nothing to abandon.
- Given the abandoned handler later returns or throws, then its write is refused and the job keeps the state this rule gave it (INV-128).
- Given the handler returns normally within the grace period, then this rule does not apply and the job is Succeeded (REQ-127); given it throws another exception within it, then REQ-129 or REQ-131 decides.
- Given the attempt number has reached maxAttempts or the retry policy declines, then REQ-186 applies instead.

### AC-5 · REQ-186 · must

> While a job is processing, its timeout token was signalled and its cancellation was not requested, if the handler is still running TimeoutGracePeriod later or throws OperationCanceledException within it, and the attempt number has reached maxAttempts or the retry policy declines another attempt, then the system shall abandon the handler if it is still running and move the job to dead-lettered with reason Timeout.
>
> *Transition:* Job: Processing → DeadLettered · *Actor:* system
>
> *Notes:* Decided by the owner on 2026-11-06: a timeout is an ordinary failure, so exhausted attempts dead-letter it. Complementary guard to REQ-138. Resolved after refiner-model 2026-11-06 F-6 (recommended option): a job whose cancellation was requested is marked cancelled instead (REQ-136, REQ-190).

- Given attempt 5 of 5, or a retry policy that declines, and a handler that ignores its token, when TimeoutGracePeriod passes after the timeout signal, then the job is DeadLettered with reason Timeout and the handler is abandoned; its later result is refused (INV-128).
- Given the handler throws OperationCanceledException within the grace period at its last attempt, then the job is DeadLettered with reason Timeout.
- Property: over random timeouts, grace-period outcomes (still running, OperationCanceledException, another exception, a normal return), attempt numbers and policy answers, exactly one of REQ-127, REQ-129, REQ-131, REQ-138 and REQ-186 decides each run, with that rule's outcome (jobs A-5).
