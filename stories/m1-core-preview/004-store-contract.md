# ST-004 — Define the job store contract and the in-memory store

**Milestone:** M1 · **Epic:** m1-core-preview · **Priority:** must · **Depends on:** ST-002

## Context

Defines the store abstraction that every store implements: one asynchronous IJobStore whose methods document their semantics (TECH-31) and the secondary index IJobIndex on which tag and correlation-id search are built (TECH-32). It ships the deterministic in-memory store in the core package (TECH-43), which every M1 behaviour story builds on before PostgreSQL exists, and makes System.TimeProvider the only source of time in the core (TECH-12), so the engine and the in-memory store can be driven with fake time.

Builds on ST-002 (job names and payloads). ST-005 falls back to the in-memory store when no store is configured (hosting REQ-15), and from ST-007 on every M1 behaviour story adds the IJobStore operations it needs, documents them and implements them on the in-memory store (TECH-31). ST-027's test harness drains jobs over this store (TECH-102); ST-029 and ST-030 implement both contracts on PostgreSQL; ST-033 and ST-044 build search and tags on IJobIndex; ST-054's conformance suite tests both contracts, and ST-055 to ST-058 implement them on SQL Server, SQLite and Redis. Those stories keep TECH-31, TECH-32 and TECH-43 holding (ST-008 keeps TECH-31 too). TECH-32 is owned before ST-033 and ST-044 build on it, TECH-43 before ST-005 and ST-027 use the in-memory store, and TECH-12 before ST-007 first reads time: each is a contract those stories code against, and REQ-36 puts the in-memory store in M1.

Lives in the core package, Bellhop: IJobStore (TECH-31), IJobIndex with AddAsync(jobId, index, value), RemoveAsync, QueryAsync(index, value, page) and CountAsync (TECH-32), the in-memory store (TECH-43), and System.TimeProvider as the time source (TECH-12). The specs name no IJobStore method; each story names the ones it adds. Whether IJobIndex is part of IJobStore, the rest of IJobIndex's signatures, the in-memory store's public name and how a TimeProvider is supplied are open questions 1 to 4.

## Acceptance criteria

### AC-1 · TECH-12 · must

> **Time source** — The core package shall take all time from System.TimeProvider.

- Build check: CI fails on any use, in the core package, of a clock other than TimeProvider: DateTime.Now and UtcNow, DateTimeOffset.Now and UtcNow, Stopwatch, Environment.TickCount, and timers or delays that do not take the TimeProvider.
- Test: with a FakeTimeProvider supplied, the in-memory store's now is the fake time; advancing the fake time is the only way time passes for the store, and real time passing changes nothing.
- How the TimeProvider is supplied, and what is used when none is, is open question 4.

### AC-2 · TECH-31 · must

> **IJobStore** — Every store shall implement only the single asynchronous IJobStore interface, which documents the semantics of each of its methods.
>
> *Notes:* The under-25-methods figure is a design target, not a hard limit.

- Test: a reflection check over IJobStore fails if any of its methods is not asynchronous (does not return a task or an asynchronous stream).
- Inspection: IJobStore is one interface; each method's documentation states what it reads and changes, what it returns and what it does in its failure cases; the method count is recorded in Notes against the design target of fewer than 25 (TECH-31's notes: a target, not a limit).
- Given the in-memory store, then the engine, and from ST-031 on the dashboard, reach it through IJobStore and IJobIndex alone: no other store interface is needed for it to work.
- Whether IJobIndex is part of IJobStore or a second interface beside it is open question 1.

### AC-3 · TECH-32 · must

> **IJobIndex** — Every store shall implement the secondary index contract IJobIndex (AddAsync(jobId, index, value), RemoveAsync, QueryAsync(index, value, page), CountAsync), on which tags and correlation-id search are built.

- Given AddAsync(j1, i, v) and AddAsync(j2, i, v), when QueryAsync(i, v, page) is called, then both jobs are returned, and CountAsync for i and v gives 2.
- Given a job added under index i with value v, then a query for i with another value, or for another index with value v, does not return it.
- Given RemoveAsync for j1's entry, then j1 is no longer returned or counted for it.
- Property: after random adds and removes, paging through every page of a query returns each job indexed under i and v exactly once, and CountAsync gives that number.
- Inspection: the in-memory store implements IJobIndex.
- RemoveAsync's and CountAsync's parameters, the page's shape and order, adding one entry twice and case sensitivity are open question 2.

### AC-4 · TECH-43 · must

> **In-memory store** — The core package shall include a deterministic in-memory job store.

- Inspection: the in-memory store is part of the core package; using it needs no other package.
- Property: the same random sequence of store calls, run twice against new in-memory stores with a FakeTimeProvider started at the same instant and advanced the same way, gives the same job states, in the same order, for the same jobs, and the same query results.
- Given no call is made, then nothing in the store changes, however far the TimeProvider advances: only calls change its contents.
- Whether job ids must repeat as well is open question 3.

## Open questions

1. **Decide in delivery** · TECH-31, TECH-32: is IJobIndex part of IJobStore (inherited or exposed by it) or a second interface that every store implements beside it? TECH-31 says a store implements "only the single" IJobStore interface, and TECH-32 that every store implements IJobIndex.
2. **Decide in delivery** · TECH-32: the parameters of RemoveAsync and CountAsync, the shape of a page and the order of its results, whether adding the same job, index and value twice counts once, and whether values are compared case-sensitively. Store authors implement this contract (TECH-105), and NFR-20 freezes it.
3. **Decide in delivery** · TECH-43, hosting REQ-15: does "deterministic" include job ids (the same calls give the same ids), and what is the in-memory store's public name, for an application that selects it explicitly? REQ-15 covers only the fallback.
4. **Decide in delivery** · TECH-12, TECH-103: how does an application or a test supply the TimeProvider (a DI registration or an option), and what is used when none is? Bellhop.Testing's FakeTimeProvider integration (ST-027) depends on it.
