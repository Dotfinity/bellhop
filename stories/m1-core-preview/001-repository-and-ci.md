# ST-001 — Set up the repository, packages and CI gates

**Milestone:** M1 · **Epic:** m1-core-preview · **Priority:** must · **Depends on:** –

## Context

Sets up the solution, the package layout and the CI gates that every later story is built inside. The gates enforce the standing constraints this story owns: both LTS target frameworks and no .NET Framework (TECH-1, TECH-2), a trimming-safe core (TECH-3), the core's dependency surface (TECH-8, TECH-9), one version for every first-party package with exact-version dependencies between them (TECH-50), no external lock service or lock library (TECH-51) and the Bellhop naming rules (TECH-124). It also puts the project's terms in place: MIT for every package (NFR-37), a vulnerability scan that fails CI (NFR-44), DCO sign-off without a CLA (NFR-45) and a README with the roadmap and best-effort triage (NFR-46). Together they are product principle P8, trustworthy versioning and licensing (hosting REQ-2).

Builds on nothing. ST-002 builds on it directly, and every later story inherits its gates, because TECH-1, TECH-2, TECH-3, TECH-8, TECH-9, TECH-50, TECH-51 and TECH-124 are standing constraints. A package added later (Bellhop.Testing in ST-027, Bellhop.PostgreSql in ST-029, Bellhop.Dashboard in ST-031) falls under the same gates as soon as it exists, because the rules say "every package".

Lives at the repository root: the solution, the core package Bellhop (TECH-124; what it contains is TECH-112, owned by ST-076), the CI configuration, the README, the licence and the governance docs, and SECURITY.md for security reports (NFR-46's notes). The specs name no CI system, scanner or DCO tool. Which Microsoft.Extensions.* packages the core may use is open question 1, and the version numbers of the M1 preview packages are open question 5.

### Background

- **REQ-2** (hosting, info): The system shall follow the product principles P1 to P9: three lines to a working system; one obvious way to define a job; correct under concurrency by construction; boring storage; secure and explicit by default; nothing is silent; testable without statics; trustworthy versioning and licensing; build in what everyone installs.
- **REQ-36** (hosting, info): The system shall be delivered in three milestones: M1 core preview (job model, IJobClient, in-memory and PostgreSQL stores, fire-and-forget, delayed and recurring jobs, retries and dead letters, leases and recovery, OpenTelemetry, health check, Bellhop.Testing, read-only dashboard); M2 1.0 (SQL Server, SQLite and Redis stores, continuations, chains and batches, unique and concurrency keys, the full dashboard, BLT-1 to BLT-12, EF Core enqueue, analyzers, conformance suite, docs, benchmark); M3 1.x (BLT-13 to BLT-19, Tier 2 Redis-compatible servers, Garnet fixture, CLI, Native AOT verification, community stores).
- **REQ-8** (hosting, info): The system shall not ship in v1: first-party MongoDB or MySQL stores, a hosted SaaS control plane, vendor-specific notification SDKs, remote execution agents, arbitrary script execution from the dashboard, Windows-specific features, or Hangfire's expression-based Enqueue(() => ...) ## Acceptance criteria

### AC-1 · TECH-1 · must

> **Target frameworks** — Every Bellhop package shall target .NET 8 and .NET 10 (both LTS).
>
> *Version:* net8.0, net10.0

- Build check: CI builds and tests the solution for net8.0 and net10.0.
- Package check: after packing, CI opens every first-party package and fails unless its target frameworks, read from its lib/ and tools/ assets or from its nuspec dependency groups, include both net8.0 and net10.0. The tools/ folder covers a dotnet tool such as Bellhop.Cli (TECH-122).
- Given a packable project that leaves out either framework, then CI fails.
- Whether analyzer assemblies count as a target is open question 3.

### AC-2 · TECH-2 · must

> **No .NET Framework** — No Bellhop package shall target .NET Framework.

- Package check: the same check, over the same assets and dependency groups, fails if any first-party package has a .NET Framework target (net48 or any other .NET Framework moniker).
- Given a project that adds a .NET Framework target, then CI fails.

### AC-3 · TECH-3 · must

> **Trimming-safe core** — The core package shall be safe for IL trimming.

- Build check: the core package is built for both target frameworks with the .NET trimming analysis on, and CI fails on any trim warning reported for the core package.
- Given a change that adds an unannotated trim-unsafe call to the core, then CI fails.
- Whether a trim-unsafe path may be annotated so that an application using it is warned instead, as reflection-based payload serialization without a JsonSerializerContext would need (TECH-5, TECH-6), is open question 2. The criteria above hold under either answer.

### AC-4 · TECH-8 · must

> **Core dependency surface** — The core package shall depend only on the BCL and Microsoft.Extensions.* abstractions.
>
> *Rationale:* Keeps provider clients such as Npgsql or StackExchange.Redis out of the core (ADR-1).

- Dependency audit: CI reads the core package's direct and transitive dependencies and fails on any package that is neither part of the BCL nor a Microsoft.Extensions.* package.
- Given a change that adds a provider client such as Npgsql or StackExchange.Redis, or any third-party package, to the core, then CI fails (TECH-8's rationale, ADR-1).
- Whether only the Microsoft.Extensions.*.Abstractions packages are allowed is open question 1; the audit's allow list follows the answer.

### AC-5 · TECH-9 · must

> **No ASP.NET Core or EF Core in core** — The core package shall not depend on ASP.NET Core or Entity Framework Core.

- Dependency audit: the same audit fails if the core package depends, directly or transitively, on a Microsoft.AspNetCore.* or Microsoft.EntityFrameworkCore.* package, or has a framework reference to ASP.NET Core.
- Given such a reference is added, then CI fails.

### AC-6 · TECH-50 · must

> **Package versioning** — All first-party NuGet packages shall ship with the same version number and declare exact-version dependencies on each other.

- Package check: after packing, CI fails unless every first-party package has the same version and every dependency of one first-party package on another is declared as that exact version, not as a minimum or a range.
- Given two packages packed with different versions, or a first-party dependency declared as a minimum version, then CI fails.
- Which version numbers the M1 preview packages carry is open question 5.

### AC-7 · TECH-51 · must

> **No external lock service** — No first-party package shall require an external lock service or a distributed-lock library such as DistributedLock; all coordination shall live in the job store.
>
> *Notes:* Handler code may still use DistributedLock for its own resources; the docs show how (NFR-29).

- Dependency audit: CI fails if any first-party package depends, directly or transitively, on DistributedLock or any of its packages.
- Inspection: the reviewer lists every first-party package's direct and transitive dependencies, confirms that none is a distributed-lock library (DistributedLock is only one example), and records the list in Notes.
- Inspection, recorded in Notes: no first-party package needs an external lock service to run; coordination is done through the job store (for example the store-native migration lock, TECH-126).
- Given a documentation sample whose handler uses DistributedLock for its own resources (NFR-29), then the gate does not fail: samples are not first-party packages (TECH-51's notes).

### AC-8 · TECH-124 · must

> **Product name and root namespace** — The packages shall use the product name Bellhop, the root C# namespace Bellhop and package ids of the form Bellhop and Bellhop.<Area>, such as Bellhop.PostgreSql and Bellhop.Dashboard.
>
> *Notes:* Decided by the owner on 2026-11-06 (§9 Q1).

- Package check: CI fails unless every first-party package id is Bellhop or has the form Bellhop.<Area>, where <Area> is one or more dot-separated segments (Bellhop.PostgreSql, Bellhop.Storage.Conformance from TECH-105), and every public type in a first-party assembly is in the namespace Bellhop or a namespace under it, apart from the registration extension classes that open question 4 is about.
- Given a package id or a public namespace outside that form, then CI fails.
- Inspection: the package metadata names the product Bellhop.

### AC-9 · NFR-37 · must

> **Licence** — The project shall license every package under MIT, permanently.
>
> *Measure:* every package declares MIT; the governance docs commit to MIT for all future versions · *Verification:* inspection

- Inspection: the reviewer checks that every first-party package declares the MIT licence in its metadata, that the repository holds the MIT licence text, and that the governance docs commit to MIT for all future versions, and records the files in Notes.
- The package check (TECH-50) also fails on a package that does not declare MIT, so packages added later keep the measure.

### AC-10 · NFR-44 · must

## Open questions

1. **Decide in delivery** · TECH-8: does "Microsoft.Extensions.* abstractions" allow only the *.Abstractions packages, or any Microsoft.Extensions.* package? The core's own items need packages that are not abstractions: HTTP jobs send through Microsoft.Extensions.Http (TECH-113, in the core by TECH-112), options are bound and validated with ValidateOnStart (TECH-10), and the health check is built on Microsoft.Extensions.Diagnostics.HealthChecks (TECH-101).
2. **Decide in delivery** · TECH-3, TECH-5, TECH-6: does "safe for IL trimming" mean that the core builds without trim warnings, with trim-unsafe paths annotated so that an application using them is warned, or that an application using the defaults trims without warnings? The default System.Text.Json serializer uses reflection unless a JsonSerializerContext is supplied, and only Native AOT (TECH-4) asks for one.
3. **Decide in delivery** · TECH-1, TECH-2: do analyzer assemblies count as a package target? The core package contains the analyzers (TECH-112; TECH-107 to TECH-111, ST-053), and the compiler loads analyzers built for netstandard2.0, which is neither net8.0 nor net10.0.
4. **Decide in delivery** · TECH-124: may the registration extension classes (AddBellhop, MapBellhopDashboard) sit in the Microsoft namespaces they extend, as many libraries do, or must every public type be under Bellhop? The check leaves those classes out until this is answered.
5. **Decide in delivery** · TECH-50: which version numbers do the M1 preview packages carry? REQ-36 calls M1 a preview, and the SemVer promise (NFR-20) is owned by the 1.0 release (ST-076).
6. **Decide in delivery** · NFR-44: how is "keep dependencies current" checked? The Measure covers only the vulnerability scan, so no criterion says when a dependency counts as out of date.
