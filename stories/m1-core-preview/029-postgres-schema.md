# ST-029 — Create and migrate the PostgreSQL schema

**Milestone:** M1 · **Epic:** m1-core-preview · **Priority:** must · **Depends on:** ST-016

## Context

Gives the PostgreSQL store its own small schema, "bellhop" by default, created and upgraded at startup by embedded, versioned, idempotent migrations (TECH-46), with the exact SQL exported for DBAs (TECH-47), concurrent migrations serialised by a PostgreSQL advisory lock (TECH-126) and migrations that only add within a major version, so rolling deploys keep working (TECH-127). It is the first real store under ST-006's and ST-016's schema rules, built with plain ADO.NET and needing no DbContext (TECH-36, TECH-48), on the reference store of TECH-37.

Builds on ST-016 (the migration lock and idempotence, REQ-24, REQ-42, REQ-56, generic over the store) and through it on ST-006 (schema check and AutoMigrate, REQ-22, REQ-23) and ST-004 (IJobStore, TECH-31). ST-030 builds on it with the job and recurring operations; ST-055 and ST-056 (SQL Server, SQLite) keep TECH-36, TECH-46, TECH-47, TECH-126 and TECH-127 holding for their stores. TECH-36 is inferred M2 but owned here: it applies to the PostgreSQL store (TECH-37), which hosting REQ-36 puts in M1, so it must hold from the first SQL store; ST-055 and ST-056 build on it as a rule already in place.

Lives in Bellhop.PostgreSql (TECH-37, TECH-124), which reaches PostgreSQL through Npgsql, the provider client TECH-8's rationale keeps out of the core. It adds the embedded migrations, BellhopSchema.GetScript(provider, fromVersion) and the parts of IJobStore that startup uses: reading the schema version, migrating and the advisory lock. The specs do not name how an application selects this store, the option for the schema name, the package that holds BellhopSchema, or the path REQ-23's message shows (open questions 1 to 3).

## Acceptance criteria

### AC-1 · TECH-36 · must

> **SQL data access** — The SQL stores shall use plain ADO.NET, without EF Core or Dapper.

- Dependency audit in CI: the resolved dependency graph of Bellhop.PostgreSql, transitive packages included, contains no Entity Framework Core package and no Dapper package. The build fails if one appears.
- Inspection: every statement the store runs goes through ADO.NET connections and commands. The reviewer records the files checked in Notes.

### AC-2 · TECH-37 · must

> **PostgreSQL store** — The Bellhop.PostgreSql package shall use PostgreSQL as the reference store implementation.
>
> *Version:* the three most recent major versions at each Bellhop release
>
> *Notes:* Decided by the owner on 2026-11-06: the last three major versions. §9 Q2 confirmed: PostgreSQL is the reference store in M1 and SQL Server follows in M2.

- The package id is Bellhop.PostgreSql (TECH-124). ST-030 runs every M1 store-level test against it, which is what makes it the reference store.
- CI matrix: this story's tests and ST-030's run against each of the three most recent PostgreSQL major versions at the time of a Bellhop release, and all three pass before a release. The M1 preview's three versions are recorded in ST-037's Notes.
- What the store does on a major version outside those three is open question 4.

### AC-3 · TECH-46 · must

> **Embedded migrations** — Each SQL store shall own a small schema in a configurable schema or prefix, "bellhop" by default, created and upgraded by embedded, versioned, idempotent migrations.
>
> *Notes:* Six tables is a design target.

- Given an empty database and AutoMigrate on (its default, hosting REQ-21), when a node starts, then the migrations create the schema under the name "bellhop", the stored schema version equals the expected version (REQ-22), and no Bellhop table, index or other object exists outside that name.
- Given the schema name is configured to another value, when a node starts on an empty database, then every Bellhop object is created under that value and none under "bellhop". How the name is configured and which values are valid is open question 1; a value that fails validation fails the start with a message that names the option (hosting REQ-9).
- Given a database at an older schema version, when a node with AutoMigrate on starts, then only the migrations after the stored version run, and a schema diff against a database migrated from empty shows no difference.
- Given every migration has been applied, when any of them is applied again, then the schema is unchanged (REQ-24).
- Given a migration was interrupted part-way (the node's connection terminated during it), when a node starts again, then it reaches the expected version and the schema diff against a clean migration shows no difference (REQ-24).
- Inspection: the migrations ship inside the Bellhop.PostgreSql assembly; a node migrates with no file from outside the package present.
- Six tables is a design target, not a pass condition: the table count is recorded in Notes.
- Whether PostgreSQL gets a schema, a table prefix or a choice of either is open question 5; the criteria above hold under every reading.

### AC-4 · TECH-47 · must

> **Schema script export** — The SQL stores shall provide BellhopSchema.GetScript(provider, fromVersion), which emits the exact SQL for DBAs.

- Given a database at stored version v and AutoMigrate off, when the script that BellhopSchema.GetScript returns for PostgreSQL from v is applied by hand, then a node starts on it without migrating (REQ-22, REQ-23), and a schema diff against a database the node migrated itself shows no difference: the script is the exact SQL.
- Given an empty database, the script from the start gives the same schema as a node migrating from empty. How the start is asked for is open question 2.
- Given the script was applied, when it is applied again, then the schema is unchanged (REQ-24).
- How the script follows a configured schema name, when GetScript takes none, and what it does with an unknown or newer fromVersion, are open question 2.

### AC-5 · TECH-48 · must

> **No DbContext required** — No store shall require the application to register, expose or migrate an Entity Framework Core DbContext.

- Given a host with AddBellhop, the PostgreSQL store, AddWorker and one job type, and no Entity Framework Core DbContext registered anywhere, when it starts on an empty database, then it migrates, reaches Running and runs an enqueued job to Succeeded.
- The TECH-36 dependency audit also shows that Bellhop.PostgreSql references no Entity Framework Core package. This is a standing rule: ST-055, ST-056 and the Redis stories keep it for their stores.

### AC-6 · TECH-126 · must

> **Store-native migration lock** — Each store shall serialise schema migrations with a lock native to that store: a PostgreSQL advisory lock, SQL Server sp_getapplock, a SQLite write transaction, or a Redis key set with NX and an expiry.
>
> *Notes:* Decided by the owner on 2026-11-06. Uses no lock library, so TECH-51 still holds.

- Given several nodes start at the same moment with AutoMigrate on against a database at an older version, then at any instant at most one of them holds the migration lock, it is a PostgreSQL advisory lock (observed in pg_locks), the others wait for it, then re-read the schema version and apply nothing (REQ-42), and each migration ran once.
- Given the node holding the lock is killed, or its connection terminated, while it migrates, then PostgreSQL releases the lock, a waiting node takes it, re-reads the version and completes the migration (REQ-56, REQ-24), and no node stays waiting.
- Given the node holding the lock leaves starting for any reason, then it releases the lock first (REQ-56) and another node can take it. What a node does when a migration statement fails is open question 6.
- Inspection: the lock is taken with PostgreSQL's advisory lock functions, and no lock library is referenced (TECH-51, ST-001's audit). Recorded in Notes.

### AC-7 · TECH-127 · must

> **Additive migrations within a major version** — Migrations within one major version shall only add schema objects or widen existing ones, so that library version N keeps working on schema N+1 until its nodes are replaced; removals wait for the next major version.
>
> *Notes:* Decided by the owner on 2026-11-06 as part of the accepted schema range (expected version or one older).

- CI check over the embedded migrations: within one major version, a migration after the first only creates objects or widens existing ones; a migration that drops, renames or narrows a table, column, index or constraint fails the check. M1 has nothing to compare against yet, but the check is in place for the next migration.
- From the second schema version on, CI runs the previous release's PostgreSQL store tests against the new schema, and they pass: library version N keeps working on schema N+1. The mixed-version conformance run is NFR-18 (ST-054).
- Removals within a major version are refused by the same check; a removal is planned for the next major version instead.
