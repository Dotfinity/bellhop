# ST-007 — Enqueue and schedule jobs

**Milestone:** M1 · **Epic:** m1-core-preview · **Priority:** must · **Depends on:** ST-006

## Context

Delivers enqueue and schedule through IJobClient (TECH-19) and EnqueueOptions (TECH-20). A job is stored as enqueued (REQ-120), as scheduled when its time is in the future by the database clock (REQ-121), or as enqueued at once when it is not (REQ-182); a worker promotes due scheduled jobs (REQ-122) exactly once however many nodes run (INV-115), deciding against the database clock (INV-105). A payload above PayloadSoftLimit is stored with a warning and one above PayloadHardLimit is rejected (REQ-105, REQ-147, REQ-148, SCN-116), and a database transaction passed to a store without transactional enqueue is rejected (REQ-153) by reading the store's capability set (TECH-33). Promotion is the first background duty, so hosting REQ-40 (no duty without a worker) is owned here.

Builds on ST-006: promotion starts with the worker when the node is marked running, so hosting REQ-18 keeps holding. It also keeps INV-123 (ST-002) holding: a queue or priority given per enqueue beats both the attribute and the fluent value (INV-123's notes), and without one the fluent value still beats the attribute. ST-008 claims what this story enqueues; ST-011 adds failed jobs waiting for a retry to the promotion (INV-115); ST-019 adds unique keys to enqueue and schedule (REQ-120, REQ-121, REQ-182; jobs A-15 counts a REQ-182 call as one that schedules); ST-030 proves INV-105 and INV-115 on PostgreSQL; ST-038, ST-039 and ST-040 give TECH-19's continuation, chain, batch, bulk, waiting and result methods their behaviour; ST-041 adds transactional enqueue (INV-101) and ST-042 the concurrency key; ST-057 lowers the hard limit on Redis (redis REQ-513) and reports Redis's capabilities (redis REQ-512); and every later background duty keeps REQ-40 holding (ST-021, ST-022, ST-026, ST-049, ST-060, ST-071, ST-078, ST-081). Failed jobs are built against what exists: INV-115's test writes failed jobs with a due retryAt into the store directly. TECH-20 and TECH-33 are contracts owned before ST-019, ST-041 and ST-057 build on them. TECH-33 is inferred M2 but owned here: EnqueueOptions carries an explicit database transaction from M1 (TECH-20), so REQ-153 and the capability set it reads must exist in M1, where REQ-36 puts IJobClient; no M1 store reports transactional enqueue, which comes with ST-041 (TECH-49's notes: transactional enqueue is M2).

Lives in the core package, Bellhop: IJobClient (TECH-19), EnqueueOptions (TECH-20), the capability set on IJobStore (TECH-33) and the promotion duty that AddWorker registers (TECH-11, TECH-128). The in-memory store implements the new store operations, and its clock, the TimeProvider (TECH-12), is the database clock. The job id's type, what GetAsync returns, the exception types and the capability set's shape are open question 5.

## Acceptance criteria

### AC-1 · REQ-105 · must

> The system shall apply a payload soft limit of PayloadSoftLimit = 64 KB and a hard limit of PayloadHardLimit = 1 MB by default.
>
> *Notes:* The Redis store lowers the hard limit to 256 KB (REQ-513).

- Given the defaults, then a payload of 64,000 bytes is stored without a warning, one of 65,537 bytes is stored with a warning (REQ-147), one of 1,000,000 bytes is stored, and one of 1,048,577 bytes is rejected (REQ-148).
- Given PayloadHardLimit configured as 2 MB, then a 1.5 MB payload is stored with a warning; given PayloadSoftLimit configured as 128 KB, then a 100 KB payload is stored without one.
- Between those sizes the readings of KB and MB differ (open question 1); no criterion is set there. The Redis store's lower default is redis REQ-513 (ST-057).

### AC-2 · REQ-120 · must

> When an application enqueues a job, the system shall store the job as enqueued and return its job id.
>
> *Transition:* Job: (new) → Enqueued · *Actor:* Application

- Given a node with the client, when the application enqueues a job, then EnqueueAsync returns a job id only once the job is stored, and GetAsync with that id shows the job Enqueued with its stable name (REQ-101), its payload and its queue.
- Given EnqueueOptions with a queue, then the job is stored in that queue, over the attribute's and the fluent value (INV-123's notes).
- Property: concurrent enqueues from several tasks and nodes each return a different id, and every returned id is a stored job.
- Given a node with only the client, then enqueue works the same (hosting REQ-52).
- Which queue a job without one goes to is open question 4, and what a call does when the store does not answer is open question 6.

### AC-3 · REQ-121 · must

> When an application schedules a job for a point in time or after a delay that is still in the future according to the database clock, the system shall store the job as scheduled with scheduledAt set to that time, or to now plus the delay, and return its job id.
>
> *Transition:* Job: (new) → Scheduled · *Actor:* Application
>
> *Notes:* Decided by the owner on 2026-11-06: a time that is not in the future is REQ-182.

- Given the database clock at T, when the application schedules a job at T plus one hour, then it is stored Scheduled with scheduledAt T plus one hour, and its id is returned.
- Given a delay of ten minutes, then scheduledAt is the database time of the call plus ten minutes, even when the node's clock differs from the database clock (INV-105).
- Given the node's clock is behind the database clock and the requested time is in the future by the node's clock but not by the database clock, then the job is not stored Scheduled (REQ-182 applies).

### AC-4 · REQ-122 · must

> While a job is scheduled, when its scheduledAt has passed according to the database clock, the system shall move the job to enqueued.
>
> *Transition:* Job: Scheduled → Enqueued · *Actor:* system

- Given a Scheduled job with scheduledAt S, when the database clock has passed S and a worker node runs promotion, then the job is Enqueued.
- Given the database clock has not reached S, then the job stays Scheduled, even when the node's clock has passed S (INV-105).
- Given only nodes without the worker run, then the job stays Scheduled however far the clock moves (REQ-40).
- How soon after S promotion runs is open question 8.

### AC-5 · REQ-147 · must

> When an application enqueues or schedules a job whose payload is larger than PayloadSoftLimit and not larger than PayloadHardLimit, the system shall store the job and log a warning with its size.
>
> *Transition:* Job: (new) → Enqueued | Scheduled · *Actor:* Application

- Given a payload above PayloadSoftLimit and not above PayloadHardLimit under both readings of KB and MB (for example 100 KB with the defaults), when it is enqueued or scheduled, then the job is stored, Enqueued or Scheduled as the call says, and one warning is logged that gives its size.
- Given a payload not above PayloadSoftLimit, then no size warning is logged.

### AC-6 · REQ-182 · must

> When an application schedules a job for a time that is not in the future according to the database clock, or with a zero or negative delay, the system shall store the job as enqueued at once, with scheduledAt recording the requested time, and return its job id.
>
> *Transition:* Job: (new) → Enqueued · *Actor:* Application
>
> *Notes:* Decided by the owner on 2026-11-06: no wait for the next scheduler pass.

- Given the database clock at T, when the application schedules a job at T minus one hour, or at T exactly, then it is stored Enqueued at once with scheduledAt recording the requested time, and its id is returned; it can be claimed without waiting for a promotion pass (REQ-182's notes).
- Given a zero delay, then the job is stored Enqueued with scheduledAt at the database time of the call.
- Given the node's clock is ahead of the database clock and the requested time is in the past by the node's clock but in the future by the database clock, then the job is stored Scheduled (REQ-121).
- What scheduledAt records for a negative delay is open question 7.

### AC-7 · INV-105 · must

> The system shall decide claims, lease expiry and due times against the database clock, never a node's local clock.

- Property: with the store's clock set apart from the node's TimeProvider by random offsets in both directions, every due-time decision this story makes (REQ-121, REQ-122, REQ-182) matches the decision computed from the store's clock and never one computed from the node's.
- Claims and lease expiry are decided in ST-008 (leaseExpiresAt from the database time, REQ-123) and ST-013 (REQ-132), which run the same property; ST-030 runs it on PostgreSQL.

### AC-8 · INV-115 · must

> The system shall promote each due scheduled or failed job exactly once however many worker nodes run, without relying on leader election for correctness.

- Concurrency test: several worker nodes in one process share one store that holds many due Scheduled jobs and many Failed jobs whose retryAt has passed (written into the store directly); with every node running promotion at once, over and over, each job leaves Scheduled or Failed exactly once, is never Enqueued twice and is never copied.
- Inspection: no promotion path depends on one node being chosen to promote; the concurrency test runs every node's promotion at the same time.
- ST-011 keeps INV-115 holding when it adds retries, and ST-030 runs the test on PostgreSQL.

### AC-9 · REQ-40 · must

> While a node has no worker registered, the system shall run no background duty on that node: no promotion of scheduled or retry jobs, recurring triggers, lease recovery, retention cleanup, outbox relay, Unroutable or orphan sweep, Redis recurring reconciliation, dashboard node-sample pruning or dashboard rollup computation.
>
> *Notes:* Decided by the owner on 2026-11-06: every background duty is part of the worker. Many workers share them safely through store-side atomic operations and leases; a process without AddWorker does none of them. Two changes from refiner-model 2026-11-06: notification checks moved to the alerts registration (REQ-59, owner's decision on integrations F-6), and dashboard sample pruning and rollups were added to the list (dashboard F-8, recommended option). A node taking a metrics sample of itself is not a background duty in this sense (dashboard REQ-314).

- Given a node with the client and no worker, and due Scheduled jobs in the store, then the node promotes nothing, however far the clock moves.
- Given the dashboard is mapped on that node as well (from ST-031 on), then the same holds.
- Property: over random registrations on several nodes, background duties run on a node exactly when the worker is registered there.
- Each duty added later is gated the same way by the story that adds it (Context, paragraph 2). A node taking a metrics sample of itself is not a background duty (REQ-40's notes, dashboard REQ-314).

### AC-10 · REQ-148 · must

> If an application enqueues or schedules a job whose payload is larger than PayloadHardLimit, then the system shall reject the call with an exception that names the size and the limit, and store nothing.

- Given a payload above PayloadHardLimit, when it is enqueued or scheduled, then the call fails with an exception whose message gives the payload's size and the limit, no job id is returned and nothing is stored (SCN-116).
- Property: over random payload sizes around both limits and both kinds of call, a job is stored exactly when its size is not above PayloadHardLimit, and a size warning is logged exactly when the job is stored and its size is above PayloadSoftLimit.

### AC-11 · REQ-153 · must

> If an application passes a database transaction to a store that does not support transactional enqueue, then the system shall reject the call with an error that names the transactional-enqueue capability and the store, and store nothing.
>
> *Notes:* Decided by the owner on 2026-11-06: rejecting is the only reading that keeps INV-101; the Redis and in-memory stores report the capability as missing (REQ-512).

- Given the in-memory store, which reports no transactional enqueue (REQ-153's notes), when the application enqueues or schedules a job with a database transaction in EnqueueOptions, then the call fails with an error that names the transactional-enqueue capability and the store, and nothing is stored.
- Given the same call without a transaction, then it succeeds.
- Every M1 store rejects such a call the same way until ST-041 adds transactional enqueue.

### AC-13 · TECH-19 · must

> **IJobClient** — The core package shall expose all scheduling through an injectable IJobClient interface with ordinary methods (EnqueueAsync, EnqueueManyAsync, ScheduleAsync with at or delay, ContinueWithAsync, ChainAsync, CreateBatchAsync(name, jobs, continuations), CancelAsync, RequeueAsync, RequeueDeadLetteredAsync(filter), DeleteAsync, GetAsync, WaitForCompletionAsync, GetResultAsync<T>) and no static entry point.
>
> *Notes:* Decided by the owner on 2026-11-06: CreateBatchAsync (WF-3, jobs REQ-177) and RequeueDeadLetteredAsync for bulk requeue by name, queue, tag or time range (RET-5, jobs REQ-142) live on IJobClient; the source named neither. Batches cannot be extended (jobs REQ-178 retired), so there is no AddToBatch.

- Inspection: IJobClient is an interface that application code receives by injection (AddClient, TECH-128), and the core package has no static entry point for scheduling: no static Enqueue or Schedule method and no static client accessor.
- Test: EnqueueAsync, ScheduleAsync with at and with delay, and GetAsync behave as REQ-120, REQ-121 and REQ-182 say, and application code can use a test double in place of IJobClient.
- CancelAsync (ST-018), RequeueAsync, RequeueDeadLetteredAsync and DeleteAsync (ST-020), ContinueWithAsync and ChainAsync (ST-038), CreateBatchAsync (ST-039), and EnqueueManyAsync, WaitForCompletionAsync and GetResultAsync<T> (ST-040) get their behaviour in those stories. Whether they are declared before then is open question 2.

### AC-14 · TECH-20 · must

> **EnqueueOptions** — EnqueueOptions shall carry queue, priority, unique key and duplicate policy, key/value tags, timeout, retry policy override, concurrency key and an explicit database transaction.

- Inspection: EnqueueOptions carries the queue, the priority, the unique key and duplicate policy, key/value tags, the timeout, a retry policy override, the concurrency key and an explicit database transaction.
- Test: the queue and the priority given in EnqueueOptions are stored with the job over the attribute's and the fluent values (INV-123's notes); a transaction leads to REQ-153's rejection on the in-memory store.
- The unique key and policy (ST-019), timeout (ST-014), retry override (ST-011), tags (ST-044) and concurrency key (ST-042) are honoured by those stories. Whether those fields exist before then, and what a value set before then does, is open question 3.

### AC-15 · TECH-33 · must

> **Store capability set** — IJobStore shall expose a capability set covering transactional enqueue, push notifications and result storage.
>
> *Notes:* Free-text payload search was removed from the set by owner decision on 2026-11-06 as overkill; tag filters cover lookups by business key.

- Inspection: IJobStore exposes a capability set that covers transactional enqueue, push notifications and result storage.
- Test: the in-memory store reports transactional enqueue as missing (REQ-153's notes), and REQ-153's check reads the capability set, not the store's type.
