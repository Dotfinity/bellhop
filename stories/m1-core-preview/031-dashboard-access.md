# ST-031 — Mount the dashboard and protect it

**Milestone:** M1 · **Epic:** m1-core-preview · **Priority:** must · **Depends on:** ST-006

## Context

Adds the Bellhop.Dashboard package, mounted with app.MapBellhopDashboard("/path") (TECH-88), and the access rules every later page and JSON API call is judged by: in Development an unprotected dashboard is open with operate permission and a notice (REQ-300); elsewhere it refuses to start unless it has an authorization requirement or AllowAnonymous() (REQ-301), and AllowAnonymous() gives anonymous viewers view only, with a warning (REQ-342). An authenticated request without the permission it needs gets 403 (INV-300), view and operate are granted by their own policies (INV-301, REQ-302), and ReadOnly() refuses every operate action (INV-302). It also adds the JSON API the UI is built on (TECH-92), kept out of the host's API explorer (TECH-90), and serves the dashboard on any node that maps it (hosting REQ-51).

Builds on ST-006: REQ-300, REQ-301 and REQ-342 are startup checks that need no store, so they run in hosting REQ-12's sequence before the store is contacted, and a node is marked running only after they pass (hosting REQ-18). Mapping the dashboard is also one of the things that stops hosting REQ-54's warning that Bellhop will do nothing on the node, so REQ-54 keeps holding with a real MapBellhopDashboard in place of whatever ST-006 tested it with. ST-032 to ST-034 add the pages and JSON API endpoints; ST-061, ST-065 to ST-068 and ST-070 add operate actions and ways in. All of them keep INV-301 holding, ST-034 and ST-068 keep INV-302, and ST-065 keeps REQ-302. The checks name RequireRole, RequireClaim and RequireBasicAuth (ST-065, ST-067) and REQ-301's message has a clause for RequireApiKey() (ST-066); none of these exists in M1, so the checks are built and tested with RequireAuthorization, and those clauses are exercised when the later stories add the methods. No operate action exists before ST-034 either, so the access rules are tested over every endpoint the dashboard maps, and later endpoints join the same run. TECH-88 is owned before any page exists, and TECH-92 before the CLI and MCP server use the API (ST-086, ST-087): both are contracts the later stories build on.

Lives in Bellhop.Dashboard (TECH-88), the package that references ASP.NET Core; the core does not (TECH-9). MapBellhopDashboard returns an endpoint convention builder; AllowAnonymous() and RequireHost are the standard ASP.NET Core conventions on it, and ReadOnly() is named by INV-302. The specs do not name how view and operate policies are configured, where ReadOnly() is called, or the JSON API's routes and OpenAPI document (open questions 2 and 5).

## Acceptance criteria

### AC-1 · REQ-300 · must

> While a node is starting, if the dashboard is mapped without RequireAuthorization, RequireRole, RequireClaim or RequireBasicAuth and the environment is Development, then the system shall treat anonymous requests as having operate permission and the principal name "anonymous", and log a notice saying so.
>
> *Transition:* hosting.Node: Starting → Starting · *Actor:* system
>
> *Notes:* refiner-model 2026-11-06 F-1 (option 1, owner decision): anonymous access is a permission grant, operate in Development, so INV-301 holds. F-10 (option 1): the authorization requirements are listed by name; RequireApiKey() is not one, because it authenticates scripts, not browsers. Run 2 F-1 (recommended option): the principal name gives every Development launch an author (REQ-320 to REQ-323). Outside Development anonymous requests can only view (REQ-342), so the name never appears on a launch there.

- Given the environment is Development and the dashboard is mapped with no authorization requirement (glossary `authorizationRequirement`), when the host starts, then the node reaches Running (hosting REQ-18) and anonymous requests are treated as having operate permission: every page and JSON API read is served, operate actions are allowed (INV-301), and the principal name the dashboard gives the request is "anonymous".
- Given that start, then exactly one notice saying that anonymous requests have operate permission is logged (SCN-301, dashboard A-3). Its level and wording are open question 4.
- Given the same set-up with AllowAnonymous() also called, then the same holds: REQ-300 does not depend on it.
- Given RequireApiKey() is the only call on the endpoint (from ST-066 on), then the grant and the notice still happen and a request without a key has operate: RequireApiKey() is not an authorization requirement (glossary; REQ-305's notes; the accepted check `Chk_ApiKeyNotBypassed`).
- Given Development and RequireAuthorization on the endpoint, then there is no grant and no notice; an anonymous request gets the authentication challenge it would get on any endpoint with that requirement (TECH-88).
- Given any environment other than Development, then REQ-300 grants nothing and logs nothing; REQ-301 or REQ-342 decides.

### AC-2 · REQ-301 · must

> While a node is starting, if the dashboard is mapped without RequireAuthorization, RequireRole, RequireClaim or RequireBasicAuth, AllowAnonymous() was not called and the environment is not Development, then the system shall fail the host's start with a message that says how to add authorization or opt in to anonymous access and, where RequireApiKey() is enabled, that API keys authenticate scripts but do not protect the pages.
>
> *Transition:* hosting.Node: Starting → StartupFailed · *Actor:* system
>
> *Notes:* refiner-model 2026-11-06 F-10 (option 1): the authorization requirements are listed by name; a dashboard protected only by RequireApiKey() still needs one of them or AllowAnonymous() outside Development. F-5: hosting REQ-18/REQ-19 name this check as a startup check, so it always runs before the node is marked running.

- Given an environment other than Development (Production in SCN-300, also Staging), the dashboard mapped with no authorization requirement and AllowAnonymous() not called, when the host starts, then the start fails, the node never reaches Running (hosting REQ-18), the store is not contacted (the check needs no store, hosting REQ-12), and the message says how to add authorization or opt in to anonymous access.
- Given the same with RequireApiKey() enabled (from ST-066 on), then the message also says that API keys authenticate scripts but do not protect the pages.
- Given Development (REQ-300), or AllowAnonymous() called (REQ-342), or RequireAuthorization on the endpoint, then this check does not fail the start.
- Given the dashboard is not mapped, then this check does not run, whatever the environment (hosting REQ-51).
- Given the failure, then neither the message nor any log line contains a connection string or other secret (NFR-41). The message's wording is open question 4.

### AC-3 · REQ-342 · must

> While a node is starting, if the dashboard is mapped without RequireAuthorization, RequireRole, RequireClaim or RequireBasicAuth, AllowAnonymous() was called and the environment is not Development, then the system shall treat anonymous requests as having view permission only and log a warning that the dashboard is open to anonymous viewers.
>
> *Transition:* hosting.Node: Starting → Starting · *Actor:* system
>
> *Notes:* refiner-model 2026-11-06 F-1 (option 1, owner decision): AllowAnonymous() outside Development grants view, never operate, so operate actions still need an authenticated principal. Before this, AllowAnonymous() had no defined effect.

- Given an environment other than Development, the dashboard mapped with no authorization requirement and AllowAnonymous() called, when the host starts, then the node reaches Running and anonymous requests are treated as having view permission only: every page and JSON API read is served, and every operate action from an anonymous request is refused and changes nothing (INV-301).
- Given that start, then exactly one warning that the dashboard is open to anonymous viewers is logged (dashboard A-3).
- An anonymous request is never authenticated (dashboard A-7), so INV-300's 403 does not decide the response to its refused action: that is open question 3.
- Given AllowAnonymous() together with RequireAuthorization, then neither REQ-300, REQ-301 nor REQ-342 applies; what anonymous requests get then is open question 6.

### AC-4 · INV-300 · must

> If an authenticated request lacks the permission the page or action needs, then the system shall respond 403 Forbidden, not 401.

- Property, over every endpoint the dashboard maps and generated authenticated principals that have view, operate or neither (through separate view and operate policies, REQ-302): whenever the principal lacks the permission the endpoint needs, the response is 403 Forbidden, never 401, and the store is unchanged.
- Given an authenticated principal with view only, when it calls an operate action, then the response is 403. Given an authenticated principal with neither permission, when it requests a page or a JSON API read, then the response is 403.
- Given an unauthenticated request to a dashboard with an authorization requirement, then it gets the authentication scheme's challenge, as on any endpoint (TECH-88); INV-300 covers authenticated requests only.

### AC-5 · INV-301 · must

> The system shall serve a dashboard page, JSON API read or MCP read only to a request with view or operate permission, and perform an operate action (retry, requeue, cancel, delete, trigger, pause, resume, edit, launch, change a limit, create or revoke an API key, acknowledge a store reset) only for a request with operate permission.
>
> *Notes:* Applies equally to every built-in page (DSH-13), the JSON API (DSH-9) and the MCP server (BLT-19). Decided by the owner on 2026-11-06: operate includes view; the view policy alone gives read-only users.

- Property, over every endpoint the dashboard maps, each classified as a read or an operate action, and requests that are anonymous in Development (REQ-300), anonymous with AllowAnonymous() elsewhere (REQ-342), or authenticated with view, operate or neither, with ReadOnly() on and off: a page or JSON API read is served only to a request with view or operate, an operate action changes the store only for a request with operate, and operate includes view (glossary). A request with the level it needs and not refused by INV-302 is served (dashboard A-5). The run compares a snapshot of the store before and after every refused action, and it fails on an endpoint that has no classification, so the endpoints of ST-032 on cannot skip it.
- MCP reads keep this rule when Bellhop.Mcp exists (TECH-121, ST-087).

### AC-6 · INV-302 · must

> Where the dashboard is configured ReadOnly(), the system shall refuse every operate action whatever the caller's permissions.
>
> *Notes:* M1 ships a read-only dashboard (§8).

- Property: with ReadOnly() configured, every operate action is refused and the store is unchanged, for every request, including an authenticated operate principal and an anonymous request in Development (REQ-300); reads are served as they would be without ReadOnly().
- Given ReadOnly() is not configured, then an operate principal's actions are performed (the INV-301 run).
- The response to a ReadOnly() refusal is open question 3 (dashboard A-16). Where ReadOnly() is called is open question 2.

### AC-7 · REQ-51 · must

> The system shall serve the dashboard on a node exactly when the application maps it, whether or not the client or the worker is registered.
>
> *Notes:* Decided by the owner on 2026-11-06: the dashboard, the client and the worker never talk to each other directly, only through the store. An instance can serve the dashboard with no worker, run a worker with no dashboard, or both.

- Given each combination of registrations (none, client, worker; the alerts registration from ST-049 on) with MapBellhopDashboard called, then the dashboard's endpoints are served, subject to INV-301. Given the same combinations without it, then no dashboard endpoint exists and a request to its path is handled as any unmapped path of the host.
- Given a node with neither the client nor the worker registered, then the dashboard still serves its pages and reads; it reads the store and never calls another process (REQ-51's notes). SCN-308 (ST-032) runs a dashboard on such a node.
- What happens when the dashboard is mapped but AddBellhop was never called is open question 7.

### AC-8 · REQ-302 · must

> Where separate policies are configured for view and operate, the system shall grant each permission level by its own policy.

- Given separate view and operate policies are configured, then a principal satisfying only the view policy has view: pages and reads are served and operate actions get 403 (INV-300); a principal satisfying only the operate policy has operate, which includes view (INV-301's notes); one satisfying both has operate; one satisfying neither gets 403 on every endpoint.
- Property, over generated principals with independent outcomes for the two policies: view is granted exactly when the view or the operate policy succeeds, and operate exactly when the operate policy succeeds.
- What a single RequireAuthorization policy grants, and the API that configures the two policies, are open questions 1 and 2.

### AC-11 · TECH-88 · must

> **Dashboard package** — The Bellhop.Dashboard package shall use ASP.NET Core endpoint routing, mounted with app.MapBellhopDashboard("/path"), which returns an endpoint convention builder so RequireAuthorization, AllowAnonymous and RequireHost work as on any endpoint.

- Compile-time test: `app.MapBellhopDashboard("/jobs")` returns an endpoint convention builder, so RequireAuthorization, AllowAnonymous and RequireHost chain on it.
- Given RequireAuthorization with a policy on it, then every dashboard endpoint (pages, JSON API, and the live updates and assets from ST-032 on) requires that policy, with the same outcome as a control endpoint with the same call in the same host.
- Given RequireHost with a host name on it, then a request for another host is not served by the dashboard, with the same outcome as the control endpoint.
- AllowAnonymous() on it has the effect REQ-300 and REQ-342 give it; together with RequireAuthorization it is open question 6.
- The package id is Bellhop.Dashboard (TECH-124), and the core package references no ASP.NET Core package (TECH-9, ST-001's audit).

### AC-12 · TECH-90 · must

> **API explorer exclusion** — The dashboard shall exclude its endpoints from the host's ASP.NET Core API explorer and Swagger documents.

- Given a host with the ASP.NET Core API explorer and a Swagger or OpenAPI document generator registered, and the dashboard mapped, then neither the API explorer's descriptions nor the generated documents contain any dashboard endpoint, while the host's own endpoints still appear.
- The check enumerates every endpoint the dashboard maps, so endpoints added by later stories stay excluded.

### AC-13 · TECH-92 · should

> **Dashboard JSON API** — The dashboard shall back its UI with a JSON API under the dashboard path, documented with OpenAPI.
>
> *Notes:* ADR-3 makes this API the official route for custom UI and therefore a public contract covered by NFR-20.

- Every JSON API endpoint is under the dashboard path, and an OpenAPI document describes it: a test compares the endpoints the dashboard maps with the operations in the document and fails on any difference, in either direction.
- From ST-032 on, the browser tests record the UI's requests and fail on any data request that is not to the JSON API under the dashboard path.
- The route layout, the naming and where the document is published are open question 5; ADR-3 makes the API a public contract covered by NFR-20 (ST-076).

6. **Decide in delivery** · REQ-301, REQ-342, TECH-88: what anonymous requests get when AllowAnonymous() and RequireAuthorization are both on the endpoint, and does a host-wide fallback authorization policy count as an authorization requirement? 7. **Decide in delivery** · REQ-51: what happens when the dashboard is mapped but AddBellhop was never called. Hosting REQ-52 assumes the store is configured with AddBellhop; no item says whether mapping fails, the start fails, or the dashboard falls back to the in-memory store as hosting REQ-15 does when no store is configured.
8. **Decide in delivery** · INV-301: do the embedded assets (TECH-91, ST-032) count as "a dashboard page", so that a request without view is refused them too? They carry no job data, but they live under the dashboard path that the policy covers.
