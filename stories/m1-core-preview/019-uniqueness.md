# ST-019 — Enforce unique keys

**Milestone:** M1 · **Epic:** m1-core-preview · **Priority:** must · **Depends on:** ST-008, ST-018

## Context

Adds unique keys, the idempotency tooling behind at-least-once delivery (hosting REQ-7, REQ-39). A job created with a key that an active job already holds creates nothing: by default the call returns the existing job (Ignore, REQ-107, REQ-150), under Error it is rejected (REQ-152), and a schedule call under ReplaceSchedule moves the existing scheduled job's time instead (REQ-151, INV-135). The store never holds two active jobs with one key, even when the calls arrive at once on different nodes (INV-100).

Builds on ST-018 (cancellation), and through it on ST-011 to ST-017, which produce the Failed, Unroutable, lease-recovered and Cancelled holders that INV-100's property test drives through real transitions, on ST-008 (claims, which move a job between active states) and on ST-007 (enqueue and schedule, REQ-120, REQ-121 and REQ-182, which must keep holding, and EnqueueOptions with its unique key and duplicate policy, TECH-20). It must keep ST-002's INV-123 holding: a duplicate policy set both by `[Unique]` and fluently uses the fluent value, and a per-enqueue policy beats both (INV-123's notes). ST-020 builds on it: a requeue skips or refuses a job whose key is held. Later stories that create jobs or change the store constrain its items: ST-030 (TECH-44's unique index on PostgreSQL), ST-038 and ST-039 (continuations, chain steps and batch members, REQ-150 and REQ-152), ST-024 and ST-026 (recurring occurrences, REQ-150 and REQ-152), ST-040 (bulk enqueue, REQ-150 and REQ-152), ST-046 (namespaces, INV-100), and ST-058, ST-061 and ST-064 (the Redis store, its reset recovery and ShardByQueue's per-queue scope, INV-100).

Lives in the Bellhop core package (TECH-112): `EnqueueAsync` and `ScheduleAsync` on IJobClient (TECH-19), the unique key and duplicate policy on EnqueueOptions (TECH-20) and the `[Unique]` attribute (TECH-17), with the check made atomically by the in-memory store (TECH-43) behind IJobStore (TECH-31). The policies Ignore, Error and ReplaceSchedule and the flag WasDuplicate are named in the specs; the type that carries WasDuplicate and the error of REQ-152 are not (open questions 1 and 2). Until ST-038 adds continuations, the Awaiting state is built against what exists: tests write an awaiting job into the store directly. Every M1 job lives in one namespace, so INV-100's per-namespace scope can only be told apart once namespaces exist (ST-046). Placement: hosting REQ-36 puts unique keys in M2, where REQ-107, REQ-150, REQ-151, REQ-152, INV-100 and INV-135 are tagged and SCN-105 follows them; the owner decided on 2026-11-10 to build all of FEAT-103 in M1, because M1's requeue rules REQ-142 and INV-129 depend on INV-100 and REQ-107.

## Acceptance criteria

### AC-1 · REQ-107 · must

> The system shall treat Scheduled, Enqueued, Processing, Awaiting, Failed and Unroutable as the active states for uniqueness, and Ignore as the default duplicate policy.
>
> *Notes:* Decided by the owner on 2026-11-06: a unique key is held until the job is Succeeded, DeadLettered or Cancelled, so no duplicate can appear while the first job waits for a retry or a handler. Widens SCH-5's list.

- Given a job e holding unique key k in each of Scheduled, Enqueued, Processing, Failed and Unroutable, and Awaiting (written into the store directly), when an application enqueues a job with key k and sets no duplicate policy, then no job is created and the call returns e's id with WasDuplicate set to true (Ignore, REQ-150).
- Given e is Succeeded, DeadLettered or Cancelled instead, when an application enqueues a job with key k, then a new job is created (REQ-120) and WasDuplicate is not set to true.
- Given the duplicate policy is set to Error or ReplaceSchedule on the call (EnqueueOptions, TECH-20), then that policy decides instead of Ignore (REQ-151, REQ-152, INV-135).
- Given a duplicate policy set by `[Unique]` on the job type and another set fluently in AddBellhop, then the fluent one decides (INV-123); given a third set on the call, then the call's policy decides over both (INV-123's notes).

### AC-2 · REQ-151 · must

> When an application schedules a job with a unique key while a scheduled job with the same key exists, if the duplicate policy is ReplaceSchedule, then the system shall move the existing job's scheduledAt to the new time, leave its payload unchanged, create no job and return the existing job's id with WasDuplicate set to true.
>
> *Transition:* Job: Scheduled → Scheduled · *Actor:* Application
>
> *Notes:* Decided by the owner on 2026-11-06: only the time moves. An existing job that is no longer Scheduled is INV-135.

- Given a scheduled job e with key k, scheduledAt t1 and payload p1, when an application schedules a job with key k, ReplaceSchedule, payload p2 and a future time t2, then e's scheduledAt is t2, its payload is still p1, no job is created, and the call returns e's id with WasDuplicate set to true. A delay instead of a time moves scheduledAt to now plus the delay (REQ-121).
- Given the same call, then only scheduledAt changes; every other attribute of e stays as it was.
- Given t2 is not in the future, then the call still schedules (jobs A-15): e's scheduledAt becomes t2, and e is promoted under REQ-122 because its scheduledAt has passed.
- Given the call is an enqueue rather than a schedule, then REQ-150 applies and e is unchanged. Given e has left Scheduled, then INV-135 applies.
- Concurrency: a ReplaceSchedule call racing e's promotion either moves e's scheduledAt while e is still Scheduled, or finds e Enqueued and changes nothing (INV-135). The call never changes e after its promotion.
- Concurrency: two ReplaceSchedule calls for key k racing each other leave e's scheduledAt at one of the two times, and create no job.

### AC-3 · INV-100 · must

> The system shall never hold two active jobs with the same unique key in the same namespace or, where the Redis ShardByQueue mode is on (redis INV-500), in the same queue, even when the enqueues arrive concurrently on different nodes.
>
> *Notes:* In the Redis ShardByQueue mode the scope is per queue instead (INV-500). Resolved after refiner-model 2026-11-06 redis F-10 (recommended option): the ShardByQueue scope is part of the sentence, not only of the notes. Every job-creating call is covered by REQ-150/REQ-152 (F-3) and bulk requeue by REQ-142 (F-4).

- Concurrency: given no active job holds key k, when many enqueue and schedule calls with key k arrive at once from clients on two or more nodes sharing one store, then exactly one job is created, and every other call returns its id with WasDuplicate set to true (Ignore, ReplaceSchedule) or fails (Error).
- Property: over random sequences of creating calls (enqueue, schedule for a future or past time, every policy, with and without a key) mixed with promotion, claims, every handler outcome, retries, Unroutable and back, cancellation and lease recovery, at most one active job holds any key after every step.
- Given the holder becomes Succeeded, DeadLettered or Cancelled, then the key is free, and the next creating call with it creates a job.
- The other ways back into an active state are attacked by the stories that build them: requeue (REQ-141 to REQ-143, INV-129, ST-020) and the Redis reset re-create (redis REQ-534, ST-061). The per-namespace scope is observable only with several namespaces (ST-046), the per-queue scope under ShardByQueue is ST-064's.

### AC-4 · INV-135 · must

> When an application schedules a job with a unique key while an active job with the same key exists that is not scheduled, if the duplicate policy is ReplaceSchedule, then the system shall create no job, change nothing and return the existing job's id with WasDuplicate set to true.
>
> *Notes:* Decided by the owner on 2026-11-06: behaves like Ignore once the existing job has left Scheduled.

- Given a job e holding key k that is Enqueued, Processing, Failed or Unroutable, or Awaiting (written into the store directly), when an application schedules a job with key k under ReplaceSchedule, then no job is created, every attribute of e is unchanged (its scheduledAt and retryAt included), and the call returns e's id with WasDuplicate set to true.
- Property: over the random sequences of INV-100, a ReplaceSchedule schedule call never changes a holder that is not Scheduled.

### AC-5 · REQ-150 · must

> When an application enqueues, schedules or otherwise creates a job (including a continuation, a chain step or a batch member) with a unique key while an active job with the same key exists, if the duplicate policy is Ignore, or the policy is ReplaceSchedule and the call does not schedule a job, then the system shall create no job and return the existing job's id with WasDuplicate set to true.
>
> *Notes:* Resolved after refiner-model 2026-11-06 F-3 (recommended option): the duplicate rules cover every call that creates a job, including recurring occurrences, so INV-100 cannot be bypassed by scheduling, by ReplaceSchedule on enqueue, or by a continuation, chain step or batch member. ReplaceSchedule on a call that does not schedule behaves like Ignore, as INV-135 does for a holder that is no longer scheduled. Same event as REQ-152 with complementary guards. Open for the owner: what a chain or batch does with the other steps when one step is ignored as a duplicate.

- Given an active job e holding key k, when an application enqueues or schedules a job with key k under Ignore, then no job is created, e is unchanged, the call returns e's id with WasDuplicate set to true, and no OnEnqueued event is raised (REQ-169), since nothing was enqueued.
- Given ReplaceSchedule on an enqueue, a call that does not schedule, then the outcome is the same as under Ignore.
- Given e has a different job name from the call, then the call is still a duplicate: INV-100's scope is the namespace, not the name.
- Given no active job holds k, or the call has no unique key, then the job is created as REQ-120, REQ-121 or REQ-182 say, and WasDuplicate is not set to true.
- Property: the random sequences of INV-100 also assert, for every duplicate under Ignore, that the returned id is the holder's id at the moment of the call.
- Continuations, chain steps and batch members (ST-038, ST-039) and recurring occurrences (this item's notes) are tested by the stories that create them.

### AC-6 · REQ-152 · must

> When an application enqueues, schedules or otherwise creates a job (including a continuation, a chain step or a batch member) with a unique key while an active job with the same key exists, if the duplicate policy is Error, then the system shall reject the call with an error and create no job.
>
> *Notes:* Resolved after refiner-model 2026-11-06 F-3 (recommended option): covers every call that creates a job; for a chain or batch, rejecting the call creates none of its jobs (REQ-176, REQ-177 are one transaction).

- Given an active job e holding key k, when an application enqueues or schedules a job with key k under Error, then the call fails with an error, no job is created and e is unchanged. The error's type and message are open question 2.
- Given no active job holds k, then a call under Error creates the job as usual.
- Concurrency: of many calls under Error with one free key arriving at once on two nodes, exactly one creates the job and every other one fails.

### AC-7 · SCN-105 · scenario

> **Duplicate unique key returns the existing job**
>
> *Given:* No jobs exist; policy Ignore.
>
> 1. REQ-120 — enqueue with UniqueKey = order-42
> 2. REQ-150 — enqueue again with UniqueKey = order-42 on another node
>
> *Then:* Exactly one active job has key order-42 and the second call returned its id with WasDuplicate = true.
