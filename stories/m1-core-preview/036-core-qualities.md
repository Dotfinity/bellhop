# ST-036 — Measure idle cost, memory, recurring scale and static state

**Milestone:** M1 · **Epic:** m1-core-preview · **Priority:** must · **Depends on:** ST-030

## Context

Measures four qualities of the M1 core: an idle node uses CPU indistinguishable from an idle host (NFR-12), memory follows in-flight jobs and not job history (NFR-13), due recurring jobs are found with one indexed range query per poll over 100,000 definitions (NFR-14), and Bellhop holds no static or ambient state, so two instances can share a process (NFR-53). The first three run on PostgreSQL, the reference store.

Builds on ST-030 (the PostgreSQL store, its NextRunAt index under TECH-45 and the idle-load test of NFR-10) and through it on all M1 behaviour; NFR-14 measures the trigger of ST-026 (REQ-216). NFR-53 is a standing rule every story has followed; its two-instance test is written now that two stores exist, the in-memory store (ST-004) and PostgreSQL. Bellhop.Testing's harness (TECH-102, ST-027) applies to NFR-53 too. ST-037 builds on this story.

The measurements are tests in the repository that run against a real PostgreSQL server; they add no package or public type. The reference machine, what counts as memory growth, and what counts as a mutable static are not in the specs (open questions 1, 2 and 5).

## Acceptance criteria

### AC-1 · NFR-12 · must

> **Idle CPU** — While a node is idle, the system shall use CPU indistinguishable from an idle host.
>
> *Measure:* ≤ 1% of one core averaged over 10 minutes with no jobs, default PollInterval, PostgreSQL store, reference machine · *Verification:* test
>
> *Notes:* Decided by the owner on 2026-11-06.

- Measurement test on the reference machine: one node with the worker registered, the PostgreSQL store, the default PollInterval (1 s, REQ-103) and no jobs. Once the node is running, the process's CPU time over 10 minutes, divided by those 10 minutes, is at most 1% of one core. That is the pass condition.
- What the reference machine is, and where the test runs, is open question 1.

### AC-2 · NFR-13 · must

> **Memory footprint** — The system shall use memory proportional to the number of in-flight jobs, not to job history.
>
> *Measure:* steady-state memory does not grow with the number of stored jobs (1k vs 1M stored, same in-flight count) · *Verification:* test

- Measurement test on PostgreSQL: the same node and workload run twice, once with 1,000 jobs stored and once with 1,000,000, with the same number of jobs in flight in both. Steady-state memory is measured in each run; it passes when the second run's memory is no larger than the first's, within the tolerance open question 2 sets.
- The stored jobs beyond those in flight are finished jobs within retention (REQ-104), which is the history the statement names. Whether a backlog of enqueued jobs must also leave memory unchanged is open question 2.
- The in-memory store keeps every job in process memory (TECH-43); whether NFR-13 applies to it is open question 3.

### AC-3 · NFR-14 · must

> **Recurring scale** — The system shall find due recurring jobs with one indexed range query per poll.
>
> *Measure:* 100,000 recurring definitions (multi-tenant) cost one range query per poll on NextRunAt · *Verification:* test

- Measurement test on PostgreSQL: 100,000 recurring definitions with nextRunAt spread over time. Over several scheduler polls, the store queries that look for due recurring jobs are counted at the server: exactly one per poll per node, and its query plan reads the NextRunAt index as a range, not the whole table (TECH-45). That is the pass condition.
- Given some definitions are due, then the same single query finds them; each due job's trigger is then its own compare-and-set (REQ-216, INV-212), which the measure does not count.
- What "multi-tenant" means for the definitions is open question 4.

### AC-4 · NFR-53 · must

> **No static state** — The system shall hold no static or ambient state, so that two independent Bellhop instances can run in one process.
>
> *Measure:* test with two instances on different stores in one process passes; 0 mutable statics · *Verification:* test

- Test: one process hosts two independent Bellhop instances, one on the in-memory store and one on PostgreSQL, each with its own options (for example a different PollInterval), job types and recurring jobs. Each runs only its own jobs, sees only its own recurring jobs and uses only its own options, and stopping one leaves the other running. Pass: the test passes.
- Test: two BellhopTestHarness instances (TECH-102) run in parallel in one process, and neither sees the other's jobs.
- Static scan in CI: a test reflects over every Bellhop assembly and finds 0 mutable static fields. Pass: 0. What counts as mutable is open question 5.

## Open questions

1. **Decide in delivery** · NFR-12: what the reference machine is (cores, CPU, operating system, and whether a shared CI runner qualifies) and where the 10-minute measurement runs. The measure names it but does not define it.
2. **Decide in delivery** · NFR-13: which memory is measured (working set, or the GC heap after a full collection), what difference counts as growth, and whether "stored jobs" means finished history only or also a backlog of enqueued jobs. The measure says only "does not grow".
3. **Decide in delivery** · NFR-13: does NFR-13 apply to the in-memory store (TECH-43), which keeps every stored job in process memory by design? It applies to "system".
4. **Decide in delivery** · NFR-14: does "multi-tenant" mean namespaces (ST-046, M2), and if so is the bound one query per poll for all namespaces or one per namespace, or does it mean many definitions in one namespace?
5. **Decide in delivery** · NFR-53: what counts as a mutable static: a static readonly field that holds a mutable object, a static AsyncLocal behind IJobContextAccessor (TECH-34), or a static ActivitySource or Meter named "Bellhop" (TECH-97, TECH-98)? The measure says "0 mutable statics"; these are the cases the specs make likely.
