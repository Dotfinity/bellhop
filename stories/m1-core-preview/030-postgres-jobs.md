# ST-030 — Run jobs and recurring jobs on PostgreSQL

**Milestone:** M1 · **Epic:** m1-core-preview · **Priority:** must · **Depends on:** ST-029, ST-021, ST-026, ST-027

## Context

Implements the job, recurring and index operations of IJobStore on the PostgreSQL schema: claims with FOR UPDATE SKIP LOCKED (TECH-39), LISTEN/NOTIFY to wake idle nodes (TECH-38), unique keys enforced by a unique index (TECH-44) and an idle node that costs the store at most one query per PollInterval (NFR-10). It then proves every M1 store behaviour on PostgreSQL by running the store-level tests of the earlier M1 stories against it, because the published conformance package (TECH-105) is M2 under hosting REQ-36.

Builds on ST-029 (schema, migrations) and on ST-021, ST-026 and ST-027, the last M1 stories that add store behaviour, so every store-level test exists when this story runs it. It must keep the store rules of ST-004 (TECH-31, TECH-32), ST-007 (INV-105, INV-115), ST-008 (INV-103), ST-019 (INV-100), ST-022 (TECH-45) and ST-026 (INV-203, INV-212) holding. ST-032 and ST-036 build on it, as do the M2 stories that change the store contract (ST-038, ST-040, ST-041, ST-042, ST-046 to ST-049), which implement each change on PostgreSQL too (TECH-31's "every store"); ST-055 and ST-056 keep TECH-44 for their stores. TECH-44 is inferred M2 but owned here: on 2026-11-10 the owner moved all of uniqueness into M1, TECH-44 on PostgreSQL included, because M1's requeue rules REQ-142 and INV-129 depend on INV-100 and REQ-107.

Lives in Bellhop.PostgreSql (TECH-37). Claims, lease expiry and due times are decided with the database clock (INV-105). Tags and correlation ids are written from ST-044 on, so IJobIndex (TECH-32) is tested by adding entries directly; namespaces come with ST-046, which must extend the unique index to them. Which transitions count as "work arrives", and which statements NFR-10 counts, are open questions 1 and 2.

## Acceptance criteria

### AC-1 · TECH-38 · must

> **PostgreSQL notifications** — The PostgreSQL store shall use LISTEN/NOTIFY to wake other nodes when work arrives.

- Given a node with only the client registered and one worker node on the same store, the worker idle and its PollInterval configured longer than the test's timeout so that polling cannot explain a wake-up, when the client node enqueues a job, then the worker is woken and claims the job within the timeout.
- Given the worker's listening connection is terminated (pg_terminate_backend), when a job is enqueued, then the worker still claims it by polling at PollInterval (REQ-103); once the database accepts connections again, a later enqueue wakes the worker by notification again.
- Inspection: the store listens on a PostgreSQL channel and the write that makes work available sends NOTIFY on it. Recorded in Notes.
- The criteria use an enqueue, which counts as work arriving under every reading; whether promotions, requeues and recurring occurrences also notify is open question 1.

### AC-2 · TECH-39 · must

> **PostgreSQL claims** — The PostgreSQL store shall claim jobs with FOR UPDATE SKIP LOCKED.

- Concurrency: several workers on separate connections claim at once from one queue holding fewer jobs than workers; every job is claimed by exactly one worker and none by two (INV-103), on each PostgreSQL version of the TECH-37 matrix.
- Given a test session holds a row lock (FOR UPDATE) on the job that is next by queue order and priority, when a worker claims, then it claims the following job without waiting for that lock; when the lock is released, the locked job is claimable again.
- Inspection: the claim statement uses FOR UPDATE SKIP LOCKED. Recorded in Notes.
- The claim guards of REQ-123 (paused queue, maintenance, queue concurrency limit) keep holding: ST-008's and ST-009's tests run on PostgreSQL.

### AC-3 · TECH-44 · must

> **Unique keys by index** — The SQL stores shall enforce unique keys with a unique index rather than a read-then-write check.
>
> *Notes:* The Redis store uses SET NX PX for the same purpose (TECH-56).

- Concurrency: enqueues of jobs with the same unique key arrive at the same moment from several nodes on separate connections; afterwards exactly one active job holds the key (INV-100), and every other call has the outcome of its duplicate policy, Ignore by default (REQ-107; ST-019's tests on PostgreSQL).
- Given the job holding key k is Scheduled, Enqueued, Processing, Awaiting, Failed or Unroutable (REQ-107's active states; Awaiting is written directly, continuations are M2), then a second active job with k cannot be created. Given it is Succeeded, DeadLettered or Cancelled, then a new job with k is created.
- Given a dead-lettered job whose key another active job holds, then a requeue of it is refused (INV-129) and a bulk requeue skips and counts it (REQ-142), on PostgreSQL.
- Inspection: the schema has a unique index over the unique key of active jobs, and no code path decides uniqueness by a read followed by a write. Recorded in Notes.

### AC-4 · NFR-10 · must

> **Idle store load** — While a node is idle and notifications are available, the system shall issue at most one lightweight store query per PollInterval.
>
> *Measure:* ≤ 1 query per PollInterval per idle node, measured at the store · *Verification:* test

- Measurement test on PostgreSQL: one node with the worker registered, an empty store, LISTEN/NOTIFY working (TECH-38) and the default PollInterval (1 s, REQ-103). From the moment the node is running, count at the server, for example with pg_stat_statements, the statements the node's connections run over a window of many PollIntervals. The poll for work is at most one statement per PollInterval in the window, which is the pass condition under every reading.
- The same test reports the total of all statements the idle node ran; that total is the pass condition instead if open question 2 settles that the bound covers every statement.
- Given two idle nodes on one store, then each node's count meets the bound separately ("per idle node").
- Given PollInterval configured to another value, then the bound follows that value.

## Open questions

1. **Decide in delivery** · TECH-38: which transitions count as "work arrives" and send a notification: only an enqueue, or also a scheduled or failed job promoted (INV-115), a requeue (REQ-141, REQ-142), a lease recovered (REQ-132) and a recurring occurrence enqueued (REQ-221)? TECH-38 does not list them; without a notification those jobs wait for a poll (REQ-103).
2. **Decide in delivery** · NFR-10: does "≤ 1 query per PollInterval per idle node" cover every statement an idle worker node runs, the background duties of hosting REQ-40 (promotion, recurring triggers, lease recovery, retention cleanup) and its heartbeat included, or only the poll for work, and what makes a query "lightweight"? Each background duty reads the store on its own, so the strict reading constrains their design.
