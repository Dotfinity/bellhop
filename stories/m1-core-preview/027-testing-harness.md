# ST-027 — Test jobs with Bellhop.Testing and inline execution

**Milestone:** M1 · **Epic:** m1-core-preview · **Priority:** must · **Depends on:** ST-021, ST-026

## Context

Lets application developers test their jobs without infrastructure (hosting REQ-2, P7: testable without statics). Bellhop.Testing's BellhopTestHarness drains jobs synchronously over the deterministic in-memory store, moves time with FakeTimeProvider and offers assertion helpers (TECH-102, TECH-103). The Inline execution mode runs a handler before the enqueue call returns and rethrows its exception to the caller (REQ-146), runs a job once with no retry (INV-131), and stores a scheduled job without running it (INV-133).

Builds on ST-021 and ST-026, the last M1 job and recurring stories, so the harness drains everything M1 can put in the store, and on ST-004 (the in-memory store, TECH-43, and `TimeProvider`, TECH-12) and ST-008 (`JobContext.CreateForTest`, TECH-104), whose items must keep holding. ST-030 and ST-083 (the Garnet fixture) build on it. ST-043 adds Inline mode's M2 rules (continuations run inline, unique and concurrency keys applied: INV-132, INV-134, INV-137) and constrains REQ-146 and INV-131.

Lives in the new Bellhop.Testing package (TECH-102), named as TECH-124 says, targeting net8.0 and net10.0 (TECH-1), and shipped with Bellhop's version and an exact-version dependency on it (TECH-50). It uses the core's in-memory store rather than one of its own (TECH-43) and the package that ships FakeTimeProvider (TECH-103). The specs name BellhopTestHarness, `RunPendingAsync()`, `AdvanceTimeAsync(...)` and `harness.Enqueued<T>()`; how Inline mode is selected and where it lives, AdvanceTimeAsync's parameters, the other helpers and what provides `Should()` are not (open questions 1, 2 and 6). Placement: TECH-102 applies to NFR-53, which ST-036 measures later; hosting REQ-36 puts Bellhop.Testing in M1, and ST-036's two-instance test then covers the harness too.

## Acceptance criteria

### AC-1 · INV-131 · must

> Where the execution mode is Inline, if a handler throws, then the system shall not retry the job.
>
> *Notes:* Decided by the owner on 2026-11-06: Inline runs a job once and rethrows (REQ-146).

- Given Inline mode and a handler that throws, when an application enqueues the job, then the handler has run exactly once, the exception reaches the caller (REQ-146), and the handler never runs again for that job, even after the fake clock is advanced past every backoff of REQ-100.
- Given the same, then this holds whatever the job's maxAttempts and retry policy, and for every kind of exception, OperationCanceledException and PermanentJobFailureException included.
- Property: over random handlers (each throwing a random exception or returning) with random maxAttempts and retry policies, every handler runs exactly once per enqueue. The state a failed Inline job is left in is open question 3.

### AC-2 · INV-133 · must

> Where the execution mode is Inline, when an application schedules a job, the system shall store the job as scheduled without running it.
>
> *Notes:* Decided by the owner on 2026-11-06. Tests advance a fake TimeProvider to run it.

- Given Inline mode, when an application schedules a job for a future time or after a positive delay, then the call returns without running the handler, and the job is stored as Scheduled with its scheduledAt (REQ-121).
- Given that job, then its handler does not run while the fake clock is before its scheduledAt, however much real time passes. Once the test advances the fake time past scheduledAt, the handler runs once; what triggers that run is open question 2.
- Property: over random schedule times and clock advances, no handler of a scheduled job runs before its scheduledAt has passed on the fake clock.
- A schedule call for a time that is not in the future is open question 4.

### AC-3 · REQ-146 · must

> Where the execution mode is Inline, when an application enqueues a job, the system shall run the handler on the caller's thread before the enqueue call returns and rethrow any handler exception to the caller.
>
> *Notes:* Decided by the owner on 2026-11-06: Inline mode runs a job once with no retries (INV-131), runs continuations inline (INV-132), stores scheduled jobs without running them (INV-133) and applies unique and concurrency keys (INV-134).

- Given Inline mode and a handler that returns, when an application calls `EnqueueAsync`, then the handler is invoked from within that call, not by a worker loop, and has run to completion before the call returns the job's id (REQ-120); the job is then Succeeded (REQ-127).
- Given a handler that throws, then the enqueue call throws the exception the handler threw, after the handler has run.
- Given a handler that itself enqueues another job, then that job's handler runs before the inner enqueue returns, so both have run when the outer call returns, and an exception from the inner handler reaches the outer handler.
- Property: over random sequences of enqueues with returning and throwing handlers, every handler has run exactly once by the time its enqueue call returns, and every call that returns normally belongs to a handler that did not throw.
- Whether "the caller's thread" also means the same OS thread is open question 5; the criteria above hold under both readings.

### AC-4 · TECH-102 · must

> **Testing package** — The Bellhop.Testing package shall provide a BellhopTestHarness with RunPendingAsync() and AdvanceTimeAsync(...) that drains jobs synchronously over the deterministic in-memory store, plus assertion helpers such as harness.Enqueued<T>().Should().ContainSingle(...).

- Test, in a sample test project that references only Bellhop and Bellhop.Testing: given a harness with one job type and its handler, when the test enqueues the job through IJobClient, then `harness.Enqueued<T>().Should().ContainSingle(...)` passes for that job, and fails when no job or two jobs of that type were enqueued.
- Test: when the test calls `RunPendingAsync()`, then every job that was pending when it was called has run by the time its task completes, and no Bellhop work is left running in the background. Running the same test twice gives the same order and the same outcomes.
- Test: given a job scheduled one hour ahead, then `RunPendingAsync()` does not run it; after `AdvanceTimeAsync(...)` past its scheduledAt and `RunPendingAsync()`, it has run.
- Test: two harnesses in one test process share no jobs and no time (NFR-53).
- Build and package check: Bellhop.Testing builds for net8.0 and net10.0 (TECH-1), its package id is Bellhop.Testing (TECH-124), and it depends on Bellhop at exactly its own version (TECH-50). Passing means the CI package checks of ST-001 pass for it.
- What `RunPendingAsync()` does with handler exceptions and with jobs the drained jobs enqueue, and whether time advances also run the other background duties, is open question 7.

### AC-5 · TECH-103 · must

> **Fake time** — Bellhop.Testing shall integrate with FakeTimeProvider.

- Test: given a harness on a FakeTimeProvider, when the test advances that FakeTimeProvider, then every time Bellhop reads moves with it (TECH-12): scheduled jobs, retries and recurring next runs are judged against the fake time, and a job due only at the new time becomes due.
- Inspection: Bellhop.Testing references the package that ships FakeTimeProvider, and neither the harness nor the in-memory store reads the system clock. Passing means the reviewer finds no clock read outside `TimeProvider` and records it in Notes.
- Whether the harness takes the test's FakeTimeProvider or creates its own is part of open question 2.

## Open questions

1. **Decide in delivery** · REQ-146, INV-131, INV-133: how is the Inline execution mode selected (method or option name), does it live in the core package or in Bellhop.Testing, and does it need the worker registered? No item names it, and TECH-112's list of core contents does not mention it.
2. **Decide in delivery** · INV-133, TECH-102, TECH-103: what runs a scheduled job once the fake time passes its scheduledAt: advancing the FakeTimeProvider by itself, `AdvanceTimeAsync(...)`, or that followed by `RunPendingAsync()`? What are AdvanceTimeAsync's parameters, and does the harness take the test's FakeTimeProvider or create its own? INV-133's notes say only "tests advance a fake TimeProvider to run it".
3. **Decide in delivery** · INV-131: which state is an Inline job left in when its handler throws? INV-131 says only that it is not retried; REQ-129 would mark it failed with a retryAt that never comes, and REQ-131 dead-letters only when attempts are used up.
4. **Decide in delivery** · REQ-146, INV-133: does Inline mode run a job scheduled for a time that is not in the future, which REQ-182 stores as enqueued at once, before the schedule call returns? REQ-146 speaks of enqueue calls and INV-133 of scheduled jobs; neither covers this case.
5. **Decide in delivery** · REQ-146: does "on the caller's thread" mean the same OS thread throughout, which an asynchronous handler cannot keep after its first await, or within the caller's call, completed before it returns? The criteria assert only the second, which holds under both readings.
6. **Decide in delivery** · TECH-102: which assertion helpers exist besides `Enqueued<T>()` ("such as"), and what provides `Should()`: an assertion library that Bellhop.Testing depends on, or its own extension? A third-party assertion library would bring its licence and release cycle into every user's test project (NFR-37, NFR-44).
7. **Decide in delivery** · TECH-102: does `RunPendingAsync()` rethrow a handler's exception or leave the job on its normal failure path, does it also run jobs that the drained jobs enqueue, and do the harness's time advances also run the other background duties (recurring triggers, lease recovery, retention cleanup)? "Drains jobs synchronously" settles none of these.
