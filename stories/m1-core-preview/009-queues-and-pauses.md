# ST-009 — Order claims by queue and priority, and pause queues or all processing

**Milestone:** M1 · **Epic:** m1-core-preview · **Priority:** must · **Depends on:** ST-008

## Context

Decides which job a worker claims next and lets an operator stop claims. Within a worker, claims follow its ordered queue list strictly (INV-110) and, within one queue, priority and then enqueue order (INV-111), with priority 0 for a job that sets none (REQ-108). A queue can carry a concurrency limit that holds across every node (INV-107). An operator can pause and resume a queue (REQ-160, REQ-161, INV-113, SCN-110) and turn the global maintenance pause on and off (REQ-162, REQ-163, INV-114). LIV-100 holds for one queue with equal priorities; starvation under strict priority is accepted (LIV-100's notes). REQ-160, REQ-161, INV-113, REQ-162, REQ-163 and INV-114 are tagged M2 and SCN-110 is inferred M2: the owner decided on 2026-11-10 to build both pauses in M1, because M1's claim rule REQ-123, the M1 queues page (dashboard REQ-312) and the recurring trigger (recurring REQ-216, INV-212) read them. REQ-108 is inferred M2 because of log capture, but INV-111 (M1) orders by its priority default; its capture level and CapturedLogLimit are only option defaults here, which ST-045 uses when it builds capture (REQ-165, INV-126).

Builds on ST-008, whose claim (REQ-123) was built with every queue active and maintenance off, and whose node limit (INV-106) must keep holding. Priority comes from EnqueueOptions (TECH-20, ST-007), the [Priority] attribute and fluent configuration (TECH-17, ST-002), where ST-002's INV-123 (the fluent value wins over the attribute) must keep holding for priority, and the queue order from AddWorker (TECH-128, ST-005). Built on by ST-026 (no recurring trigger while maintenance is on, recurring INV-210), ST-034 (the queues page's pause and resume actions), ST-042 (concurrency keys, rate limits, the LongRunning limit and weighted round-robin; it keeps INV-110 holding) and ST-045 (capture under REQ-108's defaults). INV-111's "among those its concurrency key and rate limit admit" is built against what exists: no job has a key or a rate limit before ST-042. INV-114's notes also keep lease recovery and cleanup running during maintenance; ST-013 and ST-021 build those duties.

Lives in the core package's engine and in-memory store (TECH-112, TECH-43). The pause flags and the queue limit are store state that every node's claim reads (INV-107's notes: enforced by the store at claim time); ST-030 proves the same on PostgreSQL. The specs name no method for pausing a queue or switching maintenance (open question 1), no option for a queue's concurrency limit (open question 2) and no option names for the capture defaults (open question 4).

## Acceptance criteria

### AC-1 · REQ-108 · must

> The system shall give every job a priority of 0 unless one is set, and capture log lines at Information level and above, up to CapturedLogLimit = 256 KB per job, by default.

- Given a job enqueued without a priority from EnqueueOptions (TECH-20), the [Priority] attribute or fluent configuration (TECH-17), then its stored priority is 0, and it is claimed in enqueue order among the other priority-0 jobs of its queue (INV-111).
- Given a priority set by attribute and fluently, then the fluent value is used (INV-123); given a per-enqueue priority as well, then the per-enqueue value is used (INV-123's notes).
- Given neither a capture level nor CapturedLogLimit is configured, then the effective options are Information and above, and 256 KB per job; given either is configured, the configured value is effective. What capture does with them is REQ-165 and INV-126 (ST-045).

### AC-2 · REQ-160 · must

> When an operator pauses a queue through the API or the dashboard, the system shall mark the queue paused.
>
> *Transition:* Queue: Active → Paused · *Actor:* Operator

- Given queue reports is active, when an operator pauses it through the API, then the queue is paused for every node sharing the store, and no node claims from it afterwards (INV-113, SCN-110).
- Given the pause, then the queue's jobs keep their state, attempt number and order (INV-111); only the queue changes.
- Given reports is already paused, when an operator pauses it again, then it stays paused. What the call answers in that case, and for a queue name that no job or worker uses, is open question 1.
- The dashboard's pause action is dashboard REQ-312 (ST-034).

### AC-3 · REQ-161 · must

> When an operator resumes a paused queue through the API or the dashboard, the system shall mark the queue active.
>
> *Transition:* Queue: Paused → Active · *Actor:* Operator

- Given queue reports is paused with enqueued jobs, when an operator resumes it through the API, then the queue is active for every node, and a worker serving it claims its jobs again in the order of INV-110 and INV-111.
- Given other queues are paused too, then they stay paused.
- Given reports is already active, when it is resumed, then it stays active; the call's answer is open question 1.

### AC-4 · REQ-162 · must

> When an operator turns on the global maintenance pause, the system shall mark maintenance on.
>
> *Transition:* Maintenance: Off → On · *Actor:* Operator

- Given maintenance is off, when an operator turns it on, then maintenance is on for every node sharing the store, and no node claims any job while it is on (INV-114).
- Given maintenance is on, then queue pauses are unchanged, and due scheduled jobs are still promoted (REQ-122, INV-114's notes).
- Given maintenance is already on, when it is turned on again, then it stays on. How an operator turns it on, and whether the dashboard offers it, is open question 1.

### AC-5 · REQ-163 · must

> When an operator turns off the global maintenance pause, the system shall mark maintenance off.
>
> *Transition:* Maintenance: On → Off · *Actor:* Operator

- Given maintenance is on and jobs wait in active queues, when an operator turns it off, then maintenance is off and running worker nodes claim those jobs again (REQ-123).
- Given a queue was paused before or during maintenance, when maintenance is turned off, then that queue stays paused (INV-113).
- Given maintenance is already off, when it is turned off again, then it stays off.

### AC-6 · INV-107 · must

> Where a queue has a concurrency limit, the system shall never run more jobs from that queue at once, across all nodes, than its limit.
>
> *Notes:* Decided by the owner on 2026-11-06: cluster-wide, enforced by the store at claim time like concurrency keys. Per-node capacity is the node concurrency limit (INV-106).

- Concurrency test: given queue q with concurrency limit L, several worker nodes on one store whose node limits together exceed L, and many more than L jobs in q, when the nodes claim at once while jobs finish at random, then at no observed moment are more than L jobs of q processing across all nodes.
- Given q has L jobs processing, then q's other jobs stay Enqueued while the nodes still claim from other queues (INV-110: q has no claimable job); when one of q's jobs ends, a job of q can be claimed again.
- Given a queue without a concurrency limit, then only each node's limit bounds it (INV-106).
- Where the limit is set, and what happens when it is lowered below the jobs already processing, is open question 2.

### AC-7 · INV-110 · must

> Where a worker uses strict queue priority, which is the default, the system shall claim from the first queue in the worker's ordered list before any later queue, as long as the first has a claimable job.
>
> *Notes:* Strict priority can starve later queues indefinitely; LIV-100 is written to make the model report it.

- Given a worker whose ordered list is critical then default, strict priority (the default) and claimable jobs in both queues, when it claims repeatedly, then every claim takes a job from critical until critical has no claimable job, and only then a job from default.
- Given critical has jobs that are not claimable, because critical is paused (INV-113) or at its concurrency limit (INV-107), then the worker claims from default.
- Property: over random enqueues into the listed queues and random claim and finish orders, no claim takes a job from a later queue while an earlier queue in that worker's list has a claimable job.
- Starvation of later queues is accepted (LIV-100's notes); weighted round-robin is REQ-159 (ST-042).
- Whether a job this node cannot run (no handler for its name, or the node at its LongRunning limit) counts as claimable is open question 6.

### AC-8 · INV-111 · must

> The system shall claim jobs within one queue, among those its concurrency key and rate limit admit, by highest priority first and, for equal priority, in the order they were enqueued.
>
> *Notes:* Decided by the owner on 2026-11-06: a job blocked by its key or rate limit is skipped, so it never blocks lower-priority jobs behind it.

- Given one queue with job a at priority 0 and then jobs b and c at a higher priority, enqueued in the order a, b, c, when one slot at a time is free, then the claims take b, c, a.
- Property: over random enqueues into one queue with random priorities and one free slot at a time, each claim takes an enqueued job of the highest priority present, and among equal priorities the one enqueued first.
- Given a job of the queue that returns to Enqueued after other jobs of its priority were enqueued, as a retry does (jobs A-8), then it is claimed after them. The test puts the job back into Enqueued in the store directly; the retry path itself, REQ-130, is built in ST-011. Other returns to Enqueued are open question 5.
- Given a job that its concurrency key or rate limit does not admit, then the next admitted job in this order is claimed instead, so the blocked job never holds back lower-priority jobs (INV-111's notes). Built against what exists: this criterion is closed with ST-042, which builds keys and rate limits (REQ-156).
- Which numbers count as higher priority is open question 4; whether a job this node cannot run is skipped is open question 6.

### AC-9 · INV-113 · must

> While a queue is paused, the system shall never claim a job from that queue.
>
> *Notes:* Jobs already processing keep running; scheduled jobs are still promoted into the paused queue and wait there. Both are readings, not stated.

- Concurrency test: given queue q with enqueued jobs and free workers serving it on several nodes, when an operator pauses q while the nodes claim, then no claim of a job from q commits after the pause has committed; jobs of q claimed before it keep running and end by their own rules (INV-113's notes; REQ-160's only effect is to mark the queue paused).
- Given q is paused, when a job is enqueued into q or a scheduled job of q falls due, then it is stored or promoted into q (REQ-120; REQ-122 promotes with no condition on the queue) and stays Enqueued until q is resumed (INV-113's notes).
- Given q is paused, then jobs of other queues are claimed as before.
- Property: over random interleavings of pause, resume, enqueue, claim and finish on two nodes, no job of a queue moves to Processing while that queue is paused.
- The two readings in INV-113's notes are open question 3.

### AC-10 · INV-114 · must

> While maintenance is on, the system shall never claim any job on any node.
>
> *Notes:* Decided by the owner on 2026-11-06: maintenance stops claims (here) and recurring triggers (recurring module). Promotion of scheduled jobs, lease recovery and cleanup keep running, so state stays correct and nothing piles up unseen.

- Concurrency test: given several worker nodes claiming from several queues, when an operator turns maintenance on, then no claim on any node commits after that write has committed, whatever the queue; jobs claimed before it keep running.
- Given maintenance is on, when a scheduled job falls due, then it is promoted to Enqueued (REQ-122) and waits there (INV-114's notes).
- Property: over random interleavings of maintenance on and off, pause and resume, enqueue, claim and finish on two nodes, no job moves to Processing while maintenance is on.

### AC-11 · LIV-100 · should

> While a job is enqueued in an active queue, maintenance is off and at least one running worker node serves its queue, the system shall eventually claim the job.
>
> *Notes:* Not stated as such; follows from SCH-1 'runs as soon as a worker is free'. Expected to fail under strict queue priority (INV-110), under a permanently held concurrency key, or behind a stream of higher-priority jobs. That is the finding we want the model to report. Fails by design under strict queue priority (INV-110) and job priority (INV-111) when higher-ranked work arrives continuously; weighted round-robin (REQ-159) avoids it. Holds for one queue with equal priorities. Confirmed by the model 2026-11-06 (F-12); accepted by the owner.

- Given one queue, every job at the same priority, the queue active, maintenance off and a running worker node serving the queue, when jobs are enqueued and the fake clock is advanced while the worker runs them, then every enqueued job is eventually claimed.
- Given the queue is paused or maintenance is on, then the obligation lapses (jobs A-6); once the queue is resumed and maintenance is off, the waiting jobs are eventually claimed.
- Not asserted: claims under strict queue priority (INV-110) or behind a continuous stream of higher-priority jobs (INV-111). The model shows starvation there and the owner accepted it (LIV-100's notes).

### AC-12 · SCN-110 · scenario

> **Paused queue is not drained**
>
> *Given:* Job j is enqueued in queue reports; a free worker serves reports.
>
> 1. REQ-160 — operator pauses reports
> 2. REQ-123 — worker tries to claim j
>
> *Impossible at step 2.*

## Open questions

1. **Decide in delivery** · REQ-160, REQ-161, REQ-162, REQ-163: which public methods pause and resume a queue and turn maintenance on and off, and what do they answer for a queue already in the requested state or a queue name no job or worker uses? IJobClient (TECH-19) and IRecurringJobManager (TECH-21) list none, and unlike REQ-160 the maintenance sentences do not say whether the dashboard offers the switch.
2. **Decide in delivery** · INV-107: where is a queue's concurrency limit configured, and what happens when two nodes configure different limits or the limit is lowered below the jobs already processing? TECH-128 puts queues and their order in AddWorker options, while INV-107's limit is cluster-wide and enforced by the store; REQ-158 answers the lowering question for concurrency keys only.
3. **Decide in delivery** · INV-113: confirm the two readings in INV-113's notes as rules: jobs already processing keep running, and scheduled jobs are still promoted into a paused queue. The notes call them "readings, not stated", unlike INV-114's notes, which the owner decided. The criteria follow them because REQ-160's only effect is "mark the queue paused" and REQ-122 promotes with no condition on the queue.
4. **Decide in delivery** · REQ-108, INV-111: the option names for the capture level and CapturedLogLimit, whether a larger priority number means a higher priority, and whether negative priorities are accepted. The glossary gives CapturedLogLimit as a term only, and only `Jobs_Throttle.tla` reads priority 1 as above the default 0.
5. **Decide in delivery** · INV-111: for "in the order they were enqueued", is a job that re-enters Enqueued by promotion (REQ-122), recovery (REQ-132), requeue (REQ-141) or return from Unroutable (REQ-125) ordered by that moment or by its first enqueue? jobs A-8 settles only retries.
6. **Decide in delivery** · INV-110, INV-111: does a job that this node cannot run, because it has no handler for the job's name or is at its LongRunning limit, count as "claimable" for INV-110, and is it skipped for INV-111? REQ-123 claims only for a node with a handler for the job's name, REQ-124's notes expect nodes without the handler during a rolling deploy, and jobs A-14 models one job name, so the case was never checked. Under a cluster-wide reading, such a node never claims from its later queues.
