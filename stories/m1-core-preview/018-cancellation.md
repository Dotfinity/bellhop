# ST-018 — Cancel jobs, including running ones

**Milestone:** M1 · **Epic:** m1-core-preview · **Priority:** must · **Depends on:** ST-017

## Context

Lets an application or operator cancel any unfinished job. A job that is not processing is cancelled at once (REQ-134). For a processing job the request is recorded and the handler's token is signalled wherever it runs (REQ-135). The job then ends Cancelled when the handler honours the token (REQ-136), and also when it would otherwise leave processing with attempts left, through lease expiry, a shutdown, a timeout or a retryable exception (REQ-190), so a cancelled job never runs again. Every handler that keeps running after its node gave it up is logged and recorded in its attempt (REQ-191), so abandoned work is visible rather than counted.

Builds on ST-017 (the draining node's shutdown check, whose two outcomes are REQ-140's release and REQ-190's shutdown cancellation, and hosting REQ-29's wait for them), and through it on ST-014 (timeouts and abandonment, REQ-138 and REQ-186), ST-013 (lease expiry, REQ-132 and REQ-133, and fencing, INV-128), ST-012 (Unroutable jobs), ST-011 (the failure path, REQ-129 and REQ-131) and ST-010 (IJobEvents, REQ-169). It must keep holding REQ-169 (ST-010; this story makes the first Cancelled transitions, so OnCancelled is first raised here), REQ-131, REQ-133 and REQ-186 (ST-011, ST-013, ST-014; a cancel request does not stop these dead-letters), and TECH-19 (ST-007; `CancelAsync` gets its behaviour here). It adds REQ-191's warning and record to the abandonment paths those stories built. ST-020 builds on it (a requeue clears the request), as do ST-025 (the CancelPrevious overlap policy) and ST-028 (traces and metrics). ST-038 (continuations) constrains REQ-134.

Lives in the Bellhop core package (TECH-112). The entry point is `IJobClient.CancelAsync` (TECH-19), and the token is the `CancellationToken` of `HandleAsync` (TECH-15). The operator's cancel in the dashboard is an operate action (dashboard INV-301) that the dashboard stories wire to the same behaviour. What `CancelAsync` reports and the shape of REQ-191's attempt record are not in the specs (open questions 1 and 5). Continuations, the only source of Awaiting jobs, arrive with ST-038, so REQ-134's Awaiting state is built against what exists: tests write an awaiting job into the store directly. Likewise REQ-191's case of a job that is no longer stored is set up by removing the job from the store directly, until ST-020 and ST-021 add deletion and retention.

### Modeling assumptions

Decisions the model took where the sentences were silent. Build to them, or raise an open question.

- hosting A-26 (affects REQ-29, jobs REQ-190): *(new)* Cancellation requests (jobs REQ-135) are not tracked. At the shutdown cancel, which held jobs have one is chosen freely, timed-out jobs included. `Chk_NoShutdownCancellation` is a trap: it is expected to be violated, showing that a node can mark a job cancelled at shutdown and then stop
- jobs A-3 (affects REQ-132, REQ-139, REQ-140, REQ-190, hosting REQ-29): A crash removes the node's handlers at once; its leases expire later. A draining node stops as hosting REQ-29's run-5 wording says. "In-flight job" (hosting `Node.inFlightJobs`, not defined) is a running handler that holds its job's current lease. A job settled by REQ-138/186/190, released by REQ-140 or lost to lease expiry is no longer in flight, though its handler may still be running, as hosting REQ-29's notes say. After ShutdownTimeout the node waits for its check of every in-flight run (A-19) and for the release or cancellation that check calls for. Every such attempt succeeds, because store outages are not modeled here. A stopped node's handlers stop with it.
- jobs A-5 (affects REQ-129–140, REQ-186, REQ-190): OperationCanceledException is thrown only after a token was signalled. REQ-136 and REQ-138/186 take precedence over REQ-129/131 for it (REQ-136 notes). Every other overlap between the throw rules is checked, not resolved: `Chk_SingleRule` counts the rules (holds) and `Chk_SingleOutcome` compares their outcomes (holds).
- jobs A-19 (affects REQ-139, REQ-140, REQ-190, hosting REQ-29): Cancelling a token for shutdown (REQ-139) and the node's check are separate steps. Following REQ-190's trigger and REQ-140's notes, the check is made once per in-flight run, before the node stops, and it reads the cancellation request and the timeout signal as they are then. It has three outcomes: release (REQ-140), cancel (REQ-190) or neither (a timed-out run with no request, left on its timeout path). The only remaining assumption is that the check is always made, which only REQ-140's notes say.
- jobs A-20 (affects REQ-140, REQ-190, INV-128): "The job's node" (REQ-140) and "its draining node" (REQ-190) are the node whose run holds the job's current lease token. A node whose run lost its lease to another node's claim makes no shutdown write for that job.
- jobs A-18 (affects REQ-191, INV-128): REQ-191's record and log line are history only. Abandonment is recorded as the tag `Abandoned` in the step that abandons (`AbandonOnTimeout`, both outcomes of the shutdown check in `ReleaseOnShutdown`), and `Prop_AbandonRecorded` checks that. The tag is per job, not per attempt, so the property is checked where a first attempt is abandoned. The lease-lost trigger is the predicate `LeaseLostRecordable`: a running handler on a live node whose token is not current or whose job is not processing. For a job that was deleted or removed, only the log line can be written, because "that attempt" no longer exists.

## Acceptance criteria

### AC-1 · REQ-134 · must

> When an application or operator cancels a job that is scheduled, enqueued, awaiting, failed or unroutable, the system shall mark the job cancelled immediately.
>
> *Transition:* Job: Scheduled | Enqueued | Awaiting | Failed | Unroutable → Cancelled · *Actor:* Application
>
> *Notes:* Decided by the owner on 2026-11-06: every job that is not finished and not Processing is cancelled at once. Processing is REQ-135 and REQ-136.

- Given a job that is Scheduled, Enqueued, Failed or Unroutable, or Awaiting (written into the store directly), when an application calls `CancelAsync` for it, then the job is Cancelled by the time the call returns, and IJobEvents' OnCancelled is called once, after the write has committed (REQ-169).
- Given a cancelled job, then it never runs: a scheduled one is not promoted when its scheduledAt passes (SCN-107), a failed one is not enqueued when its retryAt passes (REQ-130), an unroutable one does not return to Enqueued when a handler appears (REQ-125), and an enqueued one is never claimed (REQ-123).
- Concurrency: a cancel racing the claim of the same enqueued job ends either Cancelled and never claimed, or Processing with the request recorded and the token signalled (REQ-135). A job is never Cancelled while a handler holds its current lease.
- Concurrency: a cancel racing the promotion of a scheduled job (REQ-122) or a failed one (REQ-130) ends Cancelled either way.
- Cancelling a processing job is REQ-135. Cancelling a finished job or an unknown id is open question 2.

### AC-2 · REQ-135 · must

> While a job is processing, when an application or operator cancels it, the system shall record the cancellation request and signal the handler's cancellation token on whichever node runs the job.
>
> *Transition:* Job: Processing → Processing · *Actor:* Application

- Given job j processing on worker node B, when an application on another node calls `CancelAsync(j)`, then j's cancellation request is recorded in the store, j stays Processing, and the token of B's handler for j is signalled. How soon B signals it is open question 3.
- Given B is cut off from the store, then the request is still recorded, and j's lease expiry decides it (REQ-190, SCN-122).
- Given the request is recorded, then j's outcome follows its handler: a normal return makes it succeeded (REQ-127), an OperationCanceledException makes it cancelled (REQ-136), and any other exception goes to REQ-190 or REQ-131.
- Given the request is already recorded, when `CancelAsync(j)` is called again, then j stays Processing with its request recorded and nothing else changes.

### AC-3 · REQ-136 · must

> While a job is processing and its cancellation was requested, when its handler throws OperationCanceledException, the system shall mark the job cancelled.
>
> *Transition:* Job: Processing → Cancelled · *Actor:* Handler
>
> *Notes:* Decided by the owner on 2026-11-06: the outcome follows the handler. If it returns normally the job is Succeeded (REQ-127), because the work was done; any other exception takes the normal failure path (REQ-129, REQ-131); if it ignores the token it stays Processing until its timeout, if it has one. Resolved after refiner-model 2026-11-06 F-6/F-7: a cancelled job is never retried. If the handler throws another exception, ignores the token past a timeout, loses its lease or is released at shutdown, REQ-190 marks it cancelled instead of returning it to enqueued or failed. A normal return still marks it succeeded (REQ-127).

- Given job j processing with its cancellation requested, when its handler throws OperationCanceledException, then j is Cancelled and is never retried, at any attempt number, its last included.
- Given the same, when the OperationCanceledException comes after j's timeout token was signalled or after its token was cancelled for shutdown, then j is still Cancelled: not failed or dead-lettered for the timeout (REQ-138, REQ-186) and not released (REQ-140), whose guards exclude a requested cancellation.
- Given the request is recorded, when the handler returns normally, then j is Succeeded (REQ-127).
- Given no request is recorded, then an OperationCanceledException never makes j Cancelled; REQ-138, REQ-186, REQ-140 or the failure rules decide it.
- Given the request is recorded, when the handler throws a PermanentJobFailureException, or another exception at its last attempt or when the retry policy declines, then j is dead-lettered (REQ-131), not Cancelled.

### AC-4 · REQ-190 · must

> While a job is processing and its cancellation was requested, when its lease expires with attempts left, its draining node finds its handler still running after cancelling its token for shutdown (REQ-139), its handler is still running TimeoutGracePeriod after its timeout token was signalled, or its handler throws an exception other than OperationCanceledException or PermanentJobFailureException while the attempt number is below maxAttempts and the retry policy allows another attempt, the system shall abandon the handler if it is still running and mark the job cancelled instead of returning it to enqueued, marking it failed or dead-lettering it for the timeout.
>
> *Transition:* Job: Processing → Cancelled · *Actor:* system
>
> *Notes:* Resolved after refiner-model 2026-11-06 F-7 (recommended option): a cancellation request recorded by REQ-135 is never lost when the job leaves processing some other way, so a cancelled job does not run again. The guards of REQ-129, REQ-132, REQ-138, REQ-140 and REQ-186 exclude a requested cancellation, so exactly one rule applies. Exhausted attempts on a handler exception or lease expiry still dead-letter (REQ-131, REQ-133), because a dead-lettered job does not run again. Run 2 F-1 (recommended option): the exception branch covers exactly the failures REQ-129 would retry. A failure that would dead-letter (attempts used up, the retry policy declines, or a PermanentJobFailureException) still dead-letters under REQ-131: a cancel request stops the next attempt, it does not rewrite how this attempt ended. Run 4 F-1 (recommended option, with the trigger made explicit): the shutdown branch used to read "its node releases it at shutdown", but REQ-140 never releases a job whose cancellation was requested, so the branch had no event of its own. It now names the event REQ-140 reacts to, the token cancelled for shutdown, and hosting REQ-29 waits for it, so the outcome is Cancelled with or without attempts left. Run 5 F-2 (recommended option): the shutdown branch covers only a handler that is still running when its token is cancelled for shutdown. An OperationCanceledException thrown by a cancel-requested job, at shutdown or not, is REQ-136's, so exactly one rule decides each event again; the branch had mirrored REQ-140, which needs its exception clause because no other rule releases a cooperating handler. Run 6 F-1 (recommended option): the shutdown branch is the draining node's check after it cancels the token, the same check at which REQ-140's 'if the handler is still running' is judged, so REQ-140 and this branch are the two outcomes of one check and the cancellation request is read when the check is made. As an event inside a while, the branch had already happened when a request arrived between the token and the node's shutdown write, REQ-140's guard failed too, and the job was left to lease expiry and dead-lettered at its last attempt. A request made after that check is not part of the shutdown. Only a timed-out handler still in its grace period can be in flight then, because the check released or cancelled every other one; the node does not wait for it, and it ends as any cancel-requested job that is still processing does, by its handler's outcome or by lease expiry. Run 7 to run 9 F-1: these notes deliberately name no rules; each list or citation they gave fell out of step with the rules.

- Lease: given j processing with its cancellation requested and attempts left, when its leaseExpiresAt passes according to the database clock, then a running worker node marks j Cancelled instead of returning it to Enqueued (REQ-132), and j is never claimed again (SCN-122). At its last attempt, j is dead-lettered with reason Interrupted instead (REQ-133).
- Shutdown: given j's cancellation was requested before its draining node's shutdown check, when the node finds j's handler still running after cancelling its token for shutdown (REQ-139), then the handler is abandoned and j is Cancelled, at any attempt and whether or not its timeout token was signalled, and the node does not stop before this write was attempted (hosting REQ-29).
- Given a request made after that check, then the shutdown does not cancel j and the node does not wait for it; j ends by its handler's outcome or by lease expiry, like any cancel-requested job that is still processing.
- Timeout: given j's timeout token was signalled and its cancellation was requested, when its handler is still running TimeoutGracePeriod after the signal, then the handler is abandoned and j is Cancelled, at any attempt, not failed or dead-lettered with reason Timeout (REQ-138, REQ-186).
- Exception: given j's cancellation was requested, when its handler throws an exception other than OperationCanceledException or PermanentJobFailureException while its attempt number is below maxAttempts and the retry policy allows another attempt, then j is Cancelled, not failed (REQ-129). Otherwise the failure dead-letters it (REQ-131).
- Concurrency: a request racing a lease-expiry recovery with attempts left ends Cancelled either way: by this rule when the request is recorded first, by REQ-134 when the job is already back in Enqueued.
- Property: over random combinations of a cancellation request (none, before or after the shutdown check), the timeout signal, the shutdown signal, lease expiry, the handler's outcome (return, OperationCanceledException, retryable or permanent exception) and the attempt number, exactly one of REQ-127, REQ-129, REQ-131, REQ-132, REQ-133, REQ-136, REQ-138, REQ-140, REQ-186 and REQ-190 decides each event (jobs A-5), and a job whose cancellation was requested never leaves Processing for Enqueued or Failed.

### AC-5 · REQ-191 · must

> When the system abandons a handler that is still running, for whatever reason (a timeout, REQ-138, REQ-186, REQ-190; a release at shutdown, REQ-140; a cancellation at shutdown, REQ-190), or refuses the heartbeat of a handler that is still running because its lease token is no longer current or its job is no longer processing (INV-128), the system shall log a warning naming the job, its attempt and the node, and record in that attempt that its handler was abandoned or lost its lease and is still running outside the node's concurrency limit.
>
> *Notes:* Decided by the owner after refiner-model 2026-11-06 F-5: abandoned handlers run outside the node's limit (INV-106) and are made visible rather than counted. Run 2 F-7 (recommended option): a handler whose lease was lost (a partition or long pause, then recovery by another node) is the third way a node keeps running a handler it no longer holds a claim for, so it is recorded the same way; the node claims again as soon as it holds fewer claims than its limit (REQ-123). Run 3 F-2 (recommended option): a lease-lost handler whose job was dead-lettered or cancelled on recovery kept a current token and was never recorded, while its node claimed again; it is now caught by the 'no longer processing' test of INV-128. Run 5 F-1 (option 2, recommended in spirit): REQ-190's shutdown branch abandons a still-running handler with no timeout and no release, so the closed list of causes missed it. The trigger now covers every abandonment, and the causes are in dependsOn so that a change to any of them flags this sentence for re-checking. Why the handler was abandoned is the attempt's own outcome (timed out, released or cancelled).

- Given a handler that is still running when it is abandoned, after TimeoutGracePeriod (REQ-138, REQ-186, REQ-190), on a release at shutdown (REQ-140) or on a cancellation at shutdown (REQ-190), then a warning is logged that names the job, its attempt and the node, and that attempt records that its handler was abandoned and is still running outside the node's concurrency limit.
- Given a handler that is still running whose heartbeat is refused because its lease token is no longer current or its job is no longer processing (INV-128), then the same warning is logged and the attempt records that its handler lost its lease and is still running outside the limit (SCN-125).
- Given a handler that returned or threw before the step that would abandon it, then no such warning or record is written.
- Given an abandoned or lease-lost handler that keeps running, then its node does not count it: the node claims again as soon as it holds fewer claims than its limit (REQ-123, INV-106).
- Given the job is no longer stored when the heartbeat is refused, then only the warning is written (jobs A-18). Tests remove the job from the store directly until REQ-144 and REQ-145 exist (ST-020, ST-021).
- Property: over random runs that mix every cause above with normal returns and throws, every abandonment of a still-running handler and every refused heartbeat of one produces the warning and the record, and nothing else produces either. How often a repeated refusal logs is open question 5.

### AC-8 · SCN-125 · scenario

> **A lease-lost run of a job cancelled on recovery is fenced and recorded**
>
> *Given:* Job j is processing on node n1 with lease token 1 and attempts left. A partition stops n1's heartbeats while j's handler keeps running.
>
> 1. REQ-135 — an operator cancels j and the request is recorded
> 2. REQ-190 — j's lease expires and a running worker node marks j cancelled, with no new lease token
> 3. INV-128 — the partition heals and n1's heartbeat for j presents token 1
> 4. REQ-191 — the refused heartbeat is logged and recorded in j's attempt
>
> *Then:* j is still Cancelled and unchanged, and its attempt records that its handler lost its lease and is still running outside n1's concurrency limit.
>
> *Notes:* refiner-model 2026-11-06 run 3 F-2 regression.

## Open questions
