# ST-017 — Shut down gracefully and hand unfinished jobs to other nodes

**Milestone:** M1 · **Epic:** m1-core-preview · **Priority:** must · **Depends on:** ST-014, ST-016

## Context

Makes a host stop safe for rolling deploys. A running node stops claiming (REQ-27), gives its in-flight jobs ShutdownTimeout to finish (REQ-28), then cancels the tokens of the handlers still running (REQ-139) and releases their leases with the attempt taken back, so another node claims them at once and the interrupted run costs nothing (REQ-140). The node then stops, and a store outage never holds the stop up (REQ-29). A host stop while the node is still starting, for example while it waits out a database outage, stops the node without ever starting the worker (REQ-55).

Builds on ST-014 (timeouts: a job whose timeout token was signalled is not released, SCN-124, and settles under REQ-138 or REQ-186) and ST-016 (startup retries, REQ-25, and the migration lock that a node leaving Starting releases, REQ-56), and through them on ST-013 (lease expiry, REQ-132 and REQ-133, and fencing, INV-128) and ST-008 (claims, REQ-123). It must keep ST-011's REQ-131 holding (a failure at the last attempt still dead-letters, the shutdown OperationCanceledException excepted) and ST-014's REQ-186 (a timed-out job at its last attempt is dead-lettered, not released). ST-018 builds on it: it adds REQ-190's cancellation at shutdown and REQ-191's record of the abandoned handler, and constrains REQ-140 and REQ-29.

Lives in the Bellhop core package (TECH-112: engine and hosting integration). The host stop reaches Bellhop through the hosted service that AddBellhop registers with Microsoft.Extensions.Hosting (TECH-11), the token is the `CancellationToken` of `HandleAsync` (TECH-15), and all time comes from `TimeProvider` (TECH-12), so tests move ShutdownTimeout with a fake clock. How ShutdownTimeout relates to the host's own shutdown limit is open question 1. Cancellation requests arrive with ST-018 (REQ-135), so REQ-140's "its cancellation was not requested" and REQ-29's wait for the cancellations of REQ-190 are built against what exists: tests write a cancellation request onto the job in the store directly and check that the job is not released.

## Acceptance criteria

### AC-1 · REQ-28 · must

> The system shall give in-flight jobs ShutdownTimeout to finish after the host stops, 30 seconds by default (ShutdownTimeout).

- Given ShutdownTimeout is not configured and a running node has an in-flight handler that ignores its token, when the host stops, then the handler's token is not cancelled for shutdown while less than 30 seconds have passed since the stop, and is cancelled once they have (REQ-139).
- Given ShutdownTimeout is configured as 5 seconds, in the Bellhop configuration section or in code, then the criterion above holds with 5 seconds in place of 30; set in both places, the code value is used (hosting REQ-17).
- Given an in-flight handler that returns within ShutdownTimeout, then the job is succeeded (REQ-127) and its token is never cancelled for shutdown.
- Given ShutdownTimeout is configured longer than LeaseDuration, then a handler that returns within ShutdownTimeout still succeeds, because the heartbeat keeps renewing its lease while the node drains (REQ-126).

### AC-2 · REQ-27 · must

> While a node is running, when the host stops, the system shall stop claiming new jobs on that node.
>
> *Transition:* Node: Running → Draining · *Actor:* Host

- Given a running worker node with enqueued jobs it could claim, when the host stops, then the node is Draining and claims no job from then on, even when its in-flight jobs finish and it holds fewer claims than its concurrency limit (REQ-123 needs a running node).
- Given a second running worker node on the same store, then the jobs the draining node leaves unclaimed are claimed by the second node (REQ-123).
- Concurrency: a claim racing the host stop either lands before the node is Draining, and that job drains like any other in-flight job, or does not happen. No claim is made by a node after it is Draining (SCN-4: "it claimed nothing after the host stopped").

### AC-3 · REQ-29 · must

> While a node is draining, when every in-flight job has finished, or ShutdownTimeout has passed, the remaining jobs' tokens were cancelled and the lease releases and cancellations that jobs REQ-140 and REQ-190 call for at shutdown were attempted, the system shall stop the node.
>
> *Transition:* Node: Draining → Stopped · *Actor:* Host
>
> *Notes:* The job side (cancel token, release lease, job returns to Enqueued) is REQ-140 in the jobs module. The release is best-effort (refiner-model 2026-11-06 F-5, recommended option): a release that fails because the store is down is covered by lease expiry (jobs REQ-132), and that attempt then counts, so a store outage never blocks shutdown. jobs run 3 F-1: a job whose timeout token was signalled is not released (jobs REQ-140). It stays in flight until jobs REQ-138 or REQ-186 settles it, so the drain waits for it up to ShutdownTimeout like any other job; with the defaults (both 30 s) a timeout signalled before the stop signal settles within the drain. Only a handler that jobs REQ-138 or REQ-186 has not settled when the node stops is left to lease expiry, and its attempt counts (jobs REQ-132, REQ-133). refiner-model 2026-11-07 run 4 F-1 (recommended option): the earlier note said the drain does not wait for it, which the sentence never said. jobs run 4 F-1 (recommended option): the node also waits for the cancellations jobs REQ-190 makes at shutdown, so a job whose cancellation was requested before the node's shutdown check (jobs REQ-140, REQ-190) ends Cancelled at a graceful stop, even at its last attempt; without the wait, lease expiry dead-lettered it (jobs REQ-133). jobs run 7 and run 8 F-1: a request made after that check is not part of the shutdown. Only a timed-out handler still in its grace period can be in flight then; the node does not wait for it, and it ends as any cancel-requested job that is still processing does, by its handler's outcome or by lease expiry (jobs module); these notes deliberately name no jobs rules.

- Given a draining node whose in-flight jobs all finish before ShutdownTimeout, then the node is Stopped when the last one finishes, without waiting for ShutdownTimeout, and no token was cancelled for shutdown. With no in-flight job at the stop, it is Stopped at once.
- Given a draining node with a handler that ignores its token (SCN-4), then the node is not Stopped before ShutdownTimeout has passed. Once it has, the token is cancelled (REQ-139), the release is attempted (REQ-140), and the node is Stopped without waiting for the handler to return.
- Given the store is unreachable when the release is attempted, then the attempt fails, the node is still Stopped, and the job is later recovered by lease expiry with its attempt counted (REQ-132, or REQ-133 at its last attempt).
- Given an in-flight job whose timeout token was signalled before the stop and which REQ-138 or REQ-186 has not settled, then the node counts it as in flight: it is not Stopped before that job settles or ShutdownTimeout passes. If ShutdownTimeout passes first, the node is Stopped without releasing it, and lease expiry later recovers it with its attempt counted (REQ-132, REQ-133).
- Given a job whose cancellation was requested before the node's shutdown check (written onto the job in the store directly until ST-018 adds REQ-135), then the node does not release it. The cancellation the node attempts and waits for is REQ-190's, which ST-018 adds and checks under this item.
- Property: over random interleavings of handlers returning, throwing and ignoring their tokens, timeouts, ShutdownTimeout passing and store outages, a draining node always reaches Stopped, and never before every in-flight job has finished or ShutdownTimeout has passed with every remaining token cancelled and every release attempted.

### AC-4 · REQ-55 · must

> While a node is starting, when the host stops, the system shall stop retrying the store connection and mark the node stopped without starting the worker or any background duty.
>
> *Transition:* Node: Starting → Stopped · *Actor:* Host
>
> *Notes:* Added by refiner-model 2026-11-06 F-1 (recommended option): REQ-25 can keep a node Starting for as long as a database outage lasts, and without this rule a host stop in that window was followed by REQ-18 starting a worker that claims jobs. Same host-stop event as REQ-27, which covers a running node.

- Given a node starting with the store unreachable, retrying the connection (REQ-25), when the host stops, then the node makes no further connection attempt, is Stopped and the host's stop completes.
- Given that stop, when the store becomes reachable afterwards, then the node never becomes Running, never starts the worker or any background duty, and claims no job.
- Given a starting node at any other step before it is marked running (REQ-12), when the host stops, then it is Stopped without starting the worker or any background duty. If it holds the migration lock, it releases the lock first (REQ-56).
- Concurrency: a host stop racing hosting REQ-18 either comes first, and the node is Stopped with no worker ever started, or comes after the node is Running, and the node drains under REQ-27. A node is never Stopped with a worker or background duty started by REQ-18 after the stop.

### AC-5 · REQ-139 · must

> While the job's node is draining, when ShutdownTimeout has passed and the job is still running, the system shall signal the handler's cancellation token.
>
> *Transition:* Job: Processing → Processing · *Actor:* Host

- Given a draining node whose handler for job j is still running when ShutdownTimeout passes, then j's handler token is signalled, and j is still Processing at that point; its outcome is REQ-140's or REQ-190's.
- Given a draining node before ShutdownTimeout has passed, then no handler's token is signalled for shutdown.
- Given a handler that finished before ShutdownTimeout passed, then its token is never signalled for shutdown.

### AC-6 · REQ-140 · must

> While the job's node is draining, the job's token was cancelled for shutdown, its timeout token was not signalled and its cancellation was not requested, if the handler is still running or throws OperationCanceledException, then the system shall release the job's lease and take back the attempt it counted, so another node can claim it immediately and the interrupted run does not count towards maxAttempts.
>
> *Transition:* Job: Processing → Enqueued · *Actor:* Host
>
> *Notes:* Decided by the owner on 2026-11-06: shutdown is not the job's fault, so the attempt is not counted; a crash (lease expiry, REQ-132) still counts. The lease is released as soon as ShutdownTimeout passes. The old handler may still run in the stopping process while another node claims the job; that is an expected at-least-once duplicate, and fencing (INV-128) refuses its result. Resolved after refiner-model 2026-11-06 F-8 (recommended option): a handler that honours the shutdown token by throwing OperationCanceledException is released the same way as one that ignores it, so cooperating never costs an attempt. F-7: a job whose cancellation was requested is marked cancelled instead (REQ-190). Run 2 F-2 (recommended option): an OperationCanceledException thrown after both the timeout and the shutdown signal is a timeout (REQ-138, REQ-186), so the attempt counts and a job that keeps timing out during rolling deploys still uses up its attempts. Run 3 F-1 (recommended option): the timeout guard now covers both branches. Run 2 put it on the OperationCanceledException branch only, so a handler that ignored its tokens got its attempt back while one that cooperated did not, and a job that hangs until it times out could survive rolling deploys for ever. A job whose timeout token was signalled before the shutdown signal is a timeout whether the handler cooperates or not (REQ-138, REQ-186); the draining node counts it as in flight until it settles, up to ShutdownTimeout (hosting REQ-29); if the node stops before REQ-138 or REQ-186 settles it, lease expiry counts the attempt (REQ-132, REQ-133). hosting run 4 F-1 corrected this note, which said the drain does not wait for it. Run 6 F-1: this sentence and REQ-190's shutdown branch are judged at the same check, made by the draining node after it cancels the token, so a cancellation requested before that check makes the job cancelled (REQ-190), not released.

- Given node A is draining, ShutdownTimeout has passed and j's token was cancelled for shutdown, with no timeout signal and no cancellation request, when A finds j's handler still running, then j's lease is released, its attempt number goes back to what it was before this claim, j is Enqueued, and another running worker node can claim it at once, before LeaseDuration has passed (SCN-115).
- Given the same, when the handler throws OperationCanceledException instead, then the outcome is the same: j is released with its attempt taken back and is not marked failed (REQ-129 excludes it).
- Given j is at its last attempt, then the release still takes the attempt back, and j is Enqueued, not dead-lettered.
- Given j's timeout token was signalled before the shutdown signal, then j is not released and its attempt is not taken back, whether the handler ignores the tokens or throws OperationCanceledException; it settles under REQ-138 or REQ-186, or by lease expiry with the attempt counted if the node stops first (SCN-124).
- Given j's cancellation was requested before A's check, then j is not released (REQ-190 decides it, ST-018).
- Given j's handler throws any other exception after the shutdown signal, then j is not released and takes the failure path with its attempt counted (REQ-129, REQ-131).
- Concurrency: a handler returning while A makes its check ends with exactly one outcome, succeeded (REQ-127) or released, never both.
- Given j was released and node B has claimed it while A's old handler still runs, when the old handler returns, throws or renews, then the write is refused and logged, and j stays Processing on B with B's lease and attempt (INV-128).
- Given A's run no longer holds j's current lease token (another node claimed j after a lease expiry), then A makes no release write for j (jobs A-20; INV-128 refuses it).

### AC-7 · SCN-4 · scenario

> **Graceful shutdown**
>
> *Given:* A running node has two in-flight jobs; one finishes within ShutdownTimeout and one ignores cancellation.
>
> 1. REQ-27 — host stops
> 2. REQ-29 — timeout passes, the remaining job's token is cancelled and its lease released
>
> *Then:* The node is Stopped, it claimed nothing after the host stopped, and the second job is available to other nodes.

### AC-8 · SCN-115 · scenario

> **Shutdown hands an unfinished job to another node**
>
> *Given:* Node A is processing j, whose handler ignores cancellation; node B is running.
>
> 1. REQ-139 — A is draining, ShutdownTimeout passes, token cancelled
> 2. REQ-140 — lease released
> 3. REQ-123 — B claims j
>
> *Then:* j is Processing on B with attempt 1; the run interrupted by shutdown was not counted.

### AC-9 · SCN-124 · scenario

> **A job that timed out before shutdown is not released**
>
> *Given:* Job j is processing on node n1 at attempt 1 of 3, and its handler ignores every cancellation token.
>
> 1. REQ-137 — j runs past its timeout and its timeout token is signalled
> 2. REQ-139 — n1 is draining, ShutdownTimeout passes and j's token is cancelled for shutdown
> 3. REQ-140 — n1 tries to release j and take back its attempt
>
> *Impossible at step 3.*
>
> *Notes:* refiner-model 2026-11-06 run 3 F-1 regression: the attempt counts, through REQ-138/REQ-186 or lease expiry.
