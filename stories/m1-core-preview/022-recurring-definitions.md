# ST-022 — Declare recurring jobs in code and reconcile them across nodes

**Milestone:** M1 · **Epic:** m1-core-preview · **Priority:** must · **Depends on:** ST-003, ST-006, ST-012

## Context

Gives code-defined recurring jobs their behaviour. A job declared with [Recurring] or AddRecurring is stored with its origin and default policies (REQ-201, REQ-202). A worker node creates it or brings it up to date when it starts (REQ-203, REQ-204). A node whose code has an invalid schedule or time zone does not start (REQ-210). The scheduler keeps stored definitions in line with what running worker nodes declare: it orphans or removes a job no running worker node declares (REQ-205, REQ-207), restores it when one declares it again (REQ-206), creates it again if it is missing (REQ-203) and moves a definition that no running release has to one that some running release has (REQ-241). A schedule change computes nextRunAt from now (REQ-227). One name is one definition however many nodes start at once (INV-200), and every recurring write is one compare-and-set in the store (TECH-45).

Builds on ST-003 (schedule evaluation and ISchedule, TECH-25), ST-006 (the hosting REQ-12 startup sequence: REQ-210 runs among the checks that need no store, and reconciliation runs last before hosting REQ-18 marks the node running) and ST-012 (the registry of running worker nodes and their heartbeats; REQ-205's notes add the declared recurring names, and REQ-241's notes add each name's definition hash, to what a node already publishes for jobs REQ-124). The scheduler's reconciliation pass is a background duty, so hosting REQ-40 (ST-007) keeps it off nodes without the worker. These stories build on it: ST-023 (runtime management, which constrains REQ-227 and TECH-45), ST-024 and ST-025 (occurrences; REQ-237 adds the skipping of waiting occurrences to this story's orphaning and removal), and ST-026. ST-026 adds REQ-242's missed-instant record to the REQ-204, REQ-205, REQ-207 and REQ-241 writes, and owns INV-212, which attacks those writes. TECH-45 is owned here, before ST-026 and ST-036 build what it applies to, because it is the store contract that every recurring write uses and this story makes the first ones. ST-026 adds the trigger's maintenance condition and ST-036 measures NFR-14. Later stores keep TECH-45 holding: PostgreSQL in ST-030, the conformance suite in ST-054 and Redis in ST-058. Configuration-defined jobs arrive in ST-047, which constrains REQ-210 and REQ-202.

Lives in the Bellhop core package (TECH-112). `AddRecurring<TJob>(name, schedule, job?, options?)` (TECH-22) and the `[Recurring]` attribute (TECH-17) come from ST-002 and get their behaviour here. Schedules are evaluated with `ISchedule.GetNextOccurrence(after, timeZone)` (TECH-25). The in-memory store (TECH-43) behind IJobStore (TECH-31) gains recurring definitions keyed by name, with TECH-45's compare-and-set and NextRunAt index. Time comes from TimeProvider (TECH-12), and due times are decided against the database clock (jobs INV-105). AllowRuntimeOverride is the only option name the specs give; the names of the policy and time-zone options are open question 1. Some criteria need state that ST-023 produces: a runtime-defined job, or a runtime edit under AllowRuntimeOverride. Tests write that record into the store directly.

## Acceptance criteria

### AC-1 · REQ-201 · must

> The system shall use RunOnce as the default misfire policy and Skip as the default overlap policy.

- Given a job declared in code with no misfire or overlap policy, when a worker node creates it (REQ-203), then its stored misfire policy is RunOnce and its overlap policy is Skip.
- Given a job declared with misfire policy Skip and overlap policy Queue, then those two are stored instead.
- What each default does is tested where it is built: RunOnce in ST-026 (REQ-217), Skip in ST-024 (REQ-222). A runtime-defined job added without policies (REQ-208, ST-023) gets the same defaults.

### AC-2 · REQ-202 · must

> The system shall record each recurring job's origin as code (attribute or AddRecurring), runtime (IRecurringJobManager or dashboard) or configuration (Bellhop:RecurringJobs).

- Given a job declared with [Recurring], and another declared with AddRecurring, when a worker node creates them (REQ-203), then the origin stored for both is code.
- The stored origin can hold all three values from this story on. REQ-208 (ST-023) writes runtime, and ST-047 writes configuration and keeps REQ-202 holding.
- Given a stored job of any origin, then no reconciliation write in this story (REQ-204 to REQ-207, REQ-241) changes its origin.

### AC-3 · REQ-203 · must

> When a node with the worker registered starts, or the scheduler finds a code-defined recurring job that a running worker node declares, and that job has no stored definition with its name, the system shall create the definition from the code definition of a node that declares it, with its schedule, time mode and zone, policies and payload, a hash of that code definition, and nextRunAt computed from now.
>
> *Transition:* RecurringJob: (new) → Active · *Actor:* system
>
> *Notes:* Decided by the owner on 2026-11-06: recurring definitions belong to worker processes; a process without AddWorker neither reconciles nor declares them (hosting REQ-53 warns). refiner-model 2026-11-08 run 7 F-2 (option 2, chosen over making the orphan sweep compare heartbeats at its write): the scheduler reconciles in both directions, so stored definitions converge to what running nodes declare. A declared job that is not stored, because an orphan sweep raced a node starting during a rollback, a heartbeat was published late, or an operator removed an orphan just as it was declared again (REQ-213), is created again at the scheduler's next pass, active with nextRunAt from now. Instants while it was not stored are not missed (REQ-234), and an operator's pause of the removed job is lost with it.

- Given an empty store and a node with the worker registered whose code declares nightly-cleanup, when the node starts, then before hosting REQ-18 marks it running, nightly-cleanup is stored Active with origin code. It holds the code's schedule, time mode and zone, policies and payload, a hash of that code definition, and a nextRunAt equal to the schedule's next occurrence after now by the database clock (TECH-25, jobs INV-105).
- Given a running worker node that declares weekly-report and no stored definition named weekly-report (for example, an operator removed the orphan under REQ-213 just as it was declared again), when the scheduler next runs, then weekly-report is created Active with nextRunAt from now. No occurrence is created for the instants while it was not stored, and a pause the operator set before the removal is not restored.
- Given two running worker nodes whose code for the job differs, when either branch creates it, then the stored definition and hash are those of one of the two nodes.
- Given a stored definition with that name, of any origin and in any state, then neither branch creates a second one or changes the stored one. A runtime-defined job with the name is REQ-236's case (ST-023).
- Given a node without the worker registered whose code declares a job, when it starts, then nothing is created (REQ-203's notes; hosting REQ-53 warns). While only such nodes declare a job, the scheduler branch does not create it either, because only a running worker node's declaration counts (and the scheduler itself runs only on worker nodes, hosting REQ-40).
- Given the create loses to another create of the same name (an insert keyed by name, recurring A-8), then it stores nothing and the node's start continues (INV-200).

### AC-4 · REQ-204 · must

> When a node with the worker registered starts and the hash of a code-defined recurring job's code definition differs from the definitionHash of the stored code-defined job with that name, the system shall update the stored definition and definitionHash to match the code, keeping its paused or active state, and, if the schedule changed, compute nextRunAt from now as in REQ-227.
>
> *Transition:* RecurringJob: Active | Paused → Active | Paused · *Actor:* Host
>
> *Notes:* Decided by the owner on 2026-11-06: code is reapplied only when the code definition itself changed, so a runtime edit under AllowRuntimeOverride survives restarts and deploys that leave the code unchanged. During a rolling deploy, nodes on N and N+1 may rewrite a changed definition back and forth; the last writer wins, and once no running node's code matches the stored definition, REQ-241 brings it back to a running release (refiner-model run 2 F-2; before that, this note said it settles when the deploy ends, which fails after a rollback or a late restart of an old node). Keeping the paused state is confirmed. refiner-model 2026-11-06 F-10 (decided 2026-11-06, recommended option): a schedule change that arrives with new code recomputes nextRunAt. F-6: applies only to a stored job of code origin; a runtime job with the same name stops the node instead (REQ-236).

- Given a stored code-defined Active job with hash h1, when a worker node starts whose code for it hashes to h2 ≠ h1 with the same schedule (for example, a changed payload), then the stored definition and definitionHash become that code's. The job stays Active and nextRunAt is unchanged.
- Given the same, but the new code changes the schedule, then nextRunAt becomes the new schedule's next occurrence after now, and no occurrence is created for the old schedule (REQ-227).
- Given the stored job is Paused, then after the update it is still Paused.
- Given the starting node's code hashes to the stored definitionHash, then nothing is written. A runtime edit stored under AllowRuntimeOverride (written into the store directly), which keeps the hash (REQ-241's notes), survives the restart unchanged.
- Given two nodes with identical code for the job, then they compute the same hash, so restarting either one rewrites nothing.
- Given the stored job is Orphaned, then a node start does not update it under this rule (its transition starts from Active or Paused); REQ-206 handles it.
- Given a stored runtime-defined job with the name, then it is never updated by this rule (notes, F-6).
- Given nodes on releases N and N+1 with different code start one after the other, then after each start the stored definition is the code of the node that started last (notes: the last writer wins).

### AC-5 · REQ-205 · must

> When the scheduler finds a stored code-defined recurring job that no running worker node declares, if the job's orphanPolicy is Orphan, the default, then the system shall record the job's current state and mark it orphaned, which also pauses it, instead of deleting it.
>
> *Transition:* RecurringJob: Active | Paused → Orphaned · *Actor:* system
>
> *Notes:* Decided by the owner on 2026-11-06: nodes publish the recurring names they declare with their heartbeat, as they do handler names (jobs REQ-124), so a job is orphaned only once no live node declares it. A rolling deploy therefore no longer flips it between Active and Orphaned. refiner-model 2026-11-06 F-11 (decided 2026-11-06, recommended option): the orphan policy is a per-job attribute, orphanPolicy. Run 2 F-2: each published name carries the hash of its code definition, which REQ-241 uses.

- Given weekly-report stored as code-defined and Active, with no orphanPolicy set, and every running worker node on a release that does not declare it, when the scheduler runs, then weekly-report is Orphaned and still stored, and its recorded earlier state is Active (SCN-204).
- Given the job was Paused, then it is Orphaned with Paused recorded as its earlier state.
- Given orphanPolicy Orphan set explicitly, then the outcome is the same as with the default.
- Given any running worker node still declares the job, even on an older release, then the scheduler does not orphan it (SCN-208).
- Given only a node without the worker declares the job, then it counts as not declared and the job is orphaned (REQ-203's notes: such a process does not declare).
- Given a stored runtime-defined job that no node declares, then it is never orphaned.
- Given no worker node runs, then nothing is orphaned, because the scheduler does not run (hosting REQ-40).
- An orphaned job creates no occurrence on schedule (INV-201, ST-026). Its waiting occurrences are skipped (REQ-237, ST-025), and instants it had missed are recorded (REQ-242, ST-026).

### AC-6 · REQ-206 · must

> When the scheduler finds an orphaned recurring job that a running worker node declares, the system shall return the job to the state it had before it was orphaned, update the stored definition and definitionHash to match that node's code definition if its hash differs from the stored definitionHash, and compute nextRunAt from now.
>
> *Transition:* RecurringJob: Orphaned → Active | Paused · *Actor:* system
>
> *Notes:* Decided by the owner on 2026-11-06: a job whose removal is rolled back comes back Active or Paused, as it was. Instants missed while orphaned are not caught up. refiner-model 2026-11-06 F-5 (decided 2026-11-06, recommended option): a job that comes back with changed code takes the code definition at once. Run 5 F-1: instants already missed when the job was orphaned are recorded by the orphaning (REQ-242); only those that fall due while it is orphaned are dropped without a record. refiner-model 2026-11-08 run 8 F-1 (recommended option): the restore is the scheduler's, like REQ-203's scheduler branch, so it is obliged to happen. With actor Host nothing obliged it, so a job orphaned during a rollback, or by an orphan sweep that landed just after a node that declares it started (INV-212 notes), could stay orphaned until the next node start. Run 9 F-1 (recommended option): the definition is taken only when the code changed, the rule REQ-204 and REQ-241 already follow, so a runtime edit under AllowRuntimeOverride survives a rolled-back removal as it survives a restart; changed code still takes over at once (F-5). Unconditional, a rollback to the same code reverted the operator's edit with no signal.

- Given weekly-report Orphaned from Paused, when a running worker node that declares it appears, then at the scheduler's next pass weekly-report is Paused again with nextRunAt from now (SCN-209). An orphan from Active comes back Active.
- Given that node's code hashes to the stored definitionHash, then the stored definition and hash are kept, including a runtime edit made under AllowRuntimeOverride before the orphaning (written into the store directly).
- Given that node's code hashes to something else, then the stored definition and definitionHash become that node's code.
- Given hourly instants fell due while the job was Orphaned, then no occurrence is created for them after the restore. They are not caught up (notes).
- Given no running worker node declares the job, then it stays Orphaned.
- Given the maintenance pause is on (ST-009), then the restore still happens (INV-210's notes, recurring A-20).
- Which declaring node's code is compared when several run different code is open question 5. Either way, the stored definitionHash afterwards matches the code of one declaring node.

### AC-7 · REQ-207 · must

> When the scheduler finds a stored code-defined recurring job that no running worker node declares, if the job's orphanPolicy is Delete, then the system shall remove the definition.
>
> *Transition:* RecurringJob: Active | Paused → (removed) · *Actor:* system
>
> *Notes:* Same event as REQ-205 with the complementary guard. The source only says the orphan behaviour is 'configurable'. refiner-model 2026-11-06 F-11 (decided 2026-11-06, recommended option): the orphan policy is a per-job attribute, orphanPolicy. Run 7 F-2: the sweep judges 'no running worker node declares' from the heartbeats it read. If a node that declares the job starts before the removal lands (a rollback), the job is removed anyway, and REQ-203's scheduler branch creates it again once that node's heartbeat is published. That transient is accepted (INV-212 notes).

- Given a stored code-defined job, Active or Paused, with orphanPolicy Delete, when the scheduler finds that no running worker node declares it, then the definition is removed.
- Given any running worker node still declares it, then it is not removed.
- Given a runtime-defined job with orphanPolicy Delete (written into the store directly), then this rule never removes it.
- Given the removal lands after a node that declares the job has started (a rollback), then the job is removed anyway. Once that node's heartbeat is published, the scheduler's next pass creates it again, Active with nextRunAt from now (REQ-203).
- Waiting occurrences skipped with reason Removed: REQ-237 (ST-025). Missed instants recorded: REQ-242 (ST-026).

### AC-8 · REQ-210 · must

> While a node is starting, if a code-defined or configuration-defined recurring job has an invalid schedule expression, or its time mode is Local without a valid IANA time zone, then the system shall fail the host's start with a message that names the job and the problem.
>
> *Transition:* hosting.Node: Starting → StartupFailed · *Actor:* Host

- Given a node whose code declares nightly-cleanup with a schedule expression that TECH-23 does not accept, when the host starts, then the start fails, the node never reaches Running (hosting REQ-18), and the message names nightly-cleanup and the problem with the expression.
- Given time mode Local with no time zone, or with an id that is not a valid IANA time zone (TECH-24), then the start fails the same way, and the message names the job and the zone problem.
- Given time mode Utc (the default, REQ-200) and no time zone, then this check passes.
- Given the store is unreachable, then this check still runs and fails the start first, because it is one of the checks that need no store (hosting REQ-12). No definition is written.
- Every job valid: the check does not fail the start. Configuration-defined jobs are checked once ST-047 loads them; ST-047 keeps REQ-210 holding. Whether the check runs on a node without the worker is open question 6.

### AC-9 · REQ-227 · must

> When a recurring job's schedule changes, the system shall compute nextRunAt from now, never from the last execution, and create no catch-up occurrence for the old schedule.
>
> *Transition:* RecurringJob: Active | Paused → Active | Paused · *Actor:* Operator
>
> *Notes:* refiner-model 2026-11-07 run 4 F-1: no catch-up still holds, but instants that were already missed when the schedule changes are recorded as dropped (REQ-242), so the miss is alerted. Run 5 F-2: that includes an instant that passed moments before the change and was not triggered yet (REQ-234).

- Given a job that runs hourly, last ran at 09:00, and whose schedule changes at 09:30 to daily at 08:00, then nextRunAt is 08:00 tomorrow and no occurrence is created for 08:00 today or for 10:00 (SCN-203). In this story the change arrives with new code, through REQ-204 at a node start or REQ-241 at a scheduler pass. ST-023 keeps REQ-227 holding for an operator's edit (REQ-212).
- Given the job's last execution was long before the change, then nextRunAt is the new schedule's next occurrence after now, never one counted from the last execution.
- Given the job is Paused, then nextRunAt is recomputed the same way and it stays Paused.
- Given the change passes over an instant that was already missed, then that instant is not run. ST-026 records it as dropped by the schedule change (REQ-242).
- Whether a change of time mode or zone alone counts as a schedule change is open question 3.

### AC-10 · REQ-241 · must

> When the scheduler finds a stored code-defined recurring job that running worker nodes declare but whose definitionHash matches the code definition of none of them, the system shall update the stored definition and definitionHash to the code definition of one of those nodes, keeping its paused or active state, and, if the schedule changed, compute nextRunAt from now as in REQ-227.
>
> *Transition:* RecurringJob: Active | Paused → Active | Paused · *Actor:* system
>
> *Rationale:* REQ-204 runs only when a node starts, so after a rollback, or after an old node restarted late in a deploy, the stored definition can belong to a release that no running node runs.
>
> *Notes:* refiner-model 2026-11-06 run 2 F-2 (recommended option). Nodes publish each declared name with the hash of its code definition in their heartbeat, as they already publish the names (REQ-205); the check runs with the orphan sweep, a worker duty (hosting REQ-40). While the stored hash matches any running node's code nothing changes, so there is no back-and-forth during a deploy while at least one node of the new release stays up (if all of them are down at once while old nodes run, the old definition is written back and the new one again when a new node returns, refiner-model run 3), and the definition settles as soon as the old release is gone. A runtime edit under AllowRuntimeOverride does not change definitionHash, so it survives.

- Given a stored code-defined job with the hash of release N, and running worker nodes that declare it all on release N+1 (the N nodes have stopped, for example after a rollback), when the scheduler runs, then the definition and definitionHash become N+1's code. Its Active or Paused state is kept, and nextRunAt is computed from now only if the schedule changed (REQ-227).
- Given at least one running declaring node's code hashes to the stored definitionHash, then nothing changes, whatever the other nodes run. So nothing goes back and forth while one node of the stored release is up.
- Given a runtime edit under AllowRuntimeOverride (written into the store directly) and a running node whose code hashes to the stored hash, then the edit stays.
- Given the declaring nodes run several releases and none matches, then the definition becomes the code of one of them.
- Given no running worker node declares the job, then this rule does nothing (REQ-205 or REQ-207 applies instead). Given the job is Orphaned or runtime-defined, it does nothing either.
- Given the maintenance pause is on, then the update still happens (recurring A-20).

### AC-11 · INV-200 · must

> The system shall never hold two recurring definitions with the same name, and never fail a node's startup because another node is reconciling the same definitions at the same moment.

- Concurrency: given an empty store, when several worker nodes start at the same moment, all declaring the same names (some on release N, some on N+1), then every node reaches Running (hosting REQ-18) and the store holds exactly one definition per name (SCN-207).
- Concurrency: given the scheduler's create (REQ-203) racing a node start that creates the same name, and REQ-204 or REQ-241 racing a node start that updates it, then there is one definition per name and no start fails. A create that finds the name stored reads it again and carries on (recurring A-26).
- Property: over random interleavings of node starts and stops, sweeps, restores and REQ-241 updates on several nodes, with valid code and no runtime-defined jobs, no two stored definitions ever share a name and every node start succeeds.

### AC-17 · TECH-45 · must

> **Recurring trigger storage** — Every store shall make each write that changes a recurring job's state, NextRunAt or definition, or removes the job, one atomic compare-and-set on the stored state, NextRunAt and definition, for example on a row version, that for a trigger also requires the maintenance pause to be off, and keep NextRunAt indexed.

To judge missed instants at the write rather than at the read, a write can compute them from the database time of its read and also require that the database clock has not yet reached the first due instant after that time; if it has, the write changes nothing and the caller reads again. Recurring run 7 F-1 and F-3: the definition and, for a trigger, the maintenance flag are part of the condition (INV-212).

When any one of the three changed after the read (tested one at a time), the write changes nothing, and the caller can tell that it lost.

- Unit, core package: REQ-201 and REQ-202 (stored defaults and origin), the definition hash (equal for equal code, different when the code changes; REQ-204), and REQ-227's nextRunAt computed with a fake `TimeProvider` (TECH-12).
