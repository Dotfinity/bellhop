# ST-002 — Define jobs, handlers and their payload contract

**Milestone:** M1 · **Epic:** m1-core-preview · **Priority:** must · **Depends on:** ST-001

## Context

Defines what a job is, so that every later story codes against one contract: a serializable type implementing IJob or IJob<TResult>, with its behaviour in an IJobHandler<TJob> of one shape (TECH-14, TECH-15); its stable name from [JobName], or the type's simple name, with aliases treated as the same job (REQ-101, TECH-18); the data-only metadata attributes, each also settable fluently, with the fluent value winning (TECH-17, INV-123); and the payload contract: System.Text.Json without type names behind a replaceable IJobSerializer, polymorphism only by opt-in, handlers resolved only from the registered name table, and reads that tolerate added and removed properties (TECH-5, TECH-6, TECH-7, INV-120, INV-121). This is hosting REQ-3 made concrete: a job is data, so renames, refactors and rolling deploys cannot break stored jobs.

Builds on ST-001 (packages and gates; the System.Text.Json default keeps the core inside TECH-8). ST-003 and ST-004 build on it directly, and ST-005 adds the registration calls that fill the job name table and the AddBellhop builder on which fluent values are set (TECH-22, TECH-128). ST-007 stores these payloads under the stable name and applies per-enqueue options over the attribute and fluent values (INV-123's notes), ST-008 resolves handlers from the name table, ST-012 routes by name and alias (jobs REQ-124, REQ-125), ST-022 gives [Recurring] and AddRecurring their behaviour (recurring REQ-202, REQ-203), and ST-053's analyzers check these contracts at compile time. The behaviour behind each attribute comes with its own story, and each of them keeps INV-123 holding: queue and priority (ST-007, ST-009), retry (ST-011), timeout (ST-014), unique (ST-019) and concurrency (ST-042). TECH-14 and TECH-5 are owned before any story builds the jobs module, and TECH-18 before ST-080 uses its Display property (dashboard REQ-331): they are contracts those stories code against, and REQ-36 puts the job model in M1.

Lives in the core package, Bellhop (TECH-124): IJob, IJob<TResult>, IJobHandler<TJob> and the JobContext type its signature names (TECH-14, TECH-15; JobContext's members are TECH-16 in ST-008), the attributes [JobName] with Aliases and Display, [Queue], [Priority], [Retry], [Timeout], [Unique], [Concurrency] and [Recurring] (TECH-17, TECH-18), and IJobSerializer with its System.Text.Json default (TECH-5, TECH-7). The job name table and the resolution of attribute and fluent metadata are built against what exists: the registration calls and the AddBellhop builder come with ST-005 (TECH-22, TECH-128), so this story's tests fill the table and set fluent values directly. The fluent forms, the attributes' arguments and the serializer's members are open question 1; the interface a result job's handler implements is open question 2.

### Background

- **REQ-3** (hosting, info): The system shall define a job as data (a name plus a JSON document) with behaviour in a separate DI-constructed handler, so that renames, refactors and rolling deploys cannot break stored jobs.
- **REQ-39** (hosting, info): The system shall cover several popular Hangfire add-ons through existing features rather than separate ones: multi-app shared store (namespaces), skip missed runs (misfire Skip), idempotency (unique keys) and options from configuration; jobs addressed by type-name strings are deliberately unsupported.

## Acceptance criteria

### AC-1 · REQ-101 · must

> The system shall use the stable job name from [JobName], or the type's simple name when none is given, as the job's identity in storage, and treat each alias listed on [JobName] as the same job.

- Given a job type without [JobName], when it is registered, then the name stored with its jobs is the type's simple name, without namespace or assembly.
- Given [JobName] with the name send-welcome-email on the type, then that name is stored, whatever the type is called; renaming the type or moving it to another namespace or assembly does not change it.
- Given [JobName] with the name n and an alias a, when a stored job named a is read, then it is resolved to that job type and its handler exactly as a job named n is (INV-120), and a new job of that type is stored under n, not under a.
- Given a stored job whose name is neither a registered name nor an alias, then it is not resolved to any job type.
- Two registrations that claim one name or alias are open question 3.

### AC-2 · INV-120 · must

> The system shall never use type names found in stored data to deserialize a payload, and resolve a job's handler only from the registered job name table.

- Property: over random registered job types and random stored payloads that carry type metadata ($type entries, assembly-qualified type names, names of other loaded types), reading a payload by its job name gives the type registered for that name, or nothing for a name that is not registered; no type named in the data is ever loaded or instantiated.
- Given a stored job whose name is the full name of a type that implements IJob but is not registered under that name, then no handler is resolved for it (hosting REQ-39: jobs addressed by type-name strings are unsupported).
- Given a payload type that opts into polymorphism with [JsonDerivedType] (TECH-6), then the derived type is chosen from the discriminators the job type declares, never from a type name in the data.
- Inspection: no code path that reads a payload or resolves a handler turns a string from stored data into a type.

### AC-3 · INV-121 · must

> When a stored payload is read, the system shall ignore properties the job type no longer has and give missing properties their default values.

- Property: for random job types, payloads written by one version of a type and read by another version that adds and removes properties are read without error; properties the reading type no longer has are ignored, and the properties it has that the payload lacks get their default values.
- Given a payload with a property the type no longer has, when the job is read, then the read succeeds and every other property has its stored value.
- Given a payload without a property the type now has, and that property declares no initial value, then it holds the default of its type (null, zero or false).
- Whether "default value" means the CLR default or a default the type declares, and what happens for a property marked required, is open question 4.

### AC-4 · INV-123 · must

> Where the same job metadata is set both by an attribute on the job type and fluently in AddBellhop, the system shall use the fluent value.
>
> *Notes:* Decided by the owner on 2026-11-06: the extension is confirmed; per-enqueue options override both the attribute and the fluent value (SCH-4, RET-1, REQ-100).

- Property: for each of [Queue], [Priority], [Retry], [Timeout], [Unique], [Concurrency] and [Recurring] (TECH-17), over random choices of the attribute set or not and the fluent value set or not, the job's effective value is the fluent value when one is set, the attribute's value when only that is set, and the owning item's default otherwise (for example priority 0, jobs REQ-108).
- Given queue a set by [Queue] on the type and queue b set fluently, then jobs of that type use queue b; ST-007 observes it on stored jobs. That the order of the assembly scan and the fluent call does not matter is checked with the scan in ST-005 (TECH-22).
- Per-enqueue options beat both (INV-123's notes). EnqueueOptions arrives in ST-007 (TECH-20), which tests that for the queue and the priority; the effect of each other value is tested by the story that builds it.

### AC-5 · TECH-5 · must

> **Payload serializer** — The core package shall use System.Text.Json as the default payload serializer, storing plain contracts without type names.

- Test: with no serializer configured, a payload is written with System.Text.Json as a plain JSON object of the type's properties, with no type name, $type entry or assembly name in it, and reads back equal to the original.
- Inspection: the default IJobSerializer is built on System.Text.Json, and the core references no other JSON library (the TECH-8 audit, ST-001).

### AC-6 · TECH-6 · must

> **Serializer options and polymorphism** — The core package shall serialize polymorphic payloads only when the user opts in with [JsonDerivedType], and shall accept user-supplied JsonSerializerOptions or a JsonSerializerContext.

- Given a payload property declared as a base type that holds a derived instance, with no [JsonDerivedType] on the base, then it is written with the base type's properties only and with no discriminator.
- Given the base type declares the derived type with [JsonDerivedType], then the derived instance round-trips as the derived type.
- Given user-supplied JsonSerializerOptions (for example a naming policy), then stored payloads follow them; given a JsonSerializerContext, then payloads are written and read through the context's metadata.
- How the options or the context are supplied is open question 1.

### AC-7 · TECH-7 · should

> **Replaceable serializer** — The core package shall use an IJobSerializer abstraction so the System.Text.Json default can be replaced.

- Test: an application registers its own IJobSerializer; every payload written and read goes through it (the stored payload is what it produced), and the System.Text.Json default is not used.
- Inspection: nothing in the core writes or reads a payload except through IJobSerializer.
- IJobSerializer's members and how a replacement is registered are open question 1.

### AC-8 · TECH-14 · must

> **Job definition contract** — The core package shall define a job as a serializable type implementing IJob or IJob<TResult> and its behaviour as a class implementing IJobHandler<TJob>, with no source generator or expression capture required.

- Test: a plain class implementing IJob and a class implementing IJobHandler<TJob> are accepted as a job and its handler in a test project that has no source generator and passes no expression anywhere; the same holds for a job implementing IJob<TResult>. Registering them with AddJob<TJob, THandler>() is TECH-22 (ST-005).
- Inspection: the core package ships no source generator that registration needs, and no API takes a captured expression (hosting REQ-8: no Enqueue(() => ...)).
- Given a type that implements neither IJob nor IJob<TResult>, then it is not accepted as a job.

### AC-9 · TECH-15 · must

> **Handler signature** — The core package shall support exactly one handler shape, Task HandleAsync(TJob job, JobContext ctx, CancellationToken ct), and Task<TResult> for result jobs.

- Inspection: IJobHandler<TJob> declares one method, Task HandleAsync(TJob job, JobContext ctx, CancellationToken ct), and the handler of a result job returns Task<TResult> from a method with the same parameters; the core offers no other handler shape (no synchronous, ValueTask or context-free form), and nothing in the engine looks for one.
- Test: a handler of each shape compiles against the core and is called with the job, a JobContext and a token (ST-008 runs it).
- The interface a result job's handler implements is open question 2.

### AC-10 · TECH-17 · must

> **Job metadata attributes** — The core package shall provide the data-only attributes [Queue], [Priority], [Retry], [Timeout], [Unique], [Concurrency] and [Recurring], each also settable fluently in AddBellhop.

- Inspection: the core package provides [Queue], [Priority], [Retry], [Timeout], [Unique], [Concurrency] and [Recurring], and each is data only: it holds values, has no method the engine calls and runs no code when it is read.
- Test: for each attribute, setting the same metadata fluently gives the same effective value as the attribute does (INV-123 settles a conflict); the fluent calls are reached from AddBellhop once ST-005 builds it.
- The fluent forms and the attributes' arguments are open question 1.

### AC-11 · TECH-18 · must

> **JobName attribute** — The core package shall provide [JobName("...")] with Aliases and Display properties.

- Inspection: [JobName("...")] takes the name in its constructor and has the properties Aliases and Display.
- Test: the name and aliases set on it give REQ-101's results; Display does not change the job's identity (it is shown by dashboard REQ-331, ST-080).

## Open questions

1. **Decide in delivery** · TECH-6, TECH-7, TECH-17, TECH-18: the public shapes the specs do not give: the fluent form of each attribute in AddBellhop, each attribute's arguments and properties (and the types of Aliases and Display), IJobSerializer's members and how a replacement is registered, and how JsonSerializerOptions or a JsonSerializerContext is supplied. NFR-20 later freezes attribute shapes and option names.
2. **Decide in delivery** · TECH-14, TECH-15: which interface does a result job's handler implement? IJobHandler<TJob> alone cannot declare Task<TResult> for a TResult it does not name, and TECH-14 names no second interface.
3. **Decide in delivery** · REQ-101, INV-120: what happens when two registrations claim one name (two types with the same simple name in different namespaces, a name equal to another job's alias, two handlers for one job type), and what is the simple name of a generic or nested type? No item says whether registration or startup fails, and INV-120's name table needs one entry per name. What a scan does with a job type that has no handler is ST-005's open question 6.
4. **Decide in delivery** · INV-121: does a missing property get the CLR default or a default its type declares (an initializer, a constructor parameter default), and what happens for a property marked required? System.Text.Json fails a read that lacks a required property, which INV-121 does not allow.
5. **Decide in delivery** · INV-120, INV-121: what happens to a job whose stored payload cannot be read at all (a property whose type changed, malformed JSON)? INV-121 covers only added and removed properties, and NFR-51 only says the failure is logged; the answer decides whether the attempt fails and is retried (ST-008, ST-011).
