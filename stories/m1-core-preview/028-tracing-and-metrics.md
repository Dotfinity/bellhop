# ST-028 — Emit OpenTelemetry traces and metrics

**Milestone:** M1 · **Epic:** m1-core-preview · **Priority:** must · **Depends on:** ST-010, ST-014, ST-018, ST-026, ST-021

## Context

Makes Bellhop observable through OpenTelemetry with no extra package. Traces come from a built-in ActivitySource named "Bellhop" whose spans follow the OpenTelemetry messaging semantic conventions (TECH-97): a producer span at enqueue and a consumer span at execution, linked through the trace context stored on the job (NFR-54). Metrics come from a built-in Meter named "Bellhop" (TECH-98) with the counters, histograms and gauges NFR-55 lists, and reach Prometheus through the standard OpenTelemetry exporter, with no Bellhop exporter package (TECH-99).

Builds on ST-010 (the execution pipeline, and REQ-154, which carries a running job's trace context over to the jobs its handler enqueues and must keep holding), ST-014 (timeouts), ST-018 (cancellation), ST-021 (retention, whose removals INV-118's notes count in a metric; INV-118 must keep holding) and ST-026 (recurring triggers), so every transition the instruments count exists, and through them on every earlier M1 job story. ST-035 builds on it and documents Prometheus export as a two-line setup (NFR-36). The job detail page shows the stored trace id (dashboard REQ-309, ST-033), and ST-045 masks `[Sensitive]` payload values in traces (INV-124).

Lives in the Bellhop core package, as the OpenTelemetry instrumentation TECH-112 lists. The core may depend only on the BCL and Microsoft.Extensions.* abstractions (TECH-8): ActivitySource and Meter are BCL types, so the core references no OpenTelemetry package, and only tests reference the OpenTelemetry SDK and its Prometheus exporter. Span names and attributes, instrument names, units and tags, and the meaning of several instruments are not in the specs (open questions 1 to 5). Placement: TECH-99 is owned before ST-035, which documents it under NFR-36; the metric export it constrains is built here.

## Acceptance criteria

### AC-1 · TECH-97 · must

> **Tracing** — The core package shall emit traces through a built-in ActivitySource named "Bellhop" whose spans follow the OpenTelemetry messaging semantic conventions.

- Test: an `ActivityListener` that listens to the source named "Bellhop", in a host with only the Bellhop core registered, receives a span for an enqueue and one for the job's execution; passing means both arrive with no other package or registration.
- Test: the enqueue span has kind Producer and the execution span kind Consumer (NFR-54), and each carries the messaging attributes that the semantic conventions require for its kind. The version of the conventions and Bellhop's attribute values are open question 1; the test asserts them once it is settled.
- Dependency audit: the core package references no OpenTelemetry package (TECH-8). Passing means ST-001's core dependency check stays green.
- Inspection: emitting spans makes no outbound call; spans leave the process only through exporters the application configures (NFR-39).

### AC-2 · TECH-98 · must

> **Metrics** — The core package shall emit metrics through a built-in Meter named "Bellhop".

- Test: a `MeterListener` that enables the instruments of the meter named "Bellhop", in a host with only the Bellhop core registered, receives measurements once a job has run; passing means they arrive with no other package or registration.
- Dependency audit: as for TECH-97, the core references no OpenTelemetry package (TECH-8).
- How a listener tells two Bellhop instances in one process apart is open question 6 (NFR-53).

### AC-3 · TECH-99 · must

> **Prometheus export** — Bellhop metrics shall reach Prometheus through the standard OpenTelemetry Prometheus exporter, with no Bellhop-specific exporter package.

- Integration test: a test host that adds the OpenTelemetry SDK with the meter "Bellhop" and the standard OpenTelemetry Prometheus exporter, and nothing else from Bellhop but the core, serves Bellhop's instruments in its scrape output after a job has run. Passing means every NFR-55 instrument appears in the scrape.
- Dependency audit: no Bellhop package exists for Prometheus export, and no Bellhop package references the Prometheus exporter. Passing means the solution's package list and the core's dependencies show neither.
- The documented two-line setup is NFR-36 (ST-035).

### AC-4 · NFR-54 · must

> **Tracing coverage** — The system shall emit a producer span at enqueue and a consumer span at execution, linked through the trace context stored on the job.
>
> *Measure:* every execution span links to its enqueue span in the test exporter · *Verification:* test

- Measurement, by test with the OpenTelemetry SDK's in-memory exporter: jobs are enqueued inside application spans and executed on the same node and on another node over one in-memory store. Passing means every execution span in the exporter references its job's enqueue span, by the trace id and span id stored on the job; whether as a span link or as its parent is open question 3.
- Given a job that runs more than once, after a retry (REQ-129, REQ-130), a lease-expiry recovery (REQ-132) or a release at shutdown (REQ-140), then every one of its execution spans references the same enqueue span.
- Given a job enqueued by a running handler, then its producer span belongs to the running job's trace (REQ-154), and its own execution span references that producer span.
- Which span the execution of a scheduled job, a requeued job or a recurring occurrence references is open question 2.

### AC-5 · NFR-55 · must

> **Metrics coverage** — The system shall publish counters for enqueued, started, succeeded, failed, retried, dead-lettered and interrupted jobs, histograms for execution duration and scheduling lag, and observable gauges for queue depth per queue and active workers.
>
> *Measure:* all listed instruments present on the Bellhop meter · *Verification:* test

- Measurement, by test with a `MeterListener` on the meter "Bellhop", after a run over the in-memory store that drives jobs to success, to a retried failure, to a dead letter and to a lease-expiry interruption: passing means the meter publishes counters for enqueued, started, succeeded, failed, retried, dead-lettered and interrupted jobs, histograms for execution duration and scheduling lag, and observable gauges for queue depth per queue and active workers, eleven instruments, each of the kind the statement gives.
- Given jobs that each run exactly once, then the started counter rises by one per job claimed (REQ-123), the succeeded counter by one per job marked succeeded (REQ-127), and the dead-lettered counter by one per job moved to DeadLettered (REQ-131, REQ-133, REQ-186). Whether started counts attempts or jobs, which transitions the other counters count, and what scheduling lag is measured from, is open question 4.
- Given jobs enqueued in two queues, then the queue-depth gauge reports a separate value for each queue. The tag that names the queue, and what "active workers" counts, are open question 5.

## Open questions

1. **Decide in delivery** · TECH-97: which version of the OpenTelemetry messaging semantic conventions do the spans follow, given that the conventions still change between versions, and what are Bellhop's span names and attribute values: the messaging system name, the operation names for enqueue and execution, and the destination (the queue)? Dashboards and alerts will be built on them.
2. **Decide in delivery** · NFR-54: which span does the execution of a scheduled job (REQ-121, promoted later), a requeued job (REQ-141 to REQ-143) or a recurring occurrence (REQ-216, REQ-226) reference, and does `ScheduleAsync` emit a producer span? NFR-54 speaks of enqueue only, and no application call enqueues a recurring occurrence.
3. **Decide in delivery** · NFR-54: is "linked" a span link, the producer span as the consumer span's parent, or both? The Measure says "links to"; the criteria accept either until this is settled.
4. **Decide in delivery** · NFR-55: which transitions do the counters count? Is a schedule call, a promotion (REQ-122), a retry's return to Enqueued (REQ-130) or a requeue "enqueued"; does "started" count attempts or jobs; is "failed" every failed attempt or each move to Failed; is "retried" the move to Failed with a retryAt (REQ-129, REQ-138) or the return to Enqueued (REQ-130); is a release at shutdown (REQ-140) "interrupted"? And what is scheduling lag measured from? Hosting REQ-46 uses the term without defining it.
5. **Decide in delivery** · NFR-55: what are the instruments' names, units and tags (queue, job name, outcome)? Does "active workers" mean running worker nodes or handlers running now? Does queue depth count Enqueued jobs only, and does each gauge read query the store, so that every scrape adds store load beside NFR-10's budget? All of these become public contracts that NFR-20 freezes at 1.0.
6. **Decide in delivery** · TECH-97, TECH-98: are the ActivitySource and the Meter per Bellhop instance or shared by every instance in the process, and how does a listener tell two instances apart? NFR-53 allows no mutable static state and runs two instances in one process.
