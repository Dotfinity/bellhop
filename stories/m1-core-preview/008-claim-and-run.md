# ST-008 — Claim and run jobs on a worker

**Milestone:** M1 · **Epic:** m1-core-preview · **Priority:** must · **Depends on:** ST-007

## Context

Delivers the worker loop that claims and runs jobs, which with ST-007 completes fire-and-forget (SCN-100). A running worker node with a handler for the job's name or an alias claims the next job while it holds fewer claims than its concurrency limit, 2 × ProcessorCount by default (REQ-123, REQ-106, INV-106), with a new lease token, the attempt counted and a lease of LeaseDuration that the node renews every LeaseDuration / 3 with no action by the handler (REQ-102, REQ-126); an idle node polls at PollInterval (REQ-103); only one worker ever holds an unexpired claim (INV-103, SCN-104); a handler that returns marks its job succeeded (REQ-127); and every state change is recorded (INV-116). Each execution resolves its handler in a DI scope of its own, disposed asynchronously (INV-122, TECH-13, TECH-35), and gets a JobContext (TECH-16) that IJobContextAccessor exposes (TECH-34) and that tests can build (TECH-104). A node without the worker never claims (hosting REQ-20, SCN-120).

Builds on ST-007 (enqueued jobs, and the database clock of INV-105, which leaseExpiresAt follows) and keeps hosting REQ-18 (claims start only after the node is marked running), TECH-31 (claims, renewals and completions are asynchronous IJobStore operations with documented semantics) and INV-105 (ST-007; claims and renewals set leaseExpiresAt from the database clock, never the node's) holding. REQ-123's guard is built against what exists: ST-009 adds the queue limit, the queue pause and maintenance and the order by queue and priority (INV-110, INV-111), and ST-042 concurrency keys, rate limits and the LongRunning limit; both keep REQ-123 holding, and ST-009 keeps INV-106 holding. ST-010 adds middleware and typed parameters (INV-122, TECH-16); ST-011, ST-012, ST-013 and ST-020 record the transitions they add (INV-116); ST-012 publishes each node's handlers; ST-013 fences renewals and completions by lease token (INV-128), adds lease recovery and attacks INV-103 again, as ST-030 and ST-058 do on PostgreSQL and Redis; ST-027 builds on JobContext.CreateForTest (TECH-104); ST-040 stores results (REQ-127); and ST-045 fills progress and the job logger's capture (TECH-16). The JobContext members that later stories fill (parameters and trace context ST-010, parent id ST-038, batch id ST-039, tags and correlation id ST-044, progress ST-045) are built against what exists. This story also records the enqueue, schedule and promotion transitions of ST-007, which came before the history existed (INV-116).

Lives in the core package, Bellhop: the worker loop that AddWorker registers (TECH-11, TECH-128), JobContext with JobContext.CreateForTest(...) (TECH-16, TECH-104), IJobContextAccessor (TECH-34), and resolution through IServiceProvider (TECH-13). LeaseDuration and PollInterval are options, and concurrency is a worker option on AddWorker (TECH-128's notes). Failures in the loop are logged with stable EventIds (NFR-51, standing). The node's identity and the types and names the specs leave open are open questions 1 and 4.

### Modeling assumptions

Decisions the model took where the sentences were silent. Build to them, or raise an open question.

- jobs A-2 (affects REQ-102, REQ-126, REQ-132, REQ-133, INV-104, LIV-101): A lease is a flag. It can expire at any time while processing (crash, partition or pause), and a late heartbeat from the run that holds the current token renews it (REQ-126 has no "not yet expired" guard).
- jobs A-4 (affects INV-106, REQ-123): "Holds claims on processing jobs" (REQ-123, INV-106) counts processing jobs whose current lease token is held by the node's live run. Handlers that were abandoned, released or lost their lease are not counted.
- jobs A-14 (affects REQ-101, REQ-123, REQ-124, REQ-125): One job name; "a handler for its name or one of its aliases" is a per-node handler flag that can change when a node restarts (rolling deploy).
- hosting A-6 (affects REQ-20, REQ-25, REQ-27, REQ-29): Job claims are abstracted from the jobs module: a claim needs Running, a started worker and a reachable store; 1 in-flight slot (2 in SCN-4 and the drain cfg). Handlers are not obliged to finish. A claimed job may time out (A-24)

## Acceptance criteria

### AC-1 · REQ-102 · must

> The system shall give every claim a lease of LeaseDuration, 60 seconds by default, and renew it by heartbeat every LeaseDuration / 3 (HeartbeatInterval).
>
> *Notes:* Decided by the owner on 2026-11-06: 60 s, so heartbeats run every 20 s. The docs state it as the duplicate window (EXE-5, REQ-10).

- Given the defaults, when a job is claimed at database time T, then its leaseExpiresAt is T plus 60 seconds, and while its handler runs the node renews the lease every 20 seconds; what a renewal writes is REQ-126.
- Given LeaseDuration configured as 30 seconds, then leaseExpiresAt is T plus 30 seconds and renewals come every 10 seconds.
- Given a handler that runs for several LeaseDurations while every renewal succeeds, then its job stays Processing under the same claim and its lease never expires.

### AC-2 · REQ-103 · must

> The system shall poll for work at PollInterval, 1 second by default, when no notification mechanism wakes the node (PollInterval).

- Given an idle worker node on a store that reports no push notifications (TECH-33), then it looks for work once per PollInterval, 1 second by default: with fake time, a job enqueued by another node is claimed at the node's next poll and not before.
- Given PollInterval configured as 5 seconds, then the idle node looks for work every 5 seconds.
- Waking a node by notification is TECH-38 (ST-030).

### AC-3 · REQ-106 · must

> The system shall default a node's concurrency limit to 2 × ProcessorCount (NodeConcurrency).
>
> *Notes:* Decided by the owner on 2026-11-06: 2 × ProcessorCount, without the floor of 8 the source proposed. A 1-CPU container therefore runs 2 jobs at once by default; the docs should say so for I/O-bound workloads.

- Given no concurrency configured, then the node's limit is 2 × ProcessorCount: with more jobs enqueued than that and handlers that wait, 2 × ProcessorCount of them are Processing on the node at once and no more, and the startup summary shows that limit (hosting REQ-19).
- Given a process that sees one processor, as in a 1-CPU container, then the limit is 2 (REQ-106's notes).
- Given AddWorker with a concurrency of 3, then at most 3 jobs are Processing on that node at once.

### AC-4 · REQ-123 · must

> While a job is enqueued in an active queue that is below its concurrency limit, the maintenance pause is off, its concurrency key and rate limit admit it and, for a job tagged LongRunning, the node is below its LongRunning limit, when a running node with the worker registered and a handler for the job's name or one of its aliases holds claims on fewer processing jobs than its concurrency limit and the job is the next one by queue order and priority, the system shall claim the job for that worker, record the claiming node, issue a new leaseToken, increment the attempt number and set leaseExpiresAt to the database time plus LeaseDuration.
>
> *Transition:* Job: Enqueued → Processing · *Actor:* system
>
> *Notes:* The attempt number is counted at claim time; that is what makes EXE-4 'attempt counted' hold for interrupted runs. Decided by the owner on 2026-11-06: only nodes with the worker registered claim (hosting REQ-20), a node claims only jobs it has a handler for (REQ-124), and every claim gets a fresh lease token (INV-128). Resolved after refiner-model 2026-11-06 F-2 (recommended option): the queue limit (INV-107) and the LongRunning limit (INV-112) are claim conditions here, not only in INV-107's notes. Run 2 F-7 (recommended option): 'a free worker slot' is now spelled out as fewer claims than the node's concurrency limit, the measure INV-106 uses, so a handler whose lease was lost does not keep a slot; REQ-191 records it instead.

- Given job j Enqueued in a queue the worker drains, and a running node with the worker registered, a handler for j's name and fewer claims than its limit, when the node looks for work, then j becomes Processing with leaseOwner set to that node, a new leaseToken, its attempt number increased by one and leaseExpiresAt set to the database time plus LeaseDuration (SCN-100: attempt 1).
- Given the node has a handler only for an alias of j's name (REQ-101), then it claims j the same way.
- Given the node has no handler for j's name or any of its aliases, then it does not claim j, and j stays Enqueued (Unroutable is REQ-124, ST-012).
- Given the node already holds as many claims as its limit, then it claims nothing more until one of its jobs leaves Processing (jobs A-4: only the claims of the node's live runs count).
- Given j is in a queue the worker does not drain, then that worker does not claim it.
- Given the node is not yet marked running (hosting REQ-18), or has no worker registered (hosting REQ-20), then it claims nothing.
- Given j was put into the store Enqueued with a lease token and an attempt number from an earlier attempt, then the claim issues a token different from the earlier one and sets the attempt to the earlier number plus one.
- Given the store's clock differs from the node's, then leaseExpiresAt follows the store's clock (INV-105).
- The queue limit, the queue pause and maintenance (ST-009) and concurrency keys, rate limits and the LongRunning limit (ST-042) join the guard in those stories.

### AC-5 · REQ-126 · must

> While a job is processing, when HeartbeatInterval has passed since the last renewal, the system shall extend leaseExpiresAt by LeaseDuration without any action by the handler.
>
> *Transition:* Job: Processing → Processing · *Actor:* system

- Given job j is processing with the defaults, when the fake clock advances one HeartbeatInterval (20 s) at a time, then after each interval the lease is renewed and leaseExpiresAt is later than before and at least the database time of the renewal plus LeaseDuration, while the handler only awaits and never touches its JobContext.
- Given j runs for ten times LeaseDuration with every heartbeat reaching the store, then its leaseExpiresAt never passes by the database clock (INV-105). That no node recovers it is INV-104 and SCN-103 (ST-013).
- Given the heartbeats stop reaching the store, then leaseExpiresAt is not extended and passes by the database clock; recovering the job is REQ-132 and REQ-133 (ST-013).
- Given the lease has passed but no node has recovered the job, when the run that holds the current token renews, then the renewal is applied (jobs A-2: REQ-126 has no "not yet expired" guard).
- Refusing the renewal of a run whose token is no longer current, or whose job is no longer processing, is INV-128 (ST-013). The value a renewal gives leaseExpiresAt is open question 5.

### AC-6 · REQ-127 · must

> While a job is processing, when its handler returns without an exception, the system shall mark the job succeeded.
>
> *Transition:* Job: Processing → Succeeded · *Actor:* Handler
>
> *Notes:* Decided by the owner on 2026-11-06: a run whose lease was taken over cannot complete the job; see INV-128.

- Given j Processing under a claim, when its handler returns without an exception, then j is Succeeded and no longer counts against the node's limit, so the node can claim another job.
- Given a result job whose handler returns a value, then j is Succeeded; storing the result is REQ-184 and REQ-185 (ST-040).
- Given the handler throws, then j is not marked Succeeded (REQ-129 to REQ-131, ST-011).
- A run whose lease was taken over cannot complete the job (INV-128, ST-013). What the node does when the success write fails is open question 3.

### AC-7 · INV-103 · must

> The system shall never let more than one worker hold an unexpired claim on the same job.

- Concurrency test: several worker nodes in one process, each with several slots, race to claim the same set of Enqueued jobs on one store; at every observed moment no job has more than one unexpired claim, and each job is claimed once (SCN-104).
- The test repeats with random handler durations and random start orders. Lease expiry and recovery (ST-013), PostgreSQL's SKIP LOCKED (ST-030) and the Redis scripts (ST-058) attack INV-103 again in those stories.

### AC-8 · INV-106 · must

> The system shall never hold claims on more processing jobs at once on a node than the node's concurrency limit.
>
> *Notes:* Decided by the owner after refiner-model 2026-11-06 F-5: the limit counts claims, not handler code still executing. A handler abandoned after its timeout (REQ-138, REQ-186) or released at shutdown (REQ-140) keeps running in the process but no longer holds a claim, so it runs outside the limit; REQ-191 makes it visible. So does a handler whose lease was lost (run 2 F-7).

- Concurrency test: a node with limit L and three times L Enqueued jobs whose handlers wait for a signal; at every observed moment the node holds claims on at most L Processing jobs, and as handlers finish it claims more without ever passing L.
- Property: over random limits, job counts and handler durations, the number of Processing jobs claimed by the node never exceeds its limit.
- The limit counts claims, not handler code still running (INV-106's notes); abandoned handlers come with ST-014, ST-017 and ST-018 (REQ-191).

### AC-9 · INV-116 · must

> When a job changes state, the system shall record the transition with its timestamp, the node that made it and the reason.

- Given SCN-100's run, then the job's history holds three transitions, to Enqueued, to Processing and to Succeeded, each with a timestamp, the node that made it and a reason.
- Given a scheduled job that is promoted (REQ-122) or one stored Enqueued at once (REQ-182), then those transitions are recorded the same way, with the promoting node for a promotion.
- Property: over random sequences of the transitions that exist so far (enqueue, schedule, promote, claim, succeed) on several nodes, every state change appears in the job's history exactly once, in order, with a timestamp, a node and a reason.
- Which clock stamps a transition, and which reasons exist, is open question 2. ST-011, ST-012, ST-013 and ST-020 keep INV-116 holding for the transitions they add.

### AC-10 · INV-122 · must

> When a job executes, the system shall resolve its handler and execution middleware in a dependency-injection scope created for that execution and dispose the scope, asynchronously where services support it, when the execution ends.

- Given a handler that depends on a scoped service, when two executions run, at once or one after the other, then each gets its own instance, and within one execution the handler and everything resolved for it share that instance.
- Given the execution ends, by returning or by throwing, then its scope is disposed: DisposeAsync is called on a scoped service that is IAsyncDisposable, and Dispose on one that is only IDisposable.
- Middleware resolved in the same scope comes with TECH-28 (ST-010), which keeps INV-122 holding.

### AC-11 · REQ-20 · must

> While a node has no worker registered, the system shall never claim or execute a job on that node.
>
> *Notes:* Decided by the owner on 2026-11-06: node modes are replaced by registrations (REQ-52); a process without AddWorker never runs jobs.

- Given a process with AddBellhop, the client and a registered handler but no AddWorker (SCN-120), and job j Enqueued, then however far the clock moves the process never claims j, never constructs the handler and makes no claim call to the store.
- Given a worker node joins the same store, then that node claims j.
- Property: over random registrations on several nodes that share one store, every claim and every execution happens on a node with the worker registered.
