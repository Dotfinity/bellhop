# ST-005 — Register Bellhop with AddBellhop, AddClient and AddWorker

**Milestone:** M1 · **Epic:** m1-core-preview · **Priority:** must · **Depends on:** ST-004, ST-003

## Context

Delivers the registration surface of Bellhop. AddBellhop configures the store and registers the Bellhop hosted service (TECH-11); AddClient() registers IJobClient and IRecurringJobManager, and AddWorker(options) registers the worker with its queues, concurrency and background duties, and the client with it (TECH-128), in any combination including none (REQ-52). The builder also offers the job registration calls, AddJobsFromAssemblyContaining<T>() across several assemblies, AddJob<TJob, THandler>() and AddRecurring<TJob>(name, schedule, job?, options?) (TECH-22), which fill the job name table of ST-002. Options are bound from the "Bellhop" configuration section and validated with ValidateOnStart (TECH-10), and a value set in code beats configuration (REQ-17). Registering does no I/O (REQ-13), build-time tooling never starts a worker (REQ-14, REQ-57), and with no store configured the in-memory store is used (REQ-15).

Builds on ST-004 (the in-memory store), on ST-003 (the schedule types of TECH-23 and TECH-25, which AddRecurring's schedule parameter takes) and, through them, on ST-002 (the job contracts and the name table that TECH-22's calls fill). ST-006 runs the startup sequence when the hosted service starts (hosting REQ-12, REQ-18) and turns a validation failure into REQ-9's message; ST-007 and ST-008 give the client and the worker their behaviour; ST-022 creates the stored definitions of the recurring jobs AddRecurring declares (recurring REQ-203); ST-023 defines IRecurringJobManager (TECH-21), which AddClient registers from then on; ST-031 maps the dashboard independently (MapBellhopDashboard, hosting REQ-51); ST-049 adds the alerts registration, AddAlerts() on the AddBellhop builder (TECH-129, owner decision of 2026-11-10), and keeps REQ-52 holding. REQ-52's alerts combinations are built against what exists: this story covers the client and the worker, ST-049 the alerts. TECH-10 is owned before ST-006 validates options, TECH-11 before ST-006 starts the node and ST-037 demonstrates the minimal setup (NFR-1), and TECH-128 before ST-007 and ST-008 build the client and the worker: they are contracts those stories build on, and REQ-36 puts IJobClient and the job model in M1.

Lives in the core package, Bellhop: AddBellhop, AddClient() and AddWorker(options) (TECH-128), the job registration calls (TECH-22), the Bellhop hosted service and the worker's registration (TECH-11), and the options bound from the "Bellhop" section (TECH-10). Worker options (queues and their order, concurrency, the LongRunning limit) belong to AddWorker, not to the global options (TECH-128's notes). Option and key names, AddWorker's parameter and the configuration formats are open questions 1 and 2; how AddBellhop is given a store is open question 3, and AddRecurring's parameter types and what a scan does with an incomplete pair are open question 6.

## Acceptance criteria

### AC-1 · REQ-52 · must

> The system shall let a process configure the store with AddBellhop and then register the client (AddClient), the worker (AddWorker) and the alerts registration in any combination, including none, and map the dashboard independently, where registering the worker also makes the client available because handlers enqueue jobs.
>
> *Notes:* Decided by the owner on 2026-11-06, replacing the node modes of SET-7 (REQ-11 retired). Like Hangfire's AddHangfire / AddHangfireServer split: a web API registers the client and maps the dashboard; a worker service registers the worker. The pieces interact only through the store. The alerts registration was added by the owner on 2026-11-06 (refiner-model, integrations F-6): alerting runs on a worker node, a client or dashboard node, or a node that only does alerts, so a node-lost alert can fire when no worker is alive. Its API name is a TECH matter.

- Property: over every combination of AddClient() and AddWorker(...), none included, called in either order after AddBellhop, the host builds and starts; IJobClient can be resolved exactly when AddClient or AddWorker was called, and the worker's loop and background duties are registered exactly when AddWorker was called.
- Given AddWorker without AddClient, then IJobClient can be resolved, so a handler can enqueue jobs.
- Given AddClient only, then no worker loop or background duty is registered; that such a node never claims (hosting REQ-20) and runs no duty (hosting REQ-40) is tested in ST-008 and ST-007.
- Given AddBellhop alone, then the host builds and starts with neither (the warning is hosting REQ-54, ST-006).
- The alerts registration (TECH-129) joins these combinations in ST-049; mapping the dashboard is hosting REQ-51 (ST-031).

### AC-2 · REQ-57 · must

> The system shall assume that build-time tooling (OpenAPI generation, EF Core design-time services) builds the host without starting it.
>
> *Notes:* Added by refiner-model 2026-11-06 F-6 (recommended option): REQ-14 follows from this and REQ-12, because neither REQ-12 nor REQ-18 checks for build tooling. The conformance tests check the assumption against the listed tools.

- Conformance: a sample application that calls AddBellhop and AddWorker against a store that records every call is run under OpenAPI document generation and under EF Core design-time services; under both, the host is built and not started, the Bellhop hosted service never starts and the store records no call.
- Given a listed tool that does start the host, then the assumption is wrong, and the finding goes back to the specs (REQ-57's notes: the conformance tests check the assumption against the listed tools).

### AC-3 · REQ-13 · must

> While services are being registered and the host has not started, the system shall perform no I/O: no store connection, no schema check and no job reconciliation.

- Property: over random sequences of registration calls (AddBellhop with a store that records every call, AddClient, AddWorker, AddJob, AddJobsFromAssemblyContaining and AddRecurring) followed by building the host, the store records no call: no connection, no schema check and no reconciliation.
- Given the host is built and disposed without being started, then the store still records no call.
- Given the host then starts, then the first store call comes after the host's start has begun (ST-006 orders the rest).

### AC-4 · REQ-14 · must

> Where the process runs build-time tooling such as OpenAPI generation or EF Core design-time services, the system shall not start the scheduler or any worker.

- Given a host built the way the build-time tools build it, without being started (REQ-57), then no scheduler, worker loop or background duty starts and no job is claimed.
- Conformance: the REQ-57 runs under OpenAPI document generation and EF Core design-time services find no worker started.

### AC-5 · REQ-15 · must

> If no store is configured, then the system shall use the in-memory store.

- Given AddBellhop with no store configured, when the host starts, then the node uses the in-memory store (TECH-43): the store the node works against is the in-memory store, and the startup summary names it (hosting REQ-19, ST-006).
- Given a store configured, then that store is used and the in-memory store is not.
- How a store is configured, whether it can be chosen from configuration and what happens when two are configured is open question 3.

### AC-6 · REQ-17 · must

> Where an option is set both in configuration (the Bellhop section) and in code, the system shall use the value set in code.

- Property: for every option the core binds, over random choices of a value in configuration under "Bellhop" or none and a value in code or none, the effective value is the code value when one is set, the configuration value when only that is set, and the default otherwise.
- Given PollInterval in configuration and a different PollInterval in code, then the code value is used, whichever was added to the builder first.
- Given configuration that changes after the host was built, then a value set in code still wins.

### AC-7 · TECH-10 · must

> **Options binding** — The core package shall bind options from Microsoft.Extensions.Configuration under the "Bellhop" section and validate them with ValidateOnStart.

- Test: a value under the "Bellhop" section (Bellhop:PollInterval) is bound to its option; the same key outside the section (PollInterval at the root, or under another section) is not.
- Test: an invalid option fails the host's start, not its first use: the failure comes from starting the host, before the node does anything else (the message is hosting REQ-9, ST-006).
- Inspection: the options are registered with ValidateOnStart.

### AC-8 · TECH-11 · must

> **Hosted service registration** — AddBellhop shall register the Bellhop hosted service with Microsoft.Extensions.Hosting, and AddWorker its worker loop and background duties, so the developer never registers a hosted service by hand.

- Test: after AddBellhop, the Bellhop hosted service is registered with Microsoft.Extensions.Hosting while the test registered no hosted service itself; after AddWorker, its worker loop and background duties are registered too, and without AddWorker they are not.
- Given a host started with AddBellhop, then the Bellhop hosted service starts (ST-006's sequence) with no other code from the developer.
- Calling AddBellhop, AddClient or AddWorker twice is open question 4.

### AC-9 · TECH-22 · must

> **Job registration API** — AddBellhop shall offer AddJobsFromAssemblyContaining<T>(), working across several assemblies, AddJob<TJob, THandler>() and AddRecurring<TJob>(name, schedule, job?, options?).

- Test: AddJobsFromAssemblyContaining<T>() registers every job type and its handler in T's assembly; called once for each of two assemblies, it registers the jobs of both, including a job whose handler is in the other assembly.
- Test: AddJob<TJob, THandler>() registers that job and handler alone.
- Test: AddRecurring<TJob>(name, schedule, job?, options?) is accepted with and without the optional payload and options, and declares a code-defined recurring job of that name (origin code, recurring REQ-202); creating its stored definition is recurring REQ-203 (ST-022).
- Given a job type with an attribute value and a fluent value for the same metadata, with the scan before the fluent call and after it, then the fluent value is used both times (INV-123, ST-002).
- What a scan does with a job type without a handler or a handler without a job type is open question 6; two registrations for one name are ST-002's open question 3.

### AC-10 · TECH-128 · must

> **Client and worker registration** — The AddBellhop builder shall offer AddClient(), which registers IJobClient and IRecurringJobManager for application code, and AddWorker(options), which registers the worker with its queues, concurrency and background duties and also registers the client.
>
> *Notes:* Decided by the owner on 2026-11-06, replacing the node modes. Worker options (queues and their order, concurrency, the LongRunning limit) move from the global options to AddWorker. The dashboard stays MapBellhopDashboard on the endpoint builder (TECH-88).

- Test: AddClient() registers IJobClient for application code, and IRecurringJobManager once ST-023 defines it.
- Test: AddWorker() with no argument registers the worker with default options, as NFR-1's setup uses it; AddWorker(options) registers it with the given queues and their order, concurrency and LongRunning limit; both also register the client.
- Inspection: the global options have no queue, concurrency or LongRunning setting; those are AddWorker's (TECH-128's notes).
- Which queues AddWorker() drains when none are given is open question 5.
