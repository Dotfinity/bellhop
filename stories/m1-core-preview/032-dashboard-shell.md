# ST-032 — Build the dashboard shell, overview page and live updates

**Milestone:** M1 · **Epic:** m1-core-preview · **Priority:** must · **Depends on:** ST-031, ST-015, ST-030

## Context

Delivers the dashboard's front end and the shell every page sits in: React with shadcn/ui and Magic UI, embedded in the package and loading nothing from a CDN (TECH-91, TECH-93); the overview page with live job counts (REQ-307); live updates over Server-Sent Events with a polling fallback (REQ-315, TECH-89); and the banner that warns on every page when no worker is alive (REQ-341). It installs the dashboard-wide checks that every later page keeps: no inline scripts (NFR-42), reverse proxies and path bases (NFR-47), WCAG 2.2 AA and keyboard use (NFR-50), and no store load while nobody is watching (NFR-11).

Builds on ST-031 (mount point, access rules, JSON API; INV-301 keeps holding for every endpoint added here), ST-015 and through it ST-012 (worker nodes' heartbeats and NodeLostAfter, hosting REQ-60, the same notion of alive that hosting REQ-44 uses), and ST-030 (PostgreSQL, so counts and banner are tested on both stores). ST-033 and ST-034 add pages that keep NFR-42, NFR-47, NFR-48, NFR-49 and NFR-50 holding, and ST-049 adds the Notifications page to this shell. NFR-48 (themes) and NFR-49 (responsive layout) are demonstrations, recorded in ST-037 for the M1 dashboard and again in ST-077 for the full one.

Lives in Bellhop.Dashboard (TECH-88). Its front end uses React, shadcn/ui and Magic UI, whose components are copied into the repository and use Tailwind CSS (TECH-93's notes). Live updates are a Server-Sent Events stream under the dashboard path, and the JSON API also reports the no-worker condition (REQ-341's notes, TECH-92). What the overview's throughput, failures and nodes measure, the polling interval, and the banner's wording and JSON form are not in the specs (open questions 1 to 3).

## Acceptance criteria

### AC-1 · REQ-307 · must

> The system shall show an overview page with live job counts by state, throughput, failures and nodes.

- Given jobs written into the store in every Job state (Scheduled, Enqueued, Processing, Succeeded, Failed, DeadLettered, Cancelled, Awaiting, Unroutable), when the overview is opened, then it shows for each state a count equal to the number of jobs in that state in the store, on the in-memory and the PostgreSQL store.
- Property: over generated sequences of state changes written to the store while the overview is open, once the page has updated (REQ-315), every count shown equals the store's count for that state.
- The overview also shows throughput, failures and nodes; a running worker node is shown under nodes under every reading. What each measures is open question 1.

### AC-2 · REQ-315 · must

> The system shall update open pages live through Server-Sent Events and fall back to polling when Server-Sent Events are unavailable.

- Given a page is open and Server-Sent Events work, when a job changes state in the store, then the page shows the change without a reload, and the update arrived on a Server-Sent Events stream under the dashboard path (TECH-89).
- Given Server-Sent Events are unavailable, either because the browser offers no EventSource or because the stream request fails, when a job changes state, then the page still shows the change without a reload, by polling the JSON API.
- The browser test of every page asserts a live update, so the pages of ST-033 and ST-034 join it.
- The polling interval, and whether a stream that opens but delivers nothing (a buffering proxy) counts as unavailable, are open question 2.

### AC-3 · REQ-341 · must

> While no node with the worker registered has sent a heartbeat within NodeLostAfter, the system shall show a banner on every dashboard page saying that no worker is running, so enqueued and scheduled jobs will not run, with the time the last worker was seen or, if none was ever seen, that no worker has connected to this store.
>
> *Notes:* Decided by the owner on 2026-11-06. A cluster made only of client or dashboard processes otherwise accepts jobs that never run, silently (P6). NodeLostAfter (5 min, hosting REQ-60) keeps a rolling deploy from flashing the banner. The JSON API reports the same condition. refiner-model 2026-11-06 F-6 (option 1): a deployment where no worker ever connected gets the banner too, with that wording instead of a time.

- Given the only node with the worker registered sent its last heartbeat more than NodeLostAfter ago (5 min by default, hosting REQ-60), when any dashboard page is open, then it shows a banner saying that no worker is running, so enqueued and scheduled jobs will not run, with the time that worker was last seen (SCN-308).
- Given no node with the worker registered has ever sent a heartbeat to this store, then the banner says that no worker has connected to this store, and shows no time.
- Given a node with the worker registered sent a heartbeat within NodeLostAfter, then no page shows the banner; with the defaults, a worker that stopped 4 minutes ago does not bring it up.
- Given only nodes without the worker (client or dashboard only) send heartbeats, then the banner is shown: their heartbeats do not count.
- Given NodeLostAfter is configured shorter than the default, then the banner appears once that shorter time has passed without a worker heartbeat.
- Given a page is open, when the last worker heartbeat ages past NodeLostAfter, then the banner appears without a reload, and when a worker sends a heartbeat again, it disappears (REQ-315).
- Property, with a fake TimeProvider (TECH-12): over generated sequences of worker heartbeats, stops and clock advances, the banner is shown exactly while no worker heartbeat is within NodeLostAfter; an instant exactly NodeLostAfter after the last heartbeat is left out. The model abstracts the clock (dashboard A-14); this test supplies it.
- A JSON API read reports the same condition (REQ-341's notes); its form is open question 3.
