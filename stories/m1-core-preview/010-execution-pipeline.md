# ST-010 — Hook into execution: middleware, parameters and job events

**Milestone:** M1 · **Epic:** m1-core-preview · **Priority:** must · **Depends on:** ST-008

## Context

Opens execution to application code at three points: execution middleware around every handler (TECH-28), typed per-job parameters that travel with the job (TECH-30), and IJobEvents observers that hear about each transition once, on the node that made it, after the store write has committed (TECH-27, REQ-169), without ever changing the job when they throw (INV-136). It also links a job enqueued or scheduled from a handler to the running job by parentId and trace context (REQ-154). TECH-30 is owned before ST-033 and ST-068, which show and use parameters (dashboard REQ-309, REQ-320): it is a core contract they build on, and hosting REQ-36 puts the job model in M1.

Builds on ST-008: the execution scope that resolves handlers and middleware (INV-122) and JobContext with its parameters and trace context (TECH-16), both of which must keep holding; IJobContextAccessor (TECH-34) tells IJobClient which job is running. Events are raised for the transitions that exist now: enqueue (ST-007), start and success (ST-008). OnFailed and OnDeadLettered come with the transitions of ST-011, the recovering node's events with ST-013, OnCancelled with ST-018 and OnRecurringMissed with ST-026; ST-026 and ST-038 keep REQ-169 holding. "Available to middleware at enqueue" is built against what exists: enqueue middleware is TECH-29 (ST-044). ST-028 builds tracing on REQ-154's trace context and keeps it holding.

Lives in the core package (TECH-112): IJobEvents (TECH-27), IJobMiddleware with JobExecutionContext and JobExecutionDelegate (TECH-28) and ctx.Parameters with Set<T> and Get<T> (TECH-30), all resolved from IServiceProvider (TECH-13). The members of IJobEvents, the registration call for middleware and its per-type filter (open question 3) and the stored form of parameters (open question 5) are not in the specs.

## Acceptance criteria

### AC-1 · INV-136 · must

> If an IJobEvents handler throws, then the system shall log the exception and leave the job's state unchanged.
>
> *Notes:* Decided by the owner on 2026-11-06: observers are never part of the state machine.

- Given an IJobEvents handler that throws from every method, when a job is enqueued, claimed and succeeds, then the enqueue still returns the job id (REQ-120), the job's history and final state are the same as without the observer, and each exception is logged with a stable EventId and the job id (NFR-51).
- Given two handlers, the first throwing, then the second is still called for the same transition (REQ-169: every handler).
- Property: over random job runs with observers that throw at random, the job's state history equals that of the same run without observers.

### AC-2 · REQ-154 · must

> When a handler enqueues or schedules a job, the system shall set the new job's parentId to the running job and carry over the running job's trace context.

- Given job p is running, when its handler enqueues job c through IJobClient (TECH-19), then c's parentId is p's id and c carries p's trace context as p's JobContext exposes it (TECH-16).
- Given the handler schedules job d with a time or a delay, then the same holds for d.
- Given application code outside any handler enqueues job e, then e has no parentId taken from a running job.
- Concurrency: given many handlers running at once on one node, each enqueuing jobs, also from code it awaits, then every new job's parentId and trace context come from the job whose handler enqueued it, never from another running job.
- Which trace context is carried is open question 2; jobs created through continuations, chains or batches are open question 6.

### AC-3 · REQ-169 · must

> When a job is enqueued, started, succeeds, fails, is dead-lettered or cancelled, or a recurring occurrence is missed, the system shall call every IJobEvents handler registered in dependency injection with the matching event, once, on the node that made the transition, after the store write has committed.
>
> *Notes:* Decided by the owner on 2026-11-06: recovery events are raised by the recovering node. A throwing event handler never changes the job (INV-136).

- Given one IJobEvents handler registered, when a job is enqueued, claimed and succeeds, then OnEnqueued, OnStarted and OnSucceeded are each called once with that job.
- Given two handlers registered, then each is called once per transition.
- Given a job enqueued on a client-only node and run on a worker node, then OnEnqueued is called on the client node only, and OnStarted and OnSucceeded on the worker node only.
- Given a handler that reads the job from the store when called, then it sees the state the transition wrote.
- Given the store write fails, or is refused for a stale lease token (INV-128, ST-013), then no event is raised for it.
- The failed, dead-lettered, cancelled and missed-occurrence events, and a recovery's events on the recovering node (REQ-169's notes), are raised by the transitions of ST-011, ST-013, ST-018 and ST-026 (see Context).
- Which transitions count as "enqueued" and as "fails" is open question 1; a node that stops between the commit and the call is open question 4.

### AC-4 · TECH-27 · must

> **IJobEvents** — The core package shall define IJobEvents with OnEnqueued, OnStarted, OnSucceeded, OnFailed, OnDeadLettered, OnCancelled and OnRecurringMissed, resolved from DI.

- Inspection: the core package defines a public IJobEvents with OnEnqueued, OnStarted, OnSucceeded, OnFailed, OnDeadLettered, OnCancelled and OnRecurringMissed.
- Test: implementations registered in DI are resolved from the IServiceProvider and called (REQ-169); with none registered, every transition behaves as before.

### AC-5 · TECH-28 · must

> **Execution middleware** — The core package shall define IJobMiddleware with InvokeAsync(JobExecutionContext ctx, JobExecutionDelegate next), resolved from DI per execution, run in registration order and filterable per job type, replacing attribute filters.

- Inspection: the core package defines a public IJobMiddleware with InvokeAsync(JobExecutionContext ctx, JobExecutionDelegate next), and no attribute that runs code around a handler (TECH-17's attributes are data only).
- Test: middleware A and B registered in that order run as A, B, handler, then back through B and A, on every execution.
- Test: a middleware filtered to job type X runs for X and never for job type Y.
- Test: a middleware with a scoped dependency gets a new instance for each execution and the handler's instance within one (INV-122).

### AC-6 · TECH-30 · must

> **Typed per-job parameters** — The core package shall provide ctx.Parameters.Set<T>(key, value) and Get<T>(key), persisted with the job and available to middleware at enqueue and execution time.
>
> *Notes:* Correlation ids, launch principals and HTTP job responses are stored through parameters.

- Test: a middleware calls ctx.Parameters.Set<T>(key, value) before next, and the handler reads the same value with Get<T>(key) through JobContext (TECH-16); a value the handler sets is readable by the middleware after next returns.
- Test: after the execution ends, the parameter is stored with the job and read back through GetAsync (TECH-19).
- Test: a parameter written into the stored job before the claim (the test writes it into the store directly) is readable by middleware and handler at execution.
- Availability to enqueue middleware is closed with ST-044 (TECH-29).

## Open questions

1. **Decide in delivery** · REQ-169: which transitions raise OnEnqueued and OnFailed? "A job is enqueued" may mean only creation (REQ-120) or every entry into Enqueued (REQ-122, REQ-125, REQ-130, REQ-132, REQ-141), and "fails" may mean only Processing to Failed or every failed attempt, timeouts (REQ-138) and the one that dead-letters included, as integrations REQ-401's notes count them. REQ-169's notes say a recovery's events are raised by the recovering node without naming them.
2. **Decide in delivery** · REQ-154: is "the running job's trace context" the one stored on the running job at its enqueue, or the context of its execution (the consumer span that ST-028 adds, NFR-54)? They give the new job's trace different parents; ST-028 keeps REQ-154 holding.
3. **Decide in delivery** · TECH-27, TECH-28: the parameters and return types of the IJobEvents members, the call that registers middleware and its per-type filter, whether an exception thrown by middleware counts as the handler throwing (REQ-129 and REQ-131 speak of the handler), and how an execution ends whose middleware never calls next. All are public API that NFR-20 later freezes.
4. **Decide in delivery** · REQ-169: is "once" at most once, so that an event is lost when the node stops between the commit and the call, or must a missed call be made later? The latter needs the event stored with the transition.
5. **Decide in delivery** · TECH-30: how parameters are serialized and stored, what Get<T> does for a missing key or a value of another type, and when a value set during execution is written: at once, at the end of the attempt, and also when the attempt fails. The specs say only "persisted with the job"; whether a stale run's write is refused is INV-128 (ST-013).
6. **Decide in delivery** · REQ-154, REQ-170: which parentId do jobs get that a handler creates with ContinueWithAsync, ChainAsync or CreateBatchAsync (TECH-19)? REQ-170 stores a continuation with the parent it continues, REQ-154 with the running job.
