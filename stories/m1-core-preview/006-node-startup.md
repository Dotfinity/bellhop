# ST-006 — Start a node: option validation, schema checks and the startup summary

**Milestone:** M1 · **Epic:** m1-core-preview · **Priority:** must · **Depends on:** ST-005

## Context

Delivers the start of a node: the ordered sequence of REQ-12, from option validation through the store connection and the schema check to migration and reconciliation, and the step that marks the node running and starts the worker (REQ-18) with its one-screen summary (REQ-19). A node accepts the schema version it expects or one older; with AutoMigrate on, which is the default everywhere (REQ-21), it migrates first (REQ-22), and it fails the host's start on an invalid option (REQ-9), on a schema too old with AutoMigrate off (REQ-23) and on a newer schema (REQ-43). Three warnings are logged once before running (REQ-16, REQ-53, REQ-54). The secret scan of NFR-41 starts here, because the startup summary is the first place a connection string could leak.

Builds on ST-005 (registrations, options and the hosted service). ST-007 and ST-008 start their duties and claims only after REQ-18 and keep it holding. REQ-12 and REQ-18 name checks that later stories build, and those stories keep both holding: ST-016 retries an unreachable store and adds the migration lock (REQ-25, REQ-42, REQ-56), ST-022 adds reconciliation and recurring REQ-210, ST-023 recurring REQ-236, ST-029 PostgreSQL's migrations and script (REQ-22, REQ-23), ST-031 the dashboard checks (dashboard REQ-300, REQ-301, REQ-342), ST-059 the Redis connection checks (redis REQ-500, REQ-502, REQ-505) and ST-067 dashboard REQ-334; ST-049 adds the alerts registration to REQ-54. This story builds the sequence against what exists and tests each place in it by putting a failing check there, or a store in the needed schema state, directly. NFR-41 is owned before the dashboard module: the scan starts with logs and the startup summary, and dashboard responses and the Redis details join it as ST-031, ST-032, ST-059, ST-066 and ST-067 keep NFR-41 holding; REQ-36 puts the read-only dashboard in M1 as well.

Lives in the core package, Bellhop, in the Bellhop hosted service that AddBellhop registers (TECH-11), and is generic over the store: the schema version a store reports and its embedded migrations are store operations (TECH-31), which ST-029 implements for PostgreSQL; the in-memory store has the expected schema and is always reachable (hosting A-16). Options are validated with ValidateOnStart (TECH-10). Which option values are invalid, the migration-script path in REQ-23's message and the summary's format are open questions 3, 2 and 6.

## Acceptance criteria

### AC-1 · REQ-21 · must

> The system shall default AutoMigrate to true in every environment (AutoMigrate).
>
> *Notes:* Decided by the owner on 2026-11-06 (§9 Q4): true everywhere, as STO-3 says; the docs show the script export (TECH-47) on the first page.

- Given AutoMigrate is not set, in the Development, Staging and Production environments, when a node starts against a store one version older than expected, then it migrates the store (REQ-22).
- Given AutoMigrate is set to false, in code or in configuration (REQ-17), then no migration is applied, and REQ-23 decides whether the start fails.

### AC-2 · REQ-9 · must

> While a node is starting, if an option fails validation, then the system shall fail the host's start with a message that names the option and the fix.
>
> *Transition:* Node: Starting → StartupFailed · *Actor:* Host
>
> *Notes:* Decided by the owner on 2026-11-06 (refiner-model F-10, recommended option): StartupFailed fails the host's start, the .NET convention for options validation. Process exit also releases a held migration lock (REQ-56, TECH-126).

- Given PollInterval is negative in configuration (SCN-2), when the host starts, then the host's start fails with a message that names PollInterval and the fix, the node never becomes Running and no job is claimed.
- Given that failure, then the node made no store connection, schema check, migration or reconciliation before failing (REQ-12's order).
- Given every option is valid, then validation does not fail the start.
- Which values of each option fail validation, beyond SCN-2's negative PollInterval, is open question 3.

### AC-3 · REQ-12 · must

> When the host starts, the system shall start the Bellhop node, validate the options and run the startup checks that need no store (dashboard REQ-301 and REQ-334, recurring REQ-210), then connect to the store, which for Redis includes its EVAL and eviction-policy checks (redis REQ-500, REQ-502, REQ-505), check the schema (failing under REQ-23 or REQ-43) and run the startup checks that read stored data (recurring REQ-236, which reads a store that is not migrated yet), and only then migrate under REQ-22 and, where the worker is registered and the schema version is accepted with no migration pending, reconcile code-defined recurring jobs.
>
> *Transition:* Node: (new) → Starting · *Actor:* Host
>
> *Notes:* Step order fixed by refiner-model 2026-11-06 F-4 (recommended option): a node that is about to fail validation must not migrate or write to the shared store first, and recurring definitions are reconciled only into a schema the node accepts. refiner-model 2026-11-06 run 2 F-1 (recommended option): every startup check owned by another module has its place in the order, so a node that will fail any startup check never migrates the shared schema or writes recurring definitions. Checks that need no store run with option validation; checks that need the connection or the stored definitions run after the schema check and before any write. Run 3 F-1 (recommended option): the run-2 order stays, because a migration by a node that then fails a check would turn every older node Unhealthy (REQ-32) with no new node running. Recurring REQ-236 therefore runs on an unmigrated store; its own sentence says what it reads there. Run 3 F-2 (recommended option): the Redis EVAL and eviction checks are part of connecting, as redis REQ-500 and TECH-69 already say, so a server without EVAL fails the start with the --lua message instead of the schema message, and never retries for ever as if it were unreachable.

- Given a valid configuration with the worker registered, when the host starts, then a store that records every call, and a check placed in each group, see this order: option validation together with the checks that need no store; the store connection; the schema check; the checks that read stored data; the migration, where one is due; the reconciliation of code-defined recurring jobs.
- Given an option or a check that needs no store fails, then the node never connects to the store.
- Given the schema check fails (REQ-23, REQ-43), or a check that reads stored data fails, then nothing is migrated and nothing is reconciled: the store's schema and contents are unchanged.
- Given the worker is not registered, then no reconciliation runs; given the stored schema is not accepted, or a migration is still pending, then none runs either.
- Property: over random configurations (valid or invalid options, a failing check in any group or none, a stored schema from none up to one newer than expected, AutoMigrate on or off, the worker registered or not), a node never writes to the store, by migrating or reconciling, and then fails a startup check.
- The other modules' checks are built by the stories named in Context; this story tests each place with a check of its own.

### AC-4 · REQ-16 · must

> When a node starts, if no store is configured and the environment is not Development, then the system shall log a warning that the in-memory store is in use, once, before the node is marked running.
>
> *Transition:* Node: Starting → Starting · *Actor:* Host

- Given the Production environment and no store configured, when the node starts, then exactly one warning that the in-memory store is in use is logged, before the node is marked running (SCN-1).

### AC-5 · REQ-18 · must

> While a node is starting, when the store is reachable, the stored schema version is accepted (REQ-23, REQ-43), no migration is pending under REQ-22, all startup checks have passed, including option validation (REQ-9) and the dashboard checks (dashboard REQ-301, REQ-334), and, where the worker is registered, code-defined recurring jobs have been reconciled (REQ-12), the system shall mark the node running and, where the worker is registered, start the worker and its background duties.
>
> *Transition:* Node: Starting → Running · *Actor:* Host
>
> *Notes:* refiner-model 2026-11-06: 'no migration is pending' (F-2, recommended option) means that with AutoMigrate on the schema must equal the expected version, so REQ-22 always runs first and the migration releases its own lock; the accepted one-older version applies with AutoMigrate off (rolling deploys). The startup checks are named (dashboard findings F-5, recommended option) so the dashboard checks precede 'running' by definition. Run 2 F-2 (recommended option): reconciliation is part of the trigger, so the scheduler always starts on reconciled definitions; recurring REQ-203 and REQ-204 fire while the node is still starting.

- Given the store is reachable, the schema is accepted, no migration is pending, every startup check has passed and, on a worker node, reconciliation has run, then the node is marked running, and on a worker node the worker and its background duties start.
- Given the same on a node without the worker, then the node is marked running and no worker or background duty starts (hosting REQ-20 and REQ-40 are proved in ST-008 and ST-007).
- Given AutoMigrate on and a stored schema older than expected, then the node is not marked running until the migration has brought the store to the expected version (REQ-18's notes).
- Given AutoMigrate off and a stored schema one version older, then the node is marked running on it (rolling deploys, REQ-23's notes).
- Given any one of the conditions fails, then the node is never marked running and no worker starts (SCN-3).
- Whether the host's start waits until the node is running is open question 5.

### AC-6 · REQ-19 · must

> While a node is starting, when the store is reachable, the stored schema version is accepted (REQ-23, REQ-43), no migration is pending under REQ-22, all startup checks have passed, including option validation (REQ-9) and the dashboard checks (dashboard REQ-301, REQ-334), and, where the worker is registered, code-defined recurring jobs have been reconciled (REQ-12), the system shall log a one-screen summary with the store and schema version, which of the client, worker, alerts and dashboard are registered, queues and concurrency, the registered job count, recurring jobs with their next run, and the dashboard path and auth mode.
>
> *Transition:* Node: Starting → Running · *Actor:* Host
>
> *Notes:* Same event as REQ-18 with a second consequence; the agent should model one action, and the `when` text must stay identical to REQ-18's. The Redis store adds the server family to the summary (REQ-500). Secrets never appear in it (NFR-41).

- Given a worker node that is marked running, then one summary is logged at that moment with the store and schema version, which of the client, worker, alerts and dashboard are registered, the queues and concurrency, the number of registered jobs, each recurring job with its next run, and the dashboard path and auth mode.
- Given a client-only node, then the summary says that the worker is not registered.
- Given a node whose start fails, then no summary is logged.
- Given a store configured with a connection string that contains a password, then neither the connection string nor the password appears in the summary (NFR-41).
- Parts that later stories fill (recurring next runs from ST-022, the dashboard from ST-031, the alerts from ST-049, the Redis server family from ST-059) show nothing registered until then. The summary's format, and what bounds "one-screen", are open question 6.

### AC-7 · REQ-22 · must

> While a node is starting, if AutoMigrate is on and the stored schema version is older than the expected version, then the system shall apply the embedded migrations up to the expected version and log what it did.
>
> *Transition:* Node: Starting → Starting · *Actor:* Host
>
> *Notes:* Decided by the owner on 2026-11-06: concurrent starts are serialised by a store-side migration lock (REQ-42, TECH-126).

- Given AutoMigrate on and a stored schema older than expected, including a store with no Bellhop schema (hosting A-16), when the node starts, then the embedded migrations from the stored version up to the expected one are applied, the store then reports the expected version, and a log entry says what was applied.
- Given the stored schema is the expected version, then nothing is applied and no migration is logged.
- Given a stored schema newer than expected, then nothing is applied (REQ-43 fails the start).
- Concurrent starts and the migration lock are REQ-42 and REQ-56 (ST-016). What happens when a migration fails part-way is open question 4.

### AC-8 · REQ-23 · must

> While a node is starting, if AutoMigrate is off and the stored schema version is more than one version older than the expected version, then the system shall fail the host's start with a message that includes the path of the migration script.
>
> *Transition:* Node: Starting → StartupFailed · *Actor:* Host
>
> *Notes:* Decided by the owner on 2026-11-06: a node accepts the schema version it expects or one version older, so library N+1 runs on schema N as STO-5 and NFR-18 require. A newer schema is REQ-43. Migrations therefore stay additive within a major version (TECH-127). StartupFailed fails the host's start (refiner-model 2026-11-06 F-10, owner's choice of the recommended option).

- Given AutoMigrate off and a stored schema two versions older than expected (SCN-3), when the node starts, then the host's start fails with a message that includes the path of the migration script, the node never becomes Running and no worker starts.
- Given AutoMigrate off and a stored schema one version older, or the expected version, then this check does not fail the start.
- Given AutoMigrate on, then this check does not fail the start: REQ-22 migrates instead.
- Given that failure, then the message contains no connection string (NFR-41).
- What "the path of the migration script" is, and how a store with no Bellhop schema counts, are open questions 2 and 1.

### AC-9 · REQ-43 · must

> While a node is starting, if the stored schema version is newer than the expected version, then the system shall fail the host's start with a message that names both versions and says the library is older than the schema.
>
> *Transition:* Node: Starting → StartupFailed · *Actor:* Host
>
> *Notes:* Decided by the owner on 2026-11-06: a node accepts its expected schema or one version older, never a newer one, whether AutoMigrate is on or off. During a rolling deploy a node on N that restarts after an N+1 node migrated fails here; that is acceptable because it is being replaced. Failing the host's start (refiner-model 2026-11-06 F-10, owner's choice) means that restart takes the whole process down, HTTP endpoints included, until the pod is replaced.

- Given a stored schema one version newer than expected, with AutoMigrate on and with it off, when the node starts, then the host's start fails with a message that names both versions and says that the library is older than the schema, and nothing is migrated.
- Given the stored schema is the expected version or one older, then this check does not fail the start.

## Open questions

1. **Decide in delivery** · REQ-23, hosting A-16: does a store with no Bellhop schema count as one version older when the expected version is 1? If it does, a node of the first release with AutoMigrate off accepts an empty database and runs without tables; the model counts no schema as version 0 and accepts the expected version minus one.
2. **Decide in delivery** · REQ-23, TECH-47: what is "the path of the migration script": a file shipped in the package, a documentation link, or the call to BellhopSchema.GetScript(provider, fromVersion)?
3. **Decide in delivery** · REQ-9: which values of each option fail validation? Only SCN-2's negative PollInterval is given, and each option's owning story needs its rule.
4. **Decide in delivery** · REQ-22: what does the node do when a migration fails part-way (an error, missing permissions)? No item says how the start fails or what the message says; hosting REQ-24 (ST-016) makes re-applying a migration safe.
5. **Decide in delivery** · REQ-12, REQ-18: does the host's start wait until the node is running? If it waits, the host's other services and the web server stay down while REQ-25 retries an unreachable store "without stopping the host"; if it does not, REQ-9, REQ-23 and REQ-43 must still fail the host's start, which REQ-43's notes say takes the HTTP endpoints down.
6. **Decide in delivery** · REQ-19: is the summary one log entry or several, at which level and with which EventId, and what bounds "one-screen" (a node with many recurring jobs)?
7. **Decide in delivery** · NFR-41: which values count as "other secrets" for the scan (passwords inside connection strings, API keys, basic-auth hashes), and may the summary show the store's host and database names?
