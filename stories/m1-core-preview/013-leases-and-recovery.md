# ST-013 — Renew leases and recover jobs from lost nodes

**Milestone:** M1 · **Epic:** m1-core-preview · **Priority:** must · **Depends on:** ST-011, ST-012, ST-009

## Context

Delivers the lease that makes delivery at-least-once (REQ-10), on top of the heartbeat renewal that ST-008 builds (REQ-126). A job whose lease has passed by the database clock is returned to Enqueued as Interrupted with the attempt counted, or dead-lettered at its last attempt, by any running worker node (REQ-132, REQ-133, LIV-101, SCN-102). A healthy job is never recovered however long it runs (INV-104, SCN-103), and a run that lost its lease can no longer write to its job (INV-128, SCN-117). Ownership is recorded in the store with an expiry rather than held by a connection or a lock library (hosting REQ-37, TECH-51), and exactly-once is not offered (hosting REQ-7).

Builds on ST-011 (dead-lettering, which REQ-133 uses), ST-012 (the running worker nodes that recover), ST-009 (the maintenance pause, during which lease recovery keeps running while claims stop, INV-114's notes) and ST-008's claim with its leaseToken, LeaseDuration and heartbeat renewal (REQ-102, REQ-123, REQ-126); ST-008's INV-103 and INV-116 must keep holding. It also keeps ST-010's REQ-169 holding, since its recoveries raise their events on the recovering node (REQ-169's notes); ST-009's INV-114, since recovery runs during maintenance and claims nothing then; ST-007's INV-105, since every lease decision reads the database clock; and ST-007's hosting REQ-40, since recovery is a worker duty. REQ-132's "its cancellation was not requested" is built against what exists: ST-018 adds cancellation (REQ-190) and keeps REQ-132 and INV-128 holding. INV-128's progress clause is built against ReportProgressAsync as JobContext exposes it (TECH-16, ST-008); storing progress is REQ-166 (ST-045). Built on by ST-014 (an abandoned handler's late result is harmless because of INV-128), ST-017 (a run released at shutdown is fenced, REQ-140) and ST-030 (the same rules on PostgreSQL, keeping INV-103 holding).

Lives in the core package's engine and the store contract (TECH-31) with the in-memory store (TECH-43); every lease decision reads the database clock (INV-105). No new public type is named by these items.

### Modeling assumptions

Decisions the model took where the sentences were silent. Build to them, or raise an open question.

- jobs A-2 (affects REQ-102, REQ-126, REQ-132, REQ-133, INV-104, LIV-101): A lease is a flag. It can expire at any time while processing (crash, partition or pause), and a late heartbeat from the run that holds the current token renews it (REQ-126 has no "not yet expired" guard).
- jobs A-3 (affects REQ-132, REQ-139, REQ-140, REQ-190, hosting REQ-29): A crash removes the node's handlers at once; its leases expire later. A draining node stops as hosting REQ-29's run-5 wording says. "In-flight job" (hosting `Node.inFlightJobs`, not defined) is a running handler that holds its job's current lease. A job settled by REQ-138/186/190, released by REQ-140 or lost to lease expiry is no longer in flight, though its handler may still be running, as hosting REQ-29's notes say. After ShutdownTimeout the node waits for its check of every in-flight run (A-19) and for the release or cancellation that check calls for. Every such attempt succeeds, because store outages are not modeled here. A stopped node's handlers stop with it.
- jobs A-18 (affects REQ-191, INV-128): REQ-191's record and log line are history only. Abandonment is recorded as the tag `Abandoned` in the step that abandons (`AbandonOnTimeout`, both outcomes of the shutdown check in `ReleaseOnShutdown`), and `Prop_AbandonRecorded` checks that. The tag is per job, not per attempt, so the property is checked where a first attempt is abandoned. The lease-lost trigger is the predicate `LeaseLostRecordable`: a running handler on a live node whose token is not current or whose job is not processing. For a job that was deleted or removed, only the log line can be written, because "that attempt" no longer exists.
- jobs A-20 (affects REQ-140, REQ-190, INV-128): "The job's node" (REQ-140) and "its draining node" (REQ-190) are the node whose run holds the job's current lease token. A node whose run lost its lease to another node's claim makes no shutdown write for that job.
- jobs A-6 (affects LIV-100, LIV-101, LIV-102, REQ-192): "While P, eventually Q" is read as `P ~> (Q \/ ~P)`: the obligation ends when P stops holding, for example when the job is cancelled or deleted.

## Acceptance criteria

### AC-1 · REQ-10 · must

> The system shall treat job delivery as at-least-once: a job may start more than once within the duplicate window, which equals the lease length (LeaseDuration).
>
> *Notes:* Defined here because several modules rely on it; LeaseDuration itself is REQ-102 in the jobs module.

- Given the defaults (LeaseDuration 60 s, REQ-102), when the worker node running job j is cut off from the store, then another worker node starts j again once j's lease has passed (REQ-132): the job is not lost, and the second start comes no earlier than j's leaseExpiresAt (INV-104).
- Given that the first run is still running when the second starts, then its later writes are refused (INV-128), so the duplicate run cannot end the job.
- Given LeaseDuration is configured as 10 s, then the same holds with 10 s.
- Stating the duplicate window in the docs is NFR-25 (ST-035).

### AC-2 · REQ-132 · must

> While a job is processing and its cancellation was not requested, when its leaseExpiresAt has passed according to the database clock, if the attempt number is below maxAttempts, then the system shall let any running worker node return the job to enqueued with reason Interrupted, keeping the attempt counted.
>
> *Transition:* Job: Processing → Enqueued · *Actor:* system
>
> *Notes:* Resolved after refiner-model 2026-11-06 F-7: a job whose cancellation was requested is marked cancelled instead (REQ-190). REQ-133 is unchanged: a dead-lettered job does not run again.

- Given j is processing at attempt 1 of 5 on node A and A stops sending heartbeats, when leaseExpiresAt passes by the database clock, then a running worker node B returns j to Enqueued with reason Interrupted, j keeps attempt number 1, B's next claim makes it attempt 2 (REQ-123), and the transition is recorded with its time, node B and the reason (INV-116).
- Given leaseExpiresAt has not passed by the database clock, then no node recovers j, also not one whose own clock is past it (INV-104, INV-105).
- Given the attempt number has reached maxAttempts, then this rule does not apply; REQ-133 dead-letters j.
- Concurrency: given several worker nodes looking for expired leases at once, then j is recovered once: its history holds one Interrupted transition for that attempt, and a claim another node made after the recovery is untouched (INV-103).
- Given only nodes without the worker run, then j is not recovered (hosting REQ-40).

### AC-3 · REQ-133 · must

> While a job is processing, when its leaseExpiresAt has passed according to the database clock, if the attempt number has reached maxAttempts, then the system shall let any running worker node move the job to dead-lettered with reason Interrupted.
>
> *Transition:* Job: Processing → DeadLettered · *Actor:* system
>
> *Notes:* Same event as REQ-132 with the complementary guard.

- Given j is processing at attempt 5 of 5 and its lease has passed by the database clock, when a running worker node recovers it, then j is DeadLettered with reason Interrupted, the transition is recorded with its time and node (INV-116), and j is never claimed again.
- Given attempts are left, then REQ-132 applies instead. Property: for every expired lease, exactly one of REQ-132 and REQ-133 decides.
- Given its lease has not passed by the database clock, then j is not dead-lettered (INV-104).

### AC-4 · INV-104 · must

> While a processing job's leaseExpiresAt has not passed, the system shall never recover, requeue or dead-letter the job for lease expiry, however long it has been running.
>
> *Rationale:* Recovery keys off the lease deadline, never the original fetch time, so a healthy long-running job is never requeued.

- Property, with a fake clock and two or more worker nodes: over random claims, on-time and late heartbeats, clock advances and recovery passes, no job is recovered, requeued or dead-lettered for lease expiry while its leaseExpiresAt has not passed by the database clock.
- Given a node whose own clock runs ahead of the database clock by more than LeaseDuration, then it still recovers no job whose lease has not passed by the database clock (INV-105).
- Given a job processing for ten times LeaseDuration whose heartbeats keep succeeding, then it is never recovered (SCN-103).

### AC-5 · INV-128 · must

> If a run presents a lease token that is no longer the job's current leaseToken, or its job is no longer processing, when it renews the lease, reports progress, completes or fails, then the system shall refuse the write, leave the job unchanged and log a stale-completion warning.
>
> *Notes:* Decided by the owner on 2026-11-06 (fencing). After a lease expires and another node recovers the job, the original run can no longer succeed, fail or extend it, so a job never ends twice or ends while it is Processing elsewhere. Worth adding later: a refused heartbeat could cancel the stale run's token. Run 3 F-2 (recommended option): a job can leave Processing without a new claim (dead-lettered or cancelled on lease expiry, REQ-133, REQ-190; released at shutdown, REQ-140), and then its token stays current. Refusing writes for a job that is no longer processing fences those runs too; before, a run released at shutdown could still complete its job before another node claimed it.

- Given node A's run of j holds token t1, and j was recovered and claimed by node B with token t2 (SCN-117), when A's run completes, fails, renews its lease or reports progress with t1, then each write is refused, j stays Processing under B's claim with t2 and its lease unchanged, and a stale-completion warning is logged.
- Given j was dead-lettered on lease expiry (REQ-133), so that A's token is still the current one, when A's run completes, fails or renews, then the write is refused because j is no longer processing, and the warning is logged.
- Property: over random interleavings of claims, recoveries, renewals and run outcomes on two nodes, a write that carries a token other than the job's current one, or that is made for a job that is not processing, never changes the job.

### AC-6 · LIV-101 · must

> While a job is processing and its lease has expired, the system shall eventually return it to enqueued or dead-letter it, provided at least one worker node is running.

- Given j is processing, its lease has expired and at least one worker node is running, when the fake clock is advanced, then j is eventually Enqueued (attempts left) or DeadLettered (last attempt).
- Given no worker node is running, then j stays Processing; once a worker node is running, j is eventually recovered.
- How soon "eventually" comes is open question 1.

### AC-7 · SCN-102 · scenario

> **Node crash is recovered by another node**
>
> *Given:* Nodes A and B running; job j enqueued; maxAttempts = 5.
>
> 1. REQ-123 — A claims j, attempt 1
> 2. REQ-132 — A crashes; lease expires; B recovers j as Interrupted
> 3. REQ-123 — B claims j, attempt 2
> 4. REQ-127
>
> *Then:* j is Succeeded, its history shows one Interrupted attempt by A and attempt 2 by B.

### AC-8 · SCN-103 · scenario

> **Healthy long-running job is never recovered**
>
> *Given:* Job j is processing on node A for ten times LeaseDuration and A's heartbeats keep succeeding.
>
> 1. REQ-123
> 2. REQ-126 — heartbeat renews lease
> 3. REQ-132 — node B tries to recover j
>
> *Impossible at step 3.*

### AC-9 · SCN-117 · scenario

> **Stale run cannot complete a recovered job**
>
> *Given:* Nodes A and B running; job j enqueued; maxAttempts = 5. A is partitioned from the store long enough for its lease to expire.
>
> 1. REQ-123 — A claims j with token t1
> 2. REQ-132 — lease expires; B recovers j as Interrupted
> 3. REQ-123 — B claims j with token t2
> 4. REQ-127 — A's handler returns and tries to mark j succeeded with t1
>
> *Impossible at step 4.*
