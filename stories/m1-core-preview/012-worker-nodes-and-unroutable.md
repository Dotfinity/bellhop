# ST-012 — Track worker nodes and mark jobs no worker can handle as unroutable

**Milestone:** M1 · **Epic:** m1-core-preview · **Priority:** must · **Depends on:** ST-008

## Context

Gives the cluster a record of its running worker nodes: each publishes a heartbeat with the job names and aliases it has handlers for (REQ-124's notes), and a node without a heartbeat for NodeLostAfter is lost (REQ-60). On that record, a job that no live worker can run is parked as Unroutable once it has waited UnroutableAfter, without failing, retrying or deleting it (REQ-124, REQ-183), and goes back to Enqueued when a worker node with its handler appears (REQ-125, SCN-111). A misspelt job name thus surfaces in minutes, and a node without the handler during a rolling deploy never parks a job another node can run.

Builds on ST-008: a node claims only jobs it has a handler for, by name or alias (REQ-123, REQ-101), and every transition is recorded (INV-116); both must keep holding. The sweep is a worker background duty, so ST-007's hosting REQ-40 must keep holding: no node without the worker runs it. Built on by ST-013 (lease recovery by any running worker node), ST-015 (MinNodesAlive, hosting REQ-44), ST-022 (code-defined recurring jobs across nodes), ST-032 (the no-worker banner, dashboard REQ-341), ST-052 (the node-lost alert, integrations REQ-404), ST-053 (analyzers for job names and handlers) and ST-071 (the nodes page, dashboard REQ-313).

Lives in the core package's engine and the store contract (TECH-31) with the in-memory store (TECH-43); ST-029 and ST-030 bring it to PostgreSQL. The specs name neither the store members for the node record nor where NodeLostAfter and UnroutableAfter are configured (open question 1).

## Acceptance criteria

### AC-1 · REQ-60 · must

> The system shall treat a node as lost after NodeLostAfter without a heartbeat, 5 minutes by default (NodeLostAfter).
>
> *Notes:* Decided by the owner on 2026-11-06 (originally integrations REQ-411). refiner-model 2026-11-06 follow-up to dashboard F-13 and hosting F-9: NodeLostAfter is used by hosting REQ-44, dashboard REQ-341 and integrations REQ-404, and heartbeats belong to hosting, so the constant moved here from integrations REQ-411, which is retired.

- Given a worker node that keeps running and sending heartbeats, then it is never treated as lost, however long it runs.
- Given a worker node that stops sending heartbeats (its host is killed), when 5 minutes have passed since its last heartbeat, then it is treated as lost: its handlers no longer count for REQ-124, and it no longer counts as alive (hosting REQ-44); before 5 minutes have passed it still counts.
- Given NodeLostAfter is configured as 2 minutes, then the same holds with 2 minutes.

### AC-2 · REQ-183 · must

> The system shall wait UnroutableAfter, 5 minutes by default, before marking an unclaimed job unroutable (UnroutableAfter).
>
> *Notes:* Decided by the owner on 2026-11-06: longer than a typical rolling deploy, short enough that a misspelt job name surfaces quickly.

- Given UnroutableAfter is not configured and no live worker node lists a job's name, then the job is not marked Unroutable while it has been enqueued for 5 minutes or less, and is marked once it has been enqueued for longer (REQ-124).
- Given UnroutableAfter is configured as 1 minute, then the same holds with 1 minute.

### AC-3 · REQ-124 · must

> While a job is enqueued, when it has been enqueued for longer than UnroutableAfter, if no running worker node lists a handler for its name or any of its aliases, then the system shall mark the job unroutable without failing, retrying or deleting it.
>
> *Transition:* Job: Enqueued → Unroutable · *Actor:* system
>
> *Notes:* Decided by the owner on 2026-11-06: nodes publish their handler names with their heartbeat and claim only jobs they can run (REQ-123). A sweep marks a job Unroutable only when it has waited UnroutableAfter and no live node lists its name, so a node without the handler during a rolling deploy never parks a job another node can run, and a long backlog never triggers it.

- Given job j named old-report is enqueued and no running worker node lists a handler for old-report or any of its aliases, when j has been enqueued for longer than UnroutableAfter, then j is Unroutable; its attempt number, payload and earlier history are unchanged, it has no retryAt and no failed attempt, it can still be read by id (GetAsync, TECH-19), and the transition is recorded with its time, node and reason (INV-116).
- Given a running worker node lists a handler for j's name or one of its aliases, then j is never marked Unroutable, however long it waits behind a backlog (REQ-124's notes).
- Given a rolling deploy in which the running node A lacks the handler and node B, which has it, is still running or has not yet been lost (REQ-60), then j is not marked Unroutable.
- Given j has been enqueued for UnroutableAfter or less, then it stays Enqueued.
- Given no worker node is running, then nothing marks j; the sweep is a worker duty (hosting REQ-40).
- Where "enqueued for" starts counting is open question 3.

### AC-4 · REQ-125 · must

> While a job is unroutable, when a running worker node registers a handler for its name or one of its aliases, the system shall return the job to enqueued.
>
> *Transition:* Job: Unroutable → Enqueued · *Actor:* system

- Given j is Unroutable, when a worker node with a handler whose alias is old-report is marked running (hosting REQ-18), then j is Enqueued, that node can claim it (REQ-123), and the transition is recorded (INV-116).
- Given the node that starts has no handler for j's name or aliases, then j stays Unroutable.
- Given a node without the worker registered has the handler registered, then j stays Unroutable; only a running worker node returns it.
- Property: over random starts and stops of nodes with random handler sets, a job that is Unroutable returns to Enqueued once a running worker node lists its name, and no job is ever Failed or DeadLettered by REQ-124 or REQ-125.

### AC-5 · SCN-111 · scenario

> **Unroutable job resumes when its handler appears**
>
> *Given:* Job j named old-report is enqueued; no running node has a handler for it.
>
> 1. REQ-124 — UnroutableAfter passes and no live node lists old-report; j becomes Unroutable
> 2. REQ-125 — a node starts that has a handler with alias old-report
> 3. REQ-123
> 4. REQ-127
>
> *Then:* j is Succeeded and was never Failed or DeadLettered.
