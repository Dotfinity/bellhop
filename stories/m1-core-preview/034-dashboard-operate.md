# ST-034 — Operate recurring jobs, dead letters and queues from the dashboard

**Milestone:** M1 · **Epic:** m1-core-preview · **Priority:** must · **Depends on:** ST-033

## Context

Adds the M1 operator pages: recurring jobs with their next runs and time zone, last outcome, and the trigger, pause and edit actions (REQ-310); dead letters with bulk requeue (REQ-311); and queues with their depth and the pause and resume actions (REQ-312). They carry the dashboard's first operate actions, so INV-301 and INV-302 meet real actions here. Hosting REQ-36 calls the M1 dashboard "read-only", while these three items are tagged M1 and name the actions; the plan follows the tags, and open question 1 asks the owner.

Builds on ST-033 and through it on ST-031 and ST-032, whose checks these pages keep. The actions use behaviour built earlier: trigger now (REQ-226, ST-024), pause and edit (REQ-214, REQ-211, REQ-212, REQ-209, ST-023), next runs (REQ-230, ST-023), last outcome (REQ-231, ST-025), bulk requeue (REQ-142, ST-020), and queue pause and resume (REQ-160, REQ-161, ST-009), which the owner moved into M1 on 2026-11-10 because the claim rule REQ-123, this queues page and the recurring trigger read the pause. ST-072 keeps REQ-310 holding when it adds the schedule builder, occurrence history and settings (REQ-328, REQ-329); ST-035, ST-061, ST-066, ST-071 and ST-072 build on this story.

Lives in Bellhop.Dashboard (TECH-88) and its JSON API (TECH-92). Every recurring write an action makes is a compare-and-set (INV-212, ST-026), and bulk requeue by tag runs over IJobIndex (TECH-32; tags are written from ST-044 on, so the tests add index entries directly). How many next runs are shown, what an edit can change, what depth counts and which actions besides the listed ones the pages offer are not in the specs (open questions 2 to 5).

## Acceptance criteria

### AC-1 · REQ-310 · must

> The system shall show a recurring jobs page with each job's next runs and their time zone, last outcome, and the trigger, pause and edit actions.
>
> *Notes:* The time zone is shown next to every schedule (REC-4).

- Given recurring jobs defined in code and at runtime, when the recurring page is opened, then each job shows its next runs computed from its schedule in its own time zone (REQ-230), the time zone next to every schedule (REQ-310's notes), and its last outcome as recorded by REQ-231; a job that has never had an outcome shows none.
- Given a job in Local time mode whose next runs cross a daylight-saving change, then the runs shown follow REQ-228 and REQ-229.
- Given operate permission, when the operator triggers a job, then an occurrence is created at once, decided by the overlap policy like a scheduled one, and nextRunAt is unchanged (REQ-226).
- Given operate permission, when the operator pauses an active job, then it is marked paused (REQ-214), no occurrence is created for it on schedule while it stays paused (INV-201), and its waiting occurrences are recorded as skipped with reason Paused (REQ-237).
- Given operate permission and a runtime-defined job, or a code-defined one marked AllowRuntimeOverride, when the operator saves an edit, then the new definition is stored (REQ-212), and a changed schedule computes nextRunAt from now (REQ-227).
- Given a code-defined job not marked AllowRuntimeOverride, when the operator saves an edit, then it is rejected with a message saying the job is defined in code (REQ-211), shown on the page, and nothing is stored.
- Given an edit with an invalid schedule expression, or Local time mode without a valid IANA time zone, then it is rejected with an error that says what is wrong, shown on the page, and nothing is stored (REQ-209).
- Concurrency: an edit and a pause from the page race a scheduled trigger on another node; every write is a compare-and-set that, when it loses, reads the job again and decides anew (INV-212), so no edit is lost and no due instant gets two occurrences (INV-203).
- Given a principal with view only, then each of the three actions gets 403 and changes nothing (INV-300, INV-301); given ReadOnly(), each is refused whatever the permission (INV-302).

### AC-2 · REQ-311 · must

> The system shall show a dead letters page with bulk requeue.

- Given dead-lettered jobs and jobs in other states, when the dead letters page is opened, then it lists exactly the DeadLettered jobs.
- Given operate permission, when the operator requeues in bulk by name, queue, tag or time range, then each matching dead-lettered job is enqueued again in its own atomic step, with its attempt number reset to zero and its cancellation request cleared, and the JSON API returns REQ-142's three counts: requeued, skipped because the state changed, skipped because the unique key is held.
- Given a matching job whose unique key is held by another active job, then it is skipped and counted, never enqueued (INV-100, INV-129).
- Concurrency: two operators run the same bulk requeue at the same moment; each job is requeued once, and the run that comes second counts it as skipped because its state changed (REQ-142).
- Given a principal with view only, then the bulk requeue gets 403 and changes nothing; given ReadOnly(), it is refused whatever the permission (INV-302).
- What else the page offers (single requeue, delete) and how it shows the three counts is open question 4.

### AC-3 · REQ-312 · must

> The system shall show a queues page with each queue's depth and pause and resume actions.

- Given queues holding jobs, when the queues page is opened, then each queue is shown with its depth; under every reading of depth (open question 5), a queue whose only jobs are n Enqueued jobs shows n.
- Given operate permission, when the operator pauses an active queue, then it is marked paused (REQ-160), the page shows it paused, and no job is claimed from it while it stays paused (INV-113); when the operator resumes it, it is marked active (REQ-161) and its jobs are claimed again.
- Given the page is open, when jobs are enqueued or claimed, then the depths change without a reload (REQ-315).
- Given a principal with view only, then pause and resume get 403 and change nothing; given ReadOnly(), they are refused whatever the permission (INV-302).
- Which queues the page lists is open question 5.

3. **Decide in delivery** · REQ-310: how many next runs the page shows (REQ-230 leaves N open), which fields an edit can change (schedule, time mode and zone, payload, policies), and whether trigger offers REQ-226's overridden payload.
4. **Decide in delivery** · REQ-311: does the dead letters page also offer single requeue (REQ-141 says "through the API or the dashboard") and delete (REQ-144; INV-301 lists delete among operate actions), and how does it show REQ-142's three counts?
5. **Decide in delivery** · REQ-312: what a queue's depth counts (Enqueued jobs only, or also Scheduled, Failed and Processing ones) and which queues the page lists (queues holding jobs, queues a worker serves, a paused queue with no jobs).
